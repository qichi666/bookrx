## 2. 逐维比对

| 维度 | 方案 A | 方案 B | 谁更适合落地 |
|---|---|---|---|
| **目标** | 让已有资产被反复看见（旧划线、首页动态、回执聚合、关系图谱） | 补竞品标配深度（同上四项 + 检索高亮、处方笺、读完率、速度对照、双向导入） | 两者目标一致；A 更聚焦，B 更全 |
| **可行性** | 每条都标了代码落点与增量方式 | 依赖文档判断，个别项已存在 | **A 明显更可行** |
| **复杂度** | 低/中为主，标注人日 | 同为低/中，但把已完成项也算进工作量 | A 的估算可信 |
| **改动范围** | 不碰打分内核、不新增存储字段、不引依赖 | 同左，但含「书籍关系规则来源需拍板」 | A 的边界更干净 |
| **风险** | 低；唯一中等风险是关系图谱的规则质量 | 中；若按 B 的假设直接施工，会重复实现已有功能、并按「薄标签 2 本」的过时前提排优先级 | **A 风险更低** |

**互补点**（B 有而 A 弱的地方，值得吸收）：

1. B 的竞品视角指出「统计页的两个数字要**并列**展示」（读完率 + 有用率），A 只写了补读完率；
2. B 强调「检索要给**上下文**，不只是匹配」，A 只写了高亮；
3. B 明确「处方笺**默认不含处境敏感信息**，需用户主动勾选」，这条隐私纪律比 A 的「默认不含」更严格；
4. B 的「关系图谱规则来源」提问（人工 vs 自动）指向一个真实设计分歧。

## 3. 终版裁决

**以方案 A 为骨架，吸收方案 B 的四处深度主张；凡两方案都提到但代码已实现的，一律不做。**

| 项 | 来源 | 裁决 |
|---|---|---|
| 首页「今天」区块（在读 + 每日旧划线） | A 建议 1+2 / B 建议 2 | **合并做**：两者本就指向同一区块，分开做会得到两个内容重复的模块 |
| 书籍关系图谱 F15 | A 建议 4 / B 新增 1 | **做**，规则取「**人工定关系方向 + 数据算具体书**」的混合式 |
| 回执按困境聚合 | A 建议 3 / B 优化 1 | **做**，落在 `/admin`，只读 |
| 笔记检索高亮 | A 建议 5 / B 优化 4 | **做**，并补「命中在书名/引文/笔记」的说明（吸收 B 的上下文主张） |
| 读完率 | A 建议 7 / B 优化 4 | **做**，与已有有用率并列（吸收 B 的并列展示主张） |
| 处方笺书摘图 | A 建议 6 / B 新增 5 | **做**，且**默认不含任何困境标签**（取两方案里更严的那条） |
| F11 实际 vs 预估 | A 建议 8 / B 优化 5 | **做展示，不做修正**：修正式会改排期结果，而计划页的价值恰恰是「看到的下周明天还是下周」 |
| 路由兜底 | A 核验发现（两方案都没提修） | **做**：拼错地址原本是白页 |
| 档案级 JSON 导入 / 薄标签补书 / F8 一句话 / JSON 双向导入 / 预缓存全路由 | A 低优先 / B 新增 | **不做**：前两项是内容或低价值工作，后三项已完成或刻意保持现状 |

**选择理由一句话**：方案 A 唯一能保证「不重复造已经存在的轮子」，而方案 B 的价值在视野而非事实；把 B 的视野叠加到 A 的事实底座上，改动范围仍锁在「视图层 + 一个纯函数 + 一张数据表」，风险最低。

## 6. 本轮未做，以及为什么

| 项 | 理由 |
|---|---|
| 站内可读比例 2/68 | 内容侧工程（公版书录入 + 版权核查），不是视图改造；需单独立项 |
| 薄标签补书 | 实测最薄 3 本，紧迫度已下降；补书是人工标注工作，每本约 60 分钟 |
| F11 排期速度修正 | 修正系数会改变排期结果，违背「计划页要稳定」；先只展示差值 |
| 档案级 JSON 导入 | 全量 JSON 导入已可用；按档案区分属低价值增量 |
| 预缓存全部路由 | 当前运行时缓存是刻意取舍（避免装一次就把 61 个 chunk 全下下来） |
