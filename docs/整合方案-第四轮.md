## 二、两份材料都没说准的那件事

两家都把根因写成「豆瓣大类『小说』被映射到了焦虑」。**这个描述不准确，而且顺着它去修会修错地方。**

实际数据是这样：

1. 词表里 16 个豆瓣标签承担兜底职责，映射关系是 **1 对多**——「人生」对应 6 个困境标签，「职场」6 个，「自我管理」6 个，「心理学」5 个。
2. 一本书最多保留 3 个困境标签，**同权时留哪 3 个由书 id 的 FNV 散列在词表顺序上取一个轮转窗口决定**。
3. 于是「这本书被归到哪 3 个困境」实质是**抽签**，而不是分类。

实测后果（本轮重算，非引用旧结论）：

| 指标 | 数值 |
|---|---|
| 兜底证据占比 ≥80% 的标签 | **27 / 33** |
| 强证据书不足 20 本的标签 | **16 个**（`self-doubt` 6 本、`big-choice` 2 本、`emptiness` 2 本） |
| 「发言紧张 + 怕被评价」的按需池 | 修复前 **686 本** → 修复后 **15 本** |

也就是说，「书名证据不足 20 本就把兜底书放进来、逐本标『相关性较弱』」这条降级路径，**不是例外，而是 16 个标签的常态**。它把系统性错误包装成了一句免责说明。

所以本轮的处理比两家都更彻底：**兜底证据整类不进运行时**。不是"标一下较弱"，是"不展示"。池子小就如实小。

这条判断的代价写在 §五第 1 条。

## 四、执行记录

### 1. 派生层：逐标签证据等级

- `tools/derive-annotations.mjs`：`pt` 从 `[tag, weight]` 改为 `[tag, weight, source]`，`source` 取 `title` 或 `category`。索引里新增 `by_tag_source`（逐标签强弱构成 + 兜底占比）与 `strong_only`（运行时可见书数）。
- `tools/verify-derived.mjs`：独立重算的对手实现同步改造，并新增一条断言——**自称 `title` 的必须真在书名里，自称 `category` 的不得是书名命中**。只查权重不查等级，等于允许 0.4 的兜底标签自称强证据。
- `src/data/enriched.ts`：抽出纯函数 `toRuntimeTags()`，只放行 `title`；只有兜底证据的书整本不进 map。

### 2. 宽池：删掉「降级放行」这条路

- `src/engine/wide-need.ts`：移除 `MIN_POOL_FOR_STRONG` / `needFitStrong` / `isTitleEvidence` / `weak_ids`。少给几本，比给一堆不对题的书更符合「不凑数」。
- `src/engine/wide-pool.ts`：`WidePool` 去掉 `evidence` 与 `weak_ids`——它们会是恒为 `'title'` 和空集的死字段，留着只会诱使下游再写一次降级。
- `src/components/WideResults.vue`：池子 < 20 本时改成「这一条下我们能确认相关的只有 N 本，都在这里了。宁可少给，也不拿标签对不上的书来凑」。

### 3. 笔记导出与导入

- `src/domain/notes-file.ts`（纯函数）：`buildNotesFile` / `parseNotesFile` / `highlightKey`。5 类错误分开报（`E_NOT_JSON` / `E_NOT_NOTES` / `E_BAD_SHAPE` / `E_FROM_FUTURE` / `E_EMPTY`），版本只向前兼容。
- `src/domain/notes-shape.ts`：四个形状断言（章节引用 / 三种 Locator / 范围锚点 / 版本号）独立成文件。全项目**唯一**接触不可信数据的地方就在这里，单独一个文件才方便逐行审；顺带把 `notes-file.ts` 从 304 行压回 258 行，过 300 行门禁。
- `src/storage/notes-transfer.ts`：读写 IndexedDB。**本机没有的书不塞进去**——锚点是相对章节的字符偏移，书不同则偏移毫无意义，塞进去只会得到一堆点开跳错位置的划线。
- `src/components/shelf/NotesTransfer.vue`：书架页「带走我的划线」，导出/导入两个按钮 + 结果句。
- 书架页那句隐私提示同步改了：原来是「清掉站点数据 = 全部消失，且无法恢复」，现在是「清掉站点数据 = 本机副本消失。书要重新导入；划线与笔记可以用上面的导出留一份。」——**有了出口还说不出口，就是假话**。

### 4. 敏感过滤：从两个 if 变成一张表

- `src/domain/scoring/sensitive.ts`：`SENSITIVE_RULES` 声明「哪个域 / 哪些警告 / 过滤码 / 能否豁免 / 为什么」。新增关系域两条。
- `src/domain/scoring/filters.ts`：只剩执行。「人生转折」仍然不在表里，理由写在数据旁边（那一域的书大量以丧失为主题，剔了就一本不剩）。
- 新增 6 条测试：关系域触发、创伤不可豁免、选「最难也要读」时不触发、转折域不受影响、每条规则指向合法码、创伤类规则一律 `waivable: false`。

### 5. 不可信内容：核实结论与豆包不同

豆包建议「核实 EPUB 渲染是否在 sandbox iframe 里、index.html 是否有 CSP，若无则补」。核实结果是：

| 核实项 | 结论 |
|---|---|
| `v-html` / `innerHTML` / `insertAdjacentHTML` / `srcdoc` | **src 下 0 处**（115 个源文件全扫） |
| iframe | **0 处**——阅读器把书渲染成文本节点，不是 HTML |
| `index.html` 的 CSP | **已有**，`script-src 'self'` 且不含 `'unsafe-inline'`，另有 `object-src 'none'` / `base-uri 'self'` |
| 导入层对 XHTML 的处理 | 流式去标签成段落文本，书里的标签从来不交给浏览器解析 |

所以威胁模型在本实现里不成立——**不是"没防护"，是"结构上没有那个入口"**。但「现在恰好如此」不等于「以后一定如此」，一次为了省事的 `v-html` 就能打破它，而且打破时不会报错。

于是把这件事变成门禁：`tools/input-safety.mjs` 扫全部源文件（注释先剥掉）+ 检查 CSP 的最低要求，配 7 条自测（4 条必须能红、2 条不许误红、1 条扫到 0 文件必须报未验证）。

### 6. 纸墨令牌

- `docs/design-tokens.json` 与 `src/tokens.css` 同步改：中性灰从冷绿 `#F4F6F4 / #1B1F1D` 换成暖纸 `#FAF8F4 / #251C19`，主色从墨绿 `#2F6449` 换成朱砂 `#A5503A`，暗色从绿调炭黑换成暖黑 `#17130F`。
- **不是照抄方向值**：豆包给的 `#AD5C44` 在纸底上 4.51:1，刚好压线，换成了 `#A5503A`（5.20:1）。`tools/contrast-check.mjs` 27 组全部通过，最低 4.89:1。
- 新增 `--font-book` 衬线栈，只用在书名（结果卡 / 外部卡 / 宽池 / 书架 / 详情），控件保持无衬线。
- 结果页加处方笺页眉（印记 + 日期 + 一句「这张方子照你刚才的原话开，不替你做假设」），`src/styles/rx.css` 里带了打印样式：导航、按钮不进纸面。
  - 原稿写的是「不猜你喜欢什么」，被 `copy/promo` 门禁拦下（规则按子串匹配，不懂否定）。**改文案而不是给规则加否定语境**：让审计脚本去读语义，它就会从可靠变成不可靠。

### 7. 发布检查

`tools/release-check.mjs` + `npm run check:release`：查占位符、查物料齐全、查产物有没有被当仓库提交。**刻意不进 `npm run check`**——远程仓库没建时它必然红，把必然红的检查塞进 CI 等于训练所有人忽略红色。当前跑出来如实报 2 项：`docs/发布文案.md` 第 30–31 行的两个链接占位符。

## 五、关键取舍

### 1. 兜底证据整类挡掉，代价是 16 个标签的池子掉到个位数

修复后逐标签池子：`big-choice` 1 本、`emptiness` 1 本、`self-doubt` 3 本、`rumination` 5 本、`speaking-block` 5 本。界面会如实说「只找到 N 本」。

这是本轮最重的一次取舍：**从"看起来有很多相关书"退到"确实只有几本"**。理由是产品的第二条底线——不凑数。反过来说，如果哪天有人能给出千本级真标注，池子会自然长回来，接口不用改。

### 2. FSRS 不做（与豆包一致，与评述一致）

需要积累复习记录才能拟合参数，而产品连「有多少人会打开复习卡」都不知道。更关键的是：它给推荐链路引入一个需要参数拟合的子系统，而这条链路的价值主张是「同一输入永远同一结果」。

### 3. 处方卡回顾不做——但理由和两份材料都不同

两家都说「合并复习卡与读后自评」，方向我认同。不做的理由是**工作量性质**：68 本书 × 3–5 张卡 = 200–340 段预写文案，这是内容工作，不是代码工作。代码一周能写完，文案写不好就是第二个「LLM 现编理由」——正好踩在这个产品最不能退让的地方。先留着，等有人愿意按书逐本写。

### 4. 三档分组不改名

豆包建议改成「主方 / 辅方 / 加减味」。不改，两个理由：① 档位文案在 P0-5 契约里，改它会连带影响既有断言与所有历史截图；② 「加减味」在中医语境里指方剂配伍，不是"可以试试"，语义不准。隐喻改由**页眉印记 + 排序结构 + 打印样式**承担，不动文案层。

### 5. 示例书仍是 1 本

「先试手感」当前只覆盖一种篇幅。补 2 本自写短示例不违反 P0-13 的收缩理由（那三条是底本、校勘、整理者权利，自写不触发），但它不影响发布是否成立，排后。

### 6. 最小外部验证只做了数据侧

豆包的「20 个影子查询 + 5 人走查」里，5 人走查我做不了（没有真人，且用户此前明确说不安排外部人员测试）。数据侧那半其实已经被 R1 覆盖：`wide-pool.test.ts` 现在会打印真实池子与首批书名，「明显离谱」如果出现会当场看见。

真人走查仍是缺口，写进 §六。

## 七、这一轮的方法论收获

**两份评估都指对了症状，但都停在"改那条映射"上。真正的修法要去数映射的基数。**

「豆瓣大类 → 困境标签」这件事，1:1 是证据，1:多就是分类。而分类再加一步「每本只留 3 个」，就变成了抽签——**中间那一步截断把"分类不准"放大成"随机"**，这是单看一条映射看不出来的。

所以下次遇到「数据看起来不准」，先算三件事：反向映射的基数、截断规则、以及各标签的强弱证据构成。三个数字一摆，"要不要降级放行"这种争论会自己消失。
