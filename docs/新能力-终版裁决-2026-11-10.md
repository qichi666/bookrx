## 4. B 的六条偏差：采纳与否

| # | B 的主张 | 裁决 | 理由 |
|---|---|---|---|
| 1 | 弃读要写 `abandoned_at`，并在写入/读取两端显式处理 | **采纳（收窄）** | 加一个可选字段、读取端 `?? updated_at` 兜底；但**不需要**新字段也能上，先按可选做 |
| 2 | 主题层叠必须「显式属性覆盖 media、auto 回落 media」 | **采纳（再简化）** | 见 4.1：**浅色不需要复制一份令牌块**，B 的方案会让 tokens 多出 37 行重复 |
| 3 | 备份冲突按三种性质分类，并写 `sessionStorage` 回滚快照 | **分类采纳，快照不采纳** | 见 4.2：只增不删就不需要回滚；`sessionStorage` 有 5MB 上限，大库会失败，反而制造假安全感 |
| 4 | 目标要存 `history`，按 `effective_from` 分段算 | **不采纳** | 会引入第二套进度算法与「历史目标完成情况」的展示，收益不抵复杂度；改为 UI 明示「改目标会重算本年进度」 |
| 5 | 热力图窄屏降级为周视图 | **采纳** | 375px 无横向溢出是已实测的硬指标，365 格必然溢出 |
| 6 | 「零迁移」要精确措辞 | **采纳** | 统一写成「不升 `DB_VERSION`、不新增 store；新增字段一律可选、读取端兜底」 |

### 4.1 主题层叠：比 B 更省的写法

现有 `tokens.css` 的基础 `:root` 本身就是浅色，所以：

- 显式浅色**只需要写 `data-theme="light"` 这个属性**，不需要任何浅色令牌块——属性一存在，media 块就不再匹配，基础浅色自然生效；
- media 块改成 `:root:not([data-theme])`，只在「跟随系统」时生效；
- 显式深色用一个 `:root[data-theme="dark"]` 块，与 media 块内容相同（这段重复无法避免，CSS 没有变量复用）。

净效果：只需新增一个深色块 + 给 media 块加一个条件，比 B 的「浅色深色各写一份」少一半重复。

### 4.2 备份恢复：只增不删，就不需要回滚快照

`importBackup()` 的语义定为「**只新增与用户逐条确认的替换，绝不删除目标库里的任何记录**」。在这个前提下：

- 相同记录 → 跳过且不计入报告；
- 同 id 不同内容 → 进冲突列表，逐条选「保留本机 / 用备份里的」；
- 目标库没有 → 直接写入。

因为不存在自动删除，回滚快照就没有必要；需要的是**恢复前的一次确认页**（将写入 N 条、跳过 M 条、冲突 K 条）和**恢复后的结果报告**。

## 9. 风险

1. **`ShelfGroup` 是联合类型，加成员会让所有 `Record<ShelfGroup, ...>` 报错**——这是好事（编译器帮你找齐），但要一次改完 `shelf.ts` / `LibraryView` / 统计口径，别留半成品。
2. **主题层叠**是本批唯一「写错了但不报错」的地方：必须真机验证「系统深色 + 手选浅色」与「系统浅色 + 手选深色」两个组合。
3. **备份恢复是唯一的写操作**：默认路径必须是「什么都不删」，否则一次误操作会毁掉用户全部积累。
4. **统计口径**：弃读既不能进读完率分子，也不能进分母，否则这个数字会开始骗人。
