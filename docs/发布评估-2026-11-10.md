## 3. 与主要竞品的功能对比

| 维度 | **BookRx（当前）** | StoryGraph / Hardcover | Reading Well / Book Therapy | Paguely / Embertale | 微信读书 / 豆瓣 |
|---|---|---|---|---|---|

| 按困境/处境匹配 | **33 标签确定性匹配** | 仅 mood/pace，非困境粒度 | 有（人工/书单） | 有（生成式） | 无（按人群/榜单） |
| 推荐可解释 | **七因子字段级 + 一句话解释** | ML 黑箱 | 人写理由，不可扩展 | 生成式理由 | 无 |

| 书籍/元数据规模 | 68 核心 + 6551 候选（仅元数据） | **Goodreads 系规模碾压** | 小 | 依赖外部书目 | **海量正版** |

### 3.2 GitHub 开源竞品

| 项目 | 形态 | 关键差距 |
|---|---|---|
| Openreads | Flutter，本地无账号 | 隐私立场一致，但**无推荐内核** |
| PageVault | MIT，本地/自托管 | 阅读器+全文检索+20 图表，**无处境确定性打分** |
| LightRead（yzfly） | Tauri+Vue，本地 | 最接近的中文竞品；书单标来源但**非字段级可解释/可复现打分** |
| BookWyrm | 联邦、自托管 | 需选实例/服务器，无推荐算法 |
| Readest | 多端阅读器 | 强阅读器、有同步，**无诊断推荐** |
| BookNook / RAG 类 | 本地 Docker/LLM | 语义匹配但**不可复现**，与确定性内核冲突 |

### 3.3 三类差距的定性

- **功能覆盖**：BookRx 已覆盖 local-first 单人阅读管理的全部标配，并多出「处境诊断 + 可解释 + 凭证」；**落后项是统计深度与元数据规模**，但这两项都强绑定账号/云，与产品定位冲突，不应追平。
- **体验完整度**：闭环完整、离线可用、空态诚实、无负罪感设计；**唯一体验限制是内容主要靠用户自备（2/68）**。
- **差异化**：「困境因果 × 可解释 × 可复现 × 零收集 × 危机安全」五交集**无直接对等物**，是发布的核心卖点。

## 4. 是否还需新增/优化功能

### 4.1 功能层面：**无需再改即可发布**

理由与依据：

1. **所有自动化门禁全绿**，且每条门禁自带「能红/不误红」测试，结论只有通过/失败/未验证，不存在「假通过」；
2. **终版识别的全部标配深度缺口已在代码中闭合**（今日区块、关系图谱、回执聚合、检索高亮、处方笺、读完率、路由兜底均已实测存在）；
3. 剩余的「更全统计、更大书目」是**商业模式差异**而非缺陷——追平必须引入账号/云，会直接摧毁零收集与可复现的差异化，属范围冻结项；
4. 危机安全、隐私、输入净化等**发布级风险项均有硬门禁**，不是靠人工保证。

### 4.2 缺失/可增强项与优先级（**均不阻塞发布**）

| 项 | 类型 | 优先级 | 理由 |
|---|---|---|---|
| 扩公版直读，降低 2/68 站内可读比例 | 内容工程 | **P1（发布后首个立项）** | 这是定位 vs 能力唯一实质差距；但属公版录入+版权核查，非功能缺陷，不阻塞当前发布 |
| 薄标签继续补书（现最薄 3 本） | 内容 | P2 | 紧迫度已下降，按目标用户困境分布决定节奏 |
| 自愿回执回传（不破坏零收集） | 产品 | P2 | 当前只能靠用户主动导出，是否需要一种自愿回传方式待业务目标确认 |
| 真实浏览器/线上冒烟 | 验证 | **发布前必做（非开发）** | 补齐 happy-dom 看不到的 CSS/路由/CSP 与部署环境 |

### 4.3 明确不做（加了反而损害产品）

账号/云同步、星级评分、UGC 社区、ML/LLM 生成书单、心理量表、推送、打卡排行榜、预缓存全部 chunk——这些要么破坏可复现与零收集，要么违背已冻结范围，**发布后也不应加回**。

## 5. 发布前检查清单（无开发工作量）

1. 跑一次真实浏览器冒烟（Playwright + 指定 chromium），覆盖 19 路由 × 桌面/375 两视口，确认 0 横向溢出、0 console error、触控 ≥44px；
2. 确认危机资源核对日期在 90 天内（`audit:crisis` 已绿，发布当天再确认一次）；
3. 部署 GitHub Pages 后线上复验：hash 路由、刷新不 404、危机热线可点、PWA 可安装；
4. **对外口径诚实**：明确「诊断器 + 本地阅读管理，书主要自己带进来」，不得出现「68 本都能在这里读」的暗示；
5. 确认 `catalog/` 候选数据的授权提示保留（候选池不在 MIT 范围，禁止单独再分发）；
6. 保留 `check:release` 未配 key 时「未验证」的如实状态，不把它当绿灯也不强行阻断。

## 6. 发布后路线（分阶段，滚动推进）

| 阶段 | 内容 | 性质 |
|---|---|---|
| 发布后第 1 阶段 | 公版直读扩容，把站内可读从 2 本向上提升，缩小 2/68 | 内容工程，最高优先 |
| 发布后第 2 阶段 | 按真实使用的困境分布补薄标签；评估自愿回传 | 内容/产品 |
| 发布后第 3 阶段 | 基于真实阅读速度做计划页增强（仅展示，不改稳定性） | 数据积累后 |

全程保持硬约束：不碰打分内核、`domain/` 禁随机与时钟、不新增存储字段、危机配额恒 2、单文件行数红线不破。

## 7. 风险与免责

- **内容落差被误读**：若营销夸大站内可读规模，会造成预期落差；以第 5 节口径约束规避。
- **浏览器/部署差异未覆盖**：单测无法替代真实浏览器，必须执行第 5 节冒烟，否则「全绿」不等于「线上无问题」。
- **危机资源时效**：超过 90 天需重新核实官方页面，这是持续义务而非一次性。
- **数据本地风险**：清站点数据/换浏览器即丢失，界面已如实告知，导出是用户主动行为。

---

## 8. 最终裁决

**BookRx 当前版本可发布，且功能层面无需再新增或优化。** 依据是全量门禁与生产构建退出码均为 0、456 条测试全过、危机与隐私硬门禁生效、五维差异化无对手。唯一遗留的 2/68 是内容侧深度问题，不构成发布阻塞，但必须：① 对外文案诚实、② 发布后作为首个立项推进、③ 发布前完成真实浏览器与线上冒烟。
