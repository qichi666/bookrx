## V2EX（节点：分享创造 / 程序员）

**标题**：书方 BookRx — 输入困境得 5 本书，纯前端、无账号、不上报，同一输入永远同一结果

**正文**：

做了一个小工具，解决一个自己的问题：状态不好的时候想找书看，打开豆瓣被评分带着走，问 AI 得到一堆泛泛的书单，都说不出「为什么是这本」。

书方的做法是把「为什么」写进算法：

- 4 屏问卷（困境 → 具体感觉 → 读书偏好 → 自由描述），不用注册，填完直接出 5 本；
- 推荐是**本地确定性算法**：七个因子按万分制权重打分，硬过滤先于打分（难度太高的书分数再高也不出现），同一输入永远得到同一结果——刷新一万次顺序不变；
- 每本书只给档位（高度契合 / 较为契合 / 换个角度），**不给分数或百分比**——加权和不是概率，渲染成"92% 匹配"是伪造精度；
- 书库里没有的书，直接列书名标「未入库」告诉你去哪找，**不会拿不对症的书凑满 5 本**；库里一本都对不上时明说「这些都不对」，请你换个说法再讲一次；
- 一条红线：问卷里写出危机信号时，只给心理援助热线（12356），不给书单。

- 读的部分也是本地的：导入自己的 EPUB / TXT（浏览器里解压切章，零依赖、不上传），真翻页、改字号不丢位置、划线跨版式可恢复；装一次 Service Worker，之后离线也能开。

技术上：Vue 3 + Vite + TS，纯前端零后端，运行时只有 vue + vue-router 两个依赖。412 项测试锁行为，危机入口的数量、CSS 令牌是否存在、文案禁用词都有门禁守着（错了就发不了版）。另外有一条真实浏览器冒烟脚本，走完问卷→推荐→导入→阅读→划线全流程。

仓库：`https://github.com/qichi666/bookrx`（MIT，书目数据除外）
演示：`https://qichi666.github.io/bookrx/`
书库现状：68 本人工逐字段标注（参与打分）+ 6551 本只做书名/作者检索。

欢迎拍砖，尤其欢迎对打分权重设计的批评。

## 即刻（圈子：一起做产品 / 独立开发）

**标题**：做了个「困境找书」的小应用，最得意的是它会说"这些都不对"

**正文**：

市面上的找书工具都在努力"永远给你结果"，我做了一个反着来的：

状态不好想读书 → 4 个小问题 → 5 本书 + 每本为什么是它。

它有几个固执的地方：

1. 库里没有合适的书时，它说「这些都不对」，请你换个说法再讲一次——绝不拿三本不对症的书把列表填满；
2. 只给「高度契合 / 较为契合 / 换个角度」三个档位，不给 92% 这种数字——它认为那是伪造精度；
3. 你写出危机信号时，它不给书单，给心理热线。

纯前端、零后端、不上报，数据全在本机。同一输入永远同一结果，因为它压根没有"猜"的环节。

书库：68 本人工逐字段标注（参与打分）+ 6551 本只做书名/作者检索（标「未入库」，不参与打分）。

另：阅读器也是自己写的（没有引入任何现成的 EPUB 引擎）。因为标注是用户最舍不得的东西，而大多数方案把标注绑在页面 DOM 上——用户换一份版式不同的文件，高亮就会静默跑到别处。这里改成记「章节 + 字符偏移 + 原文引文」，找不到就明确告诉你找不到，不假装。

演示链接：`https://qichi666.github.io/bookrx/`

## 少数派（首页投稿）

**标题**：把「为什么是这本书」写进算法：书方 BookRx 的确定性荐书设计

**正文**：

（摘要）推荐系统的通病是给结果不给理由。本文介绍一个纯前端荐书应用的设计取舍：七因子万分制打分、档位而非分数、空结果的诚实呈现，以及为什么这些都必须以"无网络请求"为前提。

**一、为什么不用评分**

豆瓣评分回答的是"大家觉得这本书怎么样"，回答不了"这本书对你的处境有没有用"。同一本《思考，快与慢》，对决策纠结的人是四星答案，对睡前想放松的人是两星答案——书没变，人变了。

书方把"人"写进输入：4 屏问卷得到困境标签（主诉 / 次诉 / 第三标签，权重 0.60 / 0.25 / 0.15）、读书偏好（难度 / 篇幅 / 紧迫度 / 体例 / 深浅）。每本书有 34 个手工标注的字段。两者相遇，七个因子各算一个"贴合度"，按万分制定点整数加权求和——全程无浮点、无随机、无时钟，同一输入跨设备逐字节同结果。

**二、为什么只给三档不给分数**

打分是加权和不是概率。渲染成"92% 匹配"会引发三件坏事：用户开始跨次比较分数、跨版本比较分数、以及以为那个数有统计含义。三档（高度契合 / 较为契合 / 换个角度）+ 主诉未命中时封顶到「换个角度」（分数不动、标签变——这是故意的），让排序力留在排序里，语义留在标签里。

**三、空结果是特性不是故障**

书库永远小于人的困境。库内一本都对不上时，产品明说「这些都不对」，引导用户重述困境，同时列出库外书名（必标「未入库」，理由禁止引用任何打分口径——那本书没被打过分）。不凑数是产品的诚实性底线。

**四、危机信号互斥**

问卷自由文本命中危机关键词时，结果页只显示心理援助热线，不显示任何书单。这个互斥逻辑和「援助入口必须有且仅有两个」一样，由构建期门禁强制——不是文案约定，是发不了版的硬约束。

**五、为什么不联网**

推荐在本地跑完，就不需要把你的困境发给任何服务器。所有数据存本机浏览器，卸载即消失。这既是最简单的隐私方案（没有数据出口，何谈泄露），也是可复现的前提（没有 A/B、没有灰度、没有"你是不是给我降权了"）。

项目开源（MIT，书目数据除外），书库 68 本首发（人工逐字段标注），欢迎参与书目共建；也欢迎拿自己手上的书来试导入——导入链路的失败态是这一版最需要真实样本的地方。

## GitHub Release v0.1.0

> 用法：仓库页 → Releases → **Draft a new release** → Tag 选 `v0.1.0` → 标题与正文照抄下面。

**标题**：`v0.1.0 — 说困境，拿 5 本书，当场开读`

**正文**：

```markdown
第一个可以公开试用的版本。没有账号、没有后端、没有埋点。打开就能用。

**能干什么**

- 4 屏问卷 → 5 本书，每本都写清「为什么是它」
- 结果分三档（高度契合 / 较为契合 / 换个角度），**不给百分比**
- 库里一本都对不上时明说「这些都不对」，请你说得更具体一点，不拿不对症的书凑数
- 导入自己的 EPUB / TXT 就地阅读：真翻页、改字号不丢位置、划线跨版式可恢复
- 装一次 Service Worker，之后断网也能打开
- 问卷里出现危机信号 → 只给心理援助热线，不给任何书单

**书库**

| 层 | 数量 | 参与打分 | 能被搜到 |
| --- | --- | --- | --- |
| 核心库（34 字段人工逐字段标注） | 68 本 | 是 | 是 |
| 候选池 | 6551 本 | 否 | 是 |

候选池里 1872 本带有强证据困境标签，可以进同题书；其余 4679 本只做书名 / 作者检索。库外结果一律标「未入库」，理由不得引用任何打分口径——那本书没被打过分。

**怎么算的**

七因子万分制：困境 3800 / 难度 1800 / 深度 1200 / 体例 1000 / 篇幅 1000 / 可读性 700 / 可得性 500。硬过滤先于打分（难度过高的书分数再高也不出现）；`src/domain/` 里禁用了 `Math.random` / `Date.now` / `performance.now`，由测试强制——同一份输入跨设备逐字节同结果。

**怎么跑**

```bash
npm install
npm run dev     # 开发
npm run build   # 构建（会连带跑一串数据校验）
npm run check   # 门禁：412 项测试 + 10 项审计
```

Node ≥ 20。运行时依赖只有 `vue` 和 `vue-router`。

**已知的不完美（写在这里，不让你自己去撞）**

1. **书库小**。68 本只覆盖常见困境，冷门主题很可能返回「这些都不对」——这是设计，不是故障，但第一次体验确实容易撞墙。
2. **候选池没有逐字段标注**，只能被搜到，不进排序。
3. **导入链路的失败态样本很少**。你手上的 epub 越奇怪越有价值，出问题请开 issue 带上文件结构（不需要传书本身）。

**许可**：MIT。`catalog/` 下的书目数据除外，来源与限制见 `docs/数据与推荐方案.md`。

在线试用：https://qichi666.github.io/bookrx/
```

### r/SideProject

**Title**: `I built a book recommender that tells you "none of these fit" instead of padding the list to five`

**Body**:

```
Every book tool I tried optimizes for "always give an answer". Open Douban, you get
ratings. Ask an LLM, you get a list of famous books with no explanation of why *that*
book for *you*.

So I built the opposite. You describe what you're stuck on, answer four screens of
questions, and get five books — each with a specific reason tied to something you
actually said.

Three things I deliberately made worse:

**No match score.** Only three buckets: strong fit / different angle / worth a look.
A weighted sum is not a probability. Rendering it as "92% match" is fake precision,
and it makes people compare scores across sessions where the comparison is meaningless.

**It says "none of these fit".** If nothing in the library is actually relevant, it
tells you that and asks you to rephrase. It will not fill the fifth slot with a book
that has nothing to do with your problem. That is the single hardest thing to make
myself do, because an empty result feels like a bug.

**No backend at all.** The whole recommendation runs in your browser. No account, no
analytics, no third-party requests. The scoring code is not allowed to call Math.random
or Date.now — there's a test that fails the build if it does — so the same input
gives byte-identical output on any device. You can read the weights and argue with them.

What's actually in it:

- 68 books I annotated by hand across 34 fields (that's what participates in scoring)
- 6,551 more from a public catalog, search-only, always labeled "not in library"
- 7 weighted factors, 10,000-point integer scale, hard filters before scoring
- You can also import your own EPUB/TXT and read in-app, offline after the first load

The honest limitation: 68 books doesn't cover much. Niche topics will genuinely return
"none of these fit". That's the design working, but I know it's a bad first experience.

Demo: https://qichi666.github.io/bookrx/  (UI is Chinese — if there's interest I'll
translate it, I just haven't had a reason to yet)

Source: https://github.com/qichi666/bookrx

I'd rather hear what's wrong with the weighting model than what's nice about the UI.
```
