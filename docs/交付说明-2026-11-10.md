## 1. 一句话

**BookRx（书方）**：说清你此刻的困境，它给 5 本确实对味的书，每本说清为什么是它——能读的直接在这里读。

纯前端、无账号、无服务器、零第三方请求。推荐结果**确定性可复现**：同一份问卷永远得到同一份书单。

## 2. 需求分析

### 2.1 要解决的问题

所有榜单都在回答「哪些书好」，没有人回答「**以我现在的状态，我能读完哪一本，读完会变好吗**」。

两个被忽视的事实：

1. **推荐失败的主因不是书不好，而是读不完。** 8.9 分的书对一个连续 12 个月没读完一本书的人，等于 0 分。
2. **「买了等于读过」是一种代偿。** 书越堆越高，人越不敢开始。

### 2.2 目标用户

| 画像 | 占比 | 典型诉求 |
|---|---|---|
| 买了很多、读不完 | 60% | 别再给我 20 本，给我 1 本今天能翻开的 |
| 读了很多、记不住 | 30% | 读完能留下点什么，别读完就忘 |
| 想参与共建 | 10% | 能贡献标注、能反馈书单不对味 |

年龄段 22–35 岁，中文用户，有阅读意愿但近一年没有完整读完一本书。

### 2.3 与替代方案的关系

| 替代方案 | 它回答的问题 | 为什么不够 |
|---|---|---|
| 电商 / 畅销榜 | 最近什么好卖 | 买回来不对味，形成买书代偿 |
| 小红书 / 公众号书单 | 一次给 20 本 | 没有一本是为他选的，收藏完一本都不开始 |
| 豆瓣 | 大众平均分 | 无公开 API；大众平均不等于对他的适配 |
| 微信读书 | 有书、有社交 | 推荐按人群偏好，不解决「我该读哪本」 |
| `yzfly/LightRead`（最接近的开源竞品） | 阅读器 + 顺手几张书单 | 推荐藏在设置里且默认关闭；本项目是「诊断器 + 自带阅读器」，主路径就是诊断 |

### 2.4 三条业务底线（不可协商）

1. **危机优先**：诊断命中危机信号时，只给心理援助热线，不给任何推荐。援助入口全项目配额恒为 2 个，多一个或少一个构建直接失败。
2. **不凑数**：库内没有合适的书就明说，引导重述困境，同时给出库外书名（标「未入库」）。
3. **理由可追溯**：每句推荐理由要么来自预写文案，要么来自打分字段，**不允许模型现编**。界面上每句理由带来源徽章（书里写的 / 你的回答 / 书的标注）。

### 2.5 明确不做（范围已冻结，不要再提议加回来）

- 不做社区、评论、关注、打卡、排行榜
- 不做 PDF、漫画、TTS、OPDS
- 不做账号、云同步、任何上报式埋点
- 不接 LLM 打分或生成推荐理由（结果不可复现）
- 不做豆瓣评分作为匹配依据（评分只用于「别推垃圾」，不进契合度）

## 3. 方案设计

### 3.1 四条架构原则

1. **问卷主链路不被阻塞**：诊断 → 打分 → 推荐仍是第一入口，扩展模块是结果下游与回访理由，不是前置。
2. **隐私承诺的语义是「没有服务器可以上报」**，不是「承诺不上报」。新增数据只写本机 IndexedDB，导出是用户主动触发的下载。
3. **确定性内核不受污染**：`src/domain` 内禁止 `Math.random` / `Date.now` / `new Date` / `performance.now`，由测试拦下。日期、排序持久化字段一律放在 `storage` / `lib` / 视图层。
4. **单人维护现实**：治理面板只服务唯一维护者，不引入服务端权限体系。

### 3.2 产品结构：四段闭环

v1 只有第一段（推荐），后三段完全缺失。v4 方案把产品补齐为：

```
① 处方          ② 留存          ③ 积累          ④ 凭证
诊断 → 打分      想读 → 在读      时长 → 回执      打印 / JSON / 摘图
→ 推荐            → 读完          → 笔记 → 统计
   ↑                                                    |
   └────────────── 回访理由 ←───────────────────────────┘
```

| 段 | 解决什么 | 对应模块 | 竞品对标 |
|---|---|---|---|
| 处方 | 我该读什么（原先不可见、不可解释） | F1 F2 F3 F8 | Reading Well / Book Therapy |
| 留存 | 看到的不丢（原先 66/68 外链书一跳走就断） | F5 F6 | StoryGraph Up Next Queue |
| 积累 | 我读进去了（原先无时长、无天数） | F7 F9 F11 F12 | StoryGraph Stats / Hikara |
| 凭证 | 能带走（原先无任何可分享物） | F4 F10 | Reading Well 推荐表 |

### 3.3 推荐算法（核心，务必读准单位）

```
问卷 / 自由文本 → 诊断 → 硬过滤 → 七因子打分 → 六级排序 → 三档分组 → 5 张卡
```

**单位铁律**：全链路用**万分制整数基点（bp）**，不是 0–1 小数，不是百分数。权重之和恒为 10000。

**第一步：诊断**

- 问卷点选的困境标签按 `0.6 / 0.25 / 0.15` 取权重。
- 主诉由用户**显式指定**（选完标签后追问「哪个最急」），不按点击顺序猜。
- 自由文本命中词典里的标签时，按 `max(现有, 0.6)` 并入；命中新标签按 `0.15` 追加，且**只进分子不进分母**——否则「说得更具体 = 推荐更没把握」。

**第二步：硬过滤**（打分之前，7 条规则码）

| 规则码 | 拦什么 | 可否豁免 |
|---|---|---|
| `excluded-by-user` | 用户主动排除 | 否 |
| `metadata-only` | 只有元数据、无正文 | 否 |
| `no-problem-tags` | 无任何困境标签 | 否 |
| `EX-difficulty` | 难度超限 | 否 |
| `EX-load` | 认知负荷超限 | 否 |
| `EX-trauma` | 创伤内容（自杀、性暴力） | **永不可豁免** |
| `EX-terminal` | 临终丧亲 | 可被「我能接受沉重内容」开关豁免 |

原则：**开关承诺的范围必须等于放行的范围**。

**第三步：七因子打分**

| 因子 | 权重 | 算法 |
|---|---|---|
| `problem` | 3800 | 覆盖率口径：`Σ min(你的权重, 书的权重) / Σ 你的权重` |
| `difficulty` | 1800 | `10000 − bp(|书的难度 − 你的目标| / 4)` |
| `depth` | 1200 | 同档 10000 / 相邻 6000 / 跨档 1500 |
| `form` | 1000 | 文体形态：叙事 / 方法 / 框架 |
| `length` | 1000 | 篇幅档差 0/1/2/3 → 10000/6000/2500/0；「不限」→ 7000 |
| `readability` | 700 | 文字可读性，同 `difficulty` 的距离算法 |
| `availability` | 500 | 站内可读 10000 / 自备 5500 / 外链 2500 |

三条反直觉但必须遵守的规则：

- **跳答 ≠ 填中位数**：没答的那组对应因子整条移除，权重按比例重分配。填中位数会让未观测维度稳定输出 5000 分。
- **可得性不许当主角**：`availability` 归一化后也不许超过 800 基点，超出部分还给其他因子。真正承担「优先推能读的」的是排序第 4 级。
- **不给缺失字段填默认值**：字段没标过的书，对应因子整条不参与打分，并如实报出覆盖率——那是**不知道**，不是**不好**。

**第四步：六级全序排序**

```
score ↓ → problem.fit ↓ → difficulty.fit ↓ → availability ↑ → est_reading_hours ↑ → book_id ↑
```

最后一级保证全序；整条链**不含任何时间字段**，否则结果会随时间漂移。

**第五步：三档 + 两条封顶**

- 阈值：`≥8000` 较为契合 / `≥6000` 值得一读 / 其余 可以试试。
- 阈值是**绝对值不是分位数**——分位数保证每次都有「较为契合」，那档位就没有信息量了。
- 封顶一：**主诉全不命中 ⇒ 封顶「可以试试」**。其余六因子合计 6200，一本完全不沾题的书只要难度、篇幅、体例全中就能混进「值得一读」，而「较为契合」对一本没回答你问题的书是谎话。
- 封顶二：**标注覆盖率不足 ⇒ 封顶「值得一读」**（`STRONG_MIN_COVERAGE_BP = 6000`）。候选层只有困境标签一类信息，用 43% 的信息讲「高度契合」是编造。
- 界面上**只给档位，不给百分数**：避免分数崇拜，也规避版权争议。

### 3.4 三层书库（包含关系，不是并列）

| 层 | 规模 | 有什么 | 怎么用 |
|---|---|---|---|
| 核心库 | 68 本 | 34 个字段齐全，含 5 段预写文案 | 进主推荐池，能出完整理由 |
| 候选池 | 6551 本 | 元数据 + 豆瓣标签 | 宽池「和你这个困境相关的还有 N 本」 |
| 派生标注层 | 6551 本全覆盖 | 由 33 标签词表派生的困境标签 | 让没人工标注的书也能进池，并报覆盖率 |

- 其中 **1872 本**带强证据困境标签（`annotation` 0.95 / `title` 0.85–0.9），可进「同题书」；其余 4679 本只能被搜索框找到，不打分。
- `category`（豆瓣大类，0.4）**运行时不放行**：实测 27/33 个标签的兜底占比 ≥80%，拿它推书等于乱推。
- 评分数据 5646/6551 条，用贝叶斯收缩 `(rating × votes + 50 × m) / (votes + m)`，`votes < 10` 记 `null`。评分**不进契合度**，只用于质量档轮转、劣质淘汰、同分排序。

### 3.5 两处实现裁决（与早期规划不同，以这里为准）

**裁决一：读后回执不接回推荐算法。**

原方案写「回执反馈排序」。实现时否决，理由两条，第二条是硬的：① 回执是读者当下的一次主观判断，反复加权会把人困在第一次的选择里；② **一旦本机回执参与打分，同一份问卷在不同时间会得到不同结果**，直接摧毁「可复现」与六级全序。

回执的实际用途只有三个：读完不再重复弹、本机统计里的有用率、用户自己导出。它不进 `src/domain`，也不进排序。

**裁决二：本机档案按档案分库，不做全表 `profile_id`。**

原设计要给十张表改键、改索引、回填默认档案，并让每个读写函数都记得带过滤条件——漏一个就出现「切了档案还看得见上一个人的笔记」这种最伤信任的事故。

实际实现：默认档案沿用 v1 老库名 `bookrx`（**老数据零迁移**），其余档案各自一个 `bookrx:p:<id>` 库；档案清单固定写在默认库的 `profiles` 表。隔离由数据库边界保证，读写函数一行未改。

### 4.1 逐模块说明

**F0 存储层**
IndexedDB `bookrx`，`DB_VERSION = 2`，10 张表：`books` `chapters` `files` `progress` `shelf` `annotations` `notes` `sessions` `receipts` `profiles`。按库名复用连接；`closeAll()` 供档案切换与删除使用；`onversionchange` 让路给其他标签页。

**F1 首页工作台**
首屏不再只有问卷：`开始诊断` + 四张常用入口卡（书库 / 我的书架 / 阅读统计 / 怎么读书），卡片可关闭、可恢复（偏好存 `localStorage` 的 `bookrx.home.hidden`），卡片关闭键 44px。数字条（68 本 / 33 标签 / 34 字段）从数据计算，不写死。

此外有一个「今天」区块：在读的那一本带进度一键回去，另加一条用户自己以前划过的线，每天换一条，点「回到这句」跳到原段落（`?ch=&off=` 深链）。选取是确定性的（`lib/daily-pick.ts` 的 FNV-1a 散列，日期由调用方传入），同一份数据同一天刷新多少次都是同一条；没有数据时整块不渲染。

**F2 导航**
5 个入口：书库 / 书架 / 统计 / 怎么读书 / 关于。375px 下不折叠。选 5 而不是 6，是因为 6 个必然挤成汉堡，等于没扩展。

**F3 书库**
68 本全量浏览，四维筛选（困境 / 难度 / 时长 / 可得性）+ 排序，筛选状态写进网址 query。非法 query 值一律按「不筛选」处理（`?diff=abc` 不会变成空书库）。

**F4 凭证**
- A4 书方打印（`@media print` 隐藏全局导航，默认不打印困境标签）
- 带 `schema_version` 的 JSON 导出
- 书摘图（Canvas 2D 绘制，不引截图库），两种版式：通用引文卡 + 「一日一方」处方笺；两者都**不含困境标签与档位**

全部本地生成，零网络请求。

**F5 想读队列**
推荐结果、书库、详情页都能「加入想读」；`/library` 里可上移 / 下移 / 移出，不覆盖在读与读完。排序值用 `sortOrder`，未排过队的条目按 `MAX_SAFE_INTEGER - 显示位置` 折算，保证「下移」是严格一换一。

**F6 读后回执**
读到末页弹一次三选一 + 可选理由；同书不重复弹；每次会话最多邀请一次（点「以后再说」后往回翻再翻回来不再弹）。只进本机统计，不参与打分。

**F7 阅读统计**
近七天时长、连续天数（带 2 次冻结额度，断一天不清零）、时间花在哪几本、回执有用率、**读完率**（分母 = 在读 + 读完，想读不算——收藏不叫开始）。空状态不画假图表。会话计时只在页面可见时累加，单次不足 20 秒不落库；每本书的累计时长有固定基线，翻页或切后台不会重复累加。

**F8 可信度面板**
详情页把七因子写成中文得分条，并标注每一档的来源。卡片档位与面板解释共用同一个 `tierOf(score, primaryHit, coverage)` 契约（第三参数不能省，否则覆盖率封顶失效）。

**F9 书籍对比**
2–3 本并排看难度、篇幅、体例、共同标签；窄屏横向滚动，不压缩字号。

**F10 笔记总览**
跨书全文检索（命中词在引文与笔记里直接高亮，并标出命中在书名 / 引文 / 笔记），划线与笔记按书分组，可导出书摘图。划线位置由选区在段落里的真实偏移决定，同段重复句不会跳错。

**F11 读书计划**
按预计时长把想读排进四周。单本超周额度时单独占一周（不拆半本跨周）；四周装不下的书进 `overflow` 并在界面单列「四周排不完，先放在这儿」，**不塞进最后一个格子**——否则会出现「第 4 周 35 小时」和你填的「每周 6 小时」对不上。缺时长按 6 小时估并标出。有实测数据时逐本显示「你已读 X 小时」，并在两本以上时提示「实际用时是预估的百分之多少」——**这只是提示，排期仍按预估算**。

**F12 本机档案**
新建 / 切换 / 删除档案；切换后书架、笔记、阅读记录互不可见，由数据库边界保证。默认档案与正在使用的档案禁删。界面显示「这份档案里：书架 N 本 · 笔记 M 条 · 阅读记录 K 次」，让隔离可自查。

**F13 治理面板**
标签厚度、最薄标签、危机资源核实状态、本机回执聚合，以及**回执按困境聚合**（按书的最高权重标签归组，看哪一类被标「不适合我」的比例最高；n<3 标「样本太少」）。只读，不入主导航。

**F15 书籍关系图谱**
详情页「这本之后，可以接着看」：分「接着读 / 补另一半 / 换一种解法」三类，每本附一句为什么接得上。
关系**方向由人定**（`data/tag-relations.ts`，30 条），**具体哪一本由标签权重算**（`domain/relations.ts` 纯函数）。
不新增书字段、不调模型、不看时间；排序为「类型 → 权重和降序 → book_id 升序」，同一份输入永远同一份输出。

### 4.2 原有能力（v1，仍在运行）

- **推荐**：硬过滤 + 七因子打分 + 三档分档，5 张卡。

### 8.1 未解决的结构性问题

| 编号 | 问题 | 现状 |

| 单文件行数 | `src/` ≤300 行 | 已由 `audit:style` 守住，当前 167 文件全过 |

### 8.2 工程陷阱（接手必读）

1. **单位**：全链路万分制整数 bp，不要引入 0–1 小数或百分数。
2. **`domain` 不许有时间和随机**：`Date.now` / `Math.random` / `new Date` / `performance.now` 一律不许出现在 `src/domain`，测试会拦。
3. **`tierOf` 三参数不能省**：漏第三参数会默认满覆盖，覆盖率封顶失效。
4. **本机导入书的 `shelf` 行是它存在的凭证**：删掉这行，书还在库里但书架上看不到、找不回来。
5. **IndexedDB 事务清单必须完整**：事务里用到的表都要列进 `db.transaction(stores)`，少一张即 `NotFoundError`。
6. **档案删除会遇到 `onblocked`**：另一个标签页还开着该档案时会卡住，代码里已转成可读错误提示。
7. **hash 路由**：任何 `#xxx` 都会被当路由，页面内锚点不能用 `<a href="#foo">`，要用事件或 `scrollIntoView`。
8. **`check:release` 报「未验证」不是失败**：它需要 `DEEPSEEK_API_KEY`，没有 key 时门禁如实报未验证，不要当成绿灯。
9. **测试里的 `fetch` 默认被打桩**：`tests/setup.ts` 默认返回 `{ ok: false }`，任何真实网络请求都必须显式 mock。
10. **`npm run check` 不要接管道读退出码**：`npm run check | tail` 的退出码是 `tail` 的，要用 `npm run check > log 2>&1; echo $?`。

### 8.3 依赖与安全

- `npm audit` 报 14 个既有漏洞（均在 devDependencies 传递链），未擅自 `audit fix`，避免动锁文件破坏可复现构建。
- 运行时依赖只有 `vue` 与 `vue-router`，攻击面极小。
- 仅支持 HTTPS 或 localhost：Web Crypto 需要 secure context，不支持 `file://` 直接打开。
