# ADR-001：用 foliate-js 而非 epub.js 作为 EPUB 渲染引擎

## Status
Accepted（2026-10-18）

## Background

产品需要"用户自行导入 EPUB → 在浏览器里读 → 划线 → 笔记 → 章节小测"。其中"划线"是整个产品的核心资产：用户积累的标注是他换不掉这个产品的原因。因此阅读引擎的第一评价标准不是"能渲染 EPUB"，而是**在渲染过程中标注会不会丢**。

浏览器内 EPUB 渲染有两条主流路线：基于 DOM 自建分页（epub.js）与基于 CSS 多列分页（foliate-js）。这两条路线在"翻页/改字号/旋转屏幕"这些高频动作上的行为完全不同。

候选：foliate-js（MIT）、epub.js（BSD-3-Clause）、Readium ts-toolkit（BSD-3）、按需自建。

## Decision

选 **foliate-js**，通过 git submodule 锁定 commit 引入，外层以 `reader-engine` 目录隔离（ARCH.md §7.1）。

评价结果（ARCH.md §8.2）：foliate-js 4.05 / Readium ts-toolkit 3.50 / epub.js 2.55。

决定性理由只有一条：**epub.js 的 DOM 重排分页会在尺寸变化时重建 DOM**，而高亮是挂在 DOM 节点范围上的。重建之后 Range 失效，高亮要么消失要么错位。这不是 epub.js 的 bug，是它的架构选择；而本产品的核心资产恰恰是最受影响的那个。foliate-js 用 CSS 多列 + 二分查找定位，列宽变化不重建内容 DOM。

其余理由：
- foliate-js 的模块化是真的：解析层（`epub.js`/`epubcfi.js`）、渲染层（`paginator.js`/`fixed-layout.js`）、辅助层（`overlayer.js`/`progress.js`/`search.js`/`text-walker.js`）互不依赖，只依赖接口。这让我们能只取 8 个模块，也让我们能为 TXT 写一个 book interface 复用同一套渲染管线（ADR-008）。
- `epubcfi.js` 是纯函数式、不依赖 DOM 的 CFI 解析器，**可以在 Node 里直接单测**。这对锚点体系（ARCH.md §7.3）是刚需。
- 已被 Foliate（GNOME 桌面阅读器）的稳定版本使用，实测覆盖面比 star 数更可信。

## Consequences

**正面**
- 标注在改字号 / 旋转 / 窗口缩放后仍然正确。
- 一套 `overlayer` + 一套 `Locator` 同时服务 EPUB 与 TXT，每新增一个阅读功能只需实现一次。
- CFI 逻辑可脱离浏览器测试，锚点回归成本低。

**负面**
- **上游无 release，作者明确声明"API 随时会变"**。这是真实的维护风险，不是纸面风险。缓解：锁 commit + `vendor:check` 门禁 + 15 条契约测试 + 升级 runbook（ARCH.md §7.4）；连续两次升级失败则启动 fork 分支。
- 它同时会引入 fflate（MIT）、zip.js（BSD-3-Clause）等 vendored 依赖，`THIRD-PARTY-NOTICES.md` 必须声明。
- foliate 的 `reader.html`/`ui/` 不属于库，宿主容器（iframe 装配、主题注入、选区→CFI 胶水、资源释放）必须自己写，约 600–800 行。
- **不能承诺"随时可换引擎"**：真要迁移，标注/进度/分页交互/搜索全部重写，约 3–4 人周。这是选 foliate 的沉没成本，必须在架构上诚实承认。
