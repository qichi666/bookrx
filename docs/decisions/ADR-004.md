# ADR-004：符合度用规则加权打分，理由用模板渲染，均不使用 LLM

## Status
Accepted（2026-10-18，产品侧已锁定，本 ADR 记录技术依据）

## Background

"给一本书评一个符合度"和"讲清楚为什么推荐它"这两件事，都可以用 LLM 做。问题是要不要用。

本产品的四个硬要求：

1. **可解释**：用户会看着三档标识问"为什么是它"。答不上来，诊断器就退化成一个黑箱推荐器，产品的差异化消失。
2. **可单测**：推荐是这个产品的判断力所在。如果它不能被单元测试锁定，每次改动都是盲改，回归无法收敛。LLM 的输出无法被断言（除了一致性极差的语义断言）。
3. **可复现**：同一个用户同一份答案，两次得到同样结果。LLM 即使在 temperature=0 下也不保证跨版本、跨供应商复现（模型会升级、会下线）。
4. **零成本**：local-first 架构（ADR-002）下，客户端调 LLM 需要 API key —— 开源项目把 key 放进前端是不可接受的；让用户自己填 key，等于把产品的第一道门槛设成"先去注册一个 API 账号"。

## Decision

**符合度：规则加权打分（5 因子、定点整数、常数权重表、硬过滤前置、槽位化组装）。理由：模板化三段式字段渲染（S1 强制回引用户原词，S3 可整段不生成）。**

具体规格见 ARCH.md §3 与 §4。要点：
- 权重是常数表且和为 10000，写进单测锁定。
- 全过程整数 basis point 运算，无浮点比较 → 结果位级可复现。
- 排序 5 键全序（末键为 `book_id`），不依赖 `Array.sort` 稳定性。
- 理由 = S1（`user_phrase` 回引 + 标签判断句）+ S2（`structure_note` + `one_line_what`）+ S3（`one_line_gain` + `first_action`，可缺失）+ 可选 `boundary_note`。零模板引擎，30 行替换函数。

## Consequences

**正面**
- 每一次推荐都能被逐项拆开：5 个 `contribution` 相加严格等于 `score_bp`（ARCH.md §3.4），任一条推荐都可复算。
- 算法可被变异测试加固（例如：把 topic 权重的 3800 改成 3801，是否有测试变红）。
- 零运行成本、零延迟、离线可用、无 key 泄露面。
- 文案由编辑维护在 `phrases.json`，改文案不用改代码、不用重新训练任何东西。
- "禁止 AI 模板味文案"变成 CI 可执行的门禁（12 条禁用套话词表 + 长度区间 + 重复率），而不是靠人评审"感觉像不像"。

**负面**
- **表达上限受限于人工文案量**。48 个标签 × 情境句，组合空间有限；相比 LLM 的自由生成，"个性化程度"明显更低。这是有意接受的：我们要的是"每句话都站得住"，不是"每句话都新鲜"。
- 标注质量直接决定推荐质量（R2：15000 个人工标注点是本项目最重的人力成本）。规则法把质量压力全部转移到数据上，而 LLM 法会把它藏在模型里——从这个角度看，规则法的压力是**可见的**，这反而更好。
- 新增标签/新书需要人工补文案与标注，不能"自动化扩张"。→ 接受，因为核心库规模本来就要人工控制。
- 未来的"理由润色"若引入 LLM，必须严格限制在展示层，**绝不能进排序链路**（排序必须留在可复现的规则里）。这一点写在此处作为红线。
