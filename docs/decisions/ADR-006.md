# ADR-006：检索自建（构建期索引），不引入 Fuse.js / MiniSearch

## Status
Accepted（2026-10-18）

## Background

需要在 3000 条书目上做标题 / 作者 / 标签检索。可选：Fuse.js、MiniSearch、Lunr.js、自建。

先明确真实需求，而不是先看库：

1. 数据量 3000 条，字段短（书名 ≤80 字），全量都在内存。
2. **中文用户的主要输入困难是拼音输入法**：用户想找《领导梯队》，实际敲的是 `ldtd` 或 `lingdaotidui`。这不是"错字容错"问题。
3. 首屏不能为搜索付几百毫秒的索引构建时间。
4. local-first（ADR-002）下不能依赖服务端搜索。

## Decision

**自建：构建期生成索引，运行时零依赖常量级扫描。**

- 构建期（Node，`scripts/build-search-index.ts`）用 `pinyin-pro` 预计算 `title_pinyin` 与 `title_initials`，并对标签与书名做简繁双向展开，全部写进 `titles.json`。`pinyin-pro` 约 700 KB，**只做 devDependency，禁止进 bundle**（CI 检查产物中不含其标识符）。
- 运行时（`data/catalog/search.ts`）按 8 级字段优先级打分（ARCH.md §5.4），同分按 `book_id` 升序。

## Consequences

**正面**
- 0 KB 运行时体积、0 ms 启动开销（对比 Fuse.js 运行时建索引约 31 ms）。
- **拼音能力覆盖完整**：首字母、全拼、汉字子串、简繁互通。这是三款现成库都给不了的——Fuse.js 的 Bitap 按码点滑动，对 CJK 没有音节概念。
- 检索逻辑是纯函数 + 数据，可单测、可回归、可解释（每条命中都能说出"命中了哪个字段"）。
- 索引是构建产物，`git diff` 可审。

**负面**
- **没有错字容错**。用户把"领导"打成"领到"，不会命中。→ 用拼音兜底（打错的通常是读音相同/相近的字，拼音路径反而能救回来）；这是**有意识的取舍**：用 15% 权重的容错换 30% 权重的中文能力。
- 索引算法由我们自己维护，没有社区帮忙找边界情况。→ 检索需求本身很窄（4 个字段 + 拼音），且用真名列表做回归样本即可覆盖。
- 扫描是 O(n)。3000 条时约 3–6 ms，可接受；若书库扩到 3 万条需改为真正的倒排表。→ 记录触发阈值：**当 `catalog` 超过 1 万条时重评本决策**。

## 为什么不选 Fuse.js（主要竞争者）

- 体积 6.8–8.6 KB gzip，不是致命问题；致命的是它对中文的收益接近零（Bitap 是字符串编辑距离，中文按字编辑的距离没有语义）。
- 它是全量扫描型（官方 benchmark 显示其查询比倒排索引方案慢约三个数量级），在 3000 条时够用，但拿不到任何性能优势。
- 需要运行时构建索引，与"首屏 0 ms"目标冲突。

## 为什么不选 MiniSearch

- 体积最小（约 4 KB），工程实现最好，但它的设计中心是英文 stemming/tokenization。中文要么外挂 `Intl.Segmenter`（Safari 支持时间较晚）要么自带词典，两者都比"构建期预计算"贵。
- 不支持拼音，同样解决不了核心痛点。
