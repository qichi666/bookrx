# ADR-002：local-first，第一版不做后端、不做账号

## Status
Accepted（2026-10-18）

## Background

产品的数据有三类：① 诊断问卷答案（含用户对自身困境的描述，属敏感个人信息）；② 划线、笔记、复习记录（长期积累型资产）；③ 书目与理由（可公开、随版本变化）。

一个"阅读器 + 诊断器"很容易滑向"账号 + 云同步 + 社区"。但那会立刻带来：后端开发（2–3 人月）、数据库与备份、隐私合规（用户的困境自述 + 阅读偏好在服务器上是高敏感数据）、以及运营成本。MVP 阶段这些投入换不来任何验证价值——产品要验证的是"诊断 → 推荐 → 读下去"这条链是否成立，而不是"多设备能不能同步"。

候选方案：A. 全 local-first（无后端）；B. 传统后端（Node/Python + 数据库）；C. BaaS（Supabase/CloudBase）。

## Decision

**第一版全 local-first：无后端、无账号，全部数据在浏览器 IndexedDB（Dexie），书目以静态文件随应用分发。**

关键约束：这个决定要求"推荐算法必须能在客户端跑"。而我们的推荐是**规则加权打分**（ADR-004），3000 本 × 5 因子 ≈ 6 ms，完全可以客户端跑。**如果当初选了 LLM 打分，这个决策就做不成**——两个决策互为前提，这也是为什么它们都要被记录。

## Consequences

**正面**
- 用户困境自述与阅读偏好不离开他的设备。这是可以直接写进 README 的产品承诺，也是"开源 + 本地"最有说服力的部分。
- 零后端成本、零运维、零数据库备份。
- 部署形态极简：GitHub Pages 静态托管即可（MIT 开源项目几乎没有别的选择）。
- 算法与数据全部可被用户审计（开源项目里，这是信任的一部分）。

**负面**
- **数据只在这台设备的这个浏览器里**。→ 必须提供 JSON 导出/导入作为最简跨设备迁移，且导出不是 nice-to-have（见 R7：Safari 可能清掉 IndexedDB）。
- **用户清缓存 = 数据全丢**。→ 首次导入时申请 `navigator.storage.persist()`，设置页显示"存储保护"状态，并在未获授权时明确提示风险。
- 无法做服务端埋点/统计。→ 只能做本地事件记录 + 用户主动导出；产品决策不能依赖"A/B 测试数据"，要靠定性反馈与本地导出样本。
- 无法做需要服务端的能力：全文搜索跨用户书库、社区、推荐模型训练。→ 这些本来就在 out-of-scope（ARCH.md §12）。
- 首屏要下载书目数据（241 KB gzip），比"调一个 API 拿 10 条结果"重。→ 用 SW 长缓存 + 内容哈希，二次访问零网络。

## Related ADRs
- ADR-003（静态 JSON 而非 API）—— 是本决策的必然推论
- ADR-004（规则打分而非 LLM）—— 使客户端跑推荐成为可能，与本决策互为前提
