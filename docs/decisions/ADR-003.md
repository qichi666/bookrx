# ADR-003：书目数据用静态 JSON 随仓库分发，不做 API

## Status
Accepted（2026-10-18）

## Background

核心库 3000 本的元数据、标签、打分字段、理由文案需要被客户端读取。可选形态：

- A. 打包成静态文件（JSON / 二进制），随应用分发
- B. 自建 API（Node/Python 服务 + 数据库）
- C. 第三方书目 API（Google Books / OpenLibrary / 豆瓣）

数据特征很关键：**3000 本、字段固定、每周最多变几次、所有用户读到的是同一份**。这是一个典型的"可以被缓存到极致"的数据集。

C 直接不可行：豆瓣无公开 API；Google Books 与 OpenLibrary 在中国大陆网络不可达；且它们都不提供我们需要的字段（`difficulty`/`prose_accessibility`/`est_reading_hours`/`problem_tags` 全是我们的标注，任何第三方都没有）。

## Decision

**静态 JSON，构建期生成，随应用分发**（编码与分片见 ARCH.md §5）。

预算已核算到可执行（ARCH.md §5.3）：启动期需要的打分数值列 22 KB gzip、标题与拼音 85 KB gzip、文案库 14 KB gzip，合计 124 KB gzip；详情按 32 片懒加载，单请求 17 KB gzip。用 SW cache-first + 内容哈希，二次访问零网络。

## Consequences

**正面**
- 与 ADR-002 的 local-first 完全一致：无服务可宕，无 API 可超时，无 key 可泄露。
- 3000 本全量在内存，**推荐可以打分全量候选**而不是"分页拉 20 条"。这意味着多样性约束、放宽阶梯都能在本地完整实现——如果是 API 分页返回，前端根本不知道还有什么别的书可选。
- 数据可被 `git diff` 审计。对一个 MIT 开源项目，"推荐规则和数据都能被任何人检视"是产品信誉的一部分。
- 版本可复现：`data_version` 写进索引，用户报告问题时能确定他看的是哪一版数据。

**负面**
- **数据更新必须发版**。→ 用内容哈希文件名 + SW，更新只影响变更的文件；并且接受"数据每周随版本更新一次"而不是"实时"。对一个 3000 本的静态库，这是合理的。
- 首次访问要付 124 KB。→ 已核进预算并设 CI 门禁；首屏 FCP 目标 ≤1.5 s（4G）。
- 数据变更没有灰度能力（不能只对 5% 用户生效）。→ MVP 不需要；真需要时参见 Feature Flag 方案，但静态数据做 flag 成本高于收益，故不做。
- 全量内存占用：解码后约 3000 × 约 120 字节对象 ≈ 数 MB（含 JS 对象开销）。→ 可接受；`ScoringRow` 用并列数组（列式）而不是对象数组，可把开销压到 1 MB 内。
