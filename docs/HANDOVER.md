## 一、一句话说清这个项目在干什么

用户描述**当下具体的困境**（例如"开会不敢发言，怕被同事评价"），系统用一套**可复现的确定性打分算法**，从书库里挑出 ≤5 本，并**逐本说明推荐理由**（为什么是这本、契合在哪、哪里不契合）。

不是"大众高分榜"，不是"猜你喜欢"，不是 LLM 现生成推荐语。**同样的输入必须得到逐字节相同的输出**——这是可以写单测的前提，也是整个项目的技术底线。

## 二、项目背景与目标范围

### 2.1 与主流产品的差异

| 维度 | 微信读书 / 豆瓣 / Goodreads | BookRx |
|---|---|---|
| 推荐依据 | 人群偏好、协同过滤、热度 | 单人当下的困境匹配 |
| 推荐理由 | 用户评论、评分聚合 | 逐本**预写**，非运行时生成 |
| 可复现性 | 不保证 | 相同输入 → 逐字节相同输出（有测试锁死） |
| 覆盖口径 | 全库 | 只对**人工核对过 34 个字段**的书负责，其余书如实标注"未入库" |

### 2.2 明确不做（已冻结，不要提议加回来）

社区 / 评论 / 打卡 / 排行榜 / PDF / 漫画 / TTS / OPDS / 账号云同步 / 展示豆瓣原始评分 / 用 LLM 生成推荐理由（不可复现）。

### 2.3 范围与形态

- 纯前端、无后端、无账号、无网络请求（只加载本站静态资源）。
- 计划以 Web 形式发布到 GitHub Pages，代码开源。
- 5 个页面：`/`（问卷）、`/result`（结果）、`/crisis`（危机资源）、`/framework`（读书框架笔记）、`/about`（关于与隐私）。

### 2.4 业务上"必须成立"的三件事

1. **不凑数**：库内 0 本时显示"这些都不对"+ 重述引导，不拿低分书充数。
2. **危机优先**：自由文本检出危机信号时，结果页强制让位于危机资源，且这是**硬互斥**（有单测）。
3. **理由可追溯**：每句话要么来自预写文案，要么来自打分字段，不允许模型现编。

## 三、当前遇到的具体困境与阻塞点

这一节是整个交接的核心。按严重程度排序。

### 困境 1（已解决，但它是所有后续工作的起因）：推荐层覆盖率极低

**症状**：核心库只有 13 本书，只覆盖 33 个困境标签中的 16 个。**12 个标签下零本书**——用户落在「原生家庭」「倦怠」「信息过载」「失去与告别」这些标签上，核心库一本都给不出来。

**为什么更难受**：10 条金标画像可以**全绿**，因为金标恰好不测这些标签。评测通过 ≠ 产品可用。

**已做**：核心库扩到 68 本，逐标签补书，**零覆盖 12 → 0**。详见 §7.5。

### 困境 2：人工标注成本与规模的根本矛盾

- 一本核心库书要 34 个字段，含 5 段文案（`one_line_what` 60–90 字、`structure_note` ≤38、`one_line_gain` ≤35、`first_action` ≤30、`match_brief` ≤28）。**人工逐本约 8–12 分钟**。
- 60 本 ≈ 10 小时；SPEC 的目标是 300 本 ≈ 40 小时；候选池 **6551 本，逐本人肉核对在数学上不成立**。
- 微信读书有几十万本，它的做法是"入库流水线自动抽 tag + item embedding 近邻 + CTR 重排"，人工只在评测审核环节——不是逐本核对。

**已做**：分两条腿。

- **enriched 层**：把人工投入从"每本书"降到"每个标签"。33 个标签写一次中文触发词，派生 6551 本的 `problem_tags`（书名命中权重 0.85–0.9，豆瓣大类兜底 0.4）。人工从 O(书) 降到 O(标签)。
- **覆盖率降级**：没标注的书不填默认值，而是让对应因子**整条不参与打分**（复用"跳答"的权重重分配），并如实报出覆盖率。这样 6551 本能进推荐池，但**不会因为填了默认值而假装准确**。

**仍阻塞**：见困境 5。

### 困境 3（已修复）：金标闸门形同虚设

`tests/domain/golden.test.ts` 里"闸门"原本断言的是 `expect(recognized).toBeLessThanOrEqual(10)`——**恒真**。认出率 0/10 也会全绿。

已改为 SPEC §7.4 要求的各自 ≥7/10。**教训**：测试全绿和闸门通过是两件事，写断言时要问"这个断言有没有可能失败"。

### 困境 4（仍未解决，但已测量 + 已分级）：派生层"有覆盖但精度低"

派生标签靠关键词和豆瓣大类兜底，噪声很大。实测 `anxiety` 的派生命中前几名是：

| 书名 | 问题 |
|---|---|
| 《嫌疑人X的献身》 | 推理小说，与焦虑无关 |
| 《白夜行》 | 同上 |
| 《人类简史》 | 不相关 |

**根因**：豆瓣大类"小说/心理学"整体被映射到了焦虑标签（`from_tags` 太宽 + 兜底权重 0.4）。

**后果**：结果页底部「和你这个困境相关的还有 N 本」会混进大量不相关书。这个列表目前**不参与打分**，所以不影响主推荐，但影响信任感。

**本轮做了什么**（没有解决它，但把它从"感觉不准"变成"可测量的不准"）：

- **证据分级**（P1-1）：书名证据 0.85–0.9 与豆瓣大类兜底 0.4 分开，宽池默认只收书名证据；强证据不足 20 本时整池降级并逐本标 `weak_ids`，界面标"这条相关性较弱"。这挡住了《嫌疑人X的献身》这类"小说→焦虑"的直达路径，但**没有让兜底证据变得准确**。
- **抽样报表**（P1-2）：`tools/sample-audit.mjs` → `catalog/reports/sample-audit.md`，每标签 30 本，把"对不对题"的判读范围从 6551 本缩到每标签 30 本。**实测书名证据 2274 条 / 兜底 15591 条，27 个标签兜底占比 ≥80%**——这个数字不好看，但它是真的，写进报表比藏起来有用。

**仍然待定**：真标注覆盖到某本书时，该书 `problem_tags` 以真标注为准、派生层让位。见 §9 第 3 条。

### 困境 5（真正的硬阻塞）：千本级 LLM 标注通道没有解决

本轮要做的 B1 是"用 LLM 批量补 9 个闭集字段"，把覆盖率从 4300 推向接近 10000。**通道走不通**：

- 平台提供的 `workbuddy_cloud_service` keyless LLM 通道，只能从**浏览器**调用，且 Origin 必须匹配已绑定应用的域名。
- 官方文档把"前端自建 BFF / Node API route 直连模型服务"明确列为**禁止模式**。
- 而 B1 的产物是一份**离线 JSON 数据集**（进 `public/catalog/`，随构建发布），不是运行时后端调用。
- 为跑一次批处理去开通云后端、再发布一个页面消耗配额，是把工具用错了地方。

**当前折中**：本轮由 AI 直接标注了 47 本（零基建、可逐条复核）。**千本级扩量仍缺一条能在 Node 侧跑的模型通道。** 见 §9 待确认第 1 条。

### 困境 6（结构性）：9 个闭集字段 ≠ 34 个字段

即使 B1 通道解决，LLM 能补的也只是 9 个闭集/半闭集字段（`difficulty` / `depth` / `form` / `length_class` / `prose_accessibility` / `problem_tags` 权重 / `entry_level` / `content_warning` / `est_reading_hours`）。

**5 段文案（`one_line_what` 等）和 `match_brief` 必须按书预写**，这是产品的差异点所在，不能让模型批量生成——那会退回"LLM 现编理由"。所以 300 本核心库的人工投入**下不去**，只能优化。

### 困境 7（**已修**，commit `726486e`）：**写得越具体，档位越低**

这一条是本轮把自由文本命中率从 29% 提到 97% 之后**才浮出来**的——它一直是那个样子，只是以前很少有人命中，所以很少有人被它伤到。现在写一句话几乎必然命中，于是它成了最常见的情形。

**现象**（`emotion` 域、选「情绪一直很低落」+「总是担心」，其余偏好填满）：

| | 第 1 本 | 第 2 本 |
|---|---:|---:|
| 不写自由文本 | 7827（较为契合） | 7427（较为契合） |
| 写上「每次开会轮到我说话，脑子就一片空白，怕别人觉得我没准备好」 | **7127**（较为契合） | **6727**（较为契合） |

**固定掉约 700 bp，且好几本正好卡在 6000 这条线上**，一掉就 `worth → explore`。用户的感受会是："我说得更清楚了，你怎么反而更不确定了？"

**根因不是 bug，是两条规则撞在一起**：
1. 自由文本命中的**新**标签按 0.15 加入 `need_tags`（`diagnose.ts` 的 `hitByFreeText`）；
2. `problem` 因子是**覆盖率**口径 `Σ min(用户权重, 书权重) / Σ 用户权重`。

于是分母从 0.85 变成 1.15，而分子几乎不变（那两本书并不讲"开会发言"），`problemFit` 从 1.0 掉到 0.74 —— 相当于"你没覆盖我说的第三件事"，可那第三件事是我**顺口提的**。

**为什么这轮不改**：它动的是打分语义（不是修 bug），会连带影响 10 条金标（金标画像本身带 `free_text`）与所有档位分布。SPEC §7.4 对这类改动的规矩是"调权重与标注，禁止下调阈值"，且必须留数据。**该由人拍一次，不该顺手改掉。**

**三个可选方向（按我推荐的顺序）**：

| 方案 | 做法 | 代价 |
|---|---|---|
| A（推荐） | **自由文本命中的新标签只进分子、不进分母**：书覆盖了它就给分，没覆盖不扣分；`problemFit` 用 `min(1, ...)` 封顶 | 需要改 `problemFit` 一处 + 加单测；证明"多写不吃亏"可测（同输入加自由文本，`score_bp` 不得下降） |
| B | 自由文本新标签的**总权重封顶**（如合计 ≤0.15，均摊），把稀释从 26% 压到 ≤13% | 改动最小，但仍是"多写会掉"，只是掉得少 |
| C | 维持现状，把这件事写进产品文案（"多写不会更准"） | 最省事，但等于承认"信息越多越不准"是设计——**不推荐，它违背直觉且没有好处** |

## 五、架构：分层、数据、算法

### 5.1 目录分层（依赖方向单向，不许反向）

```
src/contracts/      纯类型（编译后必须零字节）。9 个模块，由 docs/types-draft.ts 机械切分
src/domain/scoring/ 纯函数打分内核：weights / numeric / fit / score / tier / rank / filters / coverage / targets
src/domain/         库外兜底 outOfLibrary.ts
src/engine/         编排：diagnose（问卷→Diagnosis）/ result（→推荐结果）/ recommend / search / wide-pool / wide-need / session / telemetry
src/data/           静态数据加载与解析：catalog / candidates / enriched / phrases / quiz / crisis / reading-framework / free-text-keywords
src/composables/    useWidePool（宽池分页取书）
src/views/          QuizView / ResultView / CrisisView / FrameworkView / AboutView
src/components/     AppHeader / BookCard / ChipRow / CrisisPanel / DomainList / ExternalCard / OuterResults / SearchPanel / TagPicker / TuneBar / WideResults
```

**规则**：`contracts` 不 import 任何东西；`domain` 不 import `engine` / `data` / `views`；打分函数必须是纯函数（输入相同 → 输出相同，无 `Date.now()`、无随机、无全局状态）。

### 5.2 数据分三层

| 层 | 规模 | 文件 | 字段覆盖 | 用途 |
|---|---|---|---|---|
| **核心库** | 68 本 | `catalog/shards/seed-core-01/02/03/04.json` | 34 字段全覆盖（人工核对） | 个性化推荐主池，可达 `strong` |
| **enriched 层** | 6551 本 | `public/catalog/enriched/derived.json` | 只有派生 `problem_tags`（覆盖率 4300） | 按需取书 / 相关书目列表 |
| **候选层** | 6551 本 | `public/catalog/candidates/all.json` | 元数据（书名/作者/出版社/年/豆瓣标签/域/口碑） | 搜索、宽池基数 |

**分片语义（重要，别搞混）**：
- `seed-core-01.json` = 13 本，**改动它等于动金标评测基线**。
- `seed-core-02/03.json` = 47 本，后续补的书，可能整批回炉重标。
- 分片是为了让"回炉一批"不用碰已验证的那批。

**身份映射**：`catalog/core-id-map.json` 记录 `core:` → 豆瓣 `subject_id`，由 `tools/map-core-to-candidates.mjs` 生成。**它不是书**，键名叫 `core_id` 而不是 `book_id`（否则会被 `catalog-audit` 当成残缺的书扫出来）。

### 5.3 打分算法（核心，务必读准单位）

**7 个因子，权重和 = 10000 基点（`bp`）**：

| 因子 | 权重 | 含义 |
|---|---|---|
| `problem` 困境契合 | **3800** | 书的困境标签 vs 用户的困境标签 |
| `difficulty` 难度匹配 | 1800 | 内容难度 vs 用户偏好 |
| `depth` 深浅匹配 | 1200 | `howto` / `howto_why` / `why` |
| `form` 体例匹配 | 1000 | `story` / `method` / `framework` |
| `length` 篇幅匹配 | 1000 | `length_class` 1–4 vs 时间预算 |
| `readability` 表达匹配 | 700 | `prose_accessibility` 1–5 |
| `availability` 可直读倾斜 | 500 | 归一化后**上限 800**，不许做主排序力 |

**档位阈值是绝对值，不是分位数**：
- `strong` ≥ 8000
- `worth` ≥ 6000
- `explore` 其他
- 主诉未命中（`primary_hit === 0`）→ **封顶 `explore`**

**跳答处理**：某项偏好没答 → 该因子**整条剔除**，剩余因子权重按比例重新归一化（`renormalizeWeights`）。**不是**按中性值 5000 处理——那会让静默失效在推荐层重犯。

**字段覆盖率降级（SPEC v2.4 §6.4，三条锁定规则）**：

1. `book_coverage_bp` = 该书**真的标注过**的因子权重之和（`availability` 恒计入）。
   - 核心库 = 10000
   - enriched 层 = 4300（`problem` 3800 + `availability` 500）
2. 缺失字段对应的因子**整条不参与打分**，**禁止填默认值**。
   - 硬约束（有单测）：未覆盖字段填 `1` 和填 `5`，**分数必须一模一样**。
3. 覆盖率 < 6000 时，档位封顶 `worth`（标记 `capped_by_low_coverage`）。

**排序**：6 级 tie-break 链，逐级比较直到分出先后（`src/domain/scoring/rank.ts`）。禁止出现任何时间字段（会让结果随维护时间漂移）。

**硬过滤**：`FILTER_RULES` 7 条（`src/domain/scoring/filters.ts`）：`EX-difficulty`（难度超阈值）/ `EX-load`（超出负荷）/ `EX-trauma`（内容预警·创伤）/ `EX-terminal`（内容预警·临终）/ `no-problem-tags`（无困境标签）/ `excluded-by-user`（用户排除）/ `metadata-only`（只有元数据，不可读）。

### 5.4 关键词单位铁律（本项目最容易犯的错）

| 位置 | 单位 | 取值范围 |
|---|---|---|
| 书侧 `problem_tags[].weight` | **0–1** | 0.1 – 1.0，一位小数 |
| 用户侧 `diagnosis.need_tags[].weight` | **0–1** | 主诉 0.6 / 次 0.25 / 三 0.15 |
| 所有 `*_fit` / `*_hit` / `score_bp` / `contribution` | **0–10000 整型基点** | bp |

**曾经出过的事故**：用户侧权重误用基点（×10000），于是 `min(6000, 0.9)` 把 `primary_hit` 压成 1–2 分；而 `tierOf` 只判 `=== 0`，所以档位看着正常，实际主诉判断全废。**改这块必须两边一起看。**

- `problemFit` 口径 = `Σ min(用户权重, 书权重) / Σ 用户权重`（覆盖率口径，**不是** Jaccard）。

## 七、方案的分步实施细节

这一节按时间顺序，每一步都写清**目的 / 做法 / 产出 / 验收**。已完成的四步是"让推荐能测、能算、能扩"，第五步是"把库填满"。

### 7.1 第一步（已完成）：金标评测——先让推荐"能被测量"

**目的**：在动任何数据之前，先回答"推荐到底准不准"。没有这个，后面所有优化都是盲改。

**做法**：
- 手写 10 条金标画像（`catalog/golden/profiles.json`），每条含场景原话、域、标签、主诉、五组偏好、自由文本、**期望书**、**为什么是这本**。
- **画像先写、分数后跑**：`expect` 只凭书的实际内容判定，绝不看引擎输出。否则就是拿答案回填考题。
- 两个计数**分开报**：认出率（期望书落 `strong`）+ 首屏率（期望书排第 1）。平均会掩盖"认出来了但排第 4，用户根本看不到"。

**产出**：`catalog/golden/profiles.json` + `tests/domain/golden.test.ts`（逐条打印 rank / tier / score / 首屏书名；未达 `strong` 的自动拆因子解释原因）。

**验收**：两个计数各 ≥7/10，且断言必须**可能失败**（第一版写成恒真，已修）。

**顺带挖到的 P0**：`buildDiagnosis` 组装 `answers` 时丢了第 3 屏五个偏好和 `free_text`——**线上所有用户实际都按"全跳答"打分**，且 `hasCrisisSignal` 永远读不到自由文本（危机互斥 P0-17 从未生效）。已修 + 3 条回归。

### 7.2 第二步（已完成）：字段覆盖率降级——让没标注的书"能进池但不算假"

**目的**：6551 本候选书只有元数据，不能假装它们能按 7 因子打分。但也得让它们进推荐池，否则用户永远只看得到 60 本。

**做法**：
- 定义 `book_coverage_bp` = 该书**真的标注过**的因子权重和。
- 缺失字段 → 该因子整条剔除，复用"跳答"的 `renormalizeWeights` 重分配权重。
- **禁止填默认值**：填默认值等于把编造的分数算进结果。
- 覆盖率 < 6000 → 封顶 `worth`（`capped_by_low_coverage`）。

**产出**：`src/domain/scoring/coverage.ts`；`computeFits` / `scoreBook` / `tierOf` 三处接入；SPEC §6.4；9 条单测。

**验收**（关键几条）：
- `coverageBp(FULL_COVERAGE) === 10000`，`PROBLEM_ONLY_COVERAGE === 4300`
- **未覆盖字段填 1 与填 5，分数完全相同**
- 5999 / 6000 边界：5999 封顶 `worth`，6000 该 `strong` 就 `strong`
- 主诉未命中**优先于**覆盖率封顶（两个原因同时存在时报主诉）

### 7.3 第三步（已完成）：派生标注（enriched 层）——把人工从 O(书) 降到 O(标签)

**目的**：6551 本不可能逐本人工标注。改成一个标签写一次词表，机器派生。

**做法**：
- `catalog/problem-lexicon.json`：33 个困境标签 × 中文触发词 + `from_tags`（豆瓣大类映射）。
- 派生成派生权重：**书名命中 = 0.85**，每多命中一次 +0.05，**上限 0.9**；书名未命中才用豆瓣标签兜底 **0.4**；每本最多留 `top_n = 3` 个。
- **先取整再排序**（用未取整的浮点权重排序会出现 `0.85+0.05=0.9000000000000001` 的逆序 bug，曾出现 37 处）。

**产出**：`tools/derive-annotations.mjs` → `public/catalog/enriched/derived.json`（664 KB）+ `index.json`；`src/data/enriched.ts` 运行时加载器。

**验收**：`tools/verify-derived.mjs` **15 项硬断言**，故意不复用 derive 的函数（独立重算才叫对账）：
- 条数、无重复 id、每条可在候选层找到同 id
- 标签全部来自词表；权重 ∈ {0.4} ∪ [0.85, 0.9] 且为 0.1 倍数
- 权重降序、同权按 tag 升序；`pt.length ≤ 3`；`how` 与长度自洽
- **每个派生标签都能溯源**（书名含关键词 或 豆瓣标签可映射）
- `index` 各计数独立重算一致；源码 `sha256` 一致；**校验前后 `all.json` 一个字节没变**

实测：6551 本全覆盖（书名命中 1872 / 标签兜底 4679）。

### 7.4 第四步（已完成）：按需取书——让宽池"真跟困境有关"

**目的**：结果页底部要能说"和你这个困境相关的还有 N 本"，这 N 本必须真相关，且不能一次把所有书塞给前端。

**做法**：
- 匹配口径与核心库 `problemFit` **完全一致**：`Σ min(用户权重, 书权重) / Σ 用户权重`（覆盖率口径，**不是** Jaccard）。
- 门槛 `MIN_DEMAND_FIT = 0.2`。
- 排序：命中率 ↓ → 质量 ↓ → 投票数 ↓ → id ↑。
- 窗口法分批取（`epoch`），保证不重复、不遗漏。

**产出**：`src/engine/wide-need.ts` + `src/engine/wide-pool.ts`（有 `demand` 时分流到 `selectByNeed`）+ `src/composables/useWidePool.ts` + `src/components/WideResults.vue`。

**验收**：读**真实** `all.json` + `derived.json`，给定"发言紧张 + 怕被评价"，断言首 5 本每本命中率 ≥ 0.19、跑满 `ceil(size/5)` 轮覆盖全池。实测 **686 本真正相关，138 轮翻完**，首批书名全部对题。

### 7.6 第六步（本轮已完成）：宽池的三处结构性修复 + 理由来源

**背景**：上一轮把核心库补到 60 本，解决了"核心库有没有书"；这一轮解决"宽池准不准、理由说不说得清"。
依据是 [`decisions/FINAL-PLAN-2026-10-20.md`](./decisions/FINAL-PLAN-2026-10-20.md)。

**三个 bug 都是静默的**——它们不抛异常、不写日志，只会让某个列表安静地变空或变小：

| 现象 | 根因 | 修法 |
|---|---|---|
| 情绪 / 习惯 / 人生转折三个域，宽池**恒为 0 本** | 候选池域（豆瓣 7 个）与 `ProblemDomain`（问卷 6 个）**只有 3 个名字撞上**，按名字求交集等于其余三个域全部落空；接口返回 `size: 0`，和"这个域真的没书"长得一样 | `catalog/domain-map.json` 显式映射表，构建期与运行时**同读一张**；未知域返回 `[]` 而不是 `[domain]`（宁可空着，也不要按名字猜出中毒池）；下限 `MIN_DOMAIN_POOL = 20` |
| `speaking-block` 在 485 本职场书里**只剩 5 本** | 派生层 `top_n=3` 同权时按 `tag` **字母升序**截断，`s` 开头的标签被 `b`/`c`/`e` 系统性挤掉 | `offset = hash32(book.id) % n` 轮转窗口：确定性保留（同输入同输出），但没有系统性偏向；`verify-derived` 增加「各标签保留率 ≥ 中位数 60%」断言 |
| 自由文本**64% 零命中** | 词表每标签只有 3–5 个说法，且只做整串 `includes` | 三级匹配：整串 → 允许插入成分（budget `min(5, len)`，仅 ≥3 字关键词）→ 区间重叠消歧（`anxiety` 等 5 个泛标签被更具体标签套住即丢弃）；词表扩到每标签 18–26 个口语说法 |

- **证据分级**（`TITLE_EVIDENCE_MIN = 0.85`）：书名直接写着这件事（0.85–0.9）和"只是同一豆瓣大类"（0.4）不是一回事。宽池默认只收书名证据；强证据池 < 20 本时**整池降级**并逐本标 `weak_ids`，界面标"这条相关性较弱"。
- **理由来源三档**（`prewritten` / `from_answer` / `from_tag_weight`）：每张卡展开后每句理由都带徽章，**没有来源的理由不许上界面**。一条说不出出处的理由比没有理由更糟——它看起来像结论。

### 7.6.1 承接（2026-10-21）：三条 P0 的补齐——哪些话能写、哪些话不能写

**目的**：SPEC §2.1 的 P0 表里有三条"文档写了、代码没有"：P0-16 域级危机条、P0-17 无 inline 域说明条、P0-7 书籍详情页。补齐它们本身不难，难的是**照抄规格书的定稿文案会变成假话**。

**做法（先立一道闸，再写界面）**：

- `src/data/capabilities.ts` → `READER_AVAILABLE = false`。规格书按"最终形态"写（有内置阅读器），而阅读器属 M2/M4，已在 P2-4 冻结。凡涉及能力的话都过这道闸：`可直接阅读` → `公版·站外可读`；`导入后就能读` → `每本书都给了找书的路径`；主操作从「阅读 / 导入」换成「到哪读」外链组。**被挡住的定稿文案不删不重写**，注释里写明怎么改回来——阅读器上线只翻一个布尔值。
- **P0-16 `CrisisBar`**：情绪与自我域结果页恒显示，替换原来那行小链接（**不叠加**，否则配额会变成 3）。`data-crisis-entry` 全项目仍是 2 个节点（结果页 1 + 关于页 1），`AppHeader` / `CrisisView` / 详情页明令不得挂。
- **P0-17 `NoInlineNote`**：显示与否**从书库算**（`domainsWithoutInline()`），当前是 `relationship` / `habits` / `thinking` / `transition`。v1.2 写死的三个域名里有 `emotion`，而情绪域其实有《曾国藩家书》——照抄就会在一个有两本公版书的域里说"基本都还在版权期内"。书库长出来时说明条自动消失，不需要谁记得回来删。
- **P0-7 详情页** `/book/:id`：`BookHead`（书名 → `match_brief` → 可用性）+ `BookReason`（命中依据 → 讲什么 → 拿到什么 → 边界 → 逐句来源）+ 档位 + 书目信息 + 同主题 3 本。没有诊断时退化成"书目页"，不假装知道用户是谁。
- **三态动词不复用**：`data/availability.ts`（公版·站外可读 / 需自备 / 站外查看）、`data/book-links.ts`（公版全文 → 微信读书 → 买一本 → 图书馆 → 豆瓣，**顺序有语义**；卡片只取前 4 个，保证被砍的是豆瓣而不是图书馆）。

**验收**：`npm run check` 33 文件 / 217 条测试全绿（新增 20 条：`crisis-bar` 6、`no-inline-note` 7、`book-detail` 7）；style-audit 96 文件；`npm run build` 通过且危机页仍是独立 chunk；`tools/smoke-browser.py` **新增 9 条断言全过**，其中"可用性区块在书名之后、理由段之前"是量真实坐标（avail 426 / reason 637），不是数 DOM 顺序。

**这一轮的教训**：`data-crisis-entry` 配额、`domainsWithoutInline`、"来源只在三档内"这三件事，**都只能靠测量**。文档写"已有"不等于代码有；文档写"这三个域"不等于现状就是三个域。

### 7.6.2 承接（2026-10-20 夜）：把阅读链路做完——以及两个单测抓不到的坑

**目的**：用户指令是"把所有尚未完成的功能实现完，整理成能上 GitHub 的仓库"。上一轮结束时，文档里 P0-8 ~ P0-15 写着"已设计"，代码里只有推荐链路。这一轮把它们全部落地。

**落地顺序有讲究**：先解析层（纯函数、能在 Node 里用真样本单测）→ 再存储层 → 再阅读器 → 最后离线与书架。理由是解析层决定了后面所有东西的形状：章节怎么切、锚点怎么存、进度记什么。反过来做，会在渲染层反复撞"文本边界"这种上游问题。

**四个关键判断**：

- **ZIP 只认中央目录**。本地文件头里的文件名与扩展字段可以被伪造（zip 混淆的常见手法），按本地头解压等于相信书里自带的一张标签。
- **编码判定顺序不能换**：`BOM → 严格 UTF-8(fatal) → UTF-16LE 启发式 → GB18030`。`TextDecoder('gb18030')` 对**任何字节**都能解出一串字，先试它等于永不失败、也永不出错——只会得到乱码。
- **不引 foliate-js**（ADR-009）。原 ADR-001 选它是为了 CSS 多列分页，但那套方案把"标注"绑在 DOM Range 上。本项目大部分书由用户自己导入，换一份版式就换一套 DOM，Range 必然失效且**静默错位**。改为自建字符流渲染 + 双锚点（字符偏移 + 引文重定位），代价是放弃固定版式、表格与原书字体——写进 ADR 的"放弃的能力"清单里。
- **删除不删笔记**。删一本书清掉 books/chapters/files/progress/shelf 五处，`annotations` / `notes` 保留：划线是位置，笔记是内容，位置没了内容更值钱。

**两个只有真实浏览器才能抓到的坑**（写在这里，因为它们会重复出现）：

1. **响应式 Proxy 写不进 IndexedDB**。`progress.value.furthest_locator` 取出来是 Vue 的 Proxy，`IDBObjectStore.put` 抛 `#<Object> could not be cloned`。而下调用是 `void session.saveProgress(...)`——异常被吞掉，症状是"进度有时候不保存"。修法双保险：`lib/plain.ts` 写库前摊平（不动 ArrayBuffer / Blob / Date），进度里再显式重建 locator。单测抓不到是因为 happy-dom 里没有真 IndexedDB。
2. **段落首子节点是 Vue 的 fragment 注释锚点**。用 `p.firstChild` 建 Range 会得到**折叠**的空选区，症状是"点了划线没反应"。真实用户用鼠标选不会撞上，但任何脚本化选区都会。

**验收**：`npm run check` 43 文件 / 306 条测试全绿；`token-audit` 新增（42 文件 362 处引用 0 未定义）；`smoke-browser.py` 42 条断言全绿，新增"示例试读 → 翻章 → 选区划线 → 划线抽屉 → 回书架"。

> **2026-10-21 更新**：全量门禁现为 **49 文件 / 376 条测试**全绿；`token-audit` 扫 44 文件 / 379 处引用 / 0 未定义；`smoke-browser.py` **45 条**断言全绿。阅读器已上线（`READER_AVAILABLE = true`），本节描述的那条「P2-4 冻结路线」已作废，见 ADR-009。

**这一轮的教训**：`--surface-raised` 这类令牌从未定义过，而类型检查、样式门禁、构建**全绿**——CSS 变量拼错不报错，只是那条声明被丢掉，在浅色底上甚至看不出异常。凡是"错了也不响"的地方，都值得一条门禁。

### 7.7 第七步（**通道已建成，未跑数据**）：千本级批量标注

> **2026-10-21 更新**：本节原设计的「补 9 个闭集字段」在落地时被**实测否掉**，改成了只标 `problem_tags`。原因见下。

**目的**：把 enriched 层的覆盖率从 4300 推向接近 10000，让 6551 本里真正被模型认得的书能参与完整 7 因子打分。**当前瓶颈已不是覆盖率，是薄标签池**：`big-choice` / `emptiness` 各只有 2 本。

**实测否掉的口径**（别再走这条路）：

- 「简介 + 同一套关键词」在 30 本人标书上精确率仅 **35%**（书名词表 84%），召回 38%。典型失败：《心流》人标 `emptiness/low-mood`，简介匹配给出 `attention-scatter/cant-see-whole/meaning-loss`，三个全错。→ **扩到千级只能靠语义判断。**
- 「补 9 个闭集字段」同样被否：`difficulty` / `prose_accessibility` / `first_action` 这类字段**要读全文**才能填，读 400 字简介写出来就是编造。→ **只在能负责的字段上标。**

**实际落地的口径**：

- 只产 `problem_tags`，权重逐标签记；每个标签必须附 **≤40 字原文逐字引文**，`normalize(evidence) ⊆ normalize(原文)`，不通过就丢弃并记账（7 类错误码）。
- 取证器只抓**内容简介**（不是作者简介——两者共用 `class="intro"`，靠 `id="link-report"` 区块 + 「作者简介」标题切边界；用 `span.short` 切会命中 67 本里的 34 本）。
- 逐标签记证据来源：`annotation` 0.95 / `title` 0.85–0.9 / `category` 0.4。运行时**只放行前两类**——大类兜底是 1 对多的抽签（实测 27/33 个标签兜底占比 ≥80%）。
- **允许弃权**：模型不认得的书必须回答「不知道」，不许用世界知识硬填。弃权的书留在 4300 覆盖率、封顶 `worth`——这正是 §7.2 设计好的降级路径。
- **验收口径**：先在 **29 本真有人标过标签的书**上校准，**精确率 ≥70%、召回 ≥50%** 才许放量（`tools/verify-annotations.mjs --strict`）。每批 500 本抽 30 本人工标、算 Cohen κ，κ < 0.6 整批回炉。
- 业界依据（已查证，勿重复调研）：LLM 零样本闭集分类与人工一致性 Cohen κ ≈ 0.73–0.88；两段式漏斗（召回 → 排序）在 <1 万件时可暴力打分，>10 万件才值得上两塔。

**阻塞**：**缺 `DEEPSEEK_API_KEY`**。通道四段（取证 → 标注 → 证据闸 → 接入）已通，详见 `docs/标注通道.md`；key **只在构建期用，运行时零模型调用**。通道未跑时派生层输出与接入前逐字节相同，所以池子变大只可能是标注带来的。

### 7.8 第八步（未开始，可选）：半监督传播

**目的**：进一步省人工。以人工核对书为种子，用 embedding 近邻给同域候选书预测字段 + 置信度，低置信进人工队列。

**业界依据**：主动学习的不确定性采样可省 30–70% 标注量，但需要 50–500 条种子（现在有 60 条，勉强够起步）。

**优先级**：低于第六步。先把通道打通再说。

## 九、仍待确认的疑问

按优先级排序。每条都写清"卡在哪"和"可选方向"。

### 1. 千本级 LLM 标注通道（**最高优先级，硬阻塞**）

- **现状**：平台 keyless LLM 只能从浏览器（Origin 绑域名）调用；官方禁止前端自建 Node 代理直连；B1 产物是离线 JSON。
- **可选方向**：
  - (a) 提供一条能在 Node 侧跑的模型 API（自备 key 或自建服务）；
  - (b) 做一个本地标注控制台页面，人开着浏览器跑批量，导出 JSON（可行但需人选模型、开着页面）；
  - (c) 暂时放弃千本级，专心把 300 本核心库做扎实（人工成本约 40 小时）。
- **影响**：卡着 §7.7 和 §7.8。

### 2. 300 本的路线

SPEC 写的是"核心库 300 本"，现在 68 本。剩下 232 本靠什么补？
- (a) 继续按标签缺口手工补（每本 8–12 分钟估算 + 文案）；
- (b) 继续按"书库覆盖"补薄标签（本轮已按这条通道补了 8 本，把 6 个最薄的标签都推到 ≥3 本；**这条路是有效的，但它只解决"有没有"，不解决"准不准"**）；
- (c) 接受 68 本，转向修其他 P0。

### 3. 派生层精度修复策略（困境 4）

- 可选方向：
  - (a) 真标注优先：某书有真标注时，派生 `problem_tags` 整条让位；
  - (b) 收紧 `problem-lexicon.json` 的 `from_tags`，去掉"小说/文学"这类过宽映射；
  - (c) 降权：兜底权重从 0.4 降到 0.25，让派生书更难通过 `MIN_DEMAND_FIT = 0.2` 门槛。
- **权衡**：收紧会降低宽池规模，放宽会混入噪声。需要定"宽池可接受的噪声率"。

### 4. 读书框架笔记是否支持导出 Markdown

倾向支持（本地导出、不上传），但依赖 P2 的功能设计。

### 5. 英文大库能否进产品

目前结论是"不能"（许可仅学术、禁再分发）。若未来改成商用授权可重开。

### 6. 危机资源文案的审核来源（**本轮已按"不写审核人"处理，但留下了可核实的替代品**）

`catalog/crisis-resources.json` 里每条现在都有 `source_url`（官方页面）+ `verified_at` + `verification_method: official-page`，
`tools/crisis-audit.mjs` 断言"没有来源 = 红灯""超 90 天 = 红灯""扫到 0 条 = 未验证"。
**没有 `verified_by` 字段**——审核人写谁这个问题本轮被明确搁置（用户要求不写审核人相关内容）。
因此当前的保证是"**每条都能点回官方页面**"，而不是"有人签字确认过"。
这两者不等价：前者防"号码写错"，后者才防"号码已停用但页面还在"。**90 天有效期是在替后者兜底，不是解决后者。**

## 十、已知陷阱：接手后最容易踩的坑

这一节价值最高，都是实际踩过的。

### 10.1 单位混用（最严重）

书侧 `problem_tags[].weight` 是 **0–1**，用户侧 `need_tags[].weight` 也是 **0–1**，所有 `*_fit` / `score_bp` 是 **0–10000 整型基点**。

曾经的 bug：用户侧误用基点（×10000）→ `min(6000, 0.9)` 把 `primary_hit` 压成 1–2 分 → `tierOf` 只判 `=== 0` 所以档位看着正常 → **主诉判断全废但测试全绿**。

### 10.2 覆盖率字段禁止填默认值

`coverage.ts` 里有单测锁死："未覆盖字段填 1 与填 5，分数必须一模一样"。如果你发现自己在给缺失字段填 `3`（中间值），方向就错了——应该让因子整条不参与。

### 10.3 vitest 并发会撞 EPERM

`vite.config.ts` 里是 `fileParallelism: false`，**不要改回去**。`cacheFs: true` 在 vitest 内硬编码、没有关闭开关，并发 worker 写临时转换缓存必撞 EPERM，worker 被杀后主进程只看到"文件数变少"，表现为"只跑了 19/21 个测试文件"却不报错。

`tests/setup.ts` 全局给 `fetch` 打了桩（happy-dom 会把相对路径解析成真实 URL，导致 `ECONNREFUSED localhost:3000` 的 unhandled error）。

### 10.4 拼音的 `ü`

`pinyin-pro` 即使 `toneType: 'none'` 也返回 `lü` 这种带 ü 的音节。若用 `[^a-z]` 过滤，`ü` 被吃掉 → 「虑」只剩 `l` → 《身份的焦虑》变成 `shen fen de jiao l` → 首字母搜索失效**且不报错**。

已修：`ü → v`，数字转汉字（`第6版` → `di liu ban`），并把"出现单字母音节"变成**硬错误**。

### 10.5 索引文件键名不能叫 `book_id`

`tools/catalog-audit.mjs` 会递归扫 `catalog/` 下任何带 `book_id` 字段的对象，按 34 字段整书校验。索引类文件（`core-id-map.json`）的键必须叫 `core_id`，否则会报几百条"缺必填字段"。

### 10.6 `.cmd` / `.bat` 的编码（Windows）

本机 `.cmd` 是 **GBK**、行尾常是 `\r\r\n`。直接文本编辑会写成 UTF-8 → 中文变花 + `call "中文路径.cmd"` 静默失效。必须按字节改。

### 10.7 emoji 禁令

`audit:style` 禁 emoji，**包括注释里**。曾经因为注释里写了一个警告符号就被打回。
emoji 的正则只在 `tools/emoji-scan.mjs` 一处定义，`style-audit` / `doc-audit` 共用——**不要再手抄第二份**：两边参数一旦分叉，同一份文档会在一条门禁里绿、在另一条里红，而人只会信更宽松的那个（这就是 `doc-audit` 一直没接线的原因之一）。

### 10.8 三态纪律

校验脚本扫到 0 个对象时必须报**「未验证」**并非零退出，不能报「通过」。"0 命中"恰恰是"根本没扫到"的典型症状——这是项目里的硬约定，所有 `tools/verify-*.mjs` 都遵守。

### 10.9 门禁写了 ≠ 门禁在跑

2026-10-21 的实际发现：`copy-audit.mjs`（329 行）和 `doc-audit.mjs`（303 行）**从写出来那天起就没被任何 `npm run` 或 CI 调用过**。它们不是"待接线"，是"看着像有"。

三条可复用的判断：
- **能在 `check` 里跑，就必须在 `check` 里**。留在 Wiki 或 README 里的检查等于没有。
- **一跑就红、且红的都是假警报**的门禁，结局一定是被注释掉。所以要修**扫描目标**，不是降**判定意图**。本项目两例：危机 chunk 里的 `track(` 来自 Vue 运行时（`Dep#track`），书目 JSON 里的「解锁」是书名。
- **门禁自己也要有测试**，而且要测两头：造一个违规样本必须红（否则是装饰），造一个已知误报样本必须不红（否则会被关掉）。见 `tests/tools/*.test.ts`。

## 十一、接手操作指引

### 11.1 跑起来

```bash
cd D:/wkbd/reading-app
npm install          # 若要装新包，务必加 --registry=https://registry.npmmirror.com
npm run check        # 全量门禁（typecheck + 169 条测试 + 枚举 + 风格 + 数据校验）
npm run build        # 生产构建（prebuild 会自动跑数据管线）
npm run dev          # 本地开发
```

**装 npm 包必须换淘宝镜像**：`registry.npmjs.org` 直连单个 metadata 请求 25–130 秒且伴随 `ECONNRESET`；换镜像后 1.6 秒出元数据。

### 11.2 改代码前必读（按顺序）

1. `docs/SPEC.md` — **唯一契约**。任何冲突以它为准。
2. 本文件 §5.3（打分算法）和 §10（陷阱）。
3. `docs/PLAN.md` — 里程碑与出口条件。
4. `docs/decisions/OPEN-DECISIONS.md` — 哪些已决、哪些还开着。
5. `docs/ARCH.md` §3.9（完整算例，可直接当单测）/ §3.10（跳答权重重分配）。

### 11.3 改数据的规矩

- **改契约先改 SPEC，再改 `src/contracts/`**，`tools/check-enums.mjs` 负责两侧对拍。
- 新增书 → 放 `seed-core-02` 或 `03`，**不要动 `01`**（评测基线）。
- 加完书 → 跑 `npm run data:map-core` 和 `npm run data:boot`，再跑 `npm run check`。
- 新增困境标签 → 同时改 `enums.ts`、`taxonomy.json`、`problem-lexicon.json` 三处，否则派生层漏标、覆盖率算错。

### 11.4 不要做的事

- 不要把 vitest 改回并发（§10.3）。
- 不要给缺失字段填默认值（§10.2）。
- 不要为了"让金标数字好看"去调权重或阈值（§7.5）。
- 不要在 tie-break 里加时间字段。
- 不要在注释或文案里用 emoji。
- 不要引入后端 / 第三方请求（违反产品承诺）。
- 不要用 LLM 在运行时生成推荐理由（不可复现）。

### 11.5 当前最该做的三件事（我的建议，供参考）

1. **定 §9 第 1 条**（千本级通道）——不定就无法推进覆盖率。
2. **补 6 个薄标签**（各 1–2 本）→ 低投入、直接改善体验。
3. **修派生层精度**（§9 第 3 条）——提升宽池可信度。
