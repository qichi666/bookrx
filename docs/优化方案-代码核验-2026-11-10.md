## 2. 市场定位 vs 实际能力：最关键的差距

### 2.1 定位主张

对外一句话（来自交付说明）：「说清你此刻的困境，它给 5 本确实对味的书，每本说清为什么是它——**能读的直接在这里读**。」

### 2.2 实际能力：68 本中仅 2 本可站内直读

对 4 片种子数据逐本统计 `availability`：

| 可得性 | 数量 | 含义 |
|---|---|---|
| `inline`（站内直读） | **2 本** | 《围炉夜话》（3h，公版）、《曾国藩家书》（12h，公版中文） |
| `bring_your_own`（需自备文件） | **66 本** | 全部为在版权现代心理/方法类书，用户须自行导入 EPUB/TXT 后才能在站内阅读 |

**这是「市场定位 vs 实际能力」最大的一处落差。** 产品叙事中的「68 本」与「能读的直接在这里读」，落到代码上是：**不依赖用户自己导入文件，开箱只能读完 2 本公版经典**；其余 66 本的「阅读—划线—笔记—统计」链路，成立前提是用户先主动找到并导入对应文件。

### 2.3 这一落差如何传导

- **留存段（F5/F6）**：想读队列、读后回执都已建好，但 66 本在导入前无法触发阅读，回执素材有限；
- **积累段（F7/F10）**：时长、笔记、统计能力完整，却依赖用户自备内容才有数据；
- **凭证段（F4）**：打印/JSON 不依赖正文，可正常工作；书摘图依赖已有划线。

> 结论：BookRx 的**工程闭环已全部接通，但「内容可在站内闭环」的比例只有 2/68**。它当前更准确的自我描述应是「一个带完整本地阅读管理能力的诊断器，内容主要靠你自己带进来」，而非「68 本都能在这里读」。

### 2.4 真实且达标的部分（无需担心）

- **`est_reading_hours` 零缺失**：68 本全部有值，区间 1.5–20h、中位 6h；仅 11 本恰为 6，分布平滑，**不是用默认值批量回填**，F11 排期的数据基础可信；
- **确定性内核纯净**：`domain/` 禁随机/时钟有测试拦截，可复现成立；
- **隐私架构**：运行时依赖仅 `vue`、`vue-router`，无服务器、无上报通道；
- **离线机制**：见第 4 节，采用运行时缓存而非硬编码清单。

## 4. 离线（Service Worker）专项结论

`public/sw.js` 采用**运行时缓存，无硬编码路由清单**，两条规则：

1. **导航请求**：网络优先，断网回退缓存或 `index.html`。本应用是 hash 路由，所有路径共享同一份 `index.html`，因此**任何路由的「页面外壳」离线都能打开**；
2. **同源静态资源**（JS/CSS/书目 JSON）：缓存优先 + 后台刷新。各视图懒加载 chunk 在**首次在线访问后**被缓存。

**含义**：新路由（/stats /notes /plan /compare /print /admin /profile）并非「未被缓存而退化」，但**用户在断网前从未访问过的路由，其 chunk 尚未缓存，离线首次进入会失败**——这与 v1 行为一致，属运行时缓存的固有取舍，而非新引入的回归。若希望「装好即全部路由离线可用」，需在构建后回填预缓存清单（当前刻意不做）。

## 5. 横向对比：商业产品与 GitHub 开源竞品

### 5.1 GitHub 开源竞品（本轮实搜）

| 项目 | 技术栈/形态 | 核心能力 | 与 BookRx 的关键差异 |
|---|---|---|---|
| **Openreads** | Flutter，iOS/Android | 本地多书架、目标、基础统计、无账号、可选加密备份 | 隐私立场一致，但**无任何推荐内核** |
| **PageVault** | MIT，本地/Flask 自托管 | EPUB/PDF 阅读器、全文检索、20+ 图表、ISBN 扫码 | 追踪/检索强，**无按处境的确定性打分推荐** |
| **Collectarr** | 离线 SQLite，多端 | 收藏管理、本地库、可选同步 | 以「收藏」为中心，非处境推荐 |
| **Readest** | 开源多端阅读器 | 高亮/笔记/分屏/TTS/云同步 | 强阅读器，**有同步、无诊断推荐** |
| **LightRead（yzfly）** | Tauri 2 + Vue 3，约 55 star | 封面书架、多格式（含 PDF 双语对照）、多书源、书单标注来源、阅读仪表盘、可选 WebDAV | 最接近的中文开源竞品；**书单标来源但非字段级可解释/可复现的处境打分，推荐不是主路径** |
| **Polka** | 自托管服务器，单二进制 | 家庭书库、浏览器内阅读、OPDS、「下一本」推荐 | 需服务器，与无服务器立场冲突 |
| **BookNook / aelm RAG** | 本地 Docker / Ollama+向量库 | 按 mood 语义匹配 5 本 | 基于 **LLM/RAG，结果不可复现**，与确定性内核冲突 |

### 5.2 商业产品（沿用 v4 实搜结论）

- **综合追踪**：StoryGraph（统计最深、ML 黑箱、Private Books）、Hardcover（双向导入、逐本隐私）、Goodreads（规模最大、隐私最弱）、Bookly/Bookmory（计时为核心）；
- **处方式**：Reading Well（累计借出 430 万册、92% 觉得有用、97% 愿推荐、90% 专业人员认可，强依赖线下图书馆）、Book Therapy（£29.99 人写 10 页报告，不可扩展）；
- **AI 情绪匹配**：Paguely、Embertale（生成式理由，不可复现，需账号）；
- **中文**：微信读书（资源/社交强、账号强制、数据在腾讯）、豆瓣（评文学价值非「此刻适合我」）、简单心理（书单仅内容营销）。

### 5.3 对比结论：差异化空位仍然成立，但胜负在「标配深度」

**五者交集——「困境因果 × 字段级可解释 × 可复现 × 零收集 × 危机安全」——在商业与开源产品中仍无直接对等物。** 开源竞品要么没有推荐内核（Openreads/PageVault），要么是不可复现的 LLM 匹配（BookNook/RAG），LightRead 最接近但不做可复现的处境打分。

**但 BookRx 真正的短板不在差异化，而在三处标配的深度与衔接：**

1. **站内可读内容太薄**（2/68），是内容侧最大缺口；
2. **已积累的划线/笔记没有「再接触」触发器**（无每日回顾、首页无动态区块）；
3. **回执数据只算整体有用率，没有按标签聚合为可行动信号**，治理价值未释放。

## 6. 功能建议清单（按优先级从高到低）

> 优先级：高=不做会在核心场景流失或浪费已有资产；中=显著增强但不致命；低=锦上添花/依赖数据积累。
> 复杂度：以「人日」与是否动存储/内核衡量；所有建议均**不触碰确定性打分内核、不引入账号/云/LLM**。

### 6.1 高优先级

#### 建议 1｜每日旧划线回顾（新增）
- **推荐理由**：Hikara 已验证「每日回看一条旧划线」是低成本再接触机制；BookRx 有 F10 笔记数据却无任何触发器，用户划线后不再回来。
- **预期价值**：把沉睡的最重用户资产重新激活，是画像 B（读了很多记不住，30%）留存的最低成本手段。
- **优先级/复杂度**：**高 / 低（约 0.5–1 人日）**。
- **实现要点**：复用 F10 查询；选取函数放 `lib/`，用 `book_id + 日期` 的哈希做确定性选取（**不用 `Math.random`**），点击跳回原段落；不进 `domain/`。

#### 建议 2｜首页「今天」区块（优化 F1）
- **推荐理由**：现首页 4 张卡是静态入口，「继续读」是底部单链接，两者未整合；首页应是「每天打开都有内容」而非导航页。
- **预期价值**：把「继续读 + 今日旧划线」合并为一个动态区块，提升日活与回访理由。
- **优先级/复杂度**：**高 / 低（约 1 人日，与建议 1 同期）**。
- **实现要点**：新增「今天」区块，左/上为在读书进度，下为一条旧划线；保留现有可关闭卡片机制。

#### 建议 3｜回执按标签聚合进治理面板（优化 F13/F6）
- **推荐理由**：现 /admin 仅整体有用率，无法回答「哪个标签下的书被标『不适合』比例最高」；Reading Well 的公信力正来自被看见的效果聚合。
- **预期价值**：让维护者第一次拥有数据判断「8000/6000 阈值是否合理、哪类标注可能有问题」，**不改变推荐算法、不破坏可复现**。
- **优先级/复杂度**：**高 / 低（约 1 人日）**。
- **实现要点**：/admin 只读，按标签聚合 `verdict` 分布；数据已在本机 IndexedDB；空态如实提示。

#### 建议 4｜书籍关系图谱 F15（新增，互补/递进/对立）
- **推荐理由**：Hikara 的 echoes/challenges/bridges 是唯一做透的「书间关系」；BookRx 有 33 标签标注，可用共现矩阵纯确定性计算，无需 AI。
- **预期价值**：把「处方」从单味药扩展到「配伍」，回答「读完这本，下一本补哪一面」，是少而精的推荐深度扩展。
- **优先级/复杂度**：**高 / 中（约 2–3 人日）**。
- **实现要点**：在 `domain/` 新增纯函数共现矩阵（不新增数据字段）；关系类型与判定规则需先定（见第 8 节第 5 条）；入口放详情页，轻量视图。

### 6.2 中优先级

#### 建议 5｜笔记检索命中高亮 + 上下文（优化 F10）
- **理由/价值**：现仅返回整段结果，无高亮/上下文，与「翻列表」无本质区别；高亮命中词并展示前后文，检索才真正可用。
- **优先级/复杂度**：**中 / 低（约 1 人日）**；纯前端字符串处理，注意转义防 XSS。

#### 建议 6｜处方笺版书摘图（新增 F4 版式）
- **理由/价值**：现仅通用引文卡（paper/night）；产品专属视觉资产是「处方笺」（日期/Rx/处境回显/分档），专属版式在社交传播的辨识度远高于通用卡（参照 Paguely Wrapped）。
- **优先级/复杂度**：**中 / 低（约 1–1.5 人日）**；Canvas 2D 新增模板，**默认不含处境敏感信息，需用户勾选**。

#### 建议 7｜统计页补「读完率」比值（优化 F7）
- **理由/价值**：现有读完绝对数与有用率，缺「读完 / 开始」比值；这是画像 B「我读进去了吗」最直接的量化答案。
- **优先级/复杂度**：**中 / 低（约 0.5 人日）**；空态不画 0 值。

### 6.3 低优先级

#### 建议 8｜F11 实际 vs 预估速度对照（优化）
- **理由/价值**：F7 积累真实速度后，计划页展示实际/预估差并可选修正系数（默认 1.0），提升排期可信度。
- **优先级/复杂度**：**低 / 低（约 1 人日）**；依赖 F7 数据积累。

#### 建议 9｜档案级 JSON 导入/导出（新增）
- **理由/价值**：交付说明待办项；现导出全量、导入未按档案区分，分库架构下自然延伸。
- **优先级/复杂度**：**低 / 低（约 1 人日）**；不阻塞核心场景。

#### 建议 10｜薄标签继续补书（内容侧，非功能）
- **理由/价值**：最薄已从 2 改善到 3，`big-choice=5`、`emptiness=4`，紧迫度下降；是否提前取决于这两类是否为目标用户高频困境。
- **优先级/复杂度**：**低（视画像可调高）/ 内容工作，每本约 60 分钟人工标注**。

### 6.4 已被代码满足、无需再提的项（避免重复投入）

- F8「一句话解释」（G5）——**已实现**；
- 书方 JSON 双向导入（G6）——**BooklistView 已实现**（含缺失标注与重算）；
- 首页卡片可关闭（G2）、打印默认最小暴露（G4）、streak 冻结额度（G1）——**均已实现**。
