## 1. 命名：三个候选

先说一个否决项：**不能叫 LightRead**。GitHub 已有同名项目 `yzfly/LightRead`（v1.19.4，Vue3+TS+Tauri2，AGPL-3.0，2.1 万部古籍书源），且它的产品逻辑与我们相反（阅读器优先、推荐是默认关闭的静态书单）。重名会让 star、issue、搜索引擎全部分流，且开源协议不同（AGPL vs MIT）会引发误解。

| 候选 | 中文名 / 英文名 | 一句话理由 | 风险 |
|---|---|---|---|
| A（推荐） | **书方 / BookRx** | 「书方」= 书 + 处方，两个字直接说清「按你的毛病开书单」，与「一个诊断器自带阅读器」的定位同构；`bookrx` 在 GitHub 搜索无同名项目，仓库名 / npm 名 / 域名（bookrx.app 类）竞争极低 | 「Rx」是医疗符号，需要在 README 第一句解释，且部分用户会误以为是药品相关 |
| B | **读得下去 / ReadThrough** | 直接命名用户的真实目标（读完），中文口语化、有画面感，比「阅读器」这类品类词更能被转述 | `readthrough` 在 GitHub 已有同名小型阅读类项目；作为产品名偏「动作」不像「物件」，不利于口口相传时说「你去用一下 XXX」 |
| C | **对症 / DuiZheng** | 极短、中文语境里「对症」已经完整表达「先诊断再开方」，且不是一个现成的产品名 | 纯拼音英文名海外不可读，GitHub 搜索可见性差；「对症」单独出现语义悬空（需配「对症读书」才完整），不利于国际化 issue |

**推荐 A**。若总监希望中文更直白、不背医疗隐喻，可选 B。命名不影响任何功能定义，此决策可在开工前 1 天内闭环。

仓库与关键词建议（只影响发现性，不影响功能）：仓库名 `bookrx`（或 `duizheng`），topics 取 `book-recommendation`、`epub-reader`、`reading-habit`、`local-first`、`chinese`。**「诊断式推荐」「按困境找书」在 GitHub 是全空位**（见第 5 章），这是最大的可发现性资产，应写进 README 首屏。

## 2. 问题陈述

**谁**：一个 22–35 岁、有一定阅读意愿、但连续 12 个月没有完整读完一本书的中文用户。他通常在通勤、睡前、或者某个情绪低点（被裁员 / 分手 / 体检报告异常 / 转岗失败）打开手机想「我是不是该读点书」。

**什么场景**：他不知道该读什么。他手上有三个失效的替代方案：

1. **电商榜单和畅销榜**：卖的是「最近什么好卖」，不是「我该读什么」。买回来发现不对味，于是书架越堆越高，形成「买了 = 读过了」的心理代偿。
2. **小红书 / 公众号书单**：一次给 20 本，没有任何一本是为他选的，看完收藏完，一本都不开始。
3. **豆瓣**：无公开 API（2017 年关停开放接口，2023 年 7 月开发者平台下线），评分是「大众平均」，不是「对我的适配度」。8.9 分的书对他是 0 分——因为他读不下去。

**为什么现有方案不行**：所有替代方案回答的都是「哪些书好」，没有人回答「**以我现在的状态，我能读完哪一本，读完会变好吗**」。而这个问题恰好有两个可解的子问题：一是**匹配**（书和我的困境对不对得上），二是**可完成性**（这本书我今天晚上真的能翻开并读下去）。市面上的产品只做第一件，且做得很粗；没有产品做第二件。

**我们这个产品的赌注**：用户不是缺书，是缺「第一步」。所以产品必须先做诊断、再做推荐、再当场给出可读的文本、最后帮他记住。这条链路上任何一环缺失，用户就退回原样。

## 3. 目标用户画像

### 画像 A：卡住的人（主要用户，占比预估 60%）

- **具体场景**：28 岁，二线城市互联网公司运营。上个月绩效面谈被主管说「你的表达没有说服力」，她当晚搜了「怎么提升表达能力」，买了一本《金字塔原理》，读了 18 页，之后再没打开。她的书架上还有 9 本同样命运的书。
- **技术水平**：会用浏览器、会装扩展、不会用命令行。给她 `.epub` 文件她会问「这个用什么打开」。
- **真实诉求**：不是「读书」，是「解决一个具体的不舒服」。她要的是今晚有事可做，且这件事看起来有希望。
- **对我们的要求**：别让她做选择题做 20 道；告诉她「先读这本，只要 2 小时」；她现在就要能开始读。
- **成功体验**：当晚读了 30 分钟，第二天又回来读了 20 分钟，并且记得自己划线的那句话。

### 画像 B：读了很多但记不住的人（次要，30%）

- **具体场景**：34 岁，产品经理，Kindle 和微信读书都有，去年读完 11 本，但被问「你最近读的那本讲了什么」时说不出来。他怀疑自己在「消费书」而不是「吸收书」。
- **诉求**：要一个能验证「我真的读进去了」的机制，而不是又一个进度条。
- **对我们的要求**：章节小测要问「理解」不是「记忆细节」；复习要能安排在通勤的 10 分钟里；笔记要能导出，不能被锁在某个 App 里（这是他离开微信读书的原因）。
- **成功体验**：三个月后能对着旧笔记复述一本书的三个核心论点。

### 画像 C：开源贡献者 / 书单策展人（生态用户，10%）

- **具体场景**：一个读过 200 本心理学书的开发者，愿意提交 PR 补全 20 本书的「这本书讲什么 / 读完能得到什么」字段，因为他也受够了烂书单。
- **诉求**：字段结构清晰、有校验脚本、有 CONTRIBUTING 说明、提交后能被合并并署名。
- **对我们的要求**：书目数据必须是纯文本可 diff 的（JSON/Markdown），不能存在数据库里；字段缺失要有明确降级规则，不能因为一个字段空着就整本无法入库。
- **成功体验**：他的 PR 在 72 小时内被 review，署名进入 CONTRIBUTORS，且他的书出现在某个真实用户的推荐结果里。

**明确排除的用户**：找免费盗版书的人（我们不提供，也不做书源爬虫）、要读 PDF 论文的人（第一版不做）、想在阅读器里社交的人（不做社区）。

## 4. 需求拆解：从「说出问题」到「拿到推荐」的 6 个心理节点

这是一条**信任漏斗**。每一节点都会流失，且流失原因不同。产品每一处设计必须对应堵住一个节点。

| # | 节点 | 用户心里的话 | 流失机制 | 产品对策（可验收） |
|---|---|---|---|---|
| 1 | 表达成本 | 「我也说不清我怎么了」 | 让他填长表单 = 直接关页 | 3 步选项式问卷（每步 4–6 个选项，可多选），允许选「说不上来 / 就是想读点东西」；自由文本框非必填（字数上限见 SPEC §5.2） |
| 2 | 信任 | 「你凭什么推荐这本」 | 黑箱推荐 = 不信 = 不读 | 每本必给三段理由（你的处境 → 这本书讲什么 → 读完能得到什么）；理由里必须回引用户自己输入的原词；不显示伪精确百分比（见 7.3） |
| 3 | 体量恐惧 | 「这书 600 页，我不可能读完」 | 厚度 = 拒绝 | 卡片正面强制展示「预计阅读时长」与「篇幅档位」；破冰位（7.4 R1）保证第 1 位一定短或一定可直读 |
| 4 | 沉没成本恐惧 | 「买了又不读，又是一次自我否定」 | 付费前置 = 放弃 | 不卖书；公版书当场直读；版权书明确给「图书馆 / 购买 / 试读章」等合法获取路径，并把「你还没有拥有这本书」说清楚，不含糊 |
| 5 | 隐私羞耻（隐性节点，容易被忽略） | 「我选的这些选项，会不会被人看到我在焦虑 / 在婚姻出问题」 | 一旦察觉被记录 = 立刻退出 | 无需注册、无需登录；所有问卷答案与阅读进度只存本地 IndexedDB；遥测默认关闭（见第 15 章） |
| 6 | 读完的落空 | 「读完了，但我什么都没剩下」 | 无反馈 = 不回来 | 章节小测（理解型）+ 间隔重复复习 + 划线回顾页；「读完」不是一个进度条 100%，而是「你能复述三个论点」 |

**节点 5 是本产品与商业阅读 App 最大的结构性差异**：微信读书、番茄等必须拿到你的账号与行为数据才能商业化，我们不商业化，所以我们可以承诺「不联网也能用」。这句话要写进首屏，它是信任的锚点。

| 维度 | yzfly/LightRead | 我们 |
|---|---|---|
| 产品重心 | 阅读器优先（多端、听书、同步、2.1 万部古籍书源） | 诊断优先（阅读器是配套，因为「推荐完不能马上读」链路就断了） |
| 推荐形态 | 设置 → 功能里，**默认关闭**；编辑精选静态书单 | 首页唯一入口，不可关闭；按用户困境逐本生成理由 |
| 个性化 | 无 | 规则加权打分 + 三段式理由（可解释、可复现） |
| 协议 | AGPL-3.0（传染性强，商用/二次分发受限） | MIT（允许任何人 fork 自建、嵌入自己产品） |
| 我们的破绽 | — | 书目数据量远小于 2.1 万部；无多端同步；无听书 |

**结论收敛成三句话**：
1. 计算机类是 GitHub 上唯一有规模的书单品类 → **我们不做计算机**，做文学/心理/思想/社科/传记，因为「按困境推荐」的需求集中在这些品类。
2. 「按处境 / 困境推荐」在 GitHub 零竞品 → 这是我们的定位护城河，必须写进 README 首句与仓库 description。
3. 「推荐 → 能当场读 → 读完帮你记住」无人打通 → 这是我们的功能闭环，也是最贵的部分，MVP 必须至少打通到「能当场读」。

## 6. 我们的差异化

**一句话**：别人的推荐是「这本书很好」，我们的推荐是「**以你现在的状态，这本书你能读完，而且读完你会拿到这一个东西**」。

具体差异（每条都可被用户当场验证，不是话术）：

| 差异点 | 用户如何当场验证 |
|---|---|
| 每本都有理由，且理由回引了你自己说的话 | 看到「你提到开会不敢发言」这句出现在理由第一段 |
| 不用百分比假装精确 | 看到的是「高度契合 / 较为契合 / 换个角度」+「命中了哪些点」，而不是「92% 匹配」 |
| 第一本是短的、能读完的 | 看到「约 2.5 小时」且可直接点开读 |
| 不用注册、数据不上传 | 断网后刷新，推荐结果与阅读进度仍在 |
| 不卖书、不导流盗版 | 版权书只给获取途径，不给正文 |

## 7. 推荐与排序的产品定义

### 7.1 用户输入形态：选项式为主，自由文本为辅（约 7:3）

设计原则：**选项保证规则引擎有可命中的结构化信号，自由文本保证用户感到「被听见」并且能补充选项覆盖不到的语境**。

| 步骤 | 内容 | 形式 | 是否必填 | 信号用途 |
|---|---|---|---|---|
| 第 1 步 | 「你现在最想解决的是哪一类？」（情绪与自我 / 关系 / 工作与意义 / 习惯与行动 / 认知与思考 / 人生转折） | 单选 6 项 + 「说不上来」 | 必填 | 映射到 6 个困境域，决定候选池 |
| 第 2 步 | 「具体是哪种感觉？」（随第 1 步联动，4–6 个多选项） | 多选，最多 3 项 | 必填 | 直接映射 `problem_tags`（受控词表，按主诉/次/第三**递减加权**），是主题契合的唯一依据；权重数值见 SPEC §6.1 / §6.2 |
| 第 3 步 | 「你现在的读书条件」——**同一屏 5 组 chip，见下方 7.1.1** | 单选 chip ×5 组 | **五组全部可跳过**（跳答处理见下，不得写成「按中性值处理」） | 分别驱动 篇幅 / 难度 / 紧迫度 / 结构需求 / 深度 五个轴 |
| 第 4 步（辅） | 「还有想说的吗？（可跳过）」 | 自由文本（字数上限见 SPEC §5.2） | 选填 | 词典匹配到 `problem_tags`，命中词用于理由第一段回引 |

#### 「哪个最想先解决」同屏追问（v1.5 新增，属 P0-1）

| 项 | 规则 |
|---|---|
| 触发条件 | **仅当第 2 步勾选 ≥2 项时出现**。只勾 1 项时它显然就是主诉，再问一遍是侮辱 |
| 位置 | 第 2 屏下方**展开一行**，不跳转、不新增屏（总屏数仍 4 屏上限） |
| 文案（逐字，不得改写） | 「这些里面，哪个是你现在最想先解决的？」 |
| 禁用文案 | **不许用「最严重」**——那是让用户给自己的痛苦排序；「最想先解决」问的是先后，不是轻重 |
| 默认值 | **不预选**。预选第一项会制造锚定，用户会顺着我们的手指点 |
| 跳过时 | **不可跳过**（v1.6 改）。勾了 ≥2 项，这一问就是必答——见下方「为什么改成必答」 |

**为什么非要问这一句**：多选 3 项时，「等权」和「按勾选顺序加权」都是在猜主诉。而主诉决定三件**用户能直接看见**的事——理由第一段回引谁、第 1 位给谁、档位封不封顶（见 7.3）。**用一个问题换掉三次猜测，这是整份问卷里性价比最高的一问。**

**为什么不能靠「勾选顺序」代替**：勾选顺序只证明「它排在第一个」，往往只是手指先碰到了它。把顺序当主诉，等于用一次误触决定他今晚读什么。**因此禁止用勾选顺序推断主诉**（SPEC §6.2 已写成硬规则）。

**为什么改成必答（v1.6，重要）**：原来设计是「可跳过，跳过则按勾选顺序兜底」。后来判定这一步是错的——主诉决定**档位封顶**（主诉未命中 ⇒ 封顶 `explore`），这是一条**只降级、不报错**的规则，猜错了的表现只是「有些人老是推荐不出高度契合」，安静、系统性、看起来像用户偏好问题。**凡是这类错误，都不该靠统计去发现，该靠不让它有发生的可能。**
代价是一次点击——用户在同一屏上已经点过两三次，多一次几乎无感；收益是 `source` 从三值收成两值（`explicit` / `single`），**「建立在猜测上的档位」这种东西直接不存在了，也就不需要埋点去数它。**

#### 7.1.1 第 3 步的 5 组 chip（**并入同一屏，不新增页面**）

| 组 | 问题 | 选项 | 驱动（字段与算法见 SPEC §6.1） |
|---|---|---|---|
| 3-a | 每天能读多久 | 10 分钟 / 30 分钟 / 1 小时以上 | 认知负荷修正 + 篇幅默认值 |
| 3-b | 能接受多难 | 越轻松越好 / 有点挑战 / 不怕难 | 认知负荷主值 + 难度硬上限 |
| 3-c | 希望多快见效 | 这三周就要用 / 一个月内 / 不着急 | 紧迫度（影响表达友好度的目标值） |
| 3-d | 想要这本书怎么带你 | 讲一个人的故事 / 讲清一套方法 / 给我完整框架 | 体例因子（对应 SPEC `form`，3 值枚举） |
| 3-e | 更想要哪种收获 | 具体做法 / 做法加为什么 / 底层原理 | 深浅因子（对应 SPEC `depth`，3 值枚举） |

**必答范围：只有第 1、2 屏必答，第 3 屏 5 组全部可跳过。** 这不是宽容，是算过的：第 3 屏每题都在追问「你打算怎么读」，而用户此刻只想「找本书」，硬拦会直接损失完成率。

**跳答处理（产品语义；实现与归一化见 SPEC §6.1）**
- 某组未答 → 该组驱动的因子**整条从本次计算中移除**，权重按比例重分配给其余因子。**不得代入中性值**：给未观测的维度填中位数，等于假装我们知道答案，那一个因子会稳定输出中分，既不可解释，又把真正有信号的因子挤薄。
- 5 组全跳过 → 退化为「主题 + 难度」两因子排序，**结果页顶部必须提示「补上读书条件能排得更准」**，并给一个直达第 3 屏的入口。不提示的话，用户不知道这次结果为什么比别人的糙。

**3-c / 3-d / 3-e 不是装饰性问题，它们是打分因子的唯一信号来源**：没有 3-c，紧迫度因子只能恒为中性；没有 3-d，体例因子拿不到输入；没有 3-e，深浅因子拿不到输入。**没有信号的因子必须删掉或补题，不许留在权重里当常数**（见 7.4 因子约束）。

**页面数量是硬约束**：问卷总屏数 **4 屏为上限**（3 屏必填 + 1 屏自由文本）。后 3 组 chip 必须**并进 3-a / 3-b 那一屏**，不得因为补了信号就新增页面——7 题的问卷在真实用户手里会被直接关掉，而这三个轴的价值远小于「完成率下降 20%」的代价。

**权重语义（产品定义，不涉及实现）**：结构化选项贡献约 70% 的匹配信号，自由文本约 30%。自由文本**不做语义理解、不做 LLM 抽取**，只做同义词词典命中（如「内耗 / 想太多 / 反复想」→ 命中内耗类受控词，正式词名以 ARCH 词表为准）。用户自由文本未命中任何标签时，不影响出结果，只少一个回引素材。

**「说不上来」不是失败态**：选它则跳过第 2 步，直接进入「最近生活里哪块最耗你」（6 个更具体的场景选项：睡不好 / 和某个人关系紧张 / 工作提不起劲 / 总在纠结一个决定 / 感觉自己落后了 / 只是空虚）。这一步是把抽象问题**降维到具体场景**，因为「说不清」的用户需要的是被提示，不是被追问。

### 7.2 推荐结果呈现结构

**一次最多给 5 本，分三档，不做无限流**（无限流会让用户重新回到「选择过载」，与产品初衷相反）。「最多」二字是关键：宁可出 3 本真对味的，也不出 5 本凑数的。

| 位置 | 分组标题（SPEC §7.2） | 档位枚举 | 数量 | 定位 | 用户该做什么 |
|---|---|---|---|---|---|
| 第 1 位 | 今晚就能开始 | `strong` | 1 本 | 今晚就能开始读、能读完的那一本。破冰逻辑见 7.4 阶段④ | 直接点开读 |
| 第 2–4 位 | 读完这本再看 | `worth` | 1–3 本 | 与第 1 本同一困境域但角度不同 / 更深一层 | 读完第 1 本再来 |
| 第 5 位 | 也可以看看 | `explore` | 0–1 本 | 相邻困境域的一本，命中 1 个次要标签；该组不显示档位方块 | 备着，可能现在不想读 |

**档位枚举只有三个值：`strong` / `worth` / `explore`**（见 SPEC §6.3⑦）。**禁止使用 `fit` / `high` / `mid` / `low`**——`fit` 在本文旧版里曾指「较为契合」，已废弃；`problem.fit` / `difficulty.fit` 是因子内部字段（因子名已由 `topic` 改为 `problem`，理由：它比的是困境标签，而主题是 `theme_tags`、且不打分），与档位枚举无关，不要混用。

**两条硬规则（防止结果「看起来很满」但实际全是凑数）**

1. **`strong` 只有 1–2 本是正常且允许的**。5 本里 `worth` 不足时，**宁可只出 3 本**，也不许把 `explore` 重新包装成「较为契合」来填满 5 个位置。
2. **第 5 位的档位标签必须显示「换个角度」**，其内部枚举是 `explore`。`explore` 书不得出现在前 4 位，也不得与 `worth` 混排在同一视觉分组里。用户看到「换个角度」这四个字，就知道这本不是对症的——这是诚实，也是防止他读完觉得被骗。

**卡片必须前置的信息（从信息架构上堵住「体量恐惧」）**：信息层级以 **SPEC §7.1 的 8 项**为准（书名 / `match_brief` + 档位 / **S2 首句（≤2 行、≤38 字）** / 可用性徽标 / `mismatch` / 难度·篇幅·预计时长 / 主按钮 / 展开区）；展开区放 S1 + S2 全文 + S3 + 命中依据 + 作者译者，**卡面上不放 S1**、**展开区不重复 B1**（理由、代价与「什么能上卡面」的判据见 8.1）。产品侧补三条语义：① 译者有译本必显，缺失时显示「译本信息待补充」；② 篇幅与预计时长必须在折叠区之前可见，否则「体量恐惧」这一关过不去；③ `match_brief` 缺失时降级为 7.3 的「命中依据」短语，不得留空位。

**是否保留「三段式书单」**：保留，但要降级为**可选的「阅读路径」视图**，不作为默认结果形态。

- 默认视图是「5 本卡片列表 + 每本三段理由」（用户诉求是「逐本说明理由」，逐本卡片最直接）。
- 「三段式路径」（第一本破冰 → 第二本深化 → 第三本行动）作为一个可切换的 Tab，只在用户选了「我想系统地解决这个问题」时默认展示。
- 理由：三段式路径在概念上优雅，但在实际使用中是一种**强制线性**——多数用户不会按路径走完三本。把它做成可选视图，既不丢这个设计资产，也不绑架用户。

### 7.3 符合度怎么呈现：档位 + 命中依据，**不显示百分比**

**明确否决「92% 匹配」这类数字**。三条理由：

1. **伪精确即不可信**：规则加权打分的输出不是概率，把它渲染成百分比是在说谎；只要用户发现两本内容相近的书一个 92% 一个 89%，整个推荐系统的可信度就崩了。
2. **数字会引发错误的比较行为**：用户会开始比较 89 和 91，而不是读理由。而我们真正希望他读的是理由。
3. **数字无法解释**：用户看到 87% 的第一反应是「为什么不是 95%」，而档位 + 命中依据恰好回答了这个问题。

**呈现方案（三层）**：

| 层 | 呈现 | 示例 | 作用 |
|---|---|---|---|
| ① 档位标签 | 三档文字标签，不排序不加星 | 「高度契合」「较为契合」「换个角度」 | 给出粗略强弱，不诱导精确比较 |
| ② 命中依据 | 2–4 个短语，取自用户自己的选项与自由文本原词。**卡片上没有独立的命中依据位**——正常态卡片第 2 行由 `match_brief` 承担同一作用（更短、更像人话），命中依据本体进**详情页与展开区** | 「命中了：开会不敢发言 · 怕被否定 · 每天能读 30 分钟」 | 这是**可解释性的实体**，也是信任的主要来源 |
| ③ 边界声明（`mismatch`） | 一句话说明「为什么不是更高档」；**必须在卡片首屏可见**，不能只放详情页 | 「不过：这本书偏理论，读起来不如第 1 本轻松」 | 主动暴露不确定性，反向增强可信度 |

**② 的卡片规则（v1.5 定稿，硬约束，验收逐条检索）**

| 状态 | 卡片第 2 行的内容 | 说明 |
|---|---|---|
| 正常态（有 `match_brief`） | `match_brief` | **没有**独立命中依据位。不允许在卡片上再加一行短语列表或「前 2 个 + 「+N」」 |
| 降级态（缺 `match_brief`） | 同位置降级为「命中了：A · B」，12px、灰、**1 行截断** | 这是**替补**，不是第二块内容。两者互斥，不同屏出现 |

**完整命中依据**（2–4 个短语）只出现在**详情页与卡片展开区**，且**不得与卡片上那行降级文案同时出现在同一视口内**——同一句话出现两次，用户会读成「系统在重复强调」，信任感反而下降。

**不使用星级**：星级（4.5 星）在中文用户心里已经等于「豆瓣评分」，会被误读为「这本书本身多好」，而我们要表达的是「这本书对你多合适」。两者混淆会直接破坏定位。

**判定语义（阈值不写在本文，见 SPEC §6.3⑦）**

| 档位枚举 | 中文显示名（固定，不得改写） | 视觉（SPEC §7.2） |
|---|---|---|
| `strong` | 高度契合 | 3 方块全填 |
| `worth` | 较为契合 | 2 方块 |
| `explore` | 换个角度 | 1 方块；该组不显示档位方块 |

- **主诉未命中的封顶规则（v1.5 新增，比校准闸门更直接地堵住「假契合」）**：**主诉标签未命中的书，档位一律封顶 `explore`，与总分无关。**
  为什么：其余六个因子满分合计约占六成总分——一本**完全不沾题**的书，只要难度、篇幅、体例、深浅全中，就能一路升到「较为契合」。而「较为契合」对一本没回答他问题的书是谎话。
  这条**只改标签、不改分数**，所以调试时会看到「分数已经过线、档位仍是 `explore`」——那是故意的，不是 bug；`tie_break_trace` 必须输出 `capped_by_primary_miss: true`，让后来人一眼看出是封顶而不是算错。
  它和校准闸门的关系：**封顶管「假契合出不去」，闸门管「真契合进得来」**，两道缺一不可。
  **主诉命中是下限，不是充分条件**：主诉命中只保证**不被封顶**，不保证进 `strong`——如果主诉一命中就 `strong`，那其余六个因子等于没用。所以「主诉命中却仍是 `worth`」是**正确结果**，不是缺陷；这一句必须写在这里，否则第一次看到这种结果的人会去「修」它。
  **两个名字别混用**：判断「哪个是主诉」读 `Diagnosis.primary_tag`（稳定、必填、可持久化）；命中程度是**派生值不落库**，只出现在分档判定与 `tie_break_trace` 里。**派生值一旦落库，一定有人开始按它排序**——那就是被否决的「用主诉覆盖率压过一切」方案的变体，只是从公式挪到了字段。
- 阈值是**绝对值**，具体数值以 SPEC §6.3⑦ 为准。本文不再复述，也不接受任何分子/分母口径的等价改写：一旦改成比值判定，分母一变档位就漂移，而「同一本书对同一个用户永远是同一档」是我们对用户的承诺。
- **校准闸门（原样锁定，写进上线检查）。分两道，顺序不能颠倒：**

  **闸门 0 · 金标正对照（必须先跑这个）**：人工写 **10 个画像**——**先写处境 → 再按常识回答问卷 → 最后才指定**那本「就是为他写的」书，再看引擎给什么。**产出两个分开计数的指标，都要 ≥7/10，不许合并求平均：**

  | 指标 | 定义 | 不达标时该改什么 |
  |---|---|---|
  | **认出率**（校准，主判据） | 金标书档位 = `strong` 的条数 | **口径 / 权重 / 标注**。这一项错，调阈值是徒劳的——问题不在靶子偏了，在靶子画错了 |
  | **首屏率**（回归，副判据） | 第 1 位档位 = `strong` 的条数 | **R1 破冰位与排序**，不是权重。第 1 位被换下去而档位没变，是排序问题不是匹配问题 |

  为什么不能合成一个「≥7/10 通过」：合成之后一次 6/10 可能是 3 条校准错 + 3 条排序错，而报告只告诉你「没过」——于是最自然的反应是去调权重，**把排序的 bug 越调越深**。**判据的价值不只是挡住不合格，还在于让失败指向正确的那一层。** 两个数同一次跑出来，报告里分两列。
  为什么它排在比例闸门之前：**如果连「人认为完美对口」的样本都给不出 `strong`，那 30% 这个比例永远达不到，调权重也调不出来——问题在口径，不在权重。没有正对照就调参，等于不知道靶子在哪就开始校准。**
  **金标集必须先冻结**：这 10 组样本要在**第一次跑之前**提交进 `tools/gold-set.json` 并入仓；跑完之后想改任何一条，必须补一份 ADR 说明改的理由。否则它一定会变成新的自欺通道——第一次 4/10 不过，于是有人把「不太典型」的挑掉、换成「更理想」的，跑到 8/10 宣布通过；而这个过程中没有一个人觉得自己在造假，**每一步都只是在「让样本更准确」。标准漂移比数据造假更难发现，因为它每一步都合理。** 10 条画像的正文见 **§10.8**。

  **闸门 1 · 比例闸门**：M2 抽样 20 画像 × 60 本，第 1 位落 `strong` 比例 ≥30% 通过；<30% **只能调权重与标注，禁止下调阈值**。理由：下调阈值是自欺——它让「高度契合」变成夸奖词，而用户一旦发现第 1 位那本他读不下去，整套诊断的可信度一次性归零。报告落在 `tools/calibration-report.md` 并入仓。

- **<30% 时的分工与边界（谁改、改什么、什么不许改）**：① **架构侧出诊断**——跑 30 组输入，打印每因子的 `fit_bp` 分布与贡献占比，指出是被哪个因子压住的（「`problem` 天花板太低」还是「`length` / `form` 惩罚过重」）；② **PM 只确认一件事**——调整后「高度契合」这四个字对用户的含义没变（判据见下条）；③ **架构侧落地**——改常量 + 重跑基线 + 更新算例，**不降阈值**。

- **调整权重的唯一合法方向**：让「更对症的书更容易进 `strong`」= 修口径，可以；让「不那么对症的书也能进 `strong`」= 降标准，一律驳回。两者在数字上都表现为「strong 变多」，区别只在于**同一批书里是哪些书往前挪**——所以每次调权重都必须带一份「调整前后 top1 名单变化」的对照，不接受只报比例。

- **为什么阈值不能动、权重可以动（这条不许被"优化"掉）**：**阈值是「对外语义」**——它在告诉用户「这本高度契合」；**权重是「内部参数」**——用户永远看不到它。改后者永远比改前者便宜，也不会削弱任何承诺。**任何为了「让 `strong` 出得来」而下调阈值的改动，都等价于把「高度契合」这个词降价。**

- **产品侧守住的语义锚点**：「高度契合」的锚点是**用户的主诉被正面命中**，不是「用户勾选的每一项都被这本书覆盖」。用户勾 3 个标签时，通常是一个主诉加两个陪衬；若口径要求全部覆盖才算 `strong`，那几乎所有书都进不了 `strong`——那时候错的是口径，因为「高度契合」**从不承诺一本书解决你所有问题**。

- **v1.5 已观测到第一个校准样本**：新七因子算例对 8.2 示例 1 的画像跑出三本全 `worth`、**零 `strong`**，属于「用户选 3 个标签、书只对上一半」。**处理顺序：先怀疑口径，不要先动阈值，也不要先加权重**；待查方向是覆盖率分母（以「用户勾选的标签总数」为分母，对「用户标签多于书标签」的情形天然苛刻）。
- 中文显示名固定为「高度契合 / 较为契合 / 换个角度」三词，不得换成「强烈推荐 / 推荐 / 你可能喜欢」之类的营销词——后者的语义是「书好不好」，我们要表达的是「对你多合适」。
- `explore` 仍然展示（「有启发价值」本身就是推荐的一部分），但必须明确标注它不是对症的（见 7.2 两条硬规则）。
- 任一硬约束不满足（难度超上限 / 触发内容安全过滤）→ 在打分前直接剔除，**不允许用高分覆盖硬约束**（见 SPEC §6.3① 与本文 7.4 的 R1、R2 及内容安全那两条）。

### 7.4 排序规则的产品语义（按 SPEC §6.3 的六阶段流水线组织）

**执行顺序是 `① hardFilter → ② score → ③ rank(tie-break) → ④ slotAssembly → ⑤ relax → ⑥ tier`，不可颠倒**（SPEC §6.3）。所以下面不再有「R4 排在 R5 前面」这种单一优先级列表——**「标签」这一列只是稳定引用标签**（别的章节会引用它），真实执行位置看「阶段」列。**编号有断档是故意的**：断掉的那一格已经改成规则名（见本节末「为什么这两条规则改用名字引用」），**不要为了「编号连续」把它补回去**。

| 标签 | 阶段 | 规则 | 理由 |
|---|---|---|---|
| R1 | ④ slotAssembly | **破冰位**：第 1 位若既不是「可直接读」又不满足短时长条件，则在 `strong` + `worth` 中找第一本满足者与之交换（判定条件与实现见 SPEC §6.3④） | 这是整个产品的第一性目标：让用户今晚开始读。第 1 本如果是一本 600 页的书，用户会在看结果的 10 秒内离开，后面所有功能都没有机会展示 |
| R2 | ① hardFilter | 难度超过用户声明上限的书，**打分前剔除** | 明知他只能读 10 分钟/天还推一本需要前置知识的书，等于设置失败 |
| **`EX-trauma` / `EX-terminal`**（规则名；改名理由见本节末） | ① hardFilter | **硬过滤（默认剔除，不是软提示）**：域=「情绪与自我」且难度偏好=「越轻松」时，`content_warning` 命中 `suicide` / `sexual_abuse`（`EX-trauma`）**或** `grief` / `terminal_illness`（`EX-terminal`）的书直接从候选池剔除，不作为「你可以自己判断」的选项交回给用户。唯一例外：用户在那一问里选了「一起看」（`include_heavy`，文案见下）后，**只有 `EX-terminal` 那一组恢复参与**；`EX-trauma` 不恢复——**不对称是刻意的，理由见下，不得补齐** | 这是**安全底线**，不是体验优化。给一个正在抑郁状态的人推《自杀论》是产品事故——「让用户自己判断」在低心力状态下等于把责任推给最没有判断力的人。`grief` / `terminal_illness` 是补的第二条：原来的取值只挡自杀与性暴力，挡不住《当呼吸化为空气》《此生未完成》这类书——它们既不含自杀也不含性暴力，但把一个说「我就想轻松点」的人推给一本讲临终的书，是这类推荐最恶劣的失败方式：**他会以为是系统在暗示他没救了** |
| R4 | ② score | 可获得性**是打分因子之一，且是低权重因子**；同时作为 ③ 的 tie-break 第 4 级键。**禁止**把 `inline` 单独提为一组排在所有 `bring_your_own` 之前。权重数值见 SPEC §6.2 | 「能立刻开始」确实该加分，但它不配压过主题契合。见下方「为什么 R4 不能做成前置分组」 |
| R5 | ② score | `score_bp` 降序即主排序 | 常规排序 |
| R6 | ④ slotAssembly | 多样性配额：前 5 本内同作者 ≤2、同 `category_l1` ≤2；不足 5 本时第二遍无配额回填（见 SPEC §6.3⑤）。**`category_l1` 指书的文体（文学 / 心理 / 思想哲学 / 社科 / 传记 / 其他），不是困境域**——两个字段数量恰好都是 6，混用不报错，只会让「同文体 ≤2」静默变成「同问题域 ≤2」，测试全绿而排序变了（定义见 SPEC §2.2） | 5 本全是心理学书会让用户觉得「你只会这一个」，且失去「换个角度」的价值 |
| R7 | ③ rank | tie-break **6 级全序链**，级序见 SPEC §6.3③。**不再包含 `completeness` 一级**（已删：它能进池的书恒为同一值，等于恒真条件），也**不得出现任何时间类字段**（如 `last_reviewed`） | 最后一级保证全序，从而保证**结果可复现**（同一输入必有同一输出，这是规则推荐的承诺，也是可单测的前提） |
| R8 | ①②④ | 用户自建条目（手动录入）**绝不进前 3 位**、**档位上限 `worth`**（永不出 `strong`）、**不参与多样性配额计数**。三条同时生效，细节见 7.5 | 见 7.5。没有人工策展的书，我们没有资格说它「高度契合」——那是在用算法的口吻替一本没读过的书背书 |

**例外那一问的文案与控件（定稿，不得改写）**：用户看到的是一个**内容**问题，不是一个**能力**问题。

> **这类内容里有涉及临终或丧亲的，要不要一起看？** —— **二选一：`一起看` / `先不用`；默认落在 `先不用`。**

**为什么是二选一，不是勾选框**：勾选框的默认态是「没选」，那只是一个**界面初始值**，用户从没对它表过态；二选一的默认态是「选了先不用」，那是一个**用户的答案**。两者在埋点里长得一样、在实现里也一样（都落到 `false`），但只有后者能保证「他看过这句话，并做了一个选择」。**这个区别只在一种情况下有用：事后要回答「他到底有没有被问过」。**

**为什么必须换成这句**：原来写的是「我可以读沉重的题材」，它要求用户先对自己的状态做一次评估——而**处在低状态的人最没能力做这个评估**。把责任推回去，正是这条过滤存在的反面。同一件事换个问法含义完全不同：**问「要不要看这类内容」是偏好，问「你承受得住吗」是让他担保自己。** 前者用户答得出来，后者只有状态好的人才答得出来——而状态好的人本来也不需要这道过滤。

字段侧：这个选择存 `include_heavy`（内容偏好，默认 `false`），**不是**存「心理状态声明」；不预选、不记忆、**每次诊断重新问**（见 SPEC §5.2.1）。「不记忆」是这句问题的一部分：上次选过「一起看」就直接带过来，等于**用户上一次的答案替这一次做了决定**，而这句问题的整个前提恰恰是他这次的状态可能已经不一样了——**对这道问题来说，记住它反而更不坦诚。**

**这条问题只承诺了「临终或丧亲」，所以它只放行「临终或丧亲」**：`include_heavy` **只豁免 `EX-terminal`，不豁免 `EX-trauma`**（规则落在 SPEC §6.3①）。

**为什么不对称**：要让它对称，就得把「自伤、性暴力」写进同一句问题里——**那等于在一个低心力用户面前摆一排最重的词**，而这道问题存在的全部理由就是「不要让他先评估自己」。两个代价都不接受，所以这一半干脆不做成选项：**想看那类书，他去书库或直接搜索，那些书在那儿，只是不被推荐。** 用户失去的是一个开关，不是一批书。

**这条不对称必须在实现里被保住，理由不是「更安全」，是「它会被人补上」**：半年后会有人看到「两条规则长得一样、只有一条有开关」，判定为漏了一个，然后把它补齐——**补上的那一刻，这句只承诺了临终与丧亲的问题，开始替用户同意他没读到的东西。** 而它不报错、不会有 issue、不会在埋点里留下任何痕迹：**「只豁免一条的 `include_heavy = true`」和「两条都豁免的 `include_heavy = true`」，在数据里是同一个值、同一条曲线、同一个转化率**，差别只在于屏幕上那句话有没有提过「自伤」。**一个「看起来对不齐」的地方，比一个「看起来对得齐」的地方更安全。**

**为什么不为「危机条 + 临终题材卡」同屏改渲染（裁定，不许再加机制）**

用户选了「一起看」之后，结果页底部有危机资源条、列表里有讲临终或丧亲的书，两者同屏。**不改渲染条件**，三条理由：

1. **同屏是他自己要的，不是系统塞的。** 危机条说「你现在可以放下读书这件事」，那张卡说「这里有一本关于失去的书」——他刚亲手回答了那个问题，第二句是他要的，**不是系统在自我辩护**。真正让危机条看起来像免责声明的情形，是**他没选却照样看到临终卡**；那一种已被 `EX-terminal` 挡住。
2. **「把临终卡下沉到『也可以看看』」这个方案不接**：那一组不是安全分组，是 `explore` **档位**分组（「有启发价值，但不是对症的」）。因为题材把一张算出来是 `strong` 的卡下沉，等于让档位标签对一个刚主动要看它的用户撒谎。**分组的依据只能是分，不能是题材。**
3. **代价与收益不对等**：域内主诉池只有 3 本，域外 30–50 本几乎全不命中主诉——**为 5 本里的 3 本、给 80–90% 的用户多一屏改动，是负收益。**（这条数字理由必须留在文档里，否则半年后会有人用「为了安全」再提一次，而它听上去永远是对的。）

**若 M1 真收到「求助号码和一本讲临终的书放在一起，看着难受」这类反馈，按三步查，顺序不能换**：

1. 查 `include_heavy` 的**三态**：`未渲染` / `渲染但未答` / `已答`。**三者必须分开计数。**
2. 若「**渲染但从未进入视口**」占多数 → **既不是文案问题，也不是规则问题，是准入条件没满足**：这个控件第一次上线时，**顶边必须在折叠线以上**，否则不许上线（折叠线的像素口径归 UIUX / SPEC，本文不写数值）。
3. **只有确认「已答，且选了先不用」之后**，才轮到讨论措辞与位置——那时改的是危机条，不是卡片。

**这条准入什么时候才需要处理**：把它拉回折叠线以上只有两条路，其中**「把问句上移」已被关闭**——上移会与 3-b「能接受多难」连成一组，被读成难度开关（**位置即语义**）。所以实际只剩「压缩第 3 屏」一条，而它动的是 3-a / 3-b 的行数。**M0 不做**：该控件在 M1 根本不渲染（唯一那一格没书），现在压缩等于为一个用不上的场景改问卷节奏。**触发条件写死：当某次书目扩充使 `emotion × easy` 这一格首次满足渲染条件时，才启动压缩；在那之前，这条准入只是一笔账，不是待办。**

**为什么第一步不能是「查落库值是不是 `false`」**：`false` 至少有三个来源，其中两个**不是**缺陷——① **没滚动到**（控件从未进入视口，多数用户会是这样）② 看到了，保持默认「先不用」③ 规则真的没生效（这才是缺陷）。**按旧流程，用户一投诉就会被判成 ③，而实际是 ①——排查方向错一整天，而且错得很有说服力。**

**「他没选」和「我们没问」在数据里长得一模一样，而默认值让它们连行为都一样——所以只能靠事件把它们分开，不能靠字段。** 字段维持 `boolean`、不改类型：三态不改变任何推荐结果，不值得为可观测性去动已冻结的 SPEC。

**这个控件不是无条件渲染的，而「渲不渲染」用的是结构条件，不是行为判据。** 如果翻动它前后推荐结果的 `book_id` 集合一样，它就是**数据层的假开关**——文案对、规则对、什么都没变，而它看起来完全正常（因为结果本来就该是那些书）。但第 3 屏渲染时用户还没答完、也还没跑过推荐，**行为判据在这里算不出来**（循环依赖）。所以运行时用一条**可预计算**的结构条件：**该用户域内存在一本难度 ≤ 本档 cap、且带 `grief` / `terminal_illness` 的书**；构建期算成布尔表（6 域 × 2 档 = 12 行，**其中只有 `emotion × easy` 由数据决定，其余 11 行结构恒 `false`**；`hard` 档不入表，查询时显式返回 `false`），运行时查表。行为判据退回它该在的位置——**验收**（见 §10.8 预检第 4 条）。

**某一格结构条件不成立时，这一格就不问这句话，也不留空位**（留白会被读成「这里本该有内容、没加载出来」，同 §8.1）。代价不对称，所以偏向「不问」：**少问一句的代价是可见的**（用户没被问、功能少了、会有人提），**问一句没用的代价是不可见的**（用户以为自己在做选择，而选择没有效果）——**后者不会有人来报告**。宁可少问一句，不要问一句什么都不变的。

**为什么这两条规则改用名字引用（旧编号 `R3` 已作废，见下）**：`R` 前缀在这个项目里被四套东西占用过——过滤记录码、availability 规则、风险表行号、本文的硬约束编号。`R3` 一度同时指「创伤题材过滤」「出处不可核验」「foliate-js 破坏性变更」「内容安全底线」。**一个前缀指四件事，等于没有前缀。** 规则名现在只用于「被别的文档引用」，其余地方写文字（「难度上限」「内容安全两条」）。**上面这张表里编号断了一格就是这件事，不是漏写。**

**⑤ relax 的文案基调（产品所有，SPEC 只定义阶梯，文案在此定稿）**

| 级 | 场景 | 用户看到的话（逐字） |
|---|---|---|
| L0 | 正常 | 不额外解释 |
| L1 | 标签升族 | 不额外解释（用户不应感知这一层） |
| L2 | 降低主题权重 | 「没有完全对口的书，这几本在难度和篇幅上最贴合你」 |
| L3 | 主题权重归零 | 「暂时没找到直接相关的，这几本也许能帮你换个角度」 |
| L4 | 返回空 | 「试试换个说法」+ 两个入口：重填问卷 / 按品类浏览 |

**放宽必须配一个可动手的出口**：出现 L2/L3 时，结果页顶部提示后必须跟一个提问入口（「是不是这几个条件太严了？改一下」→ 回到对应那一屏）。只给一句解释不够——用户要能动手，否则他只能接受一个他不满意的结果。

**因子与权重的产品约束**（数值以 SPEC §6.2 为唯一事实源，本文不复制）

| 约束 | 内容 |
|---|---|
| 每个因子必须有信号来源 | 一个因子若在问卷里没有对应题目、在数据里没有对应标注，它的权重就会变成常数项——那不是「可解释」，是**假装可解释**。这类因子必须删除，或补上输入信号 |
| 无信号时不得当中性常数 | 用户跳过某道可选题时，该因子**从本次计算中剔除，权重按比例重分配并归一化**，而不是代入中性值继续算。代入中性值会让「跳过的用户」拿到系统性偏低的 `score_bp`，进而永远进不了 `strong`。实现见 SPEC §6.1 |
| 可获得性不得做主排序力 | 它的权重上限由 SPEC §6.2 锁定，只够扳动「半档难度差」这类近似同分，扳不动主题差异。**任何把它改成前置分组或大幅提权的提案，必须先回答「为什么《论语》应该压在高度契合的书上面」** |
| 因子必须可单测 | 每个因子要有独立单测：给定输入必得固定输出。任何一个因子依赖外部状态（时间、随机数、网络），都视为缺陷 |
| 运行时权重不进任何用户可见界面 | `weights_used` / `tie_break_trace` 只用于**单测断言 + 开发期调试**（断言跳答后权重和仍为满分、被移除的因子不在 key 里），**生产构建不渲染调试面板**。用户一旦看到那套权重数字，注意力就从「这本书适不适合我」转移到「这个比例合不合理」，而他要的只是一本今晚能读的书。**明确不做面向用户的「复制诊断快照」**——那会让产品看起来像在请用户帮我们查 bug，而我们卖的是「我们懂你」，不是「我们还在调试」。写在文档里但走不通的用途，删掉比留着诚实 |
| 选项取值必须让 target 落在书的整数刻度上 | **任何让目标值落在非整数上的选项取值，都会让选了那个选项的用户拿不到满分**——书的难度、体例、深浅都是有限档位，目标值落在两档之间时，最接近的书也永远差半格，那一项因子到不了上限。**这不是偏好差异，是系统性歧视某一类答题者**：它不报错、不告警，只表现为「有些人怎么答都推荐不出高度契合」。判据一句可复用：**所有 target 取值必须能让目标落在书的整数刻度上**（各选项的具体取值见 SPEC §6.1，本文不复述）。这类缺陷只在跑算例时才看得见，所以每次新增或改写问卷选项，都要重跑一遍七项 `fit` 是否都可达满分 |
| 边界声明不许用通用文案填空 | `boundary_hints` 由标注人**按这本书最容易让人失望的那个维度**预写，运行时只取当前结果里 `fit_bp` 最低的那个因子去查；查不到就整行不出现。**禁止降级成「这本书可能比你想的难/长」这类对任何书都成立的句子**——B1 的全部价值在于它是这本书特有的，通用句等于没说，不如不给 |

**不做的排序花招**（明确列出，防镀金）：不做「随机探索位」（破坏可复现）、不做「编辑推荐位强行插队」（破坏可解释）、不做基于点击的在线学习重排（第一版无后端，且会让结果不可复现）。

**为什么 R4 不能做成前置分组（v1.4 修正，由架构师实现反馈触发）**

PRD v1.3 把「可获得性」列在「匹配分降序」之前，严格按优先级执行会产生一个荒谬结果：**所有 `inline` 书整体排在所有 `bring_your_own` 书之前**——用户会看到一本跟他毫无关系的公版古籍，压在一本高度对症的书上面。这有两个后果，都是致命的：

1. 它把「符合度排序」这个核心承诺变成了「格式排序」。用户第一次看到的错位就会得出结论：这个推荐器不懂我。
2. 它与「不是歧视版权书」自相矛盾。写在理由里的原则和实际排序不一致，是最难被发现、也最难被原谅的一类错误。

正确做法是**低权重因子 + tie-break 键 + 破冰位（R1）** 三者配合：
- 破冰位保证**第 1 位**一定「能当场开始读」——这才是「今晚就能开始」的真实机制，而不是把整个列表按格式分组；
- 可获得性作为低权重因子，可以翻转近似同分，但翻不了主题差异；
- tie-break 第 4 级只在真同分时生效。

**一个必须承认的代价**：在结构性无 inline 的域（习惯与行动 / 工作与意义 / 认知与思考），5 张卡会全是「需自备」。这个体验问题**不靠排序解决**，靠 10.3 产品结论第 2 条的顶部说明条一次性解释清楚（P0-17）。用排序去掩盖它，只会把「书不对症」换成「书对症但排在后面」，更糟。

### 7.5 「库外书」的真实定义（v1.4 修正：不存在系统自动发现的外部书库）

**先纠正一个上一版的技术性错误**：PRD v1.3 及以前把「库外兜底」写成「允许展示库外书籍（仅元数据：书名/作者/简介/ISBN/来源链接）」。这个写法预设了一个**不存在的在线书目源**。现实是：

| 数据源 | 能否用 | 原因 |
|---|---|---|
| 豆瓣 | 不能 | 无公开 API（2017 年关停开放接口，2023 年 7 月开发者平台下线） |
| Google Books / OpenLibrary | 不能 | 国内网络不可达；且 local-first 无后端 |
| 离线的全量中文书目 | 不能 | 没有合法可分发、体积可接受的来源 |

所以正确表述是：**推荐结果里的每一本书，要么来自核心库（首发 300 本，人工策展），要么来自用户自己的书架（导入或手动录入）。不存在「系统自动发现并推荐一本我们没见过的书」这条路径。**

**「库外书」实际落地为三条入库路径（以 SPEC §7.3 为准）**

| 路径 | 入口 | 用户付出 | 进推荐池？ |
|---|---|---|---|
| A 用户自带文件 | 详情页「导入后阅读」或书架页导入 | 准备好 EPUB / TXT | **否**。能读，但缺打分字段，`content_ready` 为「可读」态，**不入个性化池**（见 SPEC §7.3） |
| B 30 秒手动录入 | 「我读的书不在这里」→ 只填书名 / 作者 / 一句话为什么想读 | 约 30 秒 | **是，但有三条硬上限**（见下） |
| C 外链检索 | 搜不到 → 给外部链接，新窗口打开 | 0 | **否**。四个「不」：不落库、不入候选池、不参与打分、不生成理由 |

**路径 B 的三条硬上限（同时生效）**
1. **绝不进前 3 位。** 用户自己录的书若排到第 1，整个结果的「诊断」属性就废了——他看到的只是自己刚写下的想法。
2. **档位上限 `worth`，永不出 `strong`。** 缺失打分字段的书没有资格宣称「高度契合」。
3. **不参与多样性配额计数。** 它的标签不可信；否则用户录一本《被讨厌的勇气》，就会把同品类的真书挤出前 5，配额反而变成自建书的放大器。

**呈现硬规则（针对路径 B）**
- 必须带文字标签「你录入的书」+「暂无深度推荐」，且**不显示 S1 与 S3**（没有 `problem_tags` 与 `one_line_gain`，编造就是欺骗）。
- 位置：只能出现在列表末尾的独立分组；永不进入前 3 位。
- 文案不能只写「暂无深度推荐」六个字，必须补一句人话：「这本书是你自己加的，我们还没人工读过，没法告诉你读完能得到什么。但你可以照常读、照常划线。」

**为什么保留这个「半残」的兜底**：用户搜不到想读的书是真的会流失。给他一个 30 秒能自己加进来的入口，比让他对着空结果关掉页面好——但**不许假装我们知道这本书**，这正是本产品与「看起来很全」的书单产品的分野。

**注意路径 A 与 B 的区别（容易被混为一谈）**：导入的书「能读」但「不进推荐池」，手动录入的书「进推荐池」但「永不前 3、永不 strong」。前者是阅读能力，后者是推荐资格，两者互不替代。

## 8. 推荐理由：三段式槽位定义、示例与降级

这是本 PRD 最需要打磨的部分。用户明确要求「**逐本说明推荐理由**」，所以理由的质量等于产品的质量。

### 8.1 三段式槽位定义

固定三段，固定顺序，**用第二人称「你」，不用「读者」**。不使用任何空话（「这本书非常经典」「值得一读」为禁用短语，见 8.4）。

**长度口径（v1.5 定稿，不再设「全文总字数」）**：S1 40–70 字 · S2 60–90 字 · S3 40–70 字，**合计 140–230 字**；B1 另计，≤30 字。

> **为什么不给总区间**：总数是分段的函数，同时写两个约束，等于给未来的自己埋一次「到底以哪个为准」。旧稿在同一节里既给了分段区间、又给了一个全文总区间，两者乘起来对不上，上限那几十个字没人认领——这种数字在评审里永远吵不出结论，因为它本来就不是一个约束，是两个。
>
> **S2 比另外两段宽，是有原因的**：S2 的模板要装 `one_line_what`（本身就是 60–90 字的字段）。如果 S2 只给 40–70，模板就必须压缩素材，压掉的恰恰是「这本书区别于同题」的那部分结构信息——那正是 S2 存在的理由。

| 槽位 | 名称（对应 SPEC §5.3 `reason` 键） | 槽位目标 | 数据来源字段（见 SPEC §5.2） | 句式模板 | 长度 |
|---|---|---|---|---|---|
| — | **（卡片级）对症点** | 不进理由段，单独作为卡片第二行，是用户扫视时的第一句「它在说我」 | `match_brief` | 一句话对症点，例：「不是没毅力，是启动门槛比心力高」 | ≤28 汉字 |
| S1 | **回引你的处境**（`situation`） | 让用户确认「它在说我」。必须**回引用户自己的原词或所选选项的文字**，不能 paraphrase 成通用描述 | 用户输入（选项文本 + 自由文本命中词） | 「你提到｛用户原词 1｝和｛用户原词 2｝——这不是｛常见误判｝，而是｛我们对该处境的判断｝。」 | 40–70 字 |
| S2 | **这本书讲什么**（`promise`） | 用一句话说清书的**方法/结构**，不是内容简介。禁用「本书讲述了……」的开头 | `one_line_what` + `structure_note`（这本书区别于同题的切入） | 「这本书｛体裁/结构｝，用｛核心概念 1–2 个｝解释｛核心问题｝。」 | 全文 60–90 字；**卡面取首句 ≤2 行、≤38 字，且必须是完整句子** |
| S3 | **你读完能得到什么**（`payoff`） | 必须可操作、可当天验证。禁用「受益匪浅」「提升认知」 | `one_line_gain` + `first_action`（**必填且必须含动词短语**） | 「读完你至少能拿到｛具体工具/视角｝：｛一句可执行的动作｝。」 | 40–70 字 |
| B1 | **边界声明**（`mismatch`，可选） | 回答用户看到「高度契合」时的第一反应「凭什么不是 100%」 | `boundary_hints`（某因子低分时的诚实提示） | 「不过：｛这本书在哪个维度上不如上一本 / 弱在哪｝」 | ≤30 字 |

**卡片与展开区的分工（SPEC §7.1 已锁定，v1.5 修正）**

| 位置 | 内容 |
|---|---|
| 卡片（默认可见） | 书名（+ 书脊卡，≥768px）· `match_brief` 左 + 档位块右 · **S2 首句（≤2 行、≤38 字，完整句子）** · 可用性徽标 · `mismatch`（B1）· 难度 / 篇幅 / 预计时长 · 主按钮 |
| 展开区（点击后） | S1 / **S2 全文** / S3 · 完整命中依据 · 作者与译者（**B1 不在这里**——它已在卡面第 5 行原位展示，另起一段就是同一句出现两次） |

**一条可复用的判据（四个位置一次判完，以后加字段也能自己判）**

> **判断一句话能不能上卡面，判据不是「它重不重要」，而是「五张卡并排时它会不会重复」。会重复的下沉，不会重复的上留。**

按这条判：`match_brief` 上留（书级独有）、**S2 上留**（书级独有，但只留首句、且必须是完整句子）、S1 下沉（标签级共享）、命中依据下沉（tag 级共享）。

**S2 只留首句的理由**：完整 S2 是 60–90 字，两张卡就是四行散文，一屏只剩两张卡——而这一页的任务是「选一本开始」，不是「读完五段介绍」。所以卡面留「这本书｛体裁/结构｝，用｛核心概念｝解释｛核心问题｝」的第一句，完整 S2 进展开区。

**但首句必须允许 2 行（≤38 字），不能压成 1 行**：13px 中文在 343px 卡宽下每行约 19 字，1 行只有 19 字——把一句 30 字的话塞进 1 行，截断会发生在第 19 个字，用户读到「这本书用认知行为疗法解释……」然后没了。**那比不放这句话更糟**：半句话既不能让人判断，又占了一行版面。2 行 = 38 字，正好装下一句完整的话，不需要省略号。

**验收判据用「完整」而不是「字数」**：**卡面上的 S2 首句必须以句号结尾（未被硬截）**。字数检查挡不住这个错——38 字也可能断在半句中间，而「以句号结尾」一次就能抓出所有被硬截的情况。

`match_brief` 是**书级独有**字段，S1 是**按标签共享**的句子——同一主标签下的两本书，S1 会渲染出几乎一样的开头。五张卡都摊开 S1，页面上会出现三句重复的开场，正好毁掉「逐本说明理由」这个卖点。所以**卡面只留 `match_brief`，S1 进展开区**。

**这个取舍有一个必须当场付掉的代价**：页顶的**诊断摘要条必须逐字回引用户原词**（`user_phrase`，不许改写、不许概括成「你的情况」），且**全页只出现一次**。它承担的是 S1 原本在卡面上干的活——让用户确认「它在说我」。**这条做不到，S1 就不许离开卡面。** 验收时检索两件事：结果页存在且只存在一处逐字回引；摘要条未被改写成通用句。任一不满足视为缺陷，不是「优化空间」。

**B1（`mismatch`）必须出现在卡片首屏可见范围**，不能只放详情页：那个「凭什么不是 100%」的念头发生在看卡片的那一秒，不会等到点开详情。卡面上 1 行截断、`title` 给全文；**展开区不重复它**（重复会让「展开」看起来没带来新信息），B1 全文只在详情页。

**B1 的密度问题（v1.7 补，之前是已知缺口：卡面上同时出现几个 `mismatch` 没有上限规则。规则本体与实现判据在 SPEC §7.1，本节只给产品语义）**

五张卡里三四张都挂「不过：…」时，用户会习惯化到看不见——那时它既没帮上判断，又白占一行。**解决方式不是「限制条数」**：

**这不是一条新规则，是「卡面准入判据」的第二次应用。** 判断一句能不能上卡面，判据不是「它重不重要」，而是「**几张卡并排时它会不会重复**」——第一次应用是 S2：S1 按标签共享、五张卡会渲染出三句一样的开场，所以 S1 离开卡面（见上文）；这里是第二次，`mismatch` 按因子预写，同组几本很容易取到同一条。

| 情形 | 性质 | 处理 |
|---|---|---|
| 同组 3 张卡各有一条**不同**的缺口（这本贵、那本难） | **3 条信息** | **逐卡陈述**，组头不碰 |
| 同组 ≥2 张卡取到**同一条** hint | **1 条信息印了 N 遍** | 它是这一组的**共性**，不是这本书的**个性** → 提到组头一次，卡上不渲染 |

**判据落在「同一条提示在同组内的出现次数」，不落在「条数」，也不落在档位 / 符号这类枚举分支。** 前一句的理由：`mismatch` 唯一的价值是「这本书**独有**的那个失望点」，同组里每本都成立的那句解释不了「为什么读这本而不是那本」——它不再是这本书的理由，只是这一组的处境。后一句的理由更实操：按 `tier` 或图标分支会漏掉「两本都是 inline、但都缺同一章」这种**同形不同因**的情况——它们看起来属于不同类别，重复却是真的。

**上提之后卡上不预留空位。** B1 行消失、卡变矮，这是正常的：结果页是**单列竖排**，卡高不一致不影响阅读；反过来为对齐留一个空行，用户会把它读成「这里本该有内容，没加载出来」。**骨架卡的对齐基准也随之改为「无 B1 的真卡」**，带 B1 的卡与骨架的差值记为已知代价——具体 px 与 CLS 门槛归 UIUX / SPEC，本文不写数值。

**组头那一行的来源**：`phrases.json` 的**因子级句式**（7 个 `FactorId` 各一句，人工预写），不在运行时拼自然语言——口径与理由文本一致：模板可控、可审、可 diff。**它是 7 句一次性资产，不随书增加，因此不计入 60 本的标注工时**——摊进去会让 36–56.5 小时那个口径失去可复现性，多出一笔说不清归属的小数。它**只覆盖 7 个因子**；「因子之外」的组头说明（例如「本组没有能直接读的」）属于另一套机制（现有 P0-17 说明条那一类），**不得塞进因子表**。

**内容侧：禁止重复事实，允许写后果。** 可获得性有徽标、难度 / 篇幅 / 预计时长有元数据行，**B1 不得只把这些事实再说一遍**——徽标已经说清了，重复是纯冗余（实测里最可能撞车的就是可获得性，第 2 组几本都「需自备」）。**但它可以说那个事实对此刻的后果**：徽标说「需自备」，B1 说「所以今晚开不了，先读第 1 本」——**后果是徽标表达不了的那半句，也正是 B1 该承担的东西**。这条界线的判据只有一句：**把它删掉，用户会不会少知道一件事？** 不会 = 重复事实；会 = 后果，留着。**为什么后果值钱、事实不值钱**：用户看卡片的那个瞬间想知道的是「**我今晚能不能开始**」，不是「这本书有什么属性」——属性回答了后者，后果才回答前者。

**作用域**：第 1 组只有 1 张卡、第 3 组 0–1 张，组内不存在重复，所以这条规则**实际只会在第 2 组触发**（1–3 张）。它不是一套新系统，是第 2 组的一条特例。

**关于「按 tag 分别写 payoff」的说明**：v1.2–v1.4 曾设计 `payoff_by_tag`（同一本书对不同困境给不同 payoff）。SPEC §5.2 为 `one_line_gain` 单字段，因此该机制**不落地**，已降为 Backlog（等真有人愿意按 tag 写 300 本书的多份 payoff 再说）。当前 S3 用单条 `one_line_gain` + `first_action` 组合，靠 S1 承接个性化、S3 承接行动。

附加约束（写进文案生成规则，由架构师在渲染层实现）：

- S1 **必须**包含至少一个来自用户输入的词（选项文本或自由文本命中词）。取不到时走 8.3 降级，不允许静默生成通用 S1。
- S3 **必须**包含一个动词短语（「你会分清…」「你能判断…」「你可以用…」），不允许只有名词。
- 三段之间**不许出现总分总式套话**，不许出现「总之」「综上所述」。
- **`match_brief` 不得整句复述 `user_phrase`**。原因是硬性的：`user_phrase` 在结果页只能出现一次（由页首摘要条承担），而 `match_brief` 在五张卡上各出现一次——一旦它整句复述用户原话，那句原话就变成五次，摘要条的「一次说透」当场破功。允许引用**不同的短引**（如原话是「明明没做错什么，就是会怕」，`match_brief` 可写「不是胆子小，是怕被否定这件事太贵」），不允许复制。

### 8.2 三个完整示例（真实存在的书 + 真实困境输入）

#### 示例 1（版权书，`bring_your_own`）

**用户输入**：域=工作与意义；具体=「开会不敢发言，总怕被否定，反复想别人怎么看我」；条件=每天 30 分钟 / 有点挑战；自由文本=「明明没做错什么，就是会怕」。

**推荐第 1 位**
- 书名：《被讨厌的勇气》｜作者：岸见一郎、古贺史健｜译者：渠海霞｜篇幅：约 12 万字，预计 4 小时｜难度：中等｜可获得性：**需自备**
- 档位：**高度契合**
- 对症点（`match_brief`）：**不是你不会说话，是你在等一个不被否定的许可**
- 命中依据：命中了 — 开会不敢发言 · 怕被否定 · 反复想别人怎么看

> **S1**　你提到「开会不敢发言」和「反复想别人怎么看我」——这不叫性格内向，也不是能力不够，这是把自己的价值判断权交到了别人手里。
> **S2**　这本书是哲人与青年五个晚上的对话，用阿德勒心理学的「课题分离」和「目的论」，拆解「一切烦恼都来自人际关系」这句话到底成立在哪。
> **S3**　读完你至少能拿到一件工具：分清「别人怎么评价我」是别人的课题、「我要不要开口」是你的课题。下次会前你可以拿这句话先把自己从审判席上放下来。

*（注：这是全列表唯一一本「怕被否定」直接被书名回应的书，所以放第 1 位；但它需要自备、约 4 小时，不满足 R1 的「3 小时内可完成」，实际排序时由 R1 让位给下面的公版书——见 7.4 的取舍说明。本示例用于展示理由写法，排序结果以第 1 位实际引擎输出为准。）*

#### 示例 2（版权书，`bring_your_own`，聚焦「读不下去」）

**用户输入**：域=习惯与行动；具体=「买了很多书一本没读完，每次读几页就困」；条件=每天 10 分钟 / 越轻松越好；自由文本=「我觉得我就是没毅力」。

**推荐第 1 位**
- 书名：《微习惯》｜作者：斯蒂芬·盖斯｜译者：桂君｜篇幅：约 9 万字，预计 2.5 小时｜难度：入门｜可获得性：需自备
- 档位：**高度契合**
- 对症点（`match_brief`）：**不是你没毅力，是启动门槛比当天心力高**
- 命中依据：命中了 — 读几页就困 · 一本没读完 · 每天能读 10 分钟 · 「没毅力」

> **S1**　你说「我觉得我就是没毅力」——先把这个判断放下。每次读几页就困，通常不是毅力问题，是你给自己定的启动门槛比当天的心力高。
> **S2**　这本书从一个俯卧撑开始讲：作者把目标缩小到「小到不可能失败」，用超额完成带来的成就感替掉意志力的消耗，全书就是这套方法的完整操作步骤。
> **S3**　读完你能拿到一条今天就能用的规则：把「每天读 30 分钟」改成「每天翻开书读 2 页」。2 页这个量小到没法拒绝，而绝大多数时候你会多读几页。

#### 示例 3（公版书，`inline`，可直接读）

**用户输入**：域=人生转折 / 情绪与自我；具体=「工作三年越来越觉得没意义，不知道自己要什么」；条件=每天 30 分钟 / 有点挑战；自由文本=「好像做什么都在为别人交代」。

**推荐第 1 位**
- 书名：《庄子》（内篇）｜作者：庄周｜版本：公版原文，附白话注释｜篇幅：内七篇约 3.2 万字，预计 3 小时｜难度：中等偏难（文言）｜可获得性：**可直接读**
- 档位：**高度契合**
- 对症点（`match_brief`）：**你的价值感只剩「工作绩效」这一把尺子**
- 命中依据：命中了 — 觉得没意义 · 不知道自己要什么 · 都在为别人交代

> **S1**　你说「好像做什么都在为别人交代」——这不是矫情，是你的价值感只剩一把尺子：工作绩效。一把尺子量不完一个人，所以你才会觉得空。
> **S2**　《庄子》内七篇用寓言讲一件反直觉的事：一棵因为「不成材」而没被砍走的树，恰恰因为「没用」活了下来。它不给你答案，它拆掉你量自己的那把尺子。
> **S3**　读完《逍遥游》和《人间世》两篇，你能拿到一个备用视角：这世上有一部分事，不必换算成「有没有用」。这本书是公版原文，可以直接在这里读，每段下面有白话注释。

**三个示例共同遵守的**：S1 全部回引了用户原词（「没毅力」「为别人交代」「开会不敢发言」）；S3 全部给了当天可执行的动作；没有一句「这本书非常经典」。

### 8.3 字段缺失时的降级规则

| 缺失情况 | 降级行为 | 用户看到的 |
|---|---|---|
| 缺 `one_line_gain`（S3 无素材） | **不生成 S3**，只出 S1 + S2，并在理由区末尾加一行「这本书我们还没整理出『读完能得到什么』」 | 两段理由 + 一行说明。绝不编造 |
| 缺 `first_action` | S3 仍生成但**不写动作**，只写「拿到什么」，并在详情页标注「具体的第一步待补充」 | 三段完整，但少最后那句可执行动作。`first_action` 在 SPEC §5.2 是**必填**，此分支只应出现在用户导入的书或外部 PR 未填的场景 |
| 缺 `problem_tags` | 该书不进入个性化推荐池（`content_ready` 为「可读」态），只在书架与「按品类浏览」出现 | 不出现在诊断结果里 |
| 缺 `one_line_what`（S2 无素材） | 用 `publisher_summary` 截取 60 字代替，并标注「简介来自出版方」 | S2 带来源标注，降低可信度但不伪装 |
| 缺 `structure_note` | S2 只用 `one_line_what`，不强行补「这本书的独特切入」 | S2 变短，但不说假话 |
| 缺 `match_brief`（卡片级） | 卡片第 2 行**原位降级**为 7.3 ② 的命中依据短语（2–4 个用户原词），不放空位、不留占位符。这是**替补**而非第二块内容，与展开区/详情页里的完整命中依据**不得同屏重复** | 卡片第二行显示「命中了：怕被否定 · 开会不敢发言」，12px 灰、1 行截断 |
| 缺 `boundary_hints`（B1 无素材） | **不生成 B1**，不写「没有任何缺点」这类假话，也**不许填通用文案**（「这本书可能比你想的难/长」对任何书都成立，等于没说）。正确逻辑：取当前结果里 `fit_bp` 最低的因子 → 查这本书有没有该因子的 hint → 有就渲染，没有就整行不出现。构建期只**报告**覆盖率、不阻断（确实存在「各项都不差」的书） | 只有三段，无边界声明 |
| 用户自由文本未命中任何标签 | S1 只用选项文本回引（选项文字本身是用户的选择，可回引） | 正常三段，S1 回引选项 |
| 用户全程选「说不上来」 | S1 改为回引他选的场景词（「你说最近睡不好」） | 正常三段 |
| 译本信息缺失 | 卡片上显示「译本信息待补充」，详情页提示「不同译本差异较大，建议自行核对译者」 | 显式缺口 |

**总原则**：**宁可少一段，不可编一段**。这是产品可信度的底线，也是这个产品与 LLM 生成书单的根本分野。

### 8.4 禁用文案清单（验收时逐条检索，出现即打回）

| 禁用类型 | 具体禁用示例 | 原因 |
|---|---|---|
| 空话形容词 | 「经典」「必读」「神作」「受益匪浅」「提升认知」「干货满满」 | 零信息量，可替换到任何书上 |
| AI 模板开场 | 「本书讲述了」「在这个快节奏的时代」「让我们一起」 | 模板味 = 机器写的 = 不可信 |
| 伪精确数字 | 「92% 匹配」「匹配度 4.7 星」 | 见 7.3 |
| 说教口吻 | 「你应该」「你必须」「你需要认识到」 | 用户已经在自我否定，不需要第二个评判者 |
| 空洞承诺 | 「读完你的人生会改变」 | 无法验证的承诺反噬信任 |

**「检索命中 0」不等于「通过」。** 扫描对象为空（0 个文件、0 条记录、chunk 不在）时只能报「**未验证**」，不得报「通过」。三种结果（通过 / 失败 / 未验证）的语义与强制实现见 **SPEC §12**；「检索范围必须显式声明、范围为空视为未验证」的总则见 **UIUX 附录 A**。本文不复述，只留一句理由：**失败会有人去修，被显示成绿色的「未验证」永远不会有人发现。**

## 9. 版权书籍的处理方式

这是法律与信任的双重红线。核心原则：**推荐不含糊、正文不越界、路径给到位**。

### 9.1 用户在三个位置分别看到什么

| 位置 | `inline`（公版内置） | `bring_your_own`（版权 / 需自备） | `external`（仅书目） |
|---|---|---|---|
| **① 推荐列表卡片** | 绿色文字标签区（文字，非图标）：「可直接阅读」+ 版本说明「公版原文 · 附白话注释」 | 中性文字标签：「需自备电子书」 | 灰色文字标签：「仅书目信息」 |
| **② 详情页** | 一段说明：「本文本为公版作品（作者逝世已满 50 年）。所用版本：｛原文 / 民国旧译 / 校注本｝，来源：｛中文维基文库 / Project Gutenberg / 项目自校｝。」+ 版权声明行 | 一段明确说明：「《ｘｘｘ》为在售版权作品，本站**不提供全文**。你需要在别处准备好 EPUB 或 TXT 文件，再导入这里阅读。」+ 合法获取途径（公共图书馆 / 购买渠道 / 出版社官网）+ ISBN（便于搜索）+ 译本建议 | 「本站只有这本书的基本信息，不提供正文，也没有深入推荐。」+ 外链（标注「将离开本站」） |
| **③ 点击「开始阅读」** | 直接进入阅读器，无中间页 | 弹出导入引导面板（见 9.2），面板标题就是「导入你的《ｘｘｘ》」 | 新窗口打开外链，并提示「已离开本站」 |

**关键设计约束**：`bring_your_own` 的按钮文字**不能**是「开始阅读」，必须是「**导入后阅读**」或「**我已有文件**」。按钮文字是用户唯一必读的文案，措辞含糊等于欺骗。

### 9.2 导入引导的完整话术与失败态

**引导面板：用户感知到 3 步，校验不占步骤（一次只显示一步）**

| # | 用户感知的步骤 | 文案 |
|---|---|---|
| 1 | **说清规则** | 「这个文件不会上传到任何服务器，只存在你自己的浏览器里。关掉浏览器前请确认已保存。」 |
| 2 | **要文件** | 「选择或拖入 EPUB / TXT 文件。」+ 支持格式说明 + 「为什么暂时不支持 PDF」的一句话（PDF 是固定版式，无法重排与划线定位） |
| 3 | **对齐书目** | 「已识别为《ｘｘｘ》，与推荐的是同一本吗？」（允许手动改书名，因为文件名常常是乱码或 `book(1).epub`） |

**校验是静默的，但它不占步骤**：选完文件后立即在后台跑六项校验——格式 → 文件完整性 → DRM → 大小 → TXT 编码 → 章节结构。

> **校验静默 ≠ 校验可以失败得静默。**
>
> 「静默」的意思是：**成功时不占一步、不显示进度条、不弹「校验通过」**——通过是用户的预期结果，为预期结果加一个确认步骤，等于向用户收一次「你确定你选的是个好文件」的税。
>
> **失败时必须立刻占据整屏并给出具体原因**（下表 7 个失败态 + 1 个体积提醒 / SPEC 的 11 种失败态），不允许把用户留在「看起来在转圈」的中间态超过 3 秒而不说话。失败是用户的**意外**，意外必须被立刻、具体地解释，否则他会以为是产品坏了。任何「让失败看起来像成功、或让失败无声消失」的实现都视为缺陷，不是简化。

**失败态文案（下表是 PRD 侧定稿的 8 条文案 = 7 个失败态 + 1 个体积提醒；SPEC §2.1 P0-8 要求失败态按原因分为 11 种，其余 4 种由其细化，文案风格与本表一致。若两者冲突，以 SPEC 的**分类数**为准、以本表的**措辞**为准——分类是工程需要，措辞是产品资产）**

> **体积不设「≤50 MB 直通」这一行**，因为它不是失败态：≤50 MB 不做任何提示、不占一步，直接进入对齐书目。**提示只在需要用户做决策时出现**——提醒一个没有决策点的用户，只会让他犹豫。

| 失败类型 | 用户看到的话 | 附带动作 |
|---|---|---|
| 格式不支持 | 「这个文件是 ｛.pdf / .mobi / .azw3｝，暂时读不了。目前支持 EPUB 和 TXT。PDF 是固定版式、无法重排和划线，第一版不做。」 | 「了解」+ 「查看支持的格式」 |
| 文件损坏 / 解析失败 | 「文件打不开，可能下载不完整或不是标准 EPUB。建议重新下载一次。」 | 「查看技术详情」（折叠区，给错误码）+ 「换一个文件」 |
| 加密 / DRM | 「这本书带 DRM 加密，只有购买它的那个阅读软件能打开。我们不能也不应该绕过它。」 | 「了解」。**不提供任何破解指引、不外链解密工具** |
| 文件偏大（50–100 MB） | 「文件较大（｛x｝MB），导入后可能卡顿。」 | 「仍然导入」/「取消」。**这是提醒不是错误**（`warn` 色），用户自己决定 |
| 文件过大（>100 MB 或段落数异常） | 「超过 100 MB 的文件在浏览器里无法可靠解析。」 | 「了解」+ 「换一个文件」。**直接拒绝，不提供「仍然导入」**——50–100 的后果是卡（可恢复），>100 是解析中期内存崩（不可恢复），用同一句「可能卡顿」描述两者，等于赌一条已知会失败的路径 |
| TXT 编码识别失败 | 「这个 TXT 的编码认不出来，可能出现乱码。请选择：UTF-8 / GBK / 自动重试」 | 三选一，实时预览前 200 字 |
| TXT 无章节结构 | 「这个 TXT 没有章节标记。我们会按空行和字数自动分章，你也可以之后手动调整。」 | 「按默认分章」/「先不分章」 |
| 空间不足 | 「浏览器存储空间不够了。可以删除一些已下载的书再试。」 | 「管理已下载的书」 |

### 9.3 什么情况下**必须**明确说「需自行准备」

以下任一条件成立时，不得使用任何含糊措辞（如「暂不支持在线阅读」「获取本书」）：

1. 作品的**中文译本**仍在著作权保护期。原著公版 ≠ 中译本公版——这是最容易被开源项目踩的坑，也是本产品**唯一「错了会让整个仓库下架」**的错误类型。保护期的判定规则以 SPEC §10.1 为准，本文不复述年限。
2. 我们只有原著语言（如英文、日文）的公版原文，而目标用户是中文用户。
3. 我们只有「民国及以前旧译」，但其语言对现代用户不可读（此时标为 `external` 而不是 `inline`）。
4. 该书尚未人工核验版权状态（`translation_copyright = 'unknown'`）。**未知一律按版权书处理**，这是合规的默认方向。

**版权闸门：保持硬，不设人工豁免**

闸门的判定逻辑、六条审计规则与字段取值以 **SPEC §10.1 与 `npm run audit:copyright`** 为准，本文不复述。产品侧只锁一条语义：

> **证明不了就当作有版权。** 宁可少一本能直读的书，不可多一本要下架的书。

**唯一合法的通行方式是「改数据」，不是「关闸门」**：把 `translation_copyright` 改成 `public_domain`，`public_domain_reason` 填具体依据，并在 `docs/copyright/<book_id>.md` 里写清依据来源。写不出那份文件，就证明不了，就留在 `unknown`，就不上 inline。

> **豁免不是一次点击，是一次带证据的提交。** 这个区别决定了它会不会被滥用。

**为什么不能设豁免开关**：豁免在实践里必然退化成「谁着急谁豁免」，而这是唯一一类**代价不对称**的错误——**晚上一本书没人损失，错上一本书整个仓库下架**。所以本项目不提供任何运行时开关、环境变量或人工豁免（SPEC §10.1 已写成构建期 fail）。

**这个闸门会卡住我们自己，这是预期行为，不是故障。** 例：某家《说文解字》注本，注者卒年查不到可靠来源 → 正确的处理**不是**「拿不到证明所以豁免一次」，而是**这一版先不上 inline**，等能写出一页证据再加。贡献者的损失是多等一轮评审，项目的损失是零。

### 9.4 公版（inline）与版权（bring_your_own）的文案区分规则

避免用户误解的三条硬规则：

1. **不用同一个动词**。`inline` 用「阅读」，`bring_your_own` 用「导入」「自备」「获取」。用户扫一眼动词就知道要不要动手。
2. **不用同一个视觉层级**。`inline` 是主按钮（可直接点），`bring_your_own` 是次级按钮（点了会进导入流程，有一步额外操作）。让「多一步」这件事在视觉上就成立。
3. **`inline` 必须标注版本来源**，绝不写「全文」两个字了事。写法：`公版原文 · 附白话注释 · 来源：中文维基文库（2024-xx 校）`。因为同一个公版书的不同版本差异极大（有无注释、有无标点、底本不同），用户有权知道自己在读哪一个。

## 10. 核心库的构成建议（三层口径：首发 300 / v1.0 前 800 / 架构上限 3000）

> **全文口径统一**：本 PRD 涉及库规模一律用这三个数，不再单独出现「3000 本」作为首发或验收口径。
> 首发 **300 本**（6 个困境域 × 50 本，`content_ready = true`，字段完整、可算符合度、可生成理由）→ v1.0 前 **800 本**（靠外部 PR 摊薄）→ 架构上限 **3000 本**（12 个月目标，不承诺）。

### 10.1 品类配比

依据：GitHub 上唯一有规模的书单品类是计算机（`free-programming-books` 394k星 佐证），说明**「按品类整理的书单」需求真实存在，但计算机类的需求已经被彻底满足**。而「按困境找书」的需求集中在人的问题相关的品类。因此配比按「困境密度」而非「市场热度」分配。

| 品类 | 占比 | 首发 300 本 | v1.0 前 800 本 | 上限 3000 本 | 为什么是这个比例 | 典型困境域 |
|---|---|---|---|---|---|---|
| 文学（小说 / 散文 / 传记性写作） | 30% | **90** | 240 | 900 | 用户真正能读完的书大多是文学。纯说理的书完读率最低。这是「读得下去」的基础盘 | 情绪与自我、人生转折、关系 |
| 心理 | 20% | **60** | 160 | 600 | 「我怎么了」最直接的答案源，且中文引进量大、公版少（几乎全是版权书） | 情绪与自我、关系、习惯 |
| 思想 / 哲学 | 15% | **45** | 120 | 450 | 公版占比最高的品类（中西古典），是「可直读」的主要来源 | 认知与思考、人生转折 |
| 社科（社会 / 历史 / 经济 / 人类学） | 15% | **45** | 120 | 450 | 解释「我的处境不是我一个人的问题」，对「意义感缺失」「觉得落后了」特别有效 | 工作与意义、认知 |
| 传记 / 回忆录 | 10% | **30** | 80 | 300 | 「别人也这样过」的替代性经验，是低门槛高共鸣的品类 | 人生转折、工作与意义 |
| 其他（科普 / 方法 / 艺术 / 自然） | 10% | **30** | 80 | 300 | 兜底多样性，避免 5 本推荐全是同一个味道（配合 R6 多样性约束） | 认知、习惯 |
| 合计 | 100% | **300** | 800 | 3000 | — | — |

**「6 个问卷域 × 50 本」与「品类配比」是两套正交的切法**，执行时必须同时满足：先按品类配比备齐 300 本，再检查每个问卷域是否都有 ≥50 本 `problem_tags` 命中（不要求同域 50 本都在同一品类，跨品类分布是正常的；也不要求按族平均分布）。

**明确不收**：计算机 / 编程（已被 free-programming-books 彻底满足，且与困境推荐无关）、教辅 / 考试、成功学 / 鸡汤（与「不空洞承诺」原则冲突）、网络小说（体量巨大且版权复杂，会把库变成另一个产品）。

### 10.2 难度与篇幅分布

| 维度 | 分档 | 目标占比 | 理由 |
|---|---|---|---|
| 难度 | 入门（不需前置知识，白话） | 40% | 用户第一次来，多半处在低心力状态。入门书是「破冰位」的弹药，必须充足 |
| | 中等（需一点耐心，有结构） | 45% | 主力档 |
| | 进阶（需要背景知识 / 文言 / 学术） | 15% | 必须有，但不能多。太多了第 1 位永远选不出合适的书 |
| 预计阅读时长 | ≤2 小时 | 25% | 直接服务 R1 硬约束 |
| | 2–5 小时 | 45% | 主力 |
| | 5–10 小时 | 25% | 深化位 |
| | >10 小时 | 5% | 只给「不怕难 + 每天 1 小时以上」的用户 |

### 10.3 可直读（`inline`）的口径：首发 30–40 本，验收看「领域覆盖度」不看占比

> **本节为 v1.1 修订**：原稿曾把 inline 规模写成一个「占全库百分比」的指标，该口径已**整条删除**，本文不再出现任何占比阈值与由它反推的本数。删除理由见本节末「为什么不能按占比定指标」。

| 项 | 首发口径 | 说明 |
|---|---|---|
| `inline` 数量 | **30–40 本**（数值同 SPEC P0-13） | 数量不是按占比反推出来的。数量服从「覆盖度」，不服从百分比 |
| 覆盖度验收标准 | **意义感 / 人生选择 / 关系与孤独 / 修身与情绪 / 处世，每类至少 1 本能直读**（≥5 本硬底线）；其余 25–35 本在这 5 类内加深 | 用户点开第 1 本时，至少有一半的困境他能「当场开始读」。占比是假指标，覆盖是真相 |
| 不满足覆盖度时 | 不得凑数（如把无注释的文言原文标成 `inline`）；若某类确实无合格公版文本，该类首批可以没有 inline，但必须在 UI 上如实呈现，不得暗示「本该能读」 | 见下方「品类错配」 |
| `inline` 的中文可读性硬要求 | 文言 / 民国旧译必须配白话注释或导读，否则降级为 `external`。**注释来源只允许 SPEC §10.0 的三种**：清代及以前的旧注 / 我们自己写的导读与词条 / 明确标注 CC 或公有领域授权的整理本。**现代出版社的「题解 + 注释 + 白话翻译」整体受版权保护，搬进来和在版中译本同性质**。**每本 inline 必须在 `docs/copyright/<book_id>.md` 写清三件事：原文底本 / 注释版本 / 导读作者，缺任一项 `copyright-audit` 直接 fail** | 给现代用户一本无注释的《庄子》原文，等于没给；而随手用一本中华书局的注，等于引了一颗版权雷。**三件套之所以必须逐本留痕：这三项里只要有一项是从某本书上抄的，法律性质就变了，而它没有机器可识别的特征**——只能靠「写不出这页就不许上」 |
| `bring_your_own` | 首发 300 本中的绝对多数（约 250 本） | 心理、社科、传记、方法类几乎全在此列 |
| `external` | ≤ 10% | 只用于版权状态未知或仅有外文原文的书 |

**为什么不能按占比定指标**：占比是「库存视角」的指标，而用户感知的是「与我这一类困境相关的书，能不能直接读」。按占比反推出的本数远超公版库在首发周期内的真实产能（中文古籍 + 民国旧译 + 项目自校 + 加白话注释）；硬凑只能靠降低质量（无注释原文、错字未校、旧译语言障碍），结果是「数量达标、体验更差」。**首发这几十本覆盖 5 个领域、每本都真能读，比一个好看的占比里有大半读不动更有价值。**

**必须承认的品类错配（本节最关键的预期管理）**

公版可得性与现代困境的分布是**系统性错位**的，不是随机的：

| 现代困境（第 10.5 的域） | 公版能否覆盖 | 原因 |
|---|---|---|
| 意义感、人生选择、处世、修身与情绪 | **能** | 这是「人的恒常问题」，两千年没变：庄子、论语、传习录、菜根谭、蒙田、爱比克泰德、叔本华旧译都能对应上 |
| 关系与孤独 | **部分能** | 民国旧译的书信 / 散文 / 亲情文本可用，但缺现代亲密关系与原生家庭的分析框架——这套话语体系是 20 世纪才建立的 |
| **习惯与行动**（拖延 / 开始不了 / 坚持不了） | **不能** | 行为科学议题，最早成熟的文本也在版权期内 |
| **工作与意义**（职业迷茫 / 金钱焦虑 / 被同龄人比较） | **不能** | 「职业」「绩效」「同龄人比较」是现代社会的产物，公版文本里没有这个概念 |
| **认知与思考**（信息过载 / 表达不清 / 批判性思维） | **不能** | 信息社会议题，全部在版权期内 |

**产品结论（三条硬约束，写进设计与验收）**

1. **不是每个困境域都有 inline 书，且这个缺口是结构性的、与库存量无关**。把库扩到 3000 本，「习惯与行动」域仍然一本 inline 都没有。任何「等书多了就能直读」的承诺都是错的，不许写进任何对外文案。
2. **UI 不得暗示「这本书本该能读」**。`bring_your_own` 的呈现必须中性：只写「需自备电子书」，不出现灰掉的可读按钮、不出现「暂不可读」、不出现「资源缺失」这类措辞。用户能否接受「这本书要你自己准备」，取决于我们把它说成**常态**还是**故障**——说成常态，转化率不降；说成故障，他会等一个永远不会来的版本。
   - **补充（v1.3 定稿）：结构性无 inline 的域，结果页顶部必须一次性说清**。当用户所在域「习惯与行动 / 工作与意义 / 认知与思考」时（这三个域首发 0 本 inline），结果页顶部常驻一行说明，文案定稿为：
     > **这个方向的书基本都还在版权期内，正文需要你自己准备（EPUB 或 TXT），导入后就能读。下面的推荐和理由照常。**
   - 呈现规则：信息色（不是警示色）、一行、默认展开、可折叠成一行（折叠后仍保留「需自备」标签本身）。**不得**用「抱歉 / 暂不支持 / 资源缺失 / 敬请期待」开头——这不是缺陷公告，是流程说明。
   - 理由：让用户在**第一次**遇到就理解「这个方向要自己备文件」，比让他连看 5 张「需自备」卡片各自疑惑一次要好；一次性解释把 5 次困惑压成 1 次。
3. **导入路径是主路径，不是次要功能**。首发 300 本里约 250 本需要导入，因此导入体验（感知 3 步的引导 + 校验静默 + 按原因分类的失败态）的优先级等同推荐理由，不能排在 P0 尾部。相应地，如果出现「流派选择」（先做小测还是先把导入做顺），**先做导入**。

### 10.4 字段：只引用，不复述

**字段清单、类型、枚举取值、必填边界一律以 `SPEC §5.2` 为唯一事实源。** 本节在 v1.4 及以前有一张 26 行的「新旧名对照表」，已整表删除——它是本项目 9 处枚举漂移的主要来源之一：同一个字段在 PRD / ARCH / SPEC 里各叫一个名字，最后由执行者各写一套。

PRD 在字段层面只保留四条 **SPEC 无法表达的业务约束**：

| 约束 | 内容 | 为什么只能由 PRD 说 |
|---|---|---|
| 录入量决定首发规模 | 每本 = **5 个判断点 + 5 段文本**。判断点：`problem_tags`、`difficulty`、`est_reading_hours`、`depth`、`form`；文本：`one_line_what`、`one_line_gain`、`first_action`、`match_brief`、`structure_note`。首发 300 本 ≈ 1500 个判断点 + 1500 段文本，这就是「25–40 分钟/本」的构成 | 数据模型不关心产能，产品必须关心 |
| 判断点为什么只能人工填 | `est_reading_hours` 等判断点是**人工估算 + 区间校验**（校验规则见 SPEC §5.2），不用「字数 ÷ 固定除数」推算。理由：文言原典与通俗读物的阅读速度差着数倍，不可能共用一个除数；一旦用固定除数，时长这个判断点就对古籍系统性说谎，而它是破冰位（R1）的直接依据 | 这是产品语义，不是数据建模细节 |
| 标签标注判据 | 一本书的 `problem_tags` 只能从受控词表里取（项数上限见 SPEC §5.2），且必须能回答「这本书**读完**能缓解这个问题」，而不是「这本书**提到**了这个话题」。答不上的就标 0 个 = 不进个性化池 | 这是推荐质量的根，且无法用类型系统校验 |
| 必填的语义分级 | 核心库四个文案字段（`one_line_what` / `one_line_gain` / `first_action` / `match_brief`）全部必填、构建期 fail；用户导入的书允许缺失，此时只出 S1 + S2 并标注缺口。**参与硬过滤的字段同样必填**（如 `entry_level`，见 SPEC §5.2 与 §6.3①）——过滤字段缺失不会报错，只会让那条规则静默失效，这比缺文案更危险 | SPEC 已写必填边界，PRD 补的是「缺失时对用户怎么表现」与「为什么过滤字段不能是可选」 |

**两个已废弃字段，防拾荒者挖回去**

| 字段 | 处置 | 理由 |
|---|---|---|
| `last_reviewed` | **禁止出现在类型与排序里** | 我们没有编辑时间线，且它会让结果随数据维护时间漂移，破坏「同输入同输出」。复核留痕走 git 提交历史 |
| `completeness` | **禁止** | 它与 `availability` / `content_ready` 三重重叠，且能进池的书恒为同一值——一个恒真条件放进 tie-break，只会让人误以为它在起作用 |

### 10.5 标签体系：`problem_tags` 与 `theme_tags` 是两件事

> **词表本体与规模不在本 PRD 维护**（受控词数量、族数、每字段项数一律见 SPEC §5.2）。本节只约束**业务用法**，这些约束必须进校验脚本。

| 维度 | `problem_tags` | `theme_tags` |
|---|---|---|
| 用途 | **打分**（主题契合因子的唯一依据） | **不打分**：浏览、搜索、找相邻域用 |
| 数量 | 多值，**每项带权重**（项数与权重见 SPEC §5.2） | 多值，**不带权重**（项数见 SPEC §5.2） |
| 缺失后果 | 该书**不进个性化推荐池**（仍可读、可浏览） | 只影响浏览与相邻推荐，不影响打分 |
| 标注判据 | 必须能回答「这本书**读完**能缓解这个问题」 | 「这本书**涉及**这个主题」即可 |

**这两者不能合并**，合并会同时毁掉两件事：困境匹配失去精度（主题词混进来会稀释），以及浏览/相邻域失去依据（困境词太窄，撑不起「同主题的其他书」）。

| 约束 | 内容 |
|---|---|
| 受控词表 | 不允许策展人自由造词。新词先改词表再标书，否则校验失败（词表规模见 SPEC §5.2） |
| 与问卷的关系 | 问卷第 1 步的 **6 个困境域是用户视角的分类**，词表里的**族是数据视角的分类**（族数见 SPEC §5.2），两者**不是一一对应**。不要按 6 域去建族，也不要假设某族只服务某个域 |
| 首发覆盖目标 | 每个问卷域 ≥50 本（按 `problem_tags` 命中计），不要求按族平均 |

**6 个困境域 ⇄ 标签的对应关系（仅示意，正式映射以 SPEC 词表为准）**

| 问卷域（用户看到 6 项） | 大致落在哪些标签上 | 首发覆盖目标 |
|---|---|---|
| 情绪与自我 | 焦虑类、内耗/反复想、自我否定、情绪失控、孤独、倦怠 | 50 本 |
| 关系 | 亲密关系、原生家庭、职场人际、边界、沟通、分离 | 50 本 |
| 工作与意义 | 职业迷茫、意义感、选择困难、被否定、金钱焦虑、同龄人比较 | 50 本 |
| 习惯与行动 | 开始不了、坚持不了、注意力、时间失控、完美主义 | 50 本 |
| 认知与思考 | 看问题单一、易被说服、决策质量、表达不清、信息过载 | 50 本 |
| 人生转折 | 二十几岁迷茫、转型、中年、疾病与照护、亲人离世、身份转变 | 50 本 |

### 10.6 数据工作量与三层口径

| 规模 | 本数 | 人工工时 | 时间定位 | 谁来产出 |
|---|---|---|---|---|
| **M1（当前阶段）** | **60**（6 域 × 10，其中 7 本 inline） | **37–58 小时**（取整后的口径）：**53 本字段结构化 22–35.5 小时**（25–40 分钟/本）+ **7 本 inline 14–21 小时**（复用旧注 + 自写一篇导读，2–3 小时/本），精确合计 36–56.5 小时 | M0 之后 | 项目组 |
| 首发 | **300**（6 域 × 50，品类配比见 10.1） | **125–200 小时** | 上线前 | 项目组 + 早期贡献者 |
| 首发 inline 正文校注 | 30–40 本 | **240–480 小时**（本行按「自己断句标点、错字校勘、白话注释、导读」的重路线估，每本 8–12 小时） | 上线前，与上一行并行 | 需懂文言的贡献者，人少，是真正的瓶颈 |
| v1.0 前 | 800 | 330–530 小时（其中 200+ 小时靠外部 PR 摊薄） | 上线后 6 个月 | 外部 PR 为主 |
| 架构上限 | 3000 | 1250–2000 小时 | 12 个月目标，**不承诺** | 社区 |

**M1 采用「旧注路线」，它改变了上面那行 inline 校注的成本结构**：M1 的 **7 本** inline 全部使用**清代及以前的旧注**（郭象注《庄子》、刘孝标注《世说新语》、王先谦《荀子集解》、陶澍注《陶渊明集》、何晏《论语集解》等，作者均故去超 50 年）+ **我们自己写一篇导读**（篇幅规格见 SPEC），单本 2–3 小时，而不是 8–12 小时。其中《围炉夜话》《曾国藩家书》无旧注传统（原文短条、语句浅近），只需自写导读，成本更低。

> **如果 300 本阶段确认沿用这条路线，上方「首发 inline 正文校注 240–480 小时」应降为 60–120 小时**（30–40 本 × 2–3 小时），首发合计从 365–680 小时降到约 185–320 小时，RICE 里书目数据的 Effort 9 也应随之下调。**这是一个待 300 本阶段确认的决策点，不是已经发生的变化**——写在表里是为了让后来人看到「成本口径取决于路线」，而不是看到两个互相矛盾的数字。
>
> 为什么旧注能省这么多：最贵的是「断句、标点、校勘、注释」四件，旧注已经做完了前三件（清代刻本本身带断句，且旧注的训释就是注释）。剩下的导读反而是我们最该自己写的东西——`match_brief` 和 `one_line_what` 都从导读里长出来。

| 风险项 | 说明 |
|---|---|
| 最大单点成本 | 首发合计 **365–680 小时（约 2.3–4.3 人月）**：300 本整理 125–200 小时 + inline 校注 240–480 小时。与推荐引擎、阅读器的开发量同一量级，且它是唯一「不能靠加人加速」的部分（校注需要有文言能力的贡献者）。必须第一天启动 |
| 应对方案 | 用 `content_ready` 字段做三层区分：必填字段齐 → `content_ready = true` 才进推荐池；否则只进「按品类浏览」，不出现在诊断结果里。这样 800 / 3000 的扩张不会稀释推荐质量 |
| 版权核验 | 每本必须核 `copyright_basis` + `translation_copyright`（判定与举证见 SPEC §10.1）。**注释同样有版权**：现代整理本的「题解 + 注释 + 白话翻译」整体是编辑作品，连断句分段都可能受保护——把某出版社的注搬进仓库，性质和搬一本在版中译本一样。inline 的注释来源只允许 SPEC §10.0 的三种。漏判一本 = 一次投诉 / DMCA 风险，开源项目声誉损失不可逆 |

**每本的录入量 = 5 个判断点 + 5 段文本**：判断点是 `problem_tags`、`difficulty`、`est_reading_hours`、`depth`、`form`；文本是 `one_line_what`、`one_line_gain`、`first_action`、`match_brief`、`structure_note`。首发 300 本合计约 1500 个判断点 + 1500 段文本——这就是「25–40 分钟/本」的构成，任何想把首发量翻倍的想法都要先看这个数。

**产品结论**：**首发 300 本，不是 3000 本**。理由：推荐质量取决于单本理由的质量，不取决于库存量。300 本做好，用户可以连续用 3 个月不重样；3000 本字段半空，用户第一次就撞上「暂无深度推荐」——那是比「书少」严重得多的失败。

### 10.7 M1 的验收口径（60 本，**不看品类配比**）

M1 只上 60 本（6 域 × 10），判断标准刻意**不是**品类配比，而是三道闸并测：

| # | 闸 | 判据 | 为什么是这条 |
|---|---|---|---|
| 1 | 闸门 0 · 金标正对照 | **认出率**（金标书落 `strong`）与**首屏率**（第 1 位落 `strong`）**各自 ≥7/10**，两个数分开计数、不许合并求平均 | 见 7.3：连完美对口给不出 strong，后面谈比例没有意义。**合成一个数会让排序错误被当成校准错误去修权重**——那是最贵的一类误诊 |
| 2 | 每域对症密度 | 每域 10 本里 **≥6 本**在「该域典型画像」下能进 top3 | 这是「按困境推荐」成立的最小证据。它可直接复用闸门 0 的画像，不必另做一轮验证 |
| 3 | 每域破冰冗余 | 每域 **≥2 本**可作破冰位（≤3 小时，或 `inline`） | 第 1 组「今晚就能开始」只放 1 本。某域若只有 1 本满足条件，它一旦被硬过滤（难度 / 内容安全）剔掉，第 1 组就空了——**2 本是「允许失败一次」的最小冗余** |

**为什么 M1 不用品类配比**：M1 要验证的是「按困境推荐能不能成立」，不是库存结构。文学在「读完的落空」这个节点价值极高（替代性经验），但在「今晚就能开始」这个节点是劣势；而 M1 恰好验证后者。用 300 本的配比约束 60 本，会逼我们为凑比例收进不对症的书，**那时候验出来的「成立」是假的**。

**代价必须记账，否则半年后会被读成遗漏**：M1 这 60 本有意偏说理书，文学实际只有几本，远低于 300 本目标配比里文学应有的份额。这一条写进扩库计划，并注明原因：**扩库时文学回到目标份额，因为它承担「读得下去」的基础盘，而不是因为它更对症**。

### 10.8 M1 金标集：10 条画像（字段以 SPEC §7.4 为准）

**写法与顺序（这条顺序本身就是约束）**：每条都是**先写处境 → 再按常识回答问卷 → 最后才指定**那本「就是为他写的」书。顺序反过来，画像是「为了某本书而写的」，金标集就成了循环论证——**而且它会显示 10/10 通过**。这 10 条全部写于**未看任何打分结果**之前。

**冻结状态**：**这 10 条自本文定稿起即视为已冻结**，不再改——包括「这个例子不太典型，换个更理想的」这种看起来完全合理的改动。金标集的自欺不是造假，是标准漂移，而标准漂移每一步都合理。要改只有一条路：**ADR**。

**落盘时机（顺序本身是判据）**：**现在先不写 `tools/gold-set.json`。** `expect_book` 要填真实 `book_id`，而 60 本书目的 id 要等 M0 建目录时才生成。正确顺序是：

```
书目 id 定下来  →  写 gold-set.json 并入仓  →  才允许第一次跑
```

只要满足「**写在前、跑在后**」，冻结就是有效的；反过来先跑一次再补文件，这份金标就不再是正对照——因为它已经可以被「按跑出来的结果微调」了，而这个动作当时一定感觉不出异常。

**编号**：`book_id` 形如 `core:<6 位定宽>`，**由全局流水号分配**（`book-id-ledger.json`，永不复用、永不重排、**永久空号不回收**），**不得编码任何可变属性**。**本表不写猜出来的 id**——表里填的是书名，**书名才是真源**；等 M0 建目录、ledger 分配流水号之后，再由书名 → id 映射一次填进 `expect_book`。

**为什么不嵌域号（这条决定了 id 能不能信）**：**id 永不改，域会变**。一本书从「习惯与行动」挪到「工作与意义」是正常的策展调整；把可变分类编进不可变 key，每调整一次就多一本**id 在撒谎**的书，而且没有任何代码会报错。可读性不是 id 的职责——想知道编号含义，查 ledger 加书名对照；id 只负责稳定与定宽。

**写 id 时不许改指向**：填 `expect_book` 是「把已经定下的书名翻成 id」，**不是重新选书**。换书 = 重写金标 = ADR。另外 `core:\d{6}` 会命中项目里那条权重数字的检索（`500` / `1000` 是子串），白名单**只能对这个完整模式生效，不能给裸数字开白名单**——那会把真正的违规数字一起放过。

#### 逐条正文

> **键名只有一个出处：SPEC §6.1 第 3 屏那张表（组 / 答案键 / 选项值 / 驱动）。** 本节只写值，不另立一套清单——**这里重列一次，就一定会分叉**：本项目已经因为「同一个东西两个清单」错过三次（S2 字数、15 项 / 17 项、P0 编号），每次都不是谁记性差。
> **值一律写英文枚举**：`time_budget` = `10m` / `30m` / `1h+`；`difficulty_pref` = `easy` / `challenge` / `hard`；`urgency` = `3w` / `1m` / `none`；`form_pref` = `story` / `method` / `framework`；`depth_pref` = `howto` / `howto_why` / `why`。中文是用户看到的文案，**不进数据**。
> **`answers` 里不含派生值。** 难度上限、认知负荷 25/50/75 都是 `difficulty_pref` 映射出来的，不是答案——把派生值和选择压成一层，将来改映射就再也分不清是哪一边变了。
> `situation` 与 `why` 的长度上下限以 SPEC §7.4 为准，本文不复述数字；括号里的字数是**实测值**，用于核验，不是新参数。`answers.domain` 与顶层 `domain` 是同一个值，本表只在汇总表写一次（SPEC 把它放在两处，转 JSON 时由该列同时填入，**这是唯一的单值双写**）；**因为它是双写，校验脚本必须断言 `answers.domain === domain`，不等即 fail**——双写没有天然一致性保证，哪天只改一处，脚本会静默取其中一个，报告里就多一条「域写着 A、画像却在 B」的样本，而报错信息不会告诉你是哪一处写的。

**G10 · 父亲刚确诊（反向用例，全 10 条里唯一一条）**
- `situation`（109 字）：38 岁，父亲刚确诊晚期。她从外地赶回，一边查资料一边被亲戚问「要不要继续治」。她不知道该问医生什么，也不知道怎么跟父亲说话。夜里会想「以后怎么办」，但白天必须做决定，没有人能替她把这个决定往后拖，时间也不站在她这边。
- `answers`：`problem_tags` = 疾病与照护 / 亲人离世 / 身份转变，`primary_tag` = **疾病与照护**；`time_budget` = `1h+`，`difficulty_pref` = `hard`，`urgency` = `3w`，`form_pref` = `framework`，`depth_pref` = `howto_why`
- `why`：主诉是疾病与照护——该问医生什么、什么时候该停，是决策工具不是安慰。**它不该被任何一道硬过滤命中**：主诉清晰可映射、答案不矛盾，且她选的不是「越轻松」。

**G10 为什么必须存在**：它验的不是契合度，是「**不该被枪毙的书没被枪毙**」。《最好的告别》带 `grief` / `terminal_illness` 标注，而两条安全过滤（`EX-trauma` / `EX-terminal`）的剔除条件是「情绪与自我域 **且** 越轻松偏好」**两个同时成立**——G10 只满足一半（域是人生转折、偏好是不怕难），所以它必须活下来。**一旦它被剔除，说明这两条被实现成了「有沉重标注就一律剔除」**，而那个实现会把整个「人生转折」域清空。这条只有 G10 能测到，其余 9 条都测不到。

| ④ 构建期校验 `book_id` 存在 + `domain` 与 `primary_tag` 同域 | 待目录生成后执行。10 本书都在 60 本首发清单内；G08 的跨域情形见上文 |
| ⑤ ≥1 条反向用例 | 满足：G10 |
| ⑥ 金标画像不许跳答（**约束在 SPEC §7.4 硬约束 6，本节只引用、不重新定义**） | 满足：10 条都是五组齐全。**这条约束的是金标画像，不是问卷**：真实用户第 3 屏五组仍可全部跳过（见 §7.1）。同一个动作在两个对象上后果相反——对用户是「还能用」，对样本是「不可比」——**所以两处规则也相反，它们不矛盾**。样本为什么不能跳：跳答 → 该因子整条移除、权重按比例重分配 → 这份画像与其他样本**不在同一套 `weights_used` 下**，「≥7/10」这个计数就失去意义，而报告里看不出来 |

#### 四条预检项（落库前必须核，否则会把标注错误 / 数据缺口读成校准失败）

| # | 依赖的标注 | 若标错会怎样 | 该改哪一层 |
|---|---|---|---|
| 1 | 《被讨厌的勇气》`difficulty` 落在「越轻松越好」这一档的难度上限之内（该上限见 SPEC §6.3①） | G01 选的就是「越轻松越好」，这是三档里上限最低的一档；书标高了会被**难度上限过滤**（`EX-difficulty`）在打分前直接剔除 | **改标注**。不许把 G01 的 `difficulty_pref` 改成 `challenge` 去迁就标注——那是改金标迁就实现 |
| 2 | 《倦怠社会》`difficulty` 落在「有点挑战」这一档的上限之内 | 这本书理论密度高，标过头，G02 会被**难度上限过滤**（`EX-difficulty`）剔除 | **改标注的口径**，不是改 G02 |
| 3 | 《最好的告别》`content_warning` 含 `grief` / `terminal_illness`（取值见 SPEC §5.2），**且实现层的枚举与过滤规则是同批对齐的** | 若没标，G10 作为反向用例就**失效**——它退化成「一本没有标注的书没被过滤」，什么也没测到。若枚举装不下这两个值，这本书根本标不上，同样失效 | **改标注**；另外这条预检顺带盯一个已发生过的错配：字段表与过滤规则曾一度不同批（表里 5 值、规则 6 条），**枚举与规则必须同批改** |
| 4 | `include_heavy` 这个开关在首发数据上**真的能改变结果**（验收判据是行为型，见下） | 若不能，它是**数据层的假开关**：问题实现了、文案也对、`EX-terminal` 也跑，但首发书单里没有任何一本书会因为它出现。它比 UI 层的假按钮隐蔽得多——UI 假按钮点了没反应，这个点了「看起来也正常」，**因为结果本来就该是那些书** | **不补书、不改判据，M1 就不渲染**：该域若确实没有一本带这两个标注、且难度在「越轻松」上限内的书，这一格**不渲染该问句**并挂账（§19 第 11 条），等书目扩充到自然出现时控件自动出现。**不为让开关有手感而收一本书**——那和 §10.7 说的「为凑配额收进不对症的书」是同一个错；**也不为让它出现去动难度上限** |

**第 4 条要拆成两层。混成一句会跑不起来——这是个循环依赖**：第 3 屏渲染那一刻，用户**还没答完**（自由文本在后面）、也没跑过一次推荐；要判断「翻这个布尔值结果会不会变」，得先跑两次完整推荐，**而那时 `include_heavy` 正是还没被回答的那一题**。

**（1）验收判据（行为型；跑在 M0.5 / M1，原话，不许改写）**：

> 取同一画像，**只翻 `include_heavy` 这一个布尔值**，两次推荐结果的 `book_id` 集合必须不同。**相同 → 该画像下这个控件不得渲染。**

它证明的是「这个开关不是装饰」。

**（2）运行时渲染条件（结构型，可预计算；第 3 屏用这一条）**：

```
存在候选书 ∈ 该用户域 ∩ 难度 ≤ 该档 cap ∩ content_warning ∩ {grief, terminal_illness} ≠ ∅
```

这个查询在打分之前就能算，且**与标签、自由文本无关**，所以第 3 屏算得出来。实现上**不每次现算**：构建期生成一张 `(domain × difficulty_pref) → 是否渲染` 的布尔表（**6 域 × 2 档 `easy` / `challenge` = 12 行**；`hard` 档不入表，见下），书目一变就重算，运行时查表。

**这张表的 12 行里只有 1 行可能为 `true`，而这 12 行分两类，必须分开写：**

| 格子 | 值 | 为什么 |
|---|---|---|
| `emotion × easy` | **数据决定**（∃ 符合条件的书） | 唯一一格 `EX-terminal` 会生效（它的条件是「域 = 情绪与自我 **且** 越轻松」） |
| 其余 11 格 | **结构恒 `false`** | 规则不在这些格子里生效——布尔值翻成什么都不会改变任何结果 |

**为什么必须分开写**（后果，不是洁癖）：如果 11 格也写成「查一次书」，它们现在恰好是 `false`（因为没书），**看起来对了**；哪天 `EX-terminal` 扩到「有点挑战」，那张表会**自动**变成 `true`，而**没有任何人改过那条规则**——它会开始问一个规则还没准备好回答的问题。反过来，11 格写死 `false`，规则一扩，检查立刻红，改的人被强制看到「表的结构来自规则」。

**一句话：表的结构来自规则，表的值来自数据。混在一起，规则变了表会自己动。**

`hard` 档**不入表**（cap 最高，实际永不触发），但查询时必须**显式返回 `false`**，不许落到「表里没查着 → 默认 `true`」——**默认值不是中立的，它总是偏向「多做一步」**，而这一格要的恰好是「不做」。

**两层的关系**：结构条件是**必要条件**，行为判据是**验收标准**。结构为真而行为为假 → 说明中间有别的规则把它吃掉了（例如那本书难度超 cap），**此时红的是实现，不是判据**。

**为什么不数「有几本带 `grief` 的书」**：那本如果难度高，在「越轻松」（上限最低的一档）下**先被难度上限过滤删掉了**，勾了还是 0 本——而这恰好是 M1 首发最可能的状态（能确认带这两个标注的只有《最好的告别》，它的域是**人生转折**，对「情绪与自我 + 越轻松」的用户**永远不会**被 `EX-terminal` 删，勾不勾结果一样）。**交集数不出来，只能跑。** 这条也是 §18 第 19 步的前置：那一步验的是「勾了之后能出现」，得先保证库里真有一本会因此出现。

**一个容易被当成缺陷的一致性**：若「情绪与自我」域确实没有这类书，`EX-terminal` 在那一格**本来就惰性**（没有书会被它删）——也就是说**安全规则和这个开关同时不生效**。这不是漏了一个，是一致的：**没有那类书，就不需要那条例外通道。**

**这四条的共同点**：它们看起来都像「跑挂了」，实际是**数据没备好**。**先核标注与目录，再怀疑引擎**——顺序反了，会拿一份错的标注去把权重调歪，然后带着一份「调好了」的权重进入 M1。

## 11. 功能范围（MVP 锁定）

### 11.1 P0（不做则闭环断裂，必须进第一版）

> **编号口径**：本文 P0 条目与 `SPEC §2.1` 的 **17 项同一编号体系，无增补项**。P0-16（危机资源条）与 P0-17（结构性无 inline 域的说明条）已在 SPEC §2.1 单列并带冻结文案，本文只是把它们写成「当…时，系统应…」的可测形式，**不新增范围**。
> **本节保留 EARS 句式的理由**：SPEC 给的是验收摘要，PRD 给的是「当…时，系统应…」的可测形式，两者不重复——但**凡是数值与枚举，本文一律引用 SPEC，不复制**。

| ID | 功能 | EARS 验收标准 |
|---|---|---|
| P0-1 | 困境问卷（3 屏 + 1 屏可选自由文本；第 3 屏含 5 组 chip；第 2 屏含主诉追问且必答） | 当用户首次进入首页时，系统应展示 3 屏选项式问卷，每屏可「返回上一屏」（主诉追问除外）；第 3 屏应在**同一屏内**呈现 5 组 chip（3-a 每日时长 / 3-b 可接受难度 / 3-c 见效速度 / 3-d 带读方式 / 3-e 收获层级），**5 组全部允许跳过**，不得拆成更多屏；**当第 2 屏勾选 ≥2 项时，系统应在同一屏下方展开一行「这些里面，哪个是你现在最想先解决的？」并强制作答——不跳转、不新增屏、不预选、不可跳过、不得使用「最严重」类措辞，且不得用勾选顺序代替用户作答**；若用户在第 2 屏选择「说不上来」，则系统应跳过第 2 屏并展示 6 个具体场景选项，而不是提示错误；若第 3 屏 5 组全跳过，则系统应退化为「主题 + 难度」两因子排序并在顶部提示「补上读书条件能排得更准」 |

## 12. 明确不做（out-of-scope）与逐条原因

| # | 不做 | 原因（不是「暂时不做」，而是「这一版明确不做」） |
|---|---|---|
| 1 | **不做社区 / 评论 / 关注 / 书评** | 冷启动阶段社区必然是一片空地，空地比没有更伤（用户会认为产品已死）。且 UGC 需要审核、举报、申诉机制，成本远超一个 MIT 开源维护者的承载能力。我们的用户要的是「一个人安静地开始读」，不是来社交 |
| 2 | **不做 PDF** | PDF 是固定版式，重排、字号调整、划线定位（CFI 等价物）、深色模式全部退化，等于要写第二个阅读引擎。而用户的 PDF 多是论文与扫描件，与「按困境读一本完整的书」是两种场景。明确不做，并在导入失败态里给出原因说明 |
| 3 | **不做多端同步 / 账号体系（第一版）** | 同步 = 账号 + 后端 + 隐私政策 + 冲突解决 + 数据合规。这与 local-first 定位直接冲突，且第一版用户量不足以摊薄成本。不上传数据反而是我们的信任卖点（见节点 5） |
| 4 | **不做 AI 自由生成书单 / LLM 写推荐理由** | 三条硬理由：① 不可复现（同一输入两次结果不同，违背规则推荐的承诺，也无法写单测）；② 会编造不存在的书与虚假理由（幻觉在推荐场景是致命的，用户按推荐去买书发现查无此书 = 永久流失）；③ 有 API 成本，与「零成本、任何人可自建」的开源定位冲突。**这条是定位级决策，不是技术偏好** |
| 5 | **不做豆瓣评分 / 评论展示** | 豆瓣无公开 API（2017 年关停开放接口，2023 年 7 月开发者平台下线），抓取违反其条款且随时失效。更重要的是：豆瓣评分是「大众平均」，与我们表达的「对你的适配度」是两种语义，混在一起会破坏第 7.3 的呈现设计 |
| 6 | **不做任何盗版书源 / 书源爬虫 / 盗版聚合** | 法律风险直接摧毁开源项目（DMCA、仓库下架、维护者个人风险）。Legado 式的「用户自配书源」模式我们不复制——它把风险转移给用户，但产品因此永远无法进入正经分发渠道，也无法被公司采用 |
| 7 | **不做内置版权书全文 / 不做「试读章」抓取** | 任何形式的版权正文内置都是侵权。「试读」必须来自版权方授权，我们拿不到，所以不做——只在详情页给合法获取途径 |
| 8 | **不做向量相似度推荐** | 已锁定决策。补充产品理由：向量相似度输出的是「书和书像」，不是「书和你像」，且结果无法用一句话解释给用户。规则加权打分可解释、可单测、零成本、可复现，四个属性都直接服务「信任」这个核心节点 |
| 9 | **不做移动原生 App（第一版）** | 需要额外一套构建与分发（iOS 审核、Android 签名），团队规模不支持。做 PWA（可安装、可离线）能覆盖 80% 的移动使用场景，且与 local-first 天然契合 |
| 10 | **不做大规模书封抓取** | 书封图片版权归属复杂、外链易失效、体积拖慢首屏。用「书名著排版 + 品类色块」的占位方案，反而形成视觉识别度 |
| 11 | **不做「读完打卡 / 连续天数 / 排行榜」** | 游戏化机制会把「读书」变成「维持记录」，用户为了不断签而读 2 页垃圾内容。我们的成功指标是「读完并记住」，不是「连续 30 天打卡」 |
| 12 | **不做付费 / 会员 / 任何变现** | MIT 协议 + 开源 + 不卖书 = 无可变现路径，也就不需要设计付费墙、留存钩子、推送召回。这让所有产品决策都可以只服务用户，不做数据套利 |
| 13 | **不做「推荐理由」的用户自定义编辑** | 第一版理由由策展人写、模板填充。开放编辑需要审核与版本管理，成本高且会让理由质量不可控（这是产品最核心的资产，不能交给未审核的输入） |

## 13. RICE 优先级表

RICE = (Reach × Impact × Confidence) / Effort。Reach 按每季度受影响用户占比（1–10），Impact 0.25/0.5/1/2/3，Confidence 50%/80%/100%，Effort 人月（1–10）。

> **本表的 `Effort` 只用于相对排序**：数值之间的比例关系有意义，绝对值**不作为工时承诺**。对外的排期、里程碑与人力估算一律引用 **SPEC §2.2**。理由：RICE 的分母是为了让「贵的功能」在表里沉下去，它会随团队规模变化；而排期是对外交付承诺，两者不能共用一张表。

| 功能 | Reach | Impact | Conf | Effort | Score | 判定 |
|---|---|---|---|---|---|---|
| 三段式理由渲染（含降级） | 10 | 3 | 90% | 3 | **9.00** | P0，最高优先。这是产品唯一不可替代的资产 |
| 推荐结果卡片 + 档位呈现 | 10 | 2 | 100% | 3 | **6.67** | P0 |
| 困境问卷 + 自由文本 | 10 | 3 | 100% | 5 | **6.00** | P0 |
| 书籍详情页（含版权说明） | 10 | 2 | 100% | 4 | **5.00** | P0 |
| 规则打分 + 硬约束排序 | 10 | 3 | 90% | 7 | **3.86** | P0 |
| 划线 + 笔记 | 8 | 2 | 80% | 4 | **3.20** | P0（本地版，最小实现） |
| 推荐结果保存 / 导出 JSON | 7 | 1 | 90% | 2 | **3.15** | P0（轻量，顺手做） |
| 书目数据（300 本整理 + 30–40 本 inline 正文校注） | 9 | 3 | 80% | 9 | **2.40** | P0（最大成本项兼最长关键路径，必须最先启动；详见 10.6 的工时拆分） |
| EPUB 导入 + 本地书库 | 9 | 3 | 80% | 8 | **2.70** | P0 |
| EPUB 阅读器（foliate-js 集成） | 9 | 3 | 80% | 8 | **2.70** | P0 |
| 公版书内置直读（首发 30–40 本 inline，覆盖 5 个领域各 ≥1 本） | 6 | 3 | 70% | 7 | **1.80** | P0（口径见 10.3：验收看领域覆盖度，不看占比） |
| TXT 导入（编码 / 分章） | 8 | 2 | 80% | 4 | **3.20** | P0 |
| 书目数据校验脚本 + CONTRIBUTING | 4 | 2 | 90% | 2 | **3.60** | P0（生态入口，成本极低） |
| 章节小测（**只配 100 本**：inline 40 + 精选 60，每本 3 题 = 300 题；其余书不配题，靠划线笔记建卡） | 6 | 2 | 60% | 6 | **1.20** | P1（配题量从「全库」收敛到 100 本后 Effort 由 8 降到 6） |
| 间隔重复（复用上述 300 题的错题 + 划线，不再依赖全库配题） | 5 | 2 | 60% | 6 | **1.00** | P1 |
| 听书 TTS | 4 | 1 | 60% | 8 | **0.30** | P1 |
| 多端同步（WebDAV） | 4 | 2 | 50% | 9 | **0.44** | P1 |
| 社区 | 3 | 1 | 50% | 10 | **0.15** | 不做 |

**读法**：分数最高的前 5 项全是「推荐侧」而非「阅读侧」，这验证了产品定位——我们的稀缺价值在推荐，阅读器是可替代的（用 foliate-js 站在别人肩膀上）。但注意 `Effort` 最大的两项（书目数据 9、阅读器 8）分数中等，说明**项目排期上它们必须最早启动**（周期最长），而不是优先级低。其中书目数据的 Effort 9 对应 10.6 的 365–680 小时（约 2.3–4.3 人月），且它是唯一无法靠加人加速的部分——inline 正文校注需要有文言能力的贡献者。

## 15. 数据埋点（local-first 版本）

**前置约束**：无后端 + 隐私承诺 = **不能默认上传任何事件**。所以埋点方案分两层。

**一条凌驾于两层之上的禁令**：**危机资源条与 `/crisis` 资源页内不埋任何点**——不统计曝光、不统计点击、不统计是否返回。理由是这条资源存在的全部前提是「没人评判我」；一旦它被计入任何一个数字，它就从帮助变成了漏斗的一环，而我们无法向用户解释「为什么你们要记录我点开了求助」。这条不设例外、不因「只是想看有多少人需要」而开。要判断这条资源有没有用，看 issue 里的定性反馈，不看计数。

### 15.1 第一层：本地统计面板（默认开启，永不上传）

这是主要的数据来源。用户在「设置 → 我的阅读数据」可以看到自己的数据，同时它也是产品的验收工具。

| 事件 | 触发时机 | 用途（本地可见） |
|---|---|---|
| `questionnaire_started` | 进入问卷第 1 步 | 观察自己的流失点（不需要服务器也知道） |
| `questionnaire_completed` | 完成第 3 步（或第 2 步） | 计算完成率 |
| `include_heavy_shown` / `include_heavy_answered`（带 `value`） | 那一问被渲染（`shown`）/ 被回答（`answered` + `value` = `一起看` / `先不用`） | **只存在本地。必须三分：`未渲染` / `渲染但未答` / `已答`**，且**未渲染的格子不许上报 `answered = false`**——那是「没被问」，不是「答了不用」；两者混在一起，投诉一来就会把人误判成「规则没生效」（见 7.4 三步排查）。**「他没选」和「我们没问」在数据里长得一模一样**，只能靠事件分开。**可证伪条件（两个条件同时成立才算证据）**：「一起看」比例偏高 **且** 出现「当次选了『先不用』、随后自己搜索并打开了带 `grief` / `terminal_illness` 的书」。**单纯比例高不算证据**——多数人本来就不想看这类书，低比例是正常结果，而追问它会诱导我们去放宽过滤。若两个条件同时成立，要改的是**问法**（再加一句专门的），**不是**悄悄放开 `EX-trauma` |
| `search_performed` | 搜索结果生成时（记命中数与**首条命中书的 `content_warning` 类目**，**不记查询词原文**；**0 命中也必须上报，带命中数 `0`**，不许「没结果就丢掉这条事件」） | 让上一条的可证伪条件**有信号可测**：没有它，「选了先不用却去搜临终/丧亲类书」这件事永远观测不到。**0 命中那一次恰恰是最强的信号**——它说明这个域里根本没有这类书，那么问题就不在问法上，而在书单上。**一个只在有结果时才存在的信号，会在最该它出现的时候缺席。** 读这条时要和**当次会话的 `include_heavy` 落库值 join**，否则「选了先不用的人去搜这类书」这句话无从判定 |
| `recommendation_generated` | 结果生成完成 | 记录输入与结果，用于复现 |
| `book_detail_opened` | 打开详情页 | 判断「哪类书点得多」 |
| `import_started` / `import_succeeded` / `import_failed`（含失败类型） | 导入流程 | **最重要的漏斗**：衡量「需自备」这一步是否杀死链路 |
| `reading_session_started` / `reading_session_ended`（含时长、页数） | 阅读器内 | 完读率与停留 |
| `book_finished` | 到达最后一章且停留 > 10s | 完读率（核心指标） |
| `highlight_created` / `note_created` | 划线 / 笔记 | 深度阅读信号 |
| `recommendation_dismissed` | 用户标记「不对味」（P1 功能） | 推荐质量 |

**报表口径：`EX-*` 各规则的触发次数必须把 `0` 显示出来，不许用「无数据即不出现」的写法。** 理由和 `search_performed` 的 0 命中共用一条：**一条装上但从未生效的规则，和一条没装的规则，在「只看有数据的地方」的报表里完全一样。** 半年后有人发现「这条规则从没跑过」，第一反应会是它坏了——而真实原因可能是那个格子里本来就没有该拦的书（见 §19 第 11 条）。**绿色的空行比红色的空行更危险，因为它看着像正常。**

### 15.2 第二层：匿名聚合遥测（默认关闭，显式 opt-in）

- 用户首次进入时以**非阻断式**提示说明：「可以帮我们改进推荐吗？只发送匿名的计数，不含你输入的任何一个字。」默认不勾选。
- 只发送计数器（如「今天有 12 次推荐生成、8 次导入成功、3 次导入失败（DRM 2 次）」），**不发送**：问卷答案、自由文本、书名、划线内容、笔记、IP、设备指纹。
- 发送目标：项目自建的轻量端点，代码开源可审计，端点可配置（自建者可以指向自己的）。
- 命名规范：`{对象}_{动作}`，如 `import_failed`、`book_finished`。
- 关键指标（产品假设无法验证 = 不该上线）：
  1. 问卷完成率（验证「3 步是否太长」）
  2. 导入成功率（验证「需自备」是不是致命阻力）
  3. 从推荐到开始阅读的转化率（验证闭环是否通）
  4. 首章读完率（验证「第 1 本是否选对」）

## 16. 成功指标

**不用 DAU。** 无账号、无服务器、local-first，DAU 既测不到也不该测（测它就必然要上传行为数据，与隐私承诺冲突）。改用开源项目真正能拿到的信号：

| 层 | 指标 | 目标（上线 6 个月） | 为什么是这个指标 |
|---|---|---|---|
| 传播 | GitHub star | 1,500 | GitHub 上「推荐算法 demo」最高仅 176星、「按困境推荐」零竞品，说明这个位置空缺；1,500星 足以进入相关 topic 首页 |
| 传播 | fork 数 | 150（star:fork ≈ 10:1） | fork 是本产品最特殊的行为：任意书店 / 图书馆 / 学校可以 fork 后换自己的书库，这是我们希望的用法 |
| 传播 | 外部 PR 数（书目贡献） | 60 个 PR / 300 本书 | 验证「策展人」这个用户画像成立；这是 800 本 / 3000 本目标的唯一可持续路径 |
| 质量 | 首次推荐到「开始阅读」的转化率 | ≥ 45% | 这个数低说明推荐不可信或第 1 本选错。是整个产品的健康度总指标 |
| 质量 | 首章读完率（打开后读到第一章末尾） | ≥ 60% | 直接验证「破冰位」硬约束（R1）是否有效 |
| 质量 | 完读率（读完的书 / 开始读的书） | ≥ 20% | 行业基准通常个位数；我们靠「第一本足够短」来突破。20% 是我们的赌注 |
| 质量 | 推荐结果页的「换一批 / 重新诊断」点击率 | ≤ 20% | 太高说明推荐不准；这个指标是反向的，越低越好 |
| 使用 | 单次推荐 → 7 日内回访 | ≥ 30% | 不用 DAU，用「一次诊断是否带来一次真实阅读行为」 |
| 使用 | 划线密度（每 1000 字划线数） | ≥ 0.8 | 读完但零划线的用户不算「读进去了」 |
| 数据 | 核心库字段完整率（`one_line_what` / `one_line_gain` / `first_action` / `match_brief` / `structure_note`） | 100%（首发 300 本）/ ≥ 95%（800 本）/ ≥ 80%（3000 本） | 数据质量是本产品唯一护城河，必须当指标管 |
| 数据 | 导入成功率（排除 DRM 与格式不支持） | ≥ 85% | 低于此说明导入体验在杀人 |
| 生态 | Issue 中「书不对味」类反馈占比 | ≤ 15% | 这是最诚实的推荐质量反馈渠道 |
| 反面 | 「找不到想读的书」类 issue | ≤ 10 个 / 半年 | 若超标，说明 300 本不够，可提前启动扩容 |

**什么样的状态算「成了」**：一个陌生人从 GitHub 进来，5 分钟内完成诊断、点了第 1 本书、当晚读了 20 分钟、第二天回来继续读——并且他能说出「它说我在怕被否定，挺准的」。这句话出现了，产品就成立。

## 17. 边界条件

| 类别 | 场景 | 处理 |
|---|---|---|
| 空状态 | 首次进入（无推荐、无书） | 不展示空书架，直接进入问卷第 1 步；首屏一句话说明「这不是一个书架，是一次诊断」（不得使用「Welcome to」类文案） |
| 空状态 | 约束过严导致候选不足 2 本 | 不给「无结果」。按 SPEC §6.3⑥ 的 L1→L4 逐级放宽，每一级的文案基调见 7.4「relax 的文案基调」；L2/L3 必须配一个可动手的出口（「是不是这几个条件太严了？改一下」→ 回到对应那一屏），L4 给「重填问卷 / 按品类浏览」两个入口 |
| 空状态 | 我的书架为空 | 「你还没有导入任何书。推荐里的公版书可以直接读，不需要导入。」+ 直达 1 本 inline 书 |
| 错误状态 | 书目 JSON 加载失败 | 显示「书库没加载出来，可能网络不稳」，提供重试；已缓存的推荐结果仍可看 |
| 错误状态 | IndexedDB 不可用（隐私模式 / 被禁用） | 明确降级：可浏览推荐但无法保存进度与划线，顶部常驻一条说明，不静默失败 |
| 错误状态 | 存储配额耗尽 | 阻止导入并引导清理，不删除已有数据 |
| 加载状态 | 推荐生成（< 200ms） | 不做骨架屏（太快反而闪），直接出结果；若超过 300ms 则显示一行文字「正在对照 300 本书」 |
| 边界值 | 书名为超长 / 空 | 截断到 2 行 + 详情页完整显示；空书名用文件名兜底并提示用户改名 |
| 边界值 | 极端长 TXT（>200 万字） | 提示分章可能不准，允许「只导入前 N 章」 |
| 边界值 | EPUB 含大量图片 / 图集 | 提示加载慢，图片懒加载，不阻塞文字 |
| 并发 | 同一本书在多个标签页打开 | 进度以最后写入为准，并在另一标签页提示「这本书在另一个窗口有更新的进度」 |
| 并发 | 同时导入多个文件 | 串行处理，显示队列，不并行（避免存储写入竞争） |
| 离线 | 断网打开 | PWA 缓存策略保证壳与已读书可用；未缓存的书目分片显示「需要联网加载书目」 |
| 权限拒绝 | 用户拒绝通知权限（P1 复习提醒） | 不重复弹窗，仅在设置页显示「提醒已关闭」与开启入口 |
| 内容安全 | 「情绪与自我」域用户 + 「越轻松越好」 | **硬过滤**：`content_warning` 含 `suicide` / `sexual_abuse` / **`grief` / `terminal_illness`** 的书直接剔除，不提供「你自己判断」的选项。唯一例外：用户在那一问里选了「一起看」（`include_heavy`，文案见 7.4）后，**只有 `grief` / `terminal_illness` 恢复**；`suicide` / `sexual_abuse` **不恢复**——不对称是刻意的，理由见 7.4。同时结果页底部固定展示危机资源条（见 17.1）。这是产品底线，不是可选功能（`EX-trauma` / `EX-terminal`） |
| 可获得性 | 用户所在域结构性无 inline（习惯与行动 / 工作与意义 / 认知与思考） | 结果页顶部常驻一行流程说明（文案见 10.3 产品结论第 2 条补充），信息色、可折叠、不得使用道歉口吻 |
| 版权 | 用户导入的文件疑似盗版 | 我们不做识别、不做拦截、不上传——技术上也做不到。责任边界写在 README 免责声明：文件由用户提供，仅本地存储 |

**`violence` / `eating_disorder` / `addiction` 不触发任何安全过滤——这是想过才留白的，不是遗漏。**（PM 裁定 2026-10-18；若将来要改，先改 SPEC）

`violence` 看着最像该拦的一个：把家暴题材推给「关系」域里只想轻松点的用户，和把临终题材推给「情绪与自我」的用户，论证结构几乎一样。**但仍然不加**，判据是：

> 这条过滤防的不是「题材沉重」，是「**这本书会不会让用户觉得系统在给他下判决**」。

临终题材对低心力用户读起来像「系统在暗示我没救了」——判断权被收回；而关系域里一本讲家暴的书，指向的是「**这是伤害，你可以离开**」——判断权被交回用户。**harm 的结构不同，就不能共用一条规则。** 加上三条执行理由：

- `violence` 是跨题材粗标签（战争 / 犯罪 / 史书 / 家史 / 家暴全算），按它在整个域上剔除，被剔的里面一定有好书，**而误伤是静默的**——埋点里还挂着安全策略的码，看起来像生效；
- 真高风险的子集已被覆盖一半：这类书通常同时带 `sexual_abuse`，那个已经在触发集里；
- 难度上限已经先拦一次：说「越轻松」的用户上限最低，而这类书难度普遍不低。

**可证伪的观察项**：若 M1 的用户反馈里出现「推给我一本讲家暴的书，我只要轻松点的」，就是上面这套判据被证伪。到那时正确动作**也不是**把 `violence` 塞进触发集，而是新增一个更精确的标签（如 `domestic_abuse`）并配预检——因为这类书的共同特征是「亲密关系中的伤害」，不是「有暴力场面」。**用一个宽标签解决一个窄问题，代价永远是静默误伤；而静默误伤永远不会有 issue。**

**这一条和「关系域要不要并进触发集」是两件事，但会被同一个数据点同时证伪**（同一个用户抱怨，既可以读成「`violence` 该进」也可以读成「关系域该进」）。所以：**动其中任何一条，都必须重跑金标反向用例 G10**——G10 钉的是「人生转折域 + 不怕难」这条边界，集合一改而用例不改，G10 会**静默失效**（它还通过，但它测的东西已经不是原来那个）。

### 17.1 危机资源条（文案定稿，v1.3）

**适用范围**：用户在第 1 步选「情绪与自我」时，结果页底部常驻。

**文案（逐字，不得改写）**

> 主句：**如果你现在不太好过，读书可以先放一放。**
> 副句：这里有可以立刻联系的心理援助资源。
> 按钮：**查看心理援助资源**

**三条文案决策及理由**

| 决策 | 结论 | 理由 |
|---|---|---|
| 「状态很差」还是「不太好过」 | **用「不太好过」** | 「状态很差」是在给用户下判断（而且是负面判断）；「不太好过」是平视的描述。他此刻不需要被诊断，需要被允许 |
| 条内是否直接写热线号码 | **不写，点开进本地资源页列号码** | 号码会变更、有地区适用性，写死在 UI 里必然过期；但只给链接不给号码又不可行动。折中方案：资源页列「机构 / 地区 / 号码 / 最近核对日期」，数据来自仓库内 `crisis_resources.json`，页顶标「最近核对：YYYY-MM」，页底给「打不通或已变更，请提 issue 告诉我们」——这样「可行动」与「可维护」同时成立 |
| 「读书可以先放一放」要不要留 | **必须留** | 这句话把用户利益放在产品利益之前，是本产品「不推销自己」的唯一硬证据。删掉它，整条就退化成免责声明，用户能感觉到 |

**呈现硬规则**：不可关闭、不可 dismiss、不做 toast、不 3 秒消失、不放进折叠区、滚动时不移除。宁可常驻占 40px，也不能让一个状态很差的人在需要时找不到它。

**边界**：仅「情绪与自我」域展示；同一会话内切到其他域不延续（避免变成全站横幅，反而钝化注意力）。

**维护责任**：`crisis_resources.json` 至少每 6 个月复核一次，写进 release checklist。资源已失效而未更新，比不展示更伤信任。

## 18. 端到端验证步骤（人工走查；脚本化验证见 SPEC §12）

> **分工**：SPEC §12 是**脚本化**验证（`npm run test:domain` / `catalog:audit` / `audit:copyright` / `budget:check`），管数值与契约；本章是**人工走查**，管「用户看到的东西对不对」。两者不重复，也不互相替代：脚本过了但文案丑，产品仍然没成；文案好但算例不过，程序仍然不能发。

架构师与设计师交付后，按下述步骤走查；任何一步不通过即视为 MVP 未完成。

**核心成功流（必须全通）**

1. 清空浏览器站点数据，断网，打开应用 → 首屏可交互，显示问卷第 1 步（验证 P0-14 / 空状态）。
2. 选「情绪与自我」→ 选「开会不敢发言」「怕被否定」→ 选「每天 30 分钟」「有点挑战」→ 自由文本输入「明明没做错什么，就是会怕」→ 提交。
3. 检查结果页：出现最多 5 本、分 3 组且组标题与 7.2 一致；第 1 位满足破冰位条件（时长或可直读，判定见 SPEC §6.3④）；每本显示档位标签，第 2 行是 `match_brief`（或降级为「命中了：…」），**第 3 行是 S2 首句：≤2 行、≤38 字，且以句号结尾（未被硬截）**，命中依据短语在展开区可见且**不与降级文案同屏重复**；**卡面上不出现 S1**（S1 只在展开区），**展开区不重复 B1**，页顶诊断摘要条**逐字回引用户原词**且全页**只出现一次**；**全页检索 `%` 与 `星`，不得出现匹配度百分比或星级**（验证 P0-5 / 8.1 卡片分工）。
4. 打开第 1 本理由的第 1 段，确认其中包含用户在步骤 2 输入的原词（「开会不敢发言」或「怕被否定」）（验证 P0-4）。
5. 检索全页禁用词：`经典|必读|神作|受益匪浅|提升认知|干货满满|本书讲述了|在这个快节奏的时代`，命中数为 0（验证 8.4）。
6. 打开一本 `inline` 书 → 详情页显示版本来源与公版说明 → 点「阅读」→ 直接进入阅读器 → 翻 2 页 → 刷新 → 位置恢复（验证 P0-9 / P0-13）。
7. 打开一本 `bring_your_own` 书 → 详情页明确出现「本站不提供全文」→ 「开始阅读」按钮不存在，只有「导入后阅读」→ 点开进入**感知 3 步**的导入引导（校验静默：通过时无进度无确认；失败时整屏报具体原因）（验证 9.1 / P0-8）。
8. 导入一个正常 EPUB → 成功 → 出现在我的书架 → 断网后仍可打开（验证 P0-11）。
9. 选中一段文字 → 划线 → 写笔记 → 刷新 → 划线位置与笔记完整（验证 P0-12）。
10. 回到首页 → 「我的书单」中可见刚才的推荐 → 导出 JSON → 用编辑器打开，字段含 `book_id`、档位、理由三段（验证 P0-15 / 契约）。

**关键错误流（至少全通）**

11. 导入一个 `.pdf` → 出现「暂时读不了」+ 明确的 PDF 原因说明，且**不出现**任何「转换后即可阅读」的暗示（验证 9.2）。
12. 导入一个改名成 `.epub` 的文本文件 → 出现「文件打不开，可能下载不完整」，且有折叠的技术详情（验证 9.2）。
13. 导入一个带 DRM 的 EPUB → 出现「带 DRM 加密…我们不能也不应该绕过它」，且**全站检索不到**任何解密工具名 / 链接（验证 9.2）。
14. 导入一个 GBK 编码 TXT → 出现编码三选一 → 选 GBK → 预览区中文正常（验证 P0-10）。
15. 在问卷全部选「说不上来」→ 仍能出 5 本结果，且 S1 回引的是场景词（验证 P0-1 / 8.3）。
16. 断网状态下完成步骤 2–3 → 结果正常生成（纯本地计算）。
17. 选「习惯与行动」域（首发无 inline 覆盖）→ 结果页全页检索 `暂不可读|资源缺失|暂不支持在线阅读|灰` ，命中数为 0；`bring_your_own` 的呈现与 9.1 / 9.4 完全一致（验证 10.3 第 2 条硬约束 / P0-13）。
18. 分别用 5 个覆盖领域（意义感 / 人生选择 / 关系与孤独 / 修身与情绪 / 处世）各走一遍流程 2–3 → 每次结果的前 5 本中至少有 1 本 `inline`（验证 10.3 覆盖度验收标准）。
19. **（前置）先跑 §10.8 预检第 4 条**：该画像下只翻 `include_heavy`、结果集合必须不同；**相同则这一步标「未验证」并挂起，不许标「通过」**——库里没有那本书时，「不出现」和「出现了但我没找到」长得一模一样。**并且：M1 里这一步基本不可能通过**（只有 `emotion × easy` 一格且库里有那类书才会渲染这个问句，而 M1 那格大概率没书）——**「未验证 + 挂起」是正确的状态，不是坏了，验收时不要把它当缺陷去修**。若控件确实渲染了，还要核**⑥ 准入**：它的**顶边在折叠线以上**（像素口径归 UIUX / SPEC），在折叠线以下一律不许上线——**一个没人滚到的开关，等于没问**。**M0 不修这件事**（该控件在 M1 不渲染，现在压缩第 3 屏是为用不上的场景改问卷节奏），触发条件与「上移已关闭」的理由见 7.4。 然后：选「情绪与自我」+ 3-b「越轻松越好」→ 结果中不含 `content_warning` 含 `suicide` / `sexual_abuse` / `grief` / `terminal_illness` 的书（**专门验一本讲临终或丧亲的书**，如《当呼吸化为空气》），且界面**不出现**「你可以自己判断是否阅读」这类把决定权交回用户的选项。再在那一问里选「一起看」（`include_heavy`）重跑，五件事同时核：① **`grief` / `terminal_illness` 的书恢复出现在候选池**；② **`suicide` / `sexual_abuse` 的书仍然不出现**——这一条就是 7.4 那条不对称规则的验收，**两类全恢复 = 不对称被补齐了，判失败**；③ 控件是**二选一**（`一起看` / `先不用`），不是勾选框，初始态落在 `先不用`；④ **按节点收窄，不按词收窄**：那句问题所在的容器必须带 `data-heavy-question`，断言 **`[data-heavy-question]` 子树内「自杀」「自伤」「性暴力」三个词全 0 命中**——问题只承诺了「临终或丧亲」，容器里就不许出现比它更重的词。**不要靠「豁免『自杀』这个词」来过验收**：那样文案一旦被改回点名自杀的版本，断言照样是绿的，而那句话会承诺代码不会兑现的东西（`include_heavy` 不豁免 `EX-trauma`）。危机条不在该子树内，它的措辞完全不受影响；⑤ 退出重进诊断，**上一次的选择没有被带过来**（每次重新问）（验证 7.4 的内容安全两条是硬过滤、且不对称 / §17）。
20. 第 3 屏只填 3-a、3-b，跳过 3-c / 3-d / 3-e → 仍正常出结果，不降档、不弹补充提示、不出现「请完善信息」（验证 7.1.1 跳答走「整条剔除 + 权重归一化」，**不是**代入中性值）。
21. 检查任一结果卡片：档位文字只出现「高度契合 / 较为契合 / 换个角度」三者之一；第 5 位卡片必须显示「换个角度」；卡片上有 `match_brief`（≤28 汉字）或降级后的「命中了：…」短语，不留占位符；全页检索 `强烈推荐|你可能喜欢|猜你喜欢` 命中为 0（验证 7.2 两条硬规则 / 7.3 固定显示名）。
22. 选「情绪与自我」完成诊断 → 结果页底部出现危机资源条，文案与 17.1 逐字一致；滚动到底部仍在；页面上不存在关闭按钮；点开资源页 → 列出至少 3 条资源，每条含机构 / 地区 / 号码 / 最近核对日期，页底有「失效请提 issue」入口（验证 17.1 / P0-16）。
23. 选「习惯与行动」完成诊断 → 结果页顶部出现一行说明，文案与 10.3 定稿一致；该行使用信息色而非警示色；全页检索 `抱歉|暂不支持|资源缺失|敬请期待` 命中为 0；折叠后「需自备电子书」标签仍在每张卡片上（验证 P0-17）。

24. 在第 2 屏勾选 3 项 → 同屏下方出现一行「这些里面，哪个是你现在最想先解决的？」→ 检查五件事：**不预选任何一项**、措辞里**没有「最严重」**、**不跳转不新增屏**、**不可跳过**（不选则无法进入下一屏）、**不按勾选顺序自动带入**。再找一本「主诉标签未命中但难度篇幅都合适」的书 → 其档位必须是「换个角度」，**哪怕它的分数已经过线**（验证 P0-1 / 7.3 封顶规则 / 7.4 目标值整数判据）。

**通过标准**：24 步全通 + 第 5 / 13 / 17 / 19 / 21 / 23 步的检索结果为空 + 第 3 步无百分比、卡面无 S1、摘要条逐字回引仅一处 + 第 18 步 5 个领域全部达标 + 第 19 步**不对称成立**（临终/丧亲恢复、自杀/性暴力仍不出现，且 `[data-heavy-question]` 子树内「自杀」「自伤」「性暴力」三词零命中；**前置不成立时该步记「未验证」，不得记「通过」**）+ 第 20 步无降档 + 第 22 步危机资源条不可关闭 + 第 24 步封顶生效。

## 附：本文与下游文档的契约关系

### 附.1 数值归属与判据（v1.7 新增）

本项目已经出现过 9 处枚举 / 数值漂移，全部不是「谁不认真」，而是**同一个数字在三份文档里各有一份「记忆版」**——而记忆版和文档版在冲突之前看不出任何差别，只有对撞那一刻才暴露。归属制的作用不是分清谁错了，而是**让对撞提前到「谁该查哪儿」这一步**。

| 类别 | 唯一出处 | 例子 |
|---|---|---|
| **视觉数值** | `UIUX.md` | 行数、px、截断方式、色值、圆角、动效时长、z-index |
| **内容数值** | `SPEC.md` | 字段取值、枚举、项数、字数上下限、阈值、权重 |
| **功能范围与行为** | 本文（PRD） | 做什么、不做什么、EARS 验收、RICE 排序 |
| 工作量和商业指标 | 本文（PRD） | 数据工时、成功指标、库规模与配比 |

**引用约定（v1.16 新增，机械可判）**：**裸 `§N` 一律指本文自己的小节**；引用其他文档必须带文件名（`SPEC §N` / `UIUX §N` / `ARCH §N`）。

理由不是洁癖：裸引用**不悬空、不报错，只是读到的人找不到**。PRD 没有 §6.1（§6 是「我们的差异化」，无子节），所以「五组全用 §6.1 的枚举值」这种句子在本文里指向一个不存在的地方——**而它读起来比 `SPEC §6.1` 更顺，所以更容易被写出来**。本文已修过两处（六条硬约束 ②、附.1 的缺口实例）。

复核命令（数条目，不猜语义）：

```
grep -n "§" docs/PRD.md | grep -v "SPEC §\|UIUX §\|ARCH §\|本节\|本文"
```

**输出里剩下的裸 `§N` 如果指向本文且本文确实有这一节 → 合法**；指向别处却没写文件名 → 补文件名。**这条检查的判据是「句子里的 `§N` 能不能在本文找到对应标题」，不是「有没有出现 `§`」**——后者会把所有合法引用都算成违规，而一个会误报的检查最后一定被删掉。

**归一化那一步不能省**：同一件事本文一度有三种写法（`SPEC §5.2` / `` `SPEC.md` §5.2 `` / 裸 `§5.2`），而解析器只认第一种——**第三种会被当成自引，第二种会被当成「文件名后面跟了个裸引用」**。三种写法都合法的时候，检查看起来在跑、实际只覆盖了三分之一。现已全部归一到 `SPEC §N`。

**本文自查命令（数条目，不猜语义；括号里是当前的期望值）**

```
grep -c "^| P0-" PRD.md                       # 17（与 SPEC §2.1 同编号，无增补）
grep -c "R3" PRD.md                           # 1（且必须是那条「旧编号已作废」说明）
grep -cE "F[1-6]" PRD.md                      # 0（编号体系只在 ARCH）
grep -c "data-heavy-question" PRD.md          # 2（断言 + 通过标准各一处）
grep -c "include_heavy_shown" PRD.md          # 1（埋点三分口径）
```

**用这些数字的姿势**：**数字变了就去看原文，不要直接信「少了就是删了」。** 例如 `data-heavy-question` 从 2 掉到 1，可能是两处被合并成一句（合法），也可能是断言被改写成了变体拼写（不合法）——**而从 2 掉到 0 时，多数人只会读成「这块不用管了」。** 一条会衰减的自查命令，比没有自查更容易骗人。

**判据只有一条**：**这个数字改了之后，需要打开页面看渲染结果才能判断对不对吗？**
需要 → 视觉数值（归 UIUX）；不需要（改完是内容侧重新写一遍）→ 内容数值（归 SPEC）。

**为什么必须写判据而不只写归属**：只写归属，下次还是会为一个**新字段**重新争一次——因为归属表里没有它。判据是唯一能覆盖「表里还没有的那一行」的东西。

**但归属制只防「漂移」，防不了「缺口」——这两件事必须分开查。**

| 类型 | 是什么 | 会不会被对撞抓到 |
|---|---|---|
| **漂移** | 同一件事写了两遍，两遍不一致 | **会**。两份文档一碰就响 |
| **缺口** | 一件事**没有任何一处写全** | **不会**。没有任何两份文档互相矛盾，所以对撞永远不发生 |

本项目的第一个缺口实例：`answers` 只列了 5 个键，而问卷第 3 屏有 5 组 chip，第 5 组没有键——**三份文档当时各自都自洽**，是回头核 `SPEC §6.1` 才照出来的。所以一致性审计要**两条并列**，不能只做一条：对撞抓漂移，**覆盖抓缺口**。覆盖检查只有一种做法：**从下游往上游反查**——拿一个具体字段 / 键 / 枚举值，问「它从哪来、谁定义、谁消费」，三问答不全就是缺口。
