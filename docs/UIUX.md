### 本文阅读规则

- 每个视觉决策后都写了理由。没有理由的数值请当成 bug 报给我。
- 所有对比度由脚本按 WCAG 2.1 相对亮度公式实算（`L = 0.2126R + 0.7152G + 0.0722B`，sRGB 线性化），不是目测。凡是写「视觉上没问题」的地方一律视为未完成。
- 颜色一律通过 Token 引用。文中出现的十六进制值是**色阶定义值**，本身即 Token 的源，不是硬编码。
- **数值归属（文档契约）**：**视觉数值**（行数、px、截断方式、色值、圆角、动效时长、z-index）以**本文**为唯一出处；**内容数值**（字数、项数、字段取值、阈值）以 **SPEC** 为唯一出处。本文引用内容数值时只写「指向 SPEC 的哪一处」，不自行推导 px 与行数；PRD 侧对应的写法是「行数归 UIUX、字数归 SPEC」。这条是在一次「1 行 / ≤30 字」的算术冲突之后加上的：**同一个字段挂两个数字、两个出处，最后一定有人在某个场合只引用其中一个。**
  - **Carve-out（team-lead 2026-10-18 加的）**：**互相推导的一对数必须写在同一个出处的同一句里。** 例「2 行」是视觉值、「≤38 字」是内容值，但两者互为因果——拆到两份文档里，下一个改字号的人只会改一边。**所以这对数定义在 SPEC §5.2，本文只引用、不重写 38 这个数**（见下 S2 规格表的「这对数是引用」一句）。除此之外的 px / 行数 / 圆角 / 动效仍归本文。
- **跨文档引用必须带文件名**（`PRD §7.1` / `SPEC §7.1` / `ARCH §3.8`）；**裸 `§N` 只允许指向本文自己的章节**（v1.15，team-lead 跨四份文档跑节号检查时查出来的）。
  - 为什么：**同一个数字在三份文件里指三个地方，而阅读器不会报错**——ARCH 里裸写 `§3.9` 指 ARCH、SPEC 里裸写 `§3.9` 也指 ARCH、本文裸写 `§7.1` 实际指 PRD。它不悬空、不报错，**只是读到的人找不到**。本文 §7 只有 `## 7. 核心页面信息架构` 与 `### 7.0`，**没有 7.1 / 7.3**，那两处曾经就是死引用。
  - 这和「判断权要交给能机械判定的东西」是同一件事：**文件名前缀可 grep，"读者应该知道这是指哪份"不可 grep。**
  - 复算（行号会漂，命令不会）：`grep -nE "§ ?[0-9]" docs/UIUX.md | grep -vE "PRD §|SPEC §|ARCH §"` → 剩下的裸引用逐条确认是否指向本文；**凡是序号在本文里不存在的，就是一条"读得到、找不到"的死链**。

## 1. 设计调研

选 5 个对象，逐个说清「借什么、不借什么」。选择标准：3 个为同赛道（阅读器 / 书库），2 个为跨赛道但视觉语言值得偷。

### 1.1 Readest（开源 EPUB 阅读器，同类直接竞品）

- **排版**：阅读区居中单列，控制栏在上下边缘淡入淡出，正文周围几乎没有常驻控件。
- **留白**：正文左右留白随窗口宽度变化但行宽恒定（约 34em），这是阅读器最关键的一条。
- **色彩**：主题切换是「改变纸色」而不是「改变品牌色」——同一套正文排版换 4 种底色。
- **信息密度**：极低，阅读态下屏幕上只有文字。
- **借**：行宽恒定（不是百分比宽度）、纸色作为阅读模式而非品牌主题、控制栏自动隐退。
- **不借**：它的书架页是「封面网格 + 进度环」，在上千本且多数无封面的前提下会塌成一片灰。这正是我们要解决的问题，不是要抄的对象。

### 1.2 Kavita（自建漫画/书库服务器）

- **排版**：卡片网格 + 密集元数据标签，侧边筛选栏。
- **色彩**：深色为主，缩略图承担全部视觉重量。
- **信息密度**：高，一屏 30+ 条目，适合「我已经知道自己要什么」的用户。
- **借**：筛选与排序的控制区做成独立侧栏/抽屉，不与列表混排。
- **不借**：它的信息架构假设用户「先有目标再找书」。我们是反的——用户先有困境，书是后出现的。卡片密度必须降下来给理由腾位置。

### 1.3 Notion（跨赛道，偷信息层级）

- **排版**：靠字号 + 字重 + 灰度三件事建立层级，几乎不用色块。
- **留白**：段落间距 vs 行内间距有明确比例（约 1:0.35），层级不靠分割线。
- **色彩**：中性色承载 90% 的界面，色只出现在标签与状态。
- **借**：**用灰阶承担层级**——我们的推荐理由有三段，三段之间用灰度与缩进而非三条分割线区分。这条直接决定了我们敢不敢在卡片里放三段文字。
- **不借**：Notion 的「图标 + emoji 页面封面」体系。我们不用 emoji，也不用彩色页面图标。

### 1.4 Are.na（跨赛道，偷「无图也能有秩序」）

- **排版**：内容块高度不一，靠严格的间距网格维持秩序感；没有图片的块用纯文字排版撑住，不留灰坑。
- **色彩**：白底 + 一条极细灰线分隔，色只用在链接。
- **借**：**「没有图，就把字排好」**——这直接支撑了第 7.0 节的书脊卡决策：缺封面时不是放占位图，而是把书名排版当成设计对象。
- **不借**：它的瀑布流。我们要固定行高，否则用户无法用「第三张卡」这种位置记忆来定位。

### 1.5 Penguin 三段式书封（1935–1947）

- **排版**：2:3 比例，上下两条水平色带夹住中间书名区，品类 / 书名 / 作者三段式网格，左侧留一条书脊色。
- **色彩**：按品类分配固定色（橙=小说、绿=犯罪、深蓝=传记……），**颜色有语义**。
- **借**：三段式网格 + 左侧书脊 —— 这是「无封面也能被识别」的最成熟解法。
- **不借**：**按品类分配颜色**。Penguin 用 10 个色对应 10 个品类，我们有几百到上千本书、几十个品类，颜色会被稀释成噪音（详见第 7.0 节的实测与结论）。

### 1.6 MUJI（跨赛道，偷克制）

- **排版**：单一字族、字号阶梯极窄（正文与标题只差 2–4px），靠字重和留白分层。
- **色彩**：几乎全是纸白 + 灰 + 一点点木色，商品图是唯一饱和色。
- **借**：**字号阶梯收窄**。我们不用 48px 大标题，界面主标题最大 34px，靠间距建立区块感。
- **不借**：MUJI 的极度去信息化。我们必须在卡片里塞下理由、档位、可用性三件事，纯克制会牺牲可判断性。

### 1.7 调研结论（三句话）

1. 阅读器本体要「消失」（Readest），但推荐列表必须「在场」（Kavita 的密度要砍一半、理由要加一倍）。
2. 层级靠灰阶与间距，不靠色块和分割线（Notion / MUJI）。
3. 缺封面不是缺图问题，是排版问题（Are.na / Penguin）。

## 2. 设计定位与三条原则

### 定位一句话

> **一个把「为什么是这本」放在封面之前的阅读诊断器——页面像一份问诊记录，不像一间书店橱窗。**

这句话决定了三件事：推荐卡里理由的空间大于封面；界面不展示「猜你喜欢」这类橱窗话术；每一屏都回答「下一步做什么」，而不是「我们有多少书」。

### 原则一：理由先于封面

任何一本书出现的地方，**先给一句能被人读懂的判断，再给图像**。没有合法封面时，用书名排版承担识别功能，**不摆灰色占位方块**。

- 取舍示例：推荐卡左侧的图像区只占 25% 宽度，且在小屏（<640px）直接隐藏图像、理由上移。书店类产品不会这么做，我们做。
- 可检验标准：把全站封面图关掉，界面仍然每一屏都能判断「这本书讲什么、和我什么关系」。

### 原则二：一屏只有一个决定

每张推荐卡只推动**一个**主操作（读 / 导入我的文件 / 查看来源），其余动作收进「更多」。不做三个并列按钮。

- 理由：推荐流的任务不是「管理书籍」，是「决定读不读」。并列按钮会让用户停下来比较，而不是往前走。
- 取舍示例：「加入书架」永远是次级图标按钮，不是并列的描边按钮。即使它对我们后续的留存更有利。

### 原则三：精确是有代价的

凡是系统无法稳定保证的数值，一律降级为**档位、文字或区间**，不做假精度。

- 具体落地：符合度不给百分数、推荐列表不显示序号、导入不显示假进度条（本地解析要么瞬时要么给真实字节进度）、规则打分不暴露权重。
- 理由：几百到上千本书的规则打分是**序数**，不是基数。0.83 与 0.79 的差值不构成语义，但一旦写成「83%」，用户会开始追问这个差值，而我们答不上来。

## 3. 色彩系统

### 3.1 主色：沿用「松烟绿」#2F6449，但不沿用它的用法

上一轮已定 `#2F6449`，我重新验算后**采纳**，理由与实测如下：

| 候选 | 值 | 白底作文字 | 白字其底 | 判断 |
|---|---|---|---|---|
| 松烟绿（采纳） | `#2F6449` | 6.91:1 通过 AA | 6.91:1 通过 AA | 双向对称达标，且仍明显是绿色不是黑 |
| 豆瓣绿（否决） | `#2E8B57` | 3.79:1 **不通过** | 4.20:1 不通过 | 文字用法直接出局 |
| 墨绿（否决） | `#1F3D2E` | 11.17:1 通过 | 11.17:1 通过 | 对比度过高，屏幕上读作「近黑」，绿色感消失，品牌识别失效 |

**但用法要改**：`#2F6449` 只做**交互与状态色**（主按钮、链接、焦点环、高度契合档位），不做大面积品牌底色。理由：这是一个 Product 寄存器的工具，绿色的职责是「指向可点的东西」。一旦把它铺成页面底色或深绿 Hero，它就变成了营销页，与定位冲突。

**关于「松烟」这个命名**：它暗示低饱和的灰绿。这与我们中性色阶的设计联动——中性色不是纯灰，而是带极低绿度（色相约 140，chroma 极低），这样绿主色压在页面上不会显得是「贴上去的」。这也是我们**不用奶油米色底**的替代方案（见 3.2 与第 12 条禁令）。

**Semantic（只有三个）**

| Token | 浅色 | 暗色 | 浅色底 | 用途 |
|---|---|---|---|---|
| `--warn` | `#8A5A0B` | `#DCA95C` | `#FBF4E6` | 导入格式可疑、笔记未同步 |
| `--danger` | `#992B23` | `#F0968A` | `#FBEFED` | 导入失败、删除确认 |

**为什么没有 success 色**：品牌色本身就是绿色。再引入第二种绿会让用户在两块绿之间做无意义的区分（「这是成功了还是这是主按钮」）。成功状态一律用 `brand-600` + `CircleCheck` 图标 + 文字，不新增色相。这是主动删减，不是遗漏。

**为什么没有第 4、5 个语义色**：语义色每增加一个，界面里出现饱和色的概率就上升一档。我们有 3 个真实需要用户决策的异常态（警示/错误/信息），够了。

### 3.6 色彩使用铁律

1. 每屏可见 `--accent`（即 brand-600/300）**不超过 2 处**。推荐结果「最多 5 本、其中只有 1 本 `strong`」（PRD §7.2）让这条规则天然成立：只有 `strong` 档用 brand 色，5 张卡里最多 1 处品牌色 + 1 处主按钮。若未来放宽为 8 本，则**只给第 1 张卡加 brand-400 描边，其余回归中性**——不降级档位色（降级会让档位失真）。
2. 禁止紫→粉渐变、禁止任何 Indigo→Pink 组合、禁止渐变文字（`background-clip: text`）、禁止装饰性毛玻璃。
3. 所有颜色必须走 Token。唯一允许的裸值是 `#000`/`#FFF` 的 `rgba()` 遮罩。
4. 饱和色面积上限：单屏不超过 5%。
5. **只有 1 个强调色**（ARCH §13 同名要求）。「多强调色会让三档失去区分度」这个担心在实测下不成立，但相反的风险成立：**颜色本来就不足以区分三档**（见 §8.2），所以档位靠形状编码，强调色数量与档位无关。

### 3.7 划线：v1 单色（`--highlight`）

**结论（team-lead 2026-10-18 第二次裁定，定稿）**：v1 只做**一种划线色**。四色 + 线型方案完整备档在本节附录，**不启用**。

单色不是因为四色做不出来——四色方案已经过三轮验算，连它最硬的技术问题（等亮度 → 只能靠色相 → 红绿色盲下松绿与褐玫重合）也已经用「线型为第一编码」解决了。**不用它的原因是它没有语义。**

| 问题 | 四色方案给出的答案 | 这个答案意味着什么 |
|---|---|---|
| 用户怎么知道「疑问」和「重点」哪个该用哪个色 | 色板**不命名** | 用户不知道，只能试 |
| 用户事后怎么找回「所有疑问」 | 笔记页**不按颜色筛选** | 找不到 |
| 划线时怎么决定用哪个色 | 默认落 `hl-1`，换色要点第二次 | 按心情随手点 |

三条合起来，**剩下唯一作用是「视觉上有变化」**。为这个变化要付出：多一套色令牌、多一组线型、阅读器里多一个会打断阅读的交互。**没有语义的四种颜色是装饰；而带无障碍成本（哪怕已缓解）的装饰，是最不该上线的那一类。**

反过来——**如果哪天它们真的有语义了**（疑问 / 重点 / 共鸣 / 行动），那是一个**真功能**，需要一套自己的设计：名字在哪儿显示、读到一半怎么选而不打断、笔记页怎么分组。那是 P1 的活，不是 P0 的活。

**流程记录（写下来是为了不再重开）**：四色曾两次被提出、两次被否（v1.3 一次，v1.6 一次），v1.8 第三次确认单色。这条裁定之后，**任何人再提四色，必须先改 SPEC 的划线条款**，否则视为越过契约。设计侧不再自行发起第四次。

**为什么 token 里不留 `hl-1` 这个编号**（命名决定，容易被"顺手补一个"破坏）：v1 只有一个划线色，`color.highlight.rule` / `tint-light` 已经自解释。**留一个 `hl-1` 等于给未来留一个空槽位，而空槽位会被读成「原来有四组，现在缺了三组」**——下一个人会去找那三组，或者自己替它想出用途。**一个名字只要存在，就会有人替它想出用途**（同 §3.6 `primary_hit` 的理由）。所以键名不带编号；将来真要做四色，是一次带语义的重新设计，不是把编号补回来。

| Token | 值 | 用途 |
|---|---|---|
| `--highlight`（= `color.highlight.tint-light`） | `rgba(103, 153, 130, 0.14)` | 浅色纸上的划线底色 |
| `--highlight` 暗色版（`color.highlight.tint-dark`） | `rgba(103, 153, 130, 0.20)` | 暗色纸上的划线底色 |
| `--highlight-rule`（`color.highlight.rule`） | `#4E7A65` | 浅色 2px 下边线 |
| `--highlight-rule` 暗色版（`color.highlight.rule-dark`） | `brand-300` `#93B7A4` | 暗色 2px 下边线 |

**四种纸色上的实测（正文 `neutral-900` `#2A2F2C`，14% 叠加）**：

| 纸色 | 叠加底 | 正文对比 | 边线对纸底 | 边线对叠加底 | 叠加底 vs 纸底 |
|---|---|---|---|---|---|
| `#FFFFFF` 纸白 | `#EAF1EE` | 11.88:1 | 4.89:1 | 4.26:1 | **1.147:1** |
| `#FAFBFA` 淡绿纸 | `#E5EDE9` | 11.43:1 | 4.71:1 | 4.10:1 | **1.149:1** |
| `#F3EEDF` 米纸 | `#DFE2D2` | 10.35:1 | 4.22:1 | 3.71:1 | **1.135:1** |
| `#E9F0E9` 浅绿纸 | `#D7E4DB` | 10.39:1 | 4.21:1 | 3.73:1 | **1.131:1** |
| `#16191A` 暗色纸（20%） | `#26332F` | 10.83:1 | 5.98:1 | 5.98:1 | 1.344:1 |

**这张表里最重要的不是正文对比（都是 10+，闭眼都过），是第 6 列。** 叠加底与纸底只差 **1.13–1.15:1**——人眼几乎看不见。所以「这里有划线」这件事**不可能靠底色传达**，必须靠 2px 下边线（3.71–4.89:1，达 WCAG 1.4.11 图形 3:1 基线）。边线不是装饰，是功能。任何"为了更轻，把边线去掉"的优化都是在删功能。

**底色承担"存在"，边线承担"存在得够清楚"，两者都不承担分类。** 分类靠用户自己写的笔记，不靠颜色。

**用户想区分用途怎么办**：靠笔记文字。划线气泡里「写笔记」是唯一的第二条动作，笔记页按时间倒序展示原文 + 笔记正文（P7）。真要做"待办 / 疑问"分类，那是 v2 的标签系统，不是 v1 的调色板。

### E. 一条技术事实（纠正一个流传的说法）

有说法是「`tone` 字段现在不带，以后加要做 Dexie 迁移，所以首次建表就该带上」。**这条不成立。**

IndexedDB 存的是对象，**给对象加一个不建索引的属性不需要任何迁移**：version 不用升，`onupgradeneeded` 不用跑，旧记录读出来就是 `tone === undefined`。只有**加索引**或**改 `keyPath`** 才需要升 version——而"按颜色筛选"正是要加索引的那件事。

也就是说：**迁移成本发生在"四色变成功能"那一刻，而不是"字段存在与否"这一刻。** 先占个位省不掉迁移，只会让现在多带一个没人用的字段。所以 v1 的 `Annotation` **不设 `tone`**（`types-draft.ts` L558 已是这个写法）；真要开功能时，加字段 + 加索引 + 数据回填在同一次升级里做完。

### 3.8 与 ARCH §13 的 Token 命名桥接

ARCH 期望的变量名与本文命名不同，Phase 3 只能用一套。做法是**别名层**：本文的语义名是唯一源，ARCH 期望名作为别名指向它，两套都能用，不会漂移。

| ARCH 期望名 | 指向本文 Token | 说明 |
|---|---|---|
| `--color-ink-1` … `--color-ink-9` | `neutral-950` `900` `800` `700` `600` `500` `400` `300` `200` | 文字阶，1 最深 |
| `--color-paper-0` … `--color-paper-3` | `neutral-0` `25` `50` `100` | 背景阶，0 最亮 |

## 4. 字体系统

### 4.1 中文正文：衬线还是黑体？（这是本产品最关键的排版取舍）

结论：**双轨制，按「读」与「用」分工**。

| 场景 | 字族类型 | 字号 | 理由 |
|---|---|---|---|
| 阅读器正文 | **衬线**（宋体系） | 18px 起，5 档可调 | 长文（>500 字/屏）连续阅读时，宋体的横细竖粗在字与字之间建立了更强的边界，降低「字块粘连」；黑体在 20px 以下的密集长文中呈现均匀的灰面，眼睛失去落点，实测容易跳行。这是中文排版与拉丁排版最大的差异之一：拉丁无衬线（如 Inter）在大字号下依然有清晰的字臂与开放孔洞，中文黑体没有这些结构特征。 |
| 阅读器**标题**（章名） | 衬线 | 22–28px | 与正文同族，章名不该像 UI 弹窗。 |
| 界面层全部文字 | **黑体** | 12–34px | UI 文字的信息效率优先。宋体在 12–14px 屏幕上「发灰」（细横笔画被抗锯齿吃掉），且数字与拉丁在宋体里字重偏轻，出现在按钮上会显得禁用。 |
| 数字 / 序号 / 进度 | **等宽** | 12–14px | 阅读进度、页码、字数、页数需要纵向对齐；比例字体下 `111` 与 `888` 宽度不同会让进度数字跳动。 |

**一句话**：读的字用宋，用的字用黑，跳的数用等宽。

### 4.2 三个字族 + 一个反常识决定：不自托管中文 Webfont

| 角色 | 字体栈 | 许可 | 是否自托管 |
|---|---|---|---|
| `--font-read`（阅读衬线） | `"Source Serif 4", "Noto Serif SC", "Songti SC", "SimSun", serif` | OFL 1.1 | 拉丁自托管 subset，中文**不加载** |
| `--font-ui`（界面黑体） | `"Inter", "Noto Sans SC", "PingFang SC", "Microsoft YaHei", system-ui, sans-serif` | OFL 1.1 | 拉丁自托管 subset，中文**不加载** |
| `--font-mono` | `"JetBrains Mono", ui-monospace, "SFMono-Regular", monospace` | OFL 1.1 | 自托管 subset |

**为什么中文不加载 Webfont**（这是工程约束反推的设计约束，必须写清，否则前端会顺手引 Google Fonts）：

- Noto Serif SC 全量单字重 woff2 约 8–10 MB。本产品是 local-first、离线可读的开源应用，首屏拉一个 10 MB 的中文字体违背产品定位。
- 用 unicode-range 做中文 subset 需要按书目文本做动态切分，在「用户自带 EPUB」的场景下文本不可预知，subset 覆盖率必然残缺，会出现「半本书用 Webfont、半本书回退」的字体跳变——比统一用系统字体更糟。
- 因此：**中文一律走系统字体栈**，用 `font-family` 顺序保证各平台最佳默认（macOS/iOS 的宋体是 Songti SC，Windows 是 SimSun/中易宋，Android 需回退到 sans）。
- 拉丁与数字**自托管**：Source Serif 4 + Inter + JetBrains Mono 各 2 个字重的 latin subset，合计约 40–60 KB（woff2），这是可接受的，并且解决了「中文系统字体里拉丁字形难看」这个最刺眼的细节。

**关于拒绝默认系统字体直出**：我们没有「直出系统字体」——拉丁与数字是有明确选择的三个字族，中文是经过论证的降级方案。这两件事不同，需要在验收时说清。

### 4.3 字号阶梯

界面（固定 rem，步进比 1.13–1.25，符合 Product 寄存器）：

| Token | px | rem | 行高 | 字重 | 用途 |
|---|---|---|---|---|---|
| `--text-2xs` | 11 | 0.6875 | 1.4 | 510 | 徽标字、档位标签 |
| `--text-xs` | 12 | 0.75 | 1.5 | 400/510 | 元数据、辅助说明 |
| `--text-sm` | 13 | 0.8125 | 1.55 | 400/510 | 卡片正文、表单标签 |
| `--text-base` | 14 | 0.875 | 1.6 | 400 | UI 默认正文 |
| `--text-md` | 16 | 1 | 1.55 | 400/590 | 正文强调、输入框 |
| `--text-lg` | 18 | 1.125 | 1.45 | 590 | 卡片标题（大屏） |
| `--text-xl` | 22 | 1.375 | 1.35 | 590 | 区块标题 |

| 档 | px | 行高 | 每行字数（34em 列宽） |
|---|---|---|---|
| 特小 | 16 | 1.85 | 约 38 字 |
| 小 | 17 | 1.8 | 约 36 字 |
| **默认** | **18** | **1.8** | **约 34 字** |
| 大 | 20 | 1.75 | 约 30 字 |
| 特大 | 22 | 1.7 | 约 28 字 |

阅读列宽用 `max-width: 34em`（随字号变化，始终约 34 字/行）。中文舒适行宽为 25–38 字，34 字落在上四分之一——偏宽但仍在舒适区，因为我们要容纳「长段落连续阅读」而非「短句扫读」。**不用百分比宽度**，否则大屏会变成一行 80 字，眼睛回扫失败。

### 4.4 字距、行高、标点挤压、首行缩进

| 项 | 值 | 理由 |
|---|---|---|
| 正文（14–18px）字距 | `0` | 中文本身是等宽方块字，加字距会破坏字群节奏 |
| 小字（11–13px）字距 | `0.01em` | 极小字号下略微放开，避免笔画粘连 |
| ALL CAPS（英文徽标、`EPUB`/`TXT`） | `0.06em` | 大写字母天然拥挤，必须放开 |
| 标题（≥22px）字距 | `-0.01em` | 中文大字号的默认间距偏松，收紧后更整体 |
| 阅读正文行高 | 1.8（5 档间 1.7–1.85） | 中文无升部/降部，行高需显著大于拉丁的 1.5 才不压抑 |
| 段间距 | `0.75em`（相对正文） | 小于一行、大于半个字，视觉上成组但不断裂 |
| 首行缩进 | 默认 `0`，可开关 `2em` | 中文出版惯例是缩进 2 字；但电子阅读里段间距 + 缩进会双重分隔。默认用段间距，缩进作为用户选项 |
| 标点挤压 | `text-spacing-trim: trim-both`；回退 `text-autospace: normal` | 句号、逗号、引号后的空白在中文里应压缩，否则正文出现「洞」。Chromium 123+ 支持 `text-spacing-trim`，Safari/Firefox 不支持时退化为不压缩（可接受，不做 JS polyfill） |
| 悬挂标点 | `hanging-punctuation: allow-end`（支持则启用） | 段末标点悬挂避免最后一行「孤字 + 标点」 |
| 中西混排 | `text-autospace: normal` | 中英文之间自动加 1/4 空格，比手工敲空格正确 |
| 数字 | `font-variant-numeric: tabular-nums` | 进度、页码、统计数字纵向对齐 |

### 4.5 字重系统（三级，不加载全部字重）

| 级 | 值 | 用途 |
|---|---|---|
| Read | 400 | 正文、说明 |
| Emphasize | 510 | 小标题、按钮文字、徽标、表头 |
| Announce | 590 | 页面标题、卡片标题、数字强调 |

中文系统字体多数只有 Regular/Medium/Bold 三档，因此 400/510/590 在中文侧实际落到 400/500/600，视觉差在可接受范围。**禁止使用 700+ 做强调**：中文 Bold 在 14px 下会糊成黑块。

## 6. 图标系统

### 6.1 锁定方案

| 项 | 决定 |
|---|---|
| 库 | **Lucide** |
| 版本 | **1.0.x**（2026-03 发布首个稳定大版本，Vue 包已由 `lucide-vue-next` 更名为 `@lucide/vue`；锁定 `1.0.x` minor，不自动跨 minor 升级） |
| 许可 | **ISC**（宽松，允许商用与修改，保留版权声明即可） |
| 图标总数 | 1,600+，本项目取用 38 个 |
| 引入方式 | `import { Search, Upload } from '@lucide/vue'` —— 具名导入，构建期 tree-shaking |
| 统一参数 | `stroke-width = 1.75`（库默认 2，我改细 0.25）、`stroke-linecap = round`、`color = currentColor` |
| 尺寸 | 16px（行内文字旁）/ 20px（按钮内）/ 24px（独立导航）/ 32px（仅空状态插画位） |

**为什么把 stroke-width 改成 1.75**：Lucide 默认 2px 描边是它最容易被认出的特征，也正因为太常见，直接用会带出「AI 生成的模板产品」观感（社区已有公开批评：Lucide 被大量模板与 AI 生成组件默认采用，导致产品长得一样）。统一改细到 1.75 并不会损失可读性（16px 下仍是 1.75 物理像素，非小数渲染），但让整套图标轻一档，与「松烟绿 + 宋体」的气质一致。`@lucide/vue` 1.0 提供 Provider，可全局设置，无需每次传参。

**为什么不是 Heroicons / Phosphor / Tabler**：Heroicons 面型图标视觉重量偏大，与我们偏轻的整体色调冲突；Phosphor 多字重会诱导团队在不同字重间乱选；Tabler 的圆角半径偏大。Lucide 的几何简洁性最匹配「工具」定位。但**接受「不够独特」这个代价**，独特性由书脊卡与排版承担，不由图标承担。

**GitHub 图标的例外（重要）**：Lucide 1.0 **移除了全部品牌图标**（商标压力）。开源项目必须有 GitHub 入口，因此 `GitHub` 图标从 **Simple Icons（CC0 1.0）** 单独内联一个 SVG path，仅此一个例外，其余全部来自 Lucide。这条写进验收清单，避免实现时满项目搜 `Github` 找不到。

- **禁止**使用 Lucide 图标字体（`lucide-font`）。字体方案在 local-first 产品里控制不了子集，且失去 `currentColor` 的灵活性。
- 预期体积：38 个图标 × 约 300–400B = 约 12–15 KB（未压缩），gzip 后约 4–6 KB。
- 单一入口文件 `src/ui/icons.ts` 统一 re-export，其他组件从它引入。目的不是省体积，而是**让「本项目用了哪些图标」可被一个文件检索**，防止混入第二个图标库。

### 6.4 禁止

- 禁止 emoji 作为功能图标（U+1F300–1F9FF、U+2600–26FF、U+2700–27BF 全域）。
- 禁止混用第二个图标库（除 `github` 一例）。
- 禁止 `fill` 型与 `stroke` 型在同一界面混用。
- 禁止给图标加彩色背景圆块（图标 + 彩色圆底是模板味最重的组合之一）。
- **符合度指示器（3 个方块）与书脊卡（书名排版）不是图标**，属自绘 UI 组件，不在此体系内，也不得改用图标库实现。

## 7. 核心页面信息架构

### 7.0 先说清一个跨页面的问题：核心库没有封面

这是本项目最大的视觉风险，先单独解决。

**现实**：核心库口径为 **首发 300 / v1.0 前 800 / 架构上限 3000**（PRD §10）。这些书绝大多数为有版权的在版书，**没有可合法分发的封面图**；ARCH 的 `Book` 契约里**没有 `cover_url` 字段**。也就是说：**书脊卡不是 fallback，它就是 v1 的封面系统**。用户自己导入的 EPUB 若在 OPF 里带封面，则用真封面（那是用户本地文件，不涉及分发）。

如果放灰色占位方块，推荐页会变成一片墓碑；如果去抓封面，法律风险由开源项目承担，不可接受。

**上一轮提出的「文字封面」方案（Penguin 三段式，2:3，6 色 hash）我做了实测评估：**

| 检查项 | 结果 |
|---|---|
| 6 色方案的文本对比度 | **全部通过**（白字在其上 6.91–10.14:1）。所以「不达标」不是否决理由 |
| 首发 300 本 / 6 色 | 每色仅 **50 本**。颜色立刻失去语义，只剩装饰；而现行 3 tone 方案（300 / 3 = 每 tone 约 100 本）在 5 张卡同屏时**按鸽巢必然出现重复**，连「相邻卡片不粘连」都做不到——所以 tone 只能当纹理，不能当标识 |
| 一行 5 张卡的视觉效果 | 5 个高饱和色块并排，界面主色（松烟绿）被淹没，品牌消失 |
| 小尺寸可读性 | 列表卡图像区约 56×84px，三段式网格里的品类与作者字需 <8px，**不可读**；Penguin 的三段式只在 ≥140px 宽时成立 |

**最终判断：有条件采用，改名「书脊卡」，并做三处改造。**

1. **废弃 6 色 hash，改为单色阶 3 tone**（`brand-100` / `neutral-100` / `brand-50`），按书籍 id 的 hash 取模 3 分配。理由：颜色不再区分品类（几百本之后就已做不到），只做「相邻卡片不粘连」的微弱节奏。3 个 tone 全在低饱和区，5 张卡并排仍是一面安静的墙，松烟绿不会被抢走。
2. **尺寸分级，尺寸决定信息量**：
   - 小（列表卡，56×84）：只放「书名字首字（1 个大字，32px，`brand-700`）+ 右侧 3px 书脊色条」。不排作者，不排品类。
   - 中（详情页，160×228）：三段式启用 —— 上带品类（11px，`#255139`）、中书名（22–28px，最多 3 行，超出省略号）、下作者（12px，`#3D4340`）、左侧 6px 书脊条。
   - 大（无，不需要）。本项目没有需要大封面的场景，因此不做。
3. **优先级铁律**：用户导入的 EPUB 若自带封面，**永远用真封面**；核心库书目一律书脊卡（契约里没有封面字段）。判断在数据层（`UserBook` 是否解析出封面），组件层不用 `onerror` 兜底——后者会在弱网下闪一下灰。

| tone | 底 | 书名 | 作者 | 实测对比度 |
|---|---|---|---|---|
| tone-1 | `#DCE8E0` | `#255139` | `#3D4340` | 7.20:1 / 8.03:1 通过 |
| tone-2 | `#E8EBE8` | `#255139` | `#3D4340` | 7.55:1 / 8.42:1 通过 |
| tone-3 | `#F0F5F1` | `#255139` | `#3D4340` | 8.22:1 / 9.17:1 通过 |

一句话总结这个方案：**它是占位系统，不是装饰系统**——所以它必须安静到「用户不会注意到它的存在，只会觉得书有名有姓」。

### P1 输入页：描述困境

**路由** `/`（未完成诊断时）

**目标**：让用户在 60 秒内、不感到被审问地说清「我卡在哪儿」。转化目标 = 走完第 1 步（必填那一步）。

**设计难点**：选项问卷劝退（像考试），纯自由文本劝退（面对空框不知写什么）。解法是**分步、一屏一组、只有当前步必答、可选题直接给跳过**。

> **契约差异（待 PM/架构师裁定，不阻塞设计）**：PRD §7.1 定义 **4 步**（① 域单选 6 项 + 说不上来 ② 感受多选 ≤3 联动 ③ 读书条件 2 个单选 ④ 自由文本 ≤140 字选填）；ARCH `Question[]` 定义 **Q1–Q7 共 7 题**（Q1 多选 1–3 且附 `free_text`，其余单选，每题带 `optional`）。
> 我的设计**按 `Question[]` 数据驱动**（步数、单选/多选、是否可跳全部来自数据），因此 P0 是 4 步还是 7 步都不需要改设计，只改 `questions.json`。但**PRD 第 1 步是单选、ARCH Q1 是多选**，这个语义差异必须有人裁定——单选意味着「六选一决定候选池」，多选意味着「可跨域」，后者会让候选池膨胀、`need_tags` 超过 6 项上限。**我按单选设计**（更符合「诊断」的收敛语义），请确认。

**信息层级**（自上而下）

1. 引导标题（34px / 590）：「最近读书，卡在哪儿了？」—— 具体问句，不用「开始你的阅读之旅」这类空话
2. 副说明（13px / `#5F6660`，1 行）：「选几个就行，不用想太久。跳过的题我们会按默认值算。」——**提前声明跳过的后果**，这比事后解释便宜
3. **进度**（12px，等宽数字）：「第 1 步 / 共 4 步」+ 3px 进度条（`brand-200` 轨 + `brand-600` 进度）。**不用百分比圆环**
4. **当前组题干**（22px / 590）
5. **选项**（chip 组）
6. **主按钮**「下一步」（48px 高）/ 末步为「看看该读什么」
7. 次操作：可选题的「跳过这一步」（文字链，`#5F6660`）；不可跳的题不显示跳过，避免用户以为能绕

**四屏的内容分配（PM 裁定：4 屏上限，不许新增页面）**

| 屏 | 内容 | 必填 | 密度风险 |
|---|---|---|---|
| 第 1 屏 | 1-a「你现在最想解决的是哪一类」单选 6 项 + 「说不上来」 | 是 | 低（7 个大 chip 单列） |
| 第 2 屏 | 2-a「具体是哪种感觉」多选 ≤3，选项随 1-a 联动 | 是 | 低（12 个 pill chip 两列） |
| **第 3 屏** | **5 组问题（3-a ~ 3-e），见下表** | 3-a、3-b 必填；3-c/3-d/3-e 可跳 | **高（20 个 chip）——本页唯一的真难点** |
| 第 4 屏 | 自由文本 ≤140 字（选填，带命中词回显） | 否 | 低 |

**第 3 屏的做法：两级 chip，不分页**

5 组平均 4 项 = 20 个 chip。分成两屏会让总屏数变 5，违反 4 屏上限；平铺会让这一屏读起来像体检表。解法是把 5 组压进**两个视觉层级**，让用户先答 2 个必答、再看 3 个"顺手答"：

> **不按 5 硬编码（v1.9 提醒）**：下表是**当前**的 5 组，渲染必须由 `questions.json` 数据驱动——**数组多一组就多渲染一组，少一组不留空壳**。理由：PM 2026-10-18 发现 `SPEC §7.4` 的 `answers` 只列了 5 个键，而 3-e（收获层级 → `depth`）**没有对应键名**——那是缺口不是漂移，没有任何两份文档互相矛盾，所以只有靠「不硬编码」才不会把它变成运行时崩溃。数字 5 只是此刻的事实，不是契约。

| 组 | 题干 | 选项 | 必填 | chip 形态 | 层级 |
|---|---|---|---|---|---|
| 3-a | 每天能读多久 | 10 分钟 / 20 分钟 / 30 分钟 / 1 小时以上 | 必填 | 方角 `--radius-sm`，**48px 高**，单列 4 行 | 主级 |
| 3-b | 能接受多难 | 越轻松越好 / 有点挑战也行 / 不怕硬书 | 必填 | 方角 `--radius-sm`，48px 高，单列 3 行 | 主级 |
| 3-c | 希望多快见效 | 今晚就想有变化 / 这一周 / 慢慢来 | 可跳 | `--radius-pill`，**32px 高**，一行三个词组 | 次级 |
| 3-d | 想让它怎么带你读 | 讲清原理 / 给具体做法 / 陪我练 / 换个视角 | 可跳 | `--radius-pill`，32px 高，一行三个词组（放不下就换行，**不缩字号**） | 次级 |
| 3-e | 更想要哪种收获 | 想通一件事 / 做成一件小事 / 心里松一点 | 可跳 | `--radius-pill`，32px 高，一行三个词组 | 次级 |

三级差异必须**同时**存在，只靠一项不够：

1. **尺寸** 48px vs 32px（触摸目标都 ≥44px，次级组用 `::after` 扩命中区）
2. **形状** 方角（单选语义，与 P1 既定规则一致）vs 圆角 pill（轻量词组）
3. **题干字号** 22px/590（主级组）vs 15px/510（次级组），且次级组题干右侧带 12px `#5F6660`「可不答」

**次级组不显示「跳过这一步」链接**：整组都可选，逐个给跳过按钮会让用户以为要一个个跳过。可选题的跳过是**组级**行为——整组不选即跳过，提交时按 `axis_sources: 'default'` 处理，并在结果页如实说明（"你跳过了 2 个问题，这几本主要按主题和篇幅匹配"）。

**内容偏好问句（两态，弱化呈现）——v1.12 定稿，v1.15 从屏尾上移到 3-b 之后**

v1.12 把它放在屏尾；v1.15 按准入条件（见下「折叠线准入」）**上移到 3-b 之后、3-c 之前**。位置变了，性质没变：它仍是**例外通道**，不是五组正题之一——所以带一行 12px 的分组标签，让它读起来是"另外问一句"，而不是"第五组"。

```
另外问一句
这类内容里有涉及临终或丧亲的，要不要一起看？
[ 一起看 ]  [ 先不用 ]
```

| 项 | 规格 |
|---|---|
| 分组标签 | 12px / 1.35（约 **17px** 高）/ `#5F6660`，四字「**另外问一句**」，与题干间距 **4px**。**不能用 22px 主级题干规格**——那会让它变成第六组正题 |
| 题干 | 13px / 1.5（约 20px 高）/ `#5F6660`，单行，**不超过 24 字** |
| 控件 | 两枚 `--radius-pill`，**32px 高**，字 13px/510；选中态 `brand-600` 1px 边框 + `brand-50` 底；未选中 `--border` 1px + 透明底 |
| 间距 | 标签→题干 **4px**；题干→控件 **8px**；两枚之间 **8px**；**与 3-b 之间 24px、与 3-c 之间 24px**（v1.12 的「与 3-e 32px」**作废**：它不再是屏尾附加块，而是一个组间块——用 24/24 对称，不偏向任何一侧） |
| 默认态 | **「先不用」预先选中**。这不是"替他答"——它把默认值**显式化**了：空白态会被直接落成 `false`，分不清「他没注意这题」和「他选了不要」；给「不用」一个词，那片空白就变成一个答案 |
| 命中区 | 视觉 32px，`::after` 扩到 **44×44**（与次级 chip 同规格） |
| 整块行高 | 17 + 4 + 20 + 8 + 32 = **81px**（v1.12 的 60px 不含标签，**已作废**） |
| 字段 | `include_heavy: boolean`（SPEC §5.2.1），**内容偏好，不是心理状态声明** |

**渲染条件（v1.13，数据判据，不是产品开关）**

> 当且仅当「该用户域 ∩ 难度 ≤ 上限 ∩ 书带 `grief` / `terminal_illness`」的候选集**非空**，这个问句才渲染。

判据出自 team-lead / SPEC（**内容侧数值，归 SPEC**），**本文只规定"不渲染时视觉上怎么办"**。M1 是 6 域 × 10 本，确认带这两个标注的只有《最好的告别》，而它在**人生转折**域——所以「情绪与自我 + 越轻松」那一格是空的，**勾了也不会多出任何一本书**。

三条硬规则，一条都不能省：

1. **不留空位、不占位块、不设 `min-height`。** 它不存在时，**3-e 下面就是屏尾**。理由与 B1 那条同源：**留白会被读成「这里本该有内容、没加载出来」**——而用户本来不该知道有这个开关。若按"永远占 48px"排版，M1 里第 3 屏底部会永远多出一段说不清来历的空白，**而没人会想到去查数据**。
2. **它的高度必须按"会消失"来设计，不许当恒定一行。** 否则某个画像触发不渲染时整屏会塌一截——**而塌的那一次恰好是最低风险的那一次，没人会发现**。
3. **消失时不补偿任何文案**（不写「这类话题这次不用选」）。一句解释会让人意识到「有个问题被拿掉了」。

> **这条判据同时管 UI 和数据，不许被降级成一句文案原则。** 它的两个落点：数据层——库里没有那本书时，开关本身就是空的（首发 300 本里唯一确认带标注的《最好的告别》在别的域）；UI 层——空的那一格不渲染。**只做 UI 层是假开关（点了看起来也正常，因为结果本来就该是那些书），只做数据层是一排空按钮。**
> **一个后果，写出来免得被当 bug 修**：第 3 屏内容高度在 M1 内部就不一致（有的域有这行、有的没有）。**这是数据决定的，不是布局出错。**

**渲染条件是「结构条件」，构建期算好，运行时查表（v1.14）**

上面那句「候选集非空」在实现上要再降一维，否则会绕进一个循环（**要决定问不问，先得跑一次推荐；而推荐要等用户答完**）：

> **结构条件**：**该用户域内是否存在一本「难度 ≤ 本档 cap、且带 `grief` / `terminal_illness`」的书。** 构建期算成一张 **6 域 × 2 档 = 12 行**的布尔表，**运行时是查表，不是现算**——所以第 3 屏**不需要等推荐结果**，那个循环不存在。

- **首发书单不为这个开关补书**（已定）。所以 M1 里「情绪与自我 + 越轻松」那一格**直接不渲染**——这是预期，不是缺陷，**也不许被当成"数据没配好"去补书**。补书会把它变成另一件事：不是修 bug，是改产品范围。
- **这一行是「可能不存在」的组件，不是「一定有、只是内容不同」的组件。** 两者的设计方式差很远：后者只要保证内容合理，**前者的验收必须包含「它不存在时整屏仍然成立」**（见验收 38）。这句话决定了下面三条硬规则为什么是硬的，而不是"最好这样做"。

**第 3 屏高度账目（v1.13 两态报数；只报数，未按新形态重排版式）**

375×812 视口。可用内容高 = 812 − 应用栏 **56** − 吸底主按钮区 **80**（48 + 上 16 + 下 16）− 页脚安全区 **34** = **642px**。

|---|---|---|
| 进度区（12px 行 18 + 间距 7 + 3px 条） | 28 | P1 信息层级 3 |
| 屏首间距 | 24 | — |
| 3-a（题干 30 + 间距 12 + 4×48 + 3×8） | 258 | 题干 22/1.35 = 30；chip 48px 单列 4 行 |
| 组间距 | 24 | — |
| 3-b（30 + 12 + 3×48 + 2×8） | 202 | 同上，单列 3 行 |
| **3-b → 控件** | **24** | v1.15：对称 24/24；**不渲染时一并消失** |
| **内容偏好块（17 标签 + 4 + 20 题干 + 8 + 32 控件）** | **81**（不渲染则 **0**） | v1.15 上移至此；**按"会消失"设计，不留位** |
| **控件 → 3-c** | **24** | 同上；**不渲染时一并消失** |
| 3-c（20 + 8 + 32） | 60 | 次级题干 15/1.4 ≈ 20，pill 一行 |

- **该行行高：60px**（题干 20 + 间距 8 + 控件 32）。**与 3-e 的间距：32px，未变**。**它整块消失时带走的是 92px**（60 + 32），不是 60px——那 32px 是为它留的，控件没了它也没有理由留着。
- **第 3 屏内容总高：两种状态，各自报数**

  | 状态 | 3-d 一行 | 3-d 两行 | 溢出（可用 642） |
  |---|---|---|---|
  | **控件渲染** | 864 | **904** | 222 / **262** |
  | **控件不渲染** | 772 | **812** | 130 / **170** |

- **报数口径**：渲染态取 **904 / 溢出 262**——报高的那个不会被下一个人读成"还有余量"。**同时保留低值 812 / 170**，因为不渲染时**不能拿 904 去兜底**（那会凭空多出 92px 空白，且没人查得出原因）。
- **是否需要滚动：两态都要。** 最小值 772 > 642，**「滚不滚」在 M1 里不由这个控件决定**——所以它既不能用来解释滚动，也不能拿"反正在滚"当不留位的理由。
- **这 40px 不改变滚动性质**：同口径比较 904（v1.12 渲染态）对 864（v1.11 复选框行 20px 的合计），**溢出从 222 加到 262（+18%）**——**没有把"不滚"变成"要滚"**，它是把一条已经要滚的屏又拉长了 40px。

> **吸底主按钮与内容高无关（"按内容可能更短设计"的落点）**：它是吸底，所以内容变短时**差额由下方留白吃掉**——不许把内容块拉伸、不许 `space-between`、不许给组容器 `flex: 1`、不许给第 3 屏容器写死 `min-height: 904px`。**一旦按最长情况兜底，不渲染的那一格就会凭空多出 92px，而它看起来完全像"设计留白"。**
> 同理，**不许把第 3 屏写进「与第 1/2/4 屏等高」这类固定高度指标**。那条指标在这个格子里会逼着实现去补空行凑数——**和骨架卡那次是同一个坑**：指标看着更严，实现只能靠改行高达成，于是 CLS 漂亮而版式错位。**跨屏的一致性该由"同一套间距与字号"保证，不该由"像素等高"保证。**

**「未答」必须可观测（v1.14，不改契约、只加信号）**

`include_heavy` 的类型**不动**（契约已冻，且三态不改变任何推荐结果，不值得为它动 SPEC）。但复盘必须能分出三件事，靠两个布尔量：

| 组合 | 含义 | 谁会读它 |
|---|---|---|
| `rendered = false` | **这一格没有这个问题**（结构条件不成立） | 数据侧：不是"用户拒绝了"，是"没得问" |
| `rendered = true` · `answered = false` | **看到了，没动**（保持默认） | 产品侧：这是真·默认值 |
| `rendered = true` · `answered = true` | **改过**（点了「一起看」或点了「先不用」） | 复盘侧：开关被理解且被使用 |

- **`rendered` 可以预计算**（结构条件查表），**`answered` 只在交互时置位**。
- **一个必须写死的细节**：**「先不用」虽然预先选中，点它也必须置位 `answered = true`，不许做成 no-op。** 否则「点了确认」和「从头没动」又落进同一个 `false`——**这正是 v1.12 花一整轮消灭的那个歧义，它会从交互实现这一侧再长出来。** 视觉上"已经是选中态"和逻辑上"用户表达过"是两件事。
- **三态为什么能干净分开**：**因为准入条件把"渲染了但在折叠线以下"这种状态挡掉了**（见上）。准入一生效，`rendered = true` 就意味着"首屏可见"，「没滚动到」不再是一个可能值——**准入条件不只是上线门槛，它还是这张表成立的前提**。
- 本文只提出**信号要求**；字段名、落库位置与三态语义归 SPEC / 架构（与 PRD §19 第 11 条同步）。
- **必须跟着这个数一起看的一件事（v1.14 升为准入条件）**：控件**落在折叠线以下**——按上表累计，它的顶边在 **804–844px**，而折叠线（可用高）在 **642px**，**低了 162–202px**。

  > **我 v1.13 在这里写错过一句，留档改正**：我写过「这与『默认先不用预先选中』的设计意图一致（不滑 = 不用）」。**这句是错的。** v1.12 换掉复选框就是为了消灭那个空白态——它分不清「没注意」和「选了不要」。而控件在折叠线以下，意味着**绝大多数用户看到的就是那个空白**：换形态只解决了「看到了但没选」，**没解决「根本没看到」，我们花一整轮消灭的东西从版面这一侧又回来了**。
  > 后果很具体：复盘流程写的是「`include_heavy` 落库值 = `false` 就说明规则没生效，属缺陷」——**如果九成的 `false` 来自「没滚动」，这个诊断会把「他没看到」误判成「规则坏了」，排查方向错一整天。**

  **所以改的不是版式，是上线门槛**：

  > **该控件首次上线时**（即某次书目扩充使其满足渲染条件、开始渲染的那一次），**控件顶边必须在折叠线以上。不满足则不许上线。**

  **按当前数值，它不满足这条**：顶边 804–844 > 642。要上线**必须先减掉 162–202px 内容**，解法只有一条——**减 3-a / 3-b 的行数**（内容侧数值，归 SPEC，不在本文改）。
  **三条禁术**：① **不许加折叠提示** ② **不许加「向下还有一题」** ③ **不许把它挪到 3-e 上面**（会与 3-b 连成一组、被读成难度开关，见上）。前两个是拿提示补版面的债，第三个是拿语义补版面的债。
  **一句话理由**：**默认值与「没看到」在行为上完全等同，所以一个看不见的安全例外通道，等于把默认值当成了答案。** 这和「宁可少问一句，也不要问一句什么都不变的」是同一条——**看不见的那一问和没问一样，但它在数据里长得像一句回答。**

- **不做成开关（switch）**，不做成高亮卡片，不用 `--warn`/`--danger` 色，不加说明段。它必须看起来像"一个普通选项"——越醒目，用户越会以为选了之后会发生什么。
- **不与 3-b「能接受多难」做任何视觉联动**，即便产品逻辑上它管的是内容安全（`EX-terminal`）。一旦联动，用户会把它读成"难度开关"，而它其实是内容偏好。
- 选择后**不弹二次确认**（不出现「你确定吗？这类书可能引起不适」）。二次确认在这里等于把责任推回给最没有判断力的人。
- 结果页**不显示**「因为你选了『一起看』，我们恢复了 N 本」这类说明。它是**这一次**的内容偏好，不是需要反复提醒的授权。
- **不记忆、每次诊断重新问**——记住它就等于替用户做了下一次的诊断（人不会一直处在同一个状态）。

> **文案铁律（v1.12，写进规范不只写在这条上）**：**这个问句里只许出现开关真能豁免的那两类内容**（临终 / 丧亲 = `EX-terminal` 的两个触发值），一字不多。
> 为什么：`include_heavy` **只豁免 `EX-terminal`，不豁免 `EX-trauma`**（自杀 / 性暴力永远不可豁免）。文案一旦写「自杀」，就是在承诺代码不会兑现的东西——**而且它没有真正的修法**：
> · 要么把「自杀」从文案里删掉（现在这版）；
> · 要么真的放行自杀题材，那是**必须把「自伤、性暴力」也写进这句问句**，等于在一个低心力用户面前摆一排最重的词。
> **两个方向都不行，所以这个开关只覆盖它写得出来的那一半。**
> 以后谁要加词，**先改 `include_heavy` 的豁免范围**，再改文案——不是反过来。

**选项的两种形态必须在视觉上可区分**（否则用户不知道能不能多选）

| 类型 | 视觉 | 计数 | 示例题干 |
|---|---|---|---|
| 单选 | 方角 chip（`--radius-sm`），选中时 `brand-600` 1px 边框 + `brand-50` 底 + 左侧 2px 品牌竖条 | 无 | 「你现在最想解决的是哪一类？」（情绪与自我 / 关系 / 工作与意义 / 习惯与行动 / 认知与思考 / 人生转折 / **说不上来**） |
| 多选 | 圆角 chip（`--radius-pill`），选中时同上但**带序号角标**（1/2/3） | 右上角 `12px` 等宽「2/3」 | 「具体是哪种感觉？」（内耗 / 反复想 / 不敢开口 / 提不起劲 / 睡不好…） |

**「说不上来」不是失败态**（PRD §7.1）：选它 → 跳过第 2 步 → 直接进入「最近生活里哪块最耗你」（6 个具体场景）。设计上此处**不显示错误色、不显示提示条**，只把题干换成降维版本，并在进度上显示「第 2 步 / 共 3 步」（步数变少，用户能感到「系统替我简化了」而不是「我答错被绕过」）。

**自由文本步（可跳过）**

- textarea 3 行，上限 140 字，右下角实时计数（12px 等宽）
- placeholder 给具体示例，不给抽象引导：「比如：想搞明白为什么总是读到第 30 页就停」
- **输入 ≥8 字后，下方出现一行「我们读到了：内耗 · 想太多」（`brand-700` 12px）**——把词典命中的结果直接摊给用户看。理由：这是本产品与 LLM 书单的核心分野（我们只有词表匹配），把它可视化，用户的信任来自「它没有装懂」，而不是来自「它好像很懂」。未命中时显示「没抓到关键词，我们会只用你选的选项来找」——同样诚实。

**关键交互**

| 操作 | 反馈 |
|---|---|
| 点 chip | 120ms 过渡。多选到上限 3 时，未选中的 chip 降到 `opacity: .45` 但**仍可点**（点它会替换最早的一项），不产生「点不动」的死手感 |
| 未答必答项就点「下一步」 | 按钮保持可点（不用 disabled 吊人），点击后题干下方 8px 出现 1 行红字「先选一个最接近的，或者点『说不上来』」，同时该组获得焦点环 |
| 提交最后一步 | 规则打分在本地、耗时 <50ms，**不显示 loading**，直接路由到 P2。仅当冷启动书目未就绪（>300ms）才出骨架 |
| 前进/后退 | 浏览器返回键回到上一步（每步一个 history 条目），已选项保留 |

**状态**

- 空态：不适用（首屏即内容）。
- 加载态：**只在真的慢的时候出现**（>300ms 骨架）。不做「AI 正在思考」式编排动画——我们是规则打分，做这种动画等于撒谎。
- 错误态：`questions.json` 加载失败 → 不阻断，降级为纯自由文本模式，顶部 1 行提示「选项暂时没加载出来，直接写也行」；提交后仍能出结果（只走关键词命中路径）。
- 边界：`optional` 的题目全部跳过 → 允许提交，结果页顶部如实显示「你跳过了 3 个问题，这几本主要按主题和篇幅匹配」（对应 `axis_sources: 'default'`）。

**响应式**：手机单列，chip 两列网格，主按钮吸底（`env(safe-area-inset-bottom)` + 16px）；桌面主按钮跟随内容流，表单最大宽度 480px。

### P2 推荐结果页（最重要的页面）

**路由** `/result`

**目标**：让用户在 10 秒内决定「从哪本开始」，并清楚知道这本能不能读。**这是全产品唯一必须同时承载五类信息的地方：档位、命中依据、理由、可用性与元数据、操作。**

#### 五类信息共存的难点

- 档位：三档，需横向可比较（§8）。
- **命中依据**：2–4 个短语，取自用户自己的原词（PRD §7.3 层②，是信任的主要来源）。
- 理由：三段式 **140–230 字/本**（S1 40–70 + S2 60–90 + S3 40–70，PRD §8.1 定稿口径；**B1 ≤30 字另计**），5 本 = 700–1150 字。**不再设「全文总区间」**——总数是分段的函数，同时写两个约束只会给未来埋一次「到底以哪个为准」。
- 可用性 + 元数据：作者 / 译者 / 难度 / 篇幅与时长 / 可获得性（PRD §7.2 要求全部前置）。
- 操作：一个主按钮，动词随可用性态变（PRD §9.4）。

全展开必然拥挤。核心决策仍是：**哪些默认展开、哪些折叠**。

#### 方案对比

**方案 A「理由前置」**：图像 + 书名作者 → 三段式全展开 → 底部一行（档位 + 可用性 + 按钮）
- 优点：完全兑现「逐本给理由」，无摩擦。
- 缺点：单卡高约 460px（S1 40–70 + S2 60–90 + S3 40–70 = 合计 140–230 字，B1 另计），一屏只能看 1.5 张；5 张卡需滚 3–4 屏，用户必须读完 700–1150 字才能决定先读哪本。**档位被压到最底部，与「按档位排序」的核心心智脱节**。
- 判定：否决。

**方案 B「判断前置，理由分层」**（采纳，骨架 = **SPEC §7.1 的 8 项**，v1.7 起与之逐项一致）：书脊卡 + 书名 → **`match_brief` 对症点 + 档位（同一行）** → **S2 首句（≤2 行 / ≤38 字）** → **`mismatch`「不过：…」** → **元数据（难度 · 篇幅 · 时长，一行，不折叠）** → 可用性徽标 + 主按钮（同一行）→ **展开区（S1 + S2 全文 + S3 + 完整命中依据 + 作者译者）**
- 优点：折叠态单卡高 **约 240px**，一屏 2 张完整 + 第 3 张露出 `match_brief`（无危机条时约 2.8 张）；档位、可用性、按钮、篇幅同在首屏；**卡面上「为什么是这本」有两句：`match_brief`（这本书独有的切入角度，2 行）+ S2 首句（这本书讲什么，≤2 行）**。
- 代价：S1 被折叠（v1.5 的结构变更）；S2 在卡面只给首句、全文进展开区（v1.6）。**两条代价各有补偿，见下。**
- 判定：**采纳**。

#### 为什么 S1 从卡面移进展开区（v1.3 → v1.5 的结构变更）

v1.3 我把 S1（`reason.situation`）放在卡面，称它「本卡最重要的说服元素」。SPEC §7.1 的 7 项里没有它。我按 SPEC 改，而且改完认为这个版本更好，理由不是「上游说了算」：

1. **`match_brief` 已经在卡面承担了「它在说我」的作用，而且是以更好的方式**。`match_brief` 是书级独有（每本一句不同），S1 是 tag 级共享（主 tag 相同就会重复）。**同一屏里，卡面留独有句、折叠区放共享句，是唯一不会让五张卡同头的排法。** 两句都上卡面，反而暴露了 S1 的重复。
2. **一屏能看 3–4 张 vs 2–2.5 张**（这是 v1.5 的口径；把 S2 首句放上卡面后是 2.6–2.8 张，见下节）。这个页面的任务是「10 秒内决定从哪本开始」，不是「读完 700–1150 字」。S1 平均 30 字占 2 行、约 55px，加上它在卡面会把 `match_brief` 的第 2 行位置挤到第 3 行 —— 五张卡就是 5×55px 的滚动。
3. **展开区不再是一个空抽屉**。v1.3 的展开区只剩 S2 + S3，用户点开前对它没有预期；现在是 S1 + S2 全文 + S3 三段完整 + 命中依据 + 作者译者，**点开这个动作的回报更高**。
4. 代价是真实的：不点开就不知道「它怎么描述我的处境」。但这个损失由 `mismatch` 补了一半 —— 卡面上现在有一句诚实的代价说明，它比 S1 更能让人判断「这本是不是给我的」。

> **可逆性**：如果总监最终裁定 S1 必须回卡面，只需要把它作为一层插回 `match_brief` 之下（`match_brief` 仍是第 2 行第一句），字号 14px + 2px 竖线不变，其余不动。

#### 为什么 S2 上卡面、但只取首句（v1.8 定稿：≤2 行 / ≤38 字）

team-lead 裁定「S2 保留在卡面」，**SPEC §7.1 已从 7 项扩为 8 项**，第 3 项就是它。规格：**≤2 行、≤38 字（含结尾句号）、必须是一句独立完整的句子、必须以句号结尾（未被硬截）**。其中字数口径定义在 **SPEC §5.2**，本文只引用（见下「这对数是引用，不是定义」）。

> **一次纠正记录（写给未来的人）**：SPEC 曾一度写成「1 行 / ≤30 字」，PM 拿旧版反过来纠正我成「1 行 ≤30 字」。**1 行装不进 30 字**——13px 中文在 375px 视口下每行约 19 字。team-lead 自己改回「2 行 / ≤38 字」并说明是他写错，不是设计在压字数。**这条值得记：字数上限和行数上限是两把尺子，必须同时给，且必须能同时成立。** 只写「≤30 字」会让内容侧写到 30 字，只写「1 行」会让 UI 在 19 字处截断——两边都按自己的尺子量，最后互相判不合格。

> **再记一条（判据层面，比上面那条更通用）**：字数检查抓不住「38 字断在半句中间」。所以 SPEC 里给的验收条件是**可机器判定的**——**卡面上的 S2 首句必须以句号结尾**。它一次抓住所有硬截，而字数是抓不住的。**能写成一行断言的判据，就不要写成一条给人看的规则。**

**卡面准入判据（比结论更值钱，以后加字段自判用）**：

> **判断一句话能不能上卡面，判据不是「它重不重要」，而是「五张卡并排时它会不会重复」。会重复的下沉，不会重复的上留。**

四个位置一次判完：`match_brief` **上留**（书级独有）· S2 首句 **上留**（书级独有，只取首句）· S1 **下沉**（tag 级共享，主 tag 相同就重复）· 完整命中依据 **下沉**（tag 级共享）。

这条判据解释了我 v1.5 / v1.7 两次看起来互相抵消的结构变更：折 S1 是因为它会重复，加 S2 是因为它不会。**同一把尺子量两次得出方向相反的两个结论是正常的**——不正常的是一把尺子量出两个结论却没有尺子。

| 规则 | 规格 |
|---|---|
| 卡面渲染什么 | **`structure_note` 字段的原值**（数据侧给的 S2 首句），**≤2 行 / ≤38 字（含结尾句号，字数口径见 SPEC §5.2）**（`-webkit-line-clamp: 2`，**正常情况下永不触发**，是安全网不是分支）。**禁止在渲染层按句号切分 `promise` 来"生成"首句**——见下「三条约束」 |
| 超长 / 被截时 | 这是**数据缺陷**，不是渲染分支：`structure_note` 由构建期 `catalog:audit` 校验（≤38 字 **且以句号结尾**），不合格即 fail。渲染层只留 `line-clamp: 2` 兜底，真被截了就说明数据错了，不是"设计允许截断"。**不在卡面做第二个「展开全文」**——一个卡已经有一个展开区，两个展开控件会让人不知道点哪个 |
| 为什么不压到 1 行 | 压到 19 字就会变成「这本书用认知行为疗法解释……」然后没了——**比不放更糟**：它给了开头没给结论，用户还得点开才能知道在说什么，等于把一次点击的成本伪装成了一句摘要 |
| 展开区 | **`promise` 全文（60–90 字），段落标记「这本书讲什么」**。与卡面是同一段话的两段呈现，**不是两次不同的话** |
| 字号 | 卡面 13px / 1.6 / `#3D4340`（与 `match_brief` 同色同号）；展开区 14px / 1.75 / `#2A2F2C` |
| 缺失 | `structure_note` / `promise` 缺（不应发生，属数据错误）→ 整行不渲染、不留空位 |

**三条约束，缺一条就自相矛盾**（架构师 2026-10-18 提出，落点已写明）

| # | 约束 | 落在哪 | 性质 |
|---|---|---|---|
| 1 | `structure_note` **必须以句号结尾** | 构建期 `catalog:audit`，缺句号或 >38 字即 fail | 数据约束 |
| 2 | 卡面渲染 `structure_note` **原值**，**禁止按句号切分** | 渲染层 | 渲染约束 |
| 3 | `reason.promise` **必须以 `structure_note` 开头** | 渲染层 `startsWith` 断言 | 关系约束 |

> **为什么必须写这三条**：如果卡面用最直觉的方式取首句——`promise.split('。')[0] + '。'`——那个补上去的句号会让结果与 `structure_note` **差一个字符**，`startsWith` 直接失败。更糟的是**它在验收时会表现为「文案写错了」，而不是「实现写错了」**：人会去改文案，改完还是失败。
> 所以三件事分开：**「以句号结尾」是数据约束，「原样渲染」是渲染约束，「前缀关系」是关系约束——两者都不需要截断算法。截断才是矛盾源，只要引入「切一刀再补一刀」，就一定有人把补的那个字也算进去。**
> 这两条判据是**一对，不能为了消矛盾删掉任何一条**：`startsWith` 管「两处渲染的是不是同一段话」，句号管「这一处有没有被硬截」。只留句号，文案作者可以自造一句再补个句号；只留 `startsWith`，`structure_note` 本身可能被截到半个词。

**外加一条写作约束（不是断言，靠评审）**：`structure_note` 必须**独立成句**，自带主语和动词——不能是承接上一句的片段（「它提出了三个层次」——谁提出的？）。因为它会被单独渲染两次（卡面、详情页），脱离上下文之后仍然要成立。

> **这对数是引用，不是定义**：`≤38 字（**含**结尾句号）` 出自 **SPEC §5.2**，本文只负责「**2 行**」与「不切分、不硬截」的渲染方式。改字号/改行高的人必须同时看另一个数——**互相推导的一对数拆到两份文档里，下一个改字号的人只会改一边**（所以双方约定：定义在 SPEC，本文引用）。
> 顺带记一个 38/39 位差：若一句恰好 38 字、句号落在第 39 位，按「≤38 字」切出来仍是硬截句。**这就是把口径钉在数据侧（`structure_note` 必填 + 含句号 ≤38 字 + 构建期校验 + 渲染原值）而不是靠运行时切分的原因**——运行时切分永远要面对「切在哪儿」这个问题，数据侧不需要。

#### 卡片的三段理由各管一件事（`match_brief` / `promise` / `situation`）

| 位置 | 字段 | 数据性质 | 作用 | 重复风险 |
|---|---|---|---|---|
| 卡面第 2 行 | **`match_brief`** | **按书预写**，≤28 汉字 | 区分这一张和另外四张：**这本书对这个处境的独特切入** | 无——每本一句，书级独有 |
| 卡面第 3 行 + 展开区 | **`structure_note` / `promise`（S2）** | **按书写**，全文 60–90 字 | 这本书讲什么：卡面渲染 `structure_note` 原值（≤2 行 / ≤38 字），展开区渲染 `promise` 全文 | 无——书级独有 |
| 展开区第 1 段 | `reason.situation`（S1） | **按 tag 从 `phrases.json` 取片段 20–45 字 + 用户原词回引 → 整段 40–70 字** | 让用户确认「它在说我」 | **高**——同一用户同一次诊断里，主 tag 相同的两本书会渲染出**一模一样的一段** |

> **段名与字段名对照（一次说清，免得两边各叫一套）**：S1 = `reason.situation` ｜ S2 = `reason.promise` ｜ S3 = `reason.payoff` ｜ 边界声明 = `reason.mismatch`。**S1/S2/S3 是排版顺序的称呼（本文用），`situation/promise/payoff/mismatch` 是契约字段名（`types-draft.ts` / SPEC §5.3 用）。** 两套名字指同一批东西，不并存第三套。

**为什么三段都要**：只有 `situation`，五张卡里若 3 本主 tag 都是「情绪调节」，用户会看到三张卡说同一句话（PRD 有 CI 门禁「同列表 `situation` 重复率 ≤30%」，这条门禁只可能靠书级的 `match_brief` 满足）；只有 `match_brief`，卡片退化成书封推荐语，用户感觉不到被诊断；只有前两句没有 `promise`，用户不知道这本书要不要花 4 小时。**分工是：`match_brief` 答「为什么是这本」，`promise` 答「这本讲什么」，`situation` 答「为什么是给你」。前两个书级独有 → 上卡面；第三个 tag 级共享 → 进折叠区。**「为什么是给你」这一层在结果页由**顶部诊断摘要条**承担一次（逐字回引用户原词，全页只出现一次），不在五张卡上重复。

**视觉顺序 ≠ SPEC 编号**：SPEC 按「功能优先级」编号，我把徽标（4）与主按钮（7）**合成同一行**，因为它们必须贴在一起——徽标是在解释按钮的语义，拆开就都失效。**实际视觉顺序：1 → 2 → 3 → 5 → 6 →（4 + 7）→ 8**，即 书名 → `match_brief` + 档位 → S2 首句 → `mismatch` → 元数据 → 可用性 + 按钮 → 展开区。功能上「能不能读」比「为什么不是更高档」更硬，所以 4 排在 5 前面；`mismatch` 必须在按钮之前，所以视觉上它上移了一格。**两套编号都在上表里，不用再记第三套。**

**优先级 ≠ 视觉顺序，这里必须分开看**：功能上「能不能读」（第 6 行）比「为什么不是更高档」（第 4 行）更硬，但视觉上徽标必须与主按钮贴在同一行——徽标是在解释按钮的语义，两者拆开就失效。**整条的视觉顺序就是上表 1→7，不再有第二套。**

**B1（`mismatch`）的全文怎么读：原位长大，不另起一段（v1.8 定稿，无偏离）**

SPEC §7.1 第 8 项已写明展开区是「S1 / S2 全文 / S3 + 命中依据 + 作者 / 译者 / 出版社，**不含 B1**」。B1 是**同一个槽位的两种状态**，不是两处内容：

| 状态 | 表现 |
|---|---|
| 折叠（卡面，视觉第 4 行） | 13px / **1 行截断**（`-webkit-line-clamp: 1`），末尾 `…`；`title` 可留作桌面端补充，**但不得作为全文的唯一容器** |
| 展开（**同一个位置**） | 这一行原地变成全文，**不收起、不换位置、不在展开区另起一段** |
| 详情页 P3 | 也有全文（`mismatch` 一行本身即全文） |

**为什么不是「只放详情页」**：`title` 在触摸屏上不存在——手机上永远读不到全文，等于这句话只给了鼠标用户。
**为什么不是「展开区另起一段」**：同一句话出现两次，撞验收项 23，而且会让「展开」看起来没带来新信息。
**同一个槽位的两种状态，不算重复**——判据是「B1 在 DOM 里有几个节点」（恒为 1），不是「用户看到了几遍这个意思」。这条已写进 SPEC，**此处没有偏离可标**。

> **元数据为什么不能折叠（v1.6 已升级为硬约束）**：team-lead 2026-10-18 把这条写进了 SPEC §7.1 —— 卡面**第 6 项**（视觉第 5 行）「难度 · 篇幅 · 时长」，**20 字内，禁止折进展开区**。理由比 PRD 的原始措辞更准：**「这本书要花我多久」是决策必需信息，不是补充信息。** 用户在那个位置上的犹豫是「我今晚开始读，能不能读完」，不是「谁译的」。折起来等于让他点开五个卡片才能做一次比较——那是把决策成本乘五。**这条不再需要上游确认，也不再作为可协商项。**

**为什么 `match_brief` 在左、档位在右**：五个卡片读下来，用户实际在找的是「哪句说中了我的具体情况」，这是横向差异；档位是纵向序列（第 1 张最强），扫一眼位置就知道。把差异点放在左（阅读起点），把标量放在右（稳定不跳），两者都不牺牲。反过来排会让每张卡都从「高度契合」四个字开始读，五张同头。

**`match_brief` 的写作约束**（给内容侧，也用于 CI 检查）：
- ≤28 汉字，一句话，**必须含一个只有这本书才成立的切入角度**（写法是「它不从 X 讲，从 Y 讲」这类转折，而不是形容词堆叠）
- 不重复书名；**不整句复述 `user_phrase`**（它在页首诊断摘要条已经逐字出现一次，见下「诊断摘要条」）；不出现「经典」「神作」「必读」「受益匪浅」等空词（PRD 禁用词清单）
- 例：「先承认你没准备好，再谈怎么准备」/「把"不敢说"拆成三种具体场景」/「不劝你早睡，先解释你为什么舍不得睡」

**为什么 `mismatch` 一定在卡面、且在按钮之前**：
- 它回答的是用户看到「高度契合」那一秒的「凭什么不是 100%」。**这个念头不会等到点开详情才出现。** 放折叠区只有少数人看得到，信任收益归零。
- 必须在按钮之前：让用户在点之前看到代价。放到按钮之后就是 fine print，正是本产品反对的「措辞含糊等于欺骗」。
- **用 `neutral-800`（10.12:1），不用警告色。这是定稿，不是默认值。**
  > **决策记录**：曾考虑 `warn-600`，因五张卡里可能有四张都带这一行而否决——**若每张都挂一个琥珀三角，要么被习惯化到看不见，要么被读成「这几本都有毛病」**，而它想说的是「这本没覆盖到你的全部需求」。警告色留给真正需要行动的错误（文件过大、导入失败）。此条已锁进 SPEC §7.1「禁止 `warn` / `danger`」。**不保留「默认 A、评审时可改 B」这类退路**——那会把已经决定的事重新变成议题，每重开一次就多一个人以为自己有投票权。
- 识别靠**三角图标 + 「不过：」前缀 + 位于按钮之前**这三样，不靠颜色 —— 顺带即色盲可用。**不得改成纯文字无图标**，否则它和元数据行会读成同一层。它比元数据深一档（`neutral-800` 10.12:1 vs `neutral-700` 5.91:1），这是它"更被看见"的唯一手段。

**为什么档位排在可用性之上**：第一问是「这值不值得读」，第二问才是「我读不读得到」。反过来会让列表读起来像库存清单。

**已知缺口已关闭（v1.9）：`mismatch` 的合法性是「同组唯一」，不是「条数」**

原缺口：`mismatch` 同屏出现多个时没有上限规则，五张卡可能四张都挂这一行，「习惯化到看不见」没有任何机制去防。**现已关闭**，但关闭方式不是加阈值，是**把已有的判据再用一次**。

> **这不是新规则，是「卡面准入判据」的第二次应用。** 第一次用在 S2：S1 按标签共享 → 五张卡会渲染出三句一样的开场 → S1 离开卡面、进展开区。判据不是「它重不重要」，而是「**几张卡并排时它会不会重复**」。同一个判据第二次落在 `mismatch` 上，结论同样是「会重复的下沉」。
> 这条的额外价值：**以后第三条同类规则不用重新立法**——先问「五张卡并排时它会不会重复」，答案就出来了。

**实现判据（按「同一条提示在同组内的出现次数」，不按枚举分支）**：

| 同组内同一条 hint 的出现次数 | 处理 |
|---|---|
| **≤1 次** | **逐卡陈述**（在卡面，位置上不动） |
| **≥2 次** | **上提到组头一次**，卡上不渲染 |

**明确不按档位 / 符号这类枚举分支**：两本都是 `inline`、但都缺同一章，是同形不同因——**按枚举分会漏**。判的是「同一句提示出现几次」，不是「这两本属于哪一类」。

| 情形 | 性质 | 处理 |
|---|---|---|
| 同组 3 张卡各有一条**不同**的缺口 | **3 条信息** | **什么都不做**——没有重复就没有习惯化，砍它等于砍信息 |
| 同组 ≥2 张卡取到**同一条** hint | **1 条信息印了 3 遍** | 它是这一组的**共性**，不是这本书的**个性** → 提到**组头一行**，卡片不再重复 |

**为什么它成立**：`mismatch` 唯一的价值是「这本书**独有**的那个失望点」；同组里每本都成立的那句解释不了「为什么读这本而不是那本」，**它已经不再是这本书的理由，而是这一组的处境**。

为什么数量阈值一定错：**习惯化的成因是重复，不是频次。** 五种不同缺口是五条信息，同一种缺口五次是一条信息印五遍——**这两件事在计数上完全一样，在价值上完全相反**，所以任何「≥N 条就降级」的规则必然误伤其中一半。这也解释了「同屏 ≥2 降级」为什么被作废两次。

**卡变矮不补空行**：上提后同组会同时出现「有 B1」和「无 B1」两种卡。**不预留空位**——单列竖排卡高不一致不影响阅读，而留一个空行会被读成「这里本该有内容、没加载出来」。同理见骨架卡：骨架基准是「无 B1 的真卡」。

**内容侧界线：禁止重复事实，允许写后果（v1.11，PM 提的版本比我原来的「按维度不许写」好）**

判据只有一句：**把它删掉，用户会不会少知道一件事？** 不会 = 重复事实，删；会 = 后果，留。

| 情形 | 徽标/元数据说得出来吗 | B1 该不该写 |
|---|---|---|
| 「这本需要自备文件」 | **说得出来**（可用性徽标） | **不该**——纯冗余 |
| 「需自备，所以今晚开不了，先读第 1 本」 | 说不出来（徽标只给事实，不给后果） | **该** |
| 「这本比较长」 | 说得出来（元数据「约 8 小时」） | **不该**——纯冗余 |
| 「约 8 小时，今晚开不了」 | 说不出来 | **该** |

> **为什么换成这条而不是「按维度不许写」**：第二种情形恰恰是 B1 唯一不可替代的半句——**用户看卡片的那个瞬间想知道的是「我今晚能不能开始」，不是「这本书的属性是什么」。** 而按维度禁，得替每个维度各想一次边界；按「事实 vs 后果」禁，一条判据管全部。
> 它同时回答了「为什么不能更严」：**禁令去解决重复，会和上提机制打架**——机制本来就能处理重复，再加禁令等于同一件事管两遍，而两套规则冲突时没人说得清哪套优先。

**组头那一行怎么来**：人工预写的**因子级句式**（每个因子一句），**不在运行时拼自然语言**——与三段理由同一口径：模板可控、可审、可 diff。

**不新增机制**：按现在的分组（第 1 组 1 张、第 2 组 1–3 张、第 3 组 0–1 张），这条规则**只可能在第 2 组触发**——另外两组各只有一张卡，组内不存在重复。所以它不是一套新系统，是第 2 组的一条特例规则。

**为什么元数据只留「难度 · 篇幅 · 时长」一行**：书名 + `match_brief` 回答「是不是在说我」，难度与时长回答「我读不读得完」。前者决定要不要看下去，后者决定怎么读。**全部元数据堆上卡面**（作者 · 译者 · 出版社 · ISBN）会把第 2 行挤满，`match_brief` 就被压到第 3 行——而扫读时眼动落在第 2 行，那一行必须是差异点。所以卡面只留最影响决策的两个数字（难度、时长），其余进展开区。放在按钮之前，是因为「12 万字 / 约 4 小时」是决策参数，必须与按钮同屏可见。

**整页结构（DOM 顺序 = 视觉顺序，team-lead 2026-10-18 已固化，不再调整）**

1. **诊断摘要条**（1 行）——「被理解」的唯一落点，见下
2. **危机资源条（P0-16）**——仅「情绪与自我」域，见下。**在摘要之下、第一组之上**
3. **放宽提示**（仅 `relax_level ≥ 1` 时出现，`info` 色文字，13px）：直接用 ARCH §3.8 的口径文案，L2 为「没有完全对口的书，这几本在难度和篇幅上最贴合你的现状」。**提示后面必须跟一个提问入口**（「是不是这几个条件太严了？改一下」→ 回 P1 定位到相应步骤），而不是只给一句说明——约束过严导致的降级要让用户能动手，不能只是被告知
4. **结构性无 `inline` 域说明条（P0-17）**——见下。**与第 2 项互斥，永远不会同时出现**
5. **三组卡片**（见下）
6. 页尾：「都不太对？再描述一次」（回到 P1）

> 顺序原则：**安全 > 约束降级 > 可获得性说明 > 内容**。逐条对应上面的 2 → 3 → 4 → 5。「这些书不太对症」（放宽提示）必须排在「这些书要自备文件」（说明条）之前——前者决定他要不要继续往下看，后者只是解释怎么读。危机条排第 2 是因为它比「继续看」更优先：放页尾（v1.3 的做法）等于要求一个不太好过的人先滑过五张卡才看到出口。

#### 诊断摘要条：「被理解」在整页只出现一次（v1.6 硬规则）

S1（`situation`）移进展开区之后，卡面上不再有任何一句「它说中了我的处境」。「被理解」这件事必须由摘要条**一次说透**，否则这个页面对用户就变成「它没听懂我」。team-lead 把这条定为 S1 可以离开卡面的**前提条件**，不是补充建议。

| 项 | 规格 |
|---|---|
| 文案模板（逐字） | **「你在为『{user_phrase}』找书」** |
| `user_phrase` 的处理 | **逐字回引**：不删词、不改词、不概括成 tag 名、不做同义替换、不补全语病。它必须是用户在自由文本里**自己打出来的那串字** |
| 长度 | 整条 ≤2 行；`user_phrase` 超长时尾部 `…` 截断（**不删中间词、不重排**），完整原词进 `title` |
| 回引源优先级 | ① `free_text`（用户自己打的）→ ② 第 3 屏选中的第一个**具体场景原词** → ③ 第 1 屏所选域的中文名 |
| 全部跳过的情形 | 降级为「你在按『{域中文名}』找书」，**不出现空的『』**、不出现「（未填写）」 |
| 全页唯一性（硬规则） | 结果页内 `user_phrase` 字符串的出现次数 **= 1**（只在摘要条）。`match_brief` 的写作约束里「不重复用户原词」就是为这条服务的；卡片展开区的 S1 若引用用户的话，必须用**不同的短引**，不得整句复述 |
| 视觉 | 条高 44px，`--surface` 底 + 底部 1px `--border-soft`；文字 14px / 510 / `#2B312E`，`user_phrase` 用 `「」` 或 `『』` 包住并取 `brand-700`；右侧「改一下」13px 文字链（回 P1，保留已选） |
| 无障碍 | 普通文本，**不用 `aria-live`**（不是异步更新）；括号用中文引号而非 CSS 伪元素，保证读屏能读出边界 |
| 不做的事 | 不加「AI 总结」、不加二次改写句、不加感叹号、不与档位/数量并列（它是「我听见你了」，不是数据面板） |

**为什么放在最上面**：它是用户继续往下看的理由。放在卡片下方或页尾，等于先让他读五本「为什么适合你」再告诉他「我们听懂了你的原话」——顺序反了，说服力也就没了。

**为什么全页只能出现一次**：同一句话在摘要条说一遍、在五张卡里各说一遍，第二遍开始就变成噪音；而且 S1 是 tag 级共享句，五张卡里三张同头（这就是 v1.3 的问题）。**一次说透，胜过五张卡各说一遍。**

| 元素 | 文案 |

**与 P0-17 的互斥（写死在渲染条件里，不留实现自由）**

| 诊断域 | 危机资源条 P0-16 | 无 `inline` 说明条 P0-17 |
|---|---|---|
| 情绪与自我 | **渲染** | **不渲染** |
| 关系 | 不渲染 | 按该域 `inline` 覆盖数决定 |
| 人生转折 / 说不上来 | 不渲染 | 按该域 `inline` 覆盖数决定 |
| 工作与意义 / 习惯与行动 / 认知与思考 | 不渲染 | **渲染**（结构性 0 本 `inline`） |

```js

const showNoInline = !showCrisis && inlineCount[domain] === 0   // 这一项 !showCrisis 是互斥的物理保证
```

**为什么必须互斥**（不是排版洁癖）：这两句话的语域是冲突的——危机条说「**你可以不读**」，说明条说「**你要准备好文件才能读**」。紧挨着出现，等于先说「放下吧」再说「去准备吧」。而且「情绪与自我」域里 `inline` 本来就少，这条说明一旦出现，会把安全条往下挤、把用户的注意力从出口拉回到「准备工作」上。

**危机条与「内容安全过滤」是两条独立条件，不是同一件事的两面（v1.11）**

这两件事很容易被写成一条注释，但它们的域不同，写在一起半年后会被当 bug 修掉：

| 机制 | 触发条件 | 依据 | 覆盖不到的地方 |
|---|---|---|---|
| **危机资源条（P0-16）** | `domain === 'emotion_self'`（**用户选的域**） | 该域的用户此刻可能需要的不只是读书 | 关系 / 人生转折 / 说不上来**不渲染** |
| **内容安全过滤 `EX-terminal`**（`grief` / `terminal_illness`） | **用户域** = 情绪与自我 **且** 选「越轻松」**且** `include_heavy === false` **且** 书带该标注 | 内容偏好未开时的默认保护 | 用户勾了「一起看」即不剔除；**`include_heavy` 只豁免它** |
| **内容安全过滤 `EX-trauma`**（自杀 / 性暴力） | **三个条件同时成立才剔除**：**用户域** = 情绪与自我 **且** 选「越轻松」**且** 书带 `suicide` / `sexual_abuse` 标注。`include_heavy` **不在这个条件式里**——它不是"跟这条无关"，而是**它不参与、也不能参与** | **不可豁免**的安全底线 | **没有任何开关能关掉它**（G10《最好的告别》钉的就是这条）；这条只能靠"整本不给"实现，不能靠"给了再提示" |

> **三个必须说清的细节**：
> ① **过滤读的是「用户选的域」，不是「书的域」。** 所以「人生转折」域的书只要带 `grief` 标注，照样在「情绪与自我 + 越轻松」下被剔——**「这类书进结果页」在用户没选「一起看」之前不会发生。**
> ② **`include_heavy` 是非对称的**：它只豁免 `EX-terminal`，**不豁免 `EX-trauma`**。做成交互时不要写成一个笼统的「显示全部」，那会让自杀题材也漏出去。
> ③ **上表第三行不许写成「书带标注即可剔除」（v1.12 纠正）。** 那六个字读起来像"标注一到手就删"，但 `EX-trauma` 和 `EX-terminal` 一样是**三个条件同时成立**——缺了「用户域 = 情绪与自我」或「选越轻松」的任一条，带 `suicide` 标注的书照样正常出现在列表里。**条件写全，别用「即可」**：一个写半截的条件式，会让下一个人在排查"为什么这本书没被剔除"时先怀疑标注数据，而真正的原因是用户根本不是那个域。**「`include_heavy` 无关」说的是"这个字段不参与判断"，不是"别的条件也不参与"**——这两句话差一个字，排查方向差一天。

**不要写成「有危机条 ⇒ 有内容过滤」或反过来。** 它们在「情绪与自我」域上恰好同时存在，但那是巧合，不是依赖。

**危机条与临终题材同屏：只有一种情形会发生，而且那时不改渲染**

前提：**用户自己回答了「一起看」**。这是唯一可能的同屏场景——他没选却被塞进临终卡的情形，已经被 `EX-terminal` 挡掉了。

**这种情形下什么都不做**，理由两条：

1. **同屏是用户主动要的，不是系统塞的。** 危机条说「你现在可以放下读书这件事」，临终卡说「这里有本关于失去的书」——**他刚亲手选了「一起看」，第二句是他要的，不是系统在自我辩护。** 真正让前者变成免责声明的情形，是**他没选却照样看到临终卡**，那个已经被挡了。
2. **所以：不改位置、不改渲染条件、不因题材做任何视觉降级。**

**有一条硬禁止，值得单独写**：**不许因为题材把一张算出来是 `strong` 的卡下沉到「也可以看看」组。**
那一组不是「安全分组」，是 **`explore` 档位分组**（「有启发价值，但不是对症的」）。**分组的依据只能是分，不能是题材。** 把 `strong` 卡下沉，等于让档位标签撒谎——而且是对一个刚主动要看它的用户撒谎。
同一逻辑：也不许因为题材把该用户的选择做成空结果（**用户选了「一起看」却拿到 0 本，比不给这个开关更糟**——那等于把开关做成了假开关）。

**一个已知缺口，写出来是账、不写是坑**：**「关系」域里也可能有刚失去亲人、又选了「越轻松」的用户——上面两条现在都不会命中他们。** 这条缺口是**故意留着不处理**的（SPEC 已记），所以**设计里不许假装它被解决了**——不加「关系域也会提示」之类的说明，也不加一个看起来像已经覆盖了的降级文案。**看起来像解决了的假覆盖，比明确不覆盖更糟。**

**禁用词检索按节点收窄（v1.12，替换 v1.11「不查『自杀』」的写法）**：内容偏好问句的容器带 `data-heavy-question`，断言 **`[data-heavy-question]` 子树内「自杀」「自伤」「性暴力」三词全 0 命中**。

为什么这个写法比 v1.11 的"全局检索但把『自杀』排除在外"好，差在三处：

1. **v1.11 的写法是"这个**词**可以在某些地方出现"**，判断权在写代码的人手上——他只要不把某个目录放进扫描根（`--targets` / 当年的 `--scope`），那个目录就天然豁免了，而没人为这个豁免负责。
2. **v1.12 的写法是"这个**位置**不许出现"**，判断权在 DOM 上——容器是哪一个、子树边界在哪，`data-heavy-question` 本身就写着。**能 grep 的口径才是能守的口径**（架构师语）。
3. **它把「自杀」也纳进来了，而这恰恰是安全的**：v1.11 担心"禁了自杀，唯一该说它的地方说不出话"——那是**全局禁用**才有的问题。收窄到这一个节点后，危机资源条、`/crisis` 页、`crisis_resources.json` 全在这个子树**外面**，它们要不要说这个词、说几次，这条断言一个字都不管。**「在哪说」和「能不能说」是两件事，v1.11 把后者当成了前者的前提。**

> 另：三词里的「自伤」「性暴力」在这个节点上**本来就该是 0**——它们是 `EX-trauma` 的触发值，而这个开关**不豁免 `EX-trauma`**（见上表第三行）。所以这条断言实际上在守两件事：**句子里不许承诺开关兑现不了的东西**（三词全禁），以及**三词里的两个连提都不许提**（会让人以为这个开关管它们）。

|---|---|
| 文件可用 | 主句 + 副句 + 按钮「查看心理援助资源」（完整条） |
| 文件缺失 / 为空 / 解析失败 | **同槽位静态块**：主句不变（「如果你现在不太好过，读书可以先放一放。」）+ 兜底句「**可以在当地心理援助热线或精神卫生机构寻求帮助。**」；**去掉按钮**（无处可去，不能给一个点了报错的链接） |
| 构建期 | CI 在 `crisis_resources.json` 缺失或 schema 校验失败时**直接 fail 构建**，不允许带着空数据上线 |

理由：安全网不能因为构建出错而静默消失。按钮要去掉，是因为「点了报错」比「没有按钮」更伤——用户在你的安全提示上撞到一个 404，他对这一整条的信任就没了。

> 资源页本身的完整规格见后文 **P8 心理援助资源页**。

**文案判断（PM 定，设计侧同意并照此落地）**

1. **「状态很差」→「不太好过」**。「状态很差」是在给用户下负面判断，他此刻不需要被诊断；「不太好过」是平视的描述，是一种允许。它还能同时指情绪与处境，不逼用户承认自己是「病」。
2. **「读书可以先放一放」必须留**。这句话把用户利益放在产品利益之前，是本产品「不推销自己」的唯一硬证据。删掉它，整条就退化成免责声明——用户能感觉到那个差别。
3. **条内不写热线号码**。写死在 UI 里必然过期，而过期的号码比不展示更伤信任。

#### P0-17 结构性无 `inline` 域的说明条

「习惯与行动 / 工作与意义 / 认知与思考」三个域**结构性 0 本 `inline`**（这类书全在版权期内，扩库也解决不了）。用户进这三个域的结果页会连看 N 张「需自备电子书」，各自疑惑一次。解法是在列表**之前**给一次说明，把 N 次困惑压成 1 次。

**文案（逐字，PRD v1.5 / SPEC §2.1 P0-17 定稿）**：

> **这个方向的书基本都还在版权期内，正文需要你自己准备（EPUB 或 TXT），导入后就能读。下面的推荐和理由照常。**

| 项 | 规格 |
|---|---|
| 触发条件 | 该域 `inline` 覆盖数 = 0 **且** `domain !== 'emotion_self'`（互斥，见 P0-16 的真值表）。**数据驱动，不硬编码域名** —— 将来补进一本公版书，这条自动消失 |
| 色彩 | **`--info` 系，不是 `--warn`**。这不是问题提示，是流程说明 |
| 形态 | 一行 13px（`info-600` 字 + `info-50` 底），默认展开，`radius-sm`，内边距 12×16 |
| 可折叠 | 可以（右侧 16px 折叠箭头）。**折叠状态按域持久化**（`localStorage`），老用户不必每次念经 |
| 折叠后 | **每张卡片的「需自备电子书」标签仍然在**——说明条只是省掉重复解释，不替代状态标签。事实不能随说明条一起消失 |
| 位置 | 第 4 项，放宽提示之后、分组列表之前。不吸顶、不吸底、不浮动 |
| 禁止开头 | 「抱歉 / 暂不支持 / 资源缺失 / 敬请期待」——**一句都不许**。道歉会暗示我们在等一个修复版本，而我们没有；这是流程说明，不是缺陷公告 |
| 无障碍 | `role="note"`，不作为 `alert` 播报（它不是紧急信息）；折叠按钮 `aria-expanded` |

**为什么允许折叠却默认展开**：默认展开是为了让第一次来的人一定看到；允许折叠是因为第 3 次进来的老用户已经知道了，折叠尊重他。但折叠**不能收掉卡片上的状态标签**——说明条讲的是「为什么整体都需要自备」，标签讲的是「这一本怎么读」，两件事不能合并。

#### 分组而非混排（解决 PRD 与 ARCH 的一处冲突）

PRD §7.3 说 `explore` 档「仍然展示，因为『有启发价值』本身是推荐的一部分」；ARCH §3.8 说「禁止补足到 10 本的假象，不能把 `explore` 混进来凑数再统一叫推荐」。**两者其实不矛盾，冲突只产生在视觉上「混在一起」这个做法。**设计解法是分三组，各有独立标题：

| 分组标题 | 内容 | 说明行 | 交互 |
|---|---|---|---|
| **今晚就能开始** | 第 1 位（`strong`，且满足 R1「3 小时内可完成或可直读」） | 无 | 默认展开 |
| **读完这本再看** | 第 2–4 位（`worth`，1–3 本） | 无 | 默认展开 |
| **也可以看看** | 第 5 位（`explore`，0–1 本） | 「这几本不是对症的，只是方向相关」 | 默认展开（最多 1 本，不值得折叠），**视觉权重最低**（见下） |
| **库外书目（仅有基本信息）** | 核心库不足时补充 | 「我们只有一个简介，还没人工读过，没法告诉你读完能得到什么。可以先记下书名。」 | 默认折叠 |

这样 `explore` 既被展示（PRD），又没有伪装成「推荐」（ARCH）—— 因为标题明确说了「不是对症的」。

**第三组卡片的简化规则（硬规则，落在本节 + §8.2 + §8.4）**

`explore` 卡片与上面两组不是"同一个组件的不同参数"，是**一个简化的变体**：

| 元素 | 第 1、2 组卡片 | 第三组（`explore`）卡片 |
|---|---|---|
| 书脊卡 | 56×84 | **不渲染** |
| 书名 | 18px / 590 | **16px / 510**（降一级） |
| `match_brief` | 13px / 510，2 行 | 13px / 510，2 行（保留——它仍然是「为什么给你看这本」的唯一说明） |
| 档位方块 | 3 或 2 格 | **不渲染方块** |
| 档位文字 | 11px + 方块同一行 | **11px 独立一行，`neutral-700`，无方块**（PRD 要求第 5 位卡片必须显示「换个角度」） |
| S1 回引段 | 展开区第 1 段（14px + 2px 左竖线） | **不渲染**（这组只有 1 本，回引的边际价值低于它的视觉重量） |
| `mismatch` | 显示（若有） | 显示（若有）——**越是不对症的书，越要说清哪里不对** |
| 元数据行 | 难度 · 篇幅 · 时长 | 完整（篇幅与难度在这组更重要：用户要判断"值不值得为它破例"） |
| 可用性徽标 + 主按钮 | 有 | **有**（完整保留，不打折） |
| 展开区 | S1 + S2 + S3 + 完整命中依据 + 作者译者 | S2 + 完整命中依据 + 作者译者（**无 S1、无 S3**） |

**为什么去掉方块而不是把方块改成"1 格灰"**：用户不需要被告知"这本很弱"，需要被告知"这本是另一个方向"。前一句是判决，后一句是信息。分组标题已经说了「也可以看看」。

**为什么按钮一个都不能少**：第三组是"换个角度"，不是"废纸篓"。它照样得能被点开、能被读、能被加进想读。少了按钮，它就从"推荐"降级成"陈列"。

#### 「3 本也好看」：不做 5 个固定格子

PRD §7.2 的第一条硬规则是「宁可只出 3 本，也不出 5 本凑数」。但**设计上最容易犯的错，是把 5 个位置做成 5 个固定的格子**：一旦少于 5 本，页面就出现空白格 / 灰格 / 「暂无更多」占位——用户看到的是"系统坏了"，而不是"系统很挑"。

具体规则：

| 情形 | 页面呈现 | 绝不能出现 |
|---|---|---|
| 5 本（`strong` 1 + `worth` 3 + `explore` 1） | 三组齐全，组的顺序固定 | — |
| 4 本（`strong` 1 + `worth` 3 + `explore` 0） | **第三组整组不渲染**（含标题、说明行、分隔），页面在第二组自然结束 | 空的「也可以看看」标题 |
| 3 本（`strong` 1 + `worth` 2） | 两组，页尾一行 `13px #5F6660`：「只找到 3 本对得上的」+ 「放宽点条件」文字链 | 任何第 4、5 个格子的痕迹 |
| 2 本（`strong` 1 + `worth` 1） | 同上，文案「只找到 2 本」 | 同上 |
| 1 本（只有 `strong`） | 单组单卡，**卡片宽度不收窄**（仍是容器满宽），页尾提示同上 | 一张窄卡孤零零吊在页面中间 |

三条实现约束：
1. **分组容器按"有内容才存在"渲染**（`v-if="group.items.length"`），不是先渲染再隐藏。隐藏会留下 margin / 分隔线 / `aria` 残留。
2. **减少的是格子数，不是卡片尺寸**。3 本时卡片不比 5 本时小——用户不该因为系统挑得严而看到一堆小卡片。
3. **缺口不能用一个「查看更多」或「换一批」填**。那等于把"我们只找到 3 本"包装成"还有更多你没看到"，与 R1–R8 的诚实原则冲突。

「3 本」这个数量对本页面是**正常输出而非降级**：`strong` 档本身就限制在第 1 位（PRD §7.2 第 1 条），`worth` 是 1–3 本。所以 3 本（1+2）是设计必须优化好的主场景，5 本才是上限情形。

**可选视图「阅读路径」**（PRD §7.2）：右上角 segmented control「书单 / 阅读路径」。仅当用户在第 1 步选了「我想系统地解决这个问题」时默认切到「阅读路径」。路径视图把 3 本串成 破冰 → 深化 → 行动 的纵向时间线（左侧 1px 竖线 + 序号 3 个点），**不做流程图、不做箭头插画**。

#### 库外兜底书（PRD §7.5 硬规则）

- 标签文字：「**暂无深度推荐**」（`neutral-100` 底 + `neutral-800` 字）
- **不渲染 S1 与 S3**（没有 `problem_tags` 与 `one_line_gain`，编造即欺骗），只渲染 S2（`one_liner` / 出版方简介，带「简介来自出版方」来源标注）
- 用户被推完 5 本时，库外书不出现；只在不足 5 本时补在末尾分组内

#### 状态

- 加载：骨架卡 3 张（书脊块 + 书名条 + 两行 `match_brief` 条 + **两行 S2 首句条** + 一行元数据条 + 两枚徽标块 + 按钮块）——**不含 B1（`mismatch`）行**。
  **基准是「无 B1 的真卡」，不是「真卡」**（SPEC §7.1，v1.10 对齐）：与无 B1 真卡同高（±4px），带 B1 的卡比骨架高约 21px，**这个偏差是已知代价，不是缺陷**——结果页单列竖排，卡高不一致不影响阅读；反过来为对齐在骨架里补一行空行，用户会把它读成「这里本该有内容、没加载出来」。**所以「骨架不允许比真卡矮」这句话现在作废**：上提机制生效后，同组内本来就会同时存在有 B1 和无 B1 两种卡，「与所有真卡同高」在机制上不可能成立，保留它等于给实现阶段留一个永远达不到的指标，而凑数的方式就是改骨架行高——改完 CLS 看着更好看，实际骨架与真卡错位。**一个对不上的精度指标，比一个宽松但成立的指标更糟。**
  CLS 门槛按「**骨架 → 无 B1 卡** ≤ 0.1」判定。`brand-200` 微光扫过 1200ms，`prefers-reduced-motion` 下静态灰块。超过 3s 显示「还在算」文字。
- 空态（`empty_reason: 'no_candidate'`，放宽到 L4 仍无结果）：「这几本都还差点意思」+ 主操作「放宽点条件」+ 次操作「直接看这个领域的书单」。
- 空态（`empty_reason: 'all_excluded'`）：「你把候选都排除了」+ 主操作「恢复排除的书」+ 次操作「重新诊断」。**必须区分这两种空态**——用户自己排除了全部候选和系统找不到候选，是完全不同的两件事。
- 错误态（catalog 分片加载失败）：卡片区整块替换为「书目数据没加载出来」+ 「重试」+ 「检查网络或本地数据文件」。**不隐藏已缓存的诊断结果**，用户不必重填问卷。
- 边界：`payoff` 缺失（S3 降级，PRD §8.3）→ 展开区只出 S1 + S2 全文，末尾加一行 13px `#5F6660`「这本书我们还没整理出『读完能得到什么』」。`mismatch` **不在折叠区**，它在卡片第 4 行（S2 首句之后，见「卡片信息层级」表），13px / 1 行，`neutral-800` + `TriangleAlert` + 前缀「不过：」。
- 边界：`promise` 缺失（不应发生，属数据错误）→ 卡面第 3 行整行不渲染、不留空位，展开区同样跳过 S2；卡片回落为更矮的结构。**骨架不跟着变**——骨架恒按「无 B1 的完整卡」画，真卡缺字段时比骨架矮，**不补空行对齐**（同一条理由：留白会被读成「没加载出来」）。
- 边界：结果只有 3 本（`strong + worth` 不足）→ 页尾明确写「只找到 3 本对得上的」，**不补 `explore` 充数**。

### P3 书籍详情页

**路由** `/book/:id`

**目标**：把「为什么推荐给你」讲透，并给出**确定的下一步**。这一页是版权话术的主战场（PRD §9.1），措辞含糊等于欺骗。

**信息层级**

1. 书脊卡/真封面（中尺寸 160×228，桌面左、手机居中）+ 书名（28px）+ 作者 · 译者 · 出版社 · 年份（13px `#5F6660`）
2. **`match_brief`（顶部，紧随书名之后）**：20px / 510 / `#1B1F1D`，无装饰、不截断。**它比正文大、比书名小**——这一页的核心问题就是「为什么是这本」，所以它排在可用性之前，是版面上第二个被读到的元素
3. **可用性区块（紧随其后，不放到页面底部）**：文字标签 + 一段说明（按态不同，见下表）
4. 主操作按钮（按态与 PRD §9.4 的视觉层级规则变）
5. **推荐理由（四段，本页核心）**：
   - **S1 回引段**（`situation`）：2px `brand-600` 左竖线 + 12px 内缩，14px / 行高 1.75
   - **S2 讲什么**（`promise`）：14px / `#2A2F2C`，无装饰
   - **S3 能得到什么**（`payoff`）：14px + 段前 1 行 `NotebookPen` 16px 图标引导（这是全站唯一"图标引导段落"的位置）
   - **B1 边界声明**（`mismatch`）：13px `neutral-800` + `TriangleAlert` 16px，前缀「不过：」。**与卡片同色**——它在两处是同一件事，不该在详情页换成警告色
   - 段间 20px 间距，**不加分割线**（Notion 式灰阶层级）
6. 档位（3 方块 + 文字）+ **命中依据完整列表**（2–4 个原词 chip，`neutral-100` 底，12px）：「命中了：开会不敢发言 · 怕被否定 · 每天能读 30 分钟」
7. 元数据行：难度、篇幅档、预计时长、`category_l1/l2`、ISBN（仅 byo/external 显示，便于去图书馆或购买时检索）
8. 同一主题的其他推荐书（3 本横向滑动，书脊卡 40×60），无数据则不显示该区块，不留空框

**可用性区块的三种完整文案**（照 PRD §9.1 落地，不自行改写）

| 态 | 标签 | 说明段 | 主按钮 | 按钮层级 |
|---|---|---|---|---|
| `inline` | 可直接阅读 | 「本文本为公版作品（作者逝世已满 50 年）。所用版本：｛原文 / 民国旧译 / 校注本｝，来源：｛中文维基文库 / Project Gutenberg / 项目自校｝。」+ 版权声明行 | **「阅读」** | 主按钮（实心 brand-600） |
| `bring_your_own` | 需自备电子书 | 「《书名》为在售版权作品，本站**不提供全文**。你需要在别处准备好 EPUB 或 TXT 文件，再导入这里阅读。」+ 合法获取途径（公共图书馆 / 购买渠道 / 出版社官网）+ ISBN + 译本建议 | **「导入后阅读」** | 次级按钮（描边） |
| `external` | 仅书目信息 | 「本站只有这本书的基本信息，不提供正文，也没有深入推荐。」+ 外链（标注「将离开本站」） | **「查看来源」** | 纯文字按钮 |

三条不能破的细节（PRD §9.4）：

1. **动词不许复用**：`inline` 用「阅读」，`bring_your_own` 用「导入 / 自备 / 获取」。用户扫一眼动词就知道要不要动手。
2. **视觉层级要区分**：`inline` 是主按钮（可直接点），`bring_your_own` 是次级按钮（点了还有一步）。让「多一步」在视觉上成立，而不是等用户点进去才发现。
3. **`inline` 必须标版本来源**，绝不写「全文」了事——同一本公版书有无注释、底本不同，差异极大。

**译本警示**（PRD §8.3 边界）：`translator` 缺失时显示「译本信息待补充」，并在说明段加一行「不同译本差异较大，建议自行核对译者」。

**关键交互**：整段理由可「复制」；`inline` 点按钮直接进 P5；`bring_your_own` 点按钮进 P4 并带上 book_id；`external` 点按钮 `target="_blank" rel="noopener"` 并 toast 提示「已离开本站」。

**状态**：加载（骨架：左图像块 + 右三行文本）/ 错误（书不存在 → 「这本书不在这份书单里」+ 返回）/ 边界（超长书名详情页全展开；作者缺失显示 `author:unknown` 的映射文案「作者未收录」而不是空白）。

### P4 导入引导（点「导入后阅读」之后）

**路由** `/import?book=:id`（桌面为居中 Modal `--elev-3`；移动端为底部抽屉，高度 92vh，可下滑关闭）

**目标**：把「你得自己找文件」这个坏消息，变成一条一次走完的路径。**绝不能让它读起来像「我们推了一本你读不了的书」。**

**形态**：PRD §9.2 的契约是「4 步，一次只显示一步」。v1.6 按 team-pm 口径改成 **「感知 3 步 + 校验静默」**——用户看得见的只有 3 屏，第 3 步（校验）不占屏。**但校验静默 ≠ 校验可以失败得静默**，这是本节唯一的判据。

| 契约步骤 | 用户看得见吗 | 设计落法 |
|---|---|---|
| ① 说清规则 | 首次可见 | **仅首次导入时占一屏**；之后折叠为面板顶部一行 12px 固定说明「文件只存在你的浏览器里，不会上传」 |
| ② 要文件 | 是 | 独立一屏（拖拽区 + 格式说明 + PDF 一句解释），主操作屏 |
| ③ 校验（自动） | **否** | **不占屏、不出现在进度里、不出现「正在校验」文案**。过程中的反馈只落在 ② 屏主按钮上：按钮进 loading，文案换成「正在打开…」，禁点。**成功时不给任何确认**（无对勾、无 toast、无「校验通过」） |
| ④ 对齐书目 | 是 | 独立一屏：「已识别为《书名》，是同一本书吗？」+ 「是」/「不是，改书名」。若 ISBN 命中 `core_match` 则自动跳过此屏，直接进 P5 |

因此**用户感知是 3 步（首次 4 步），契约仍是 4 步**，两者不冲突——中间那步是产品内部的事，不该让用户等一个他说不清的环节。

**「校验静默」的边界（三条规定，越界即视为缺陷）**

1. **静默只针对等待感，不针对结果**。成功路径上用户不该看到「校验」这个词；**失败路径上任何一类失败都必须显式**：在 ② 屏原位替换为对应文案（7 类，见后文），带「换个文件」/「重试」，且 4s 内出现。
2. **不允许静默吞错**。禁止 `catch {}`、禁止只打 console、禁止让按钮无限转圈——**校验可以失败，但不能失败得没人知道**。文件损坏、DRM、编码识别不出来这些恰恰是用户最需要被明确告知的。
3. **慢不等于静默消失**。若解析超过 4s，允许在 ② 屏下方出现一行 12px `#5F6660`「文件有点大，正在打开…」，**但不写「校验中 2/4」这类编造的阶段**——我们没有那么多阶段可报，编造进度就是撒谎。

**为什么成功不给确认**：确认一个用户认为理所当然的步骤（「文件打开了」），只会让他怀疑接下来是不是有什么事要发生；而且 toast 会挡住紧接着出现的识别卡。

**第 ② 屏信息层级**

1. 标题（22px）：「导入你的《书名》」—— 面板标题就带书名，让用户确认自己在给哪本配文件
2. 拖拽区（虚线 1px `neutral-500`，`--radius-md`，高 160px，`FileUp` 24px）：「把 EPUB 或 TXT 拖进来，或点这里选择文件」
3. 格式说明（12px `#5F6660`）：「支持 EPUB / TXT，50MB 以内最稳。」—— 报「建议 ≤100MB」是不诚实的：100MB 在浏览器里本来就不稳，先说稳的那条线
4. **PDF 的一句解释**（12px，`info` 色）：「PDF 是固定版式，无法重排和划线定位，第一版不做。」
5. 次操作：「先看看别的书」返回详情页

**文件体积三段（PM 裁定，三个不同处理，不是一个阈值的三种说法）**

| 体积 | 判定 | 界面 | 色彩 | 能不能继续 |
|---|---|---|---|---|
| **≤50MB** | 正常 | **不做任何提示**：拖拽区不变色、不加文案、不出现"已选择"行，选完直接进静默校验 | — | 可以 |
| **50–100MB** | 提醒（不是错误） | 选中文件后立刻在拖拽区位置显示一行 `warn`：「文件较大（｛x｝MB），导入后可能卡顿。」+ 双按钮「仍然导入」/「取消」 | `--warn`（`#8A5A0B`，白底 5.92:1） | **可以**，用户自己决定 |
| **>100MB** | 拒绝 | 「超过 100MB 的文件在浏览器里无法可靠解析。」+「了解」/「换一个文件」。**不出现「仍然导入」** | `--danger` | 不可以 |

为什么把 >100MB 从「仍然导入」改成「直接拒绝」：
- 50–100MB 的后果是**卡**（可恢复的体验问题），>100MB 的后果是**解析中途内存崩**（不可恢复的失败）。用同一句「可能卡顿」描述两者，是在拿用户的 3 分钟赌一个我们已知会失败的路径。
- 拒绝文案里给出**原因**（「浏览器里」）而不是"不支持"，因为这是能力边界不是内容限制——用户换到桌面阅读器还能打开这本书，我们不拦着他去。
- **拒绝态必须同时给「换一个文件」**，否则用户在这一屏就卡死了。

**第 ④ 屏**：识别结果卡（书名 + 作者 + 若有封面则显示 40×60）+ 两个按钮「是，就是这本」（主）/「不是，改书名」（次，点开展开输入框）。

**关键交互**

| 操作 | 反馈 |
|---|---|
| 拖拽悬停 | 边框变 `brand-600` 实线 + 底 `brand-50`，120ms |
| 选择文件 | 立即显示文件名 + 大小 + 移除按钮，进入校验 |
| 校验中 | 真实阶段文字（「检查文件完整性…」「读取章节…」），不用假进度条；<300ms 不显示 |
| 成功 | ④ 屏确认后 → 成功态（`CircleCheck` + 「已导入，共 12 章」）→ 400ms 后主按钮变「开始读」，**不自动跳转**（让用户看清结果） |
| 失败 | 在原位置替换为错误块（不弹 toast），错误码折叠在「查看技术详情」里 |

**失败态文案（照 PRD §9.2 表格逐条落地，验收按此表检查）**

| 失败类型 | 用户看到的话 | 附带动作 |
|---|---|---|
| 格式不支持 | 「这个文件是 ｛.pdf / .mobi / .azw3｝，暂时读不了。目前支持 EPUB 和 TXT。」 | 「了解」+「查看支持的格式」 |
| 文件损坏 / 解析失败 | 「文件打不开，可能下载不完整或不是标准 EPUB。建议重新下载一次。」 | 「查看技术详情」（折叠，给错误码）+「换一个文件」 |
| 加密 / DRM | 「这本书带 DRM 加密，只有购买它的那个阅读软件能打开。我们不能也不应该绕过它。」 | 「了解」。**不提供任何破解指引、不外链解密工具** |
| 文件偏大（50–100MB） | 「文件较大（｛x｝MB），导入后可能卡顿。」 | 「仍然导入」/「取消」。**用 `--warn` 不用 `--danger`**，这是提醒不是错误 |
| 文件过大（>100MB） | 「超过 100MB 的文件在浏览器里无法可靠解析。」 | 「了解」+「换一个文件」。**直接拒绝**，不给「仍然导入」——这个体积不是卡顿，是大概率解析中途崩溃，让用户冒险等于看他白等 3 分钟 |
| TXT 编码识别失败 | 「这个 TXT 的编码认不出来，可能出现乱码。请选择：UTF-8 / GBK / 自动重试」 | 三选一 + **实时预览前 200 字** |
| TXT 无章节结构 | 「这个 TXT 没有章节标记。我们会按空行和字数自动分章，你也可以之后手动调整。」 | 「按默认分章」/「先不分章」 |
| 空间不足 | 「浏览器存储空间不够了。可以删除一些已下载的书再试。」 | 「管理已下载的书」 |

**这 7 类失败是 7 个独立界面，不是一张通用 error 页**（PM 硬约束）。其中 4 个带有独特的交互控件或独立形态，不能复用一个错误模板：
- 编码识别失败 → 三选一单选组 + 前 200 字实时预览区（换编码即刷新预览）
- 文件偏大（50–100MB）→ 确认式双按钮（「仍然导入」/「取消」），**不是错误**（用 `--warn` 不用 `--danger`）
- 文件过大（>100MB）→ 拒绝态，**只有一个「换一个文件」**（不能给「仍然导入」），用 `--danger`
- TXT 无章节 → 二选一（「按默认分章」/「先不分章」），**也是选择不是错误**（用 `--info`）

错误码与文案的映射写成 `code → { 文案, 图标, 语义色, 附加控件 }` 四元组；缺映射时降级为「导入没成功，换个文件试试」+ 强制显示错误码，**不允许静默失败**。

**11 个错误码 → 7 个界面（SPEC P0-8 的要求，PRD 定的是 7 类措辞）**

SPEC 的 P0-8 按原因分 **11 种**失败态，PRD 定的是 **7 类**主因的措辞。两者不冲突：**界面是 7 个，码是 11 个，同族的码共用一个界面、只换文案**。三条规则：

| 规则 | 说明 |
|---|---|
| 一码一界面归属 | 11 个码必须全部映射到 7 个界面之一，不允许出现「没有界面的码」（`default` 兜底界面也算一个，但它必须存在且给错误码） |
| 同族换文案不换版式 | 例如编码族内部的 GBK / GB18030 / UTF-8 推断失败，界面完全一样（三选一 + 200 字预览），只有顶部那句话换；**不允许为同族的码各画一屏** |
| 跨族不共用文案 | 「文件损坏」与「格式不支持」不许共用「导入没成功，换个文件试试」——前者要建议重新下载，后者要说明支持什么格式。共用文案等于把 7 类压成 1 类 |

> 码表以 ARCH `ImportError` 的 11 个码为准（`E_IMPORT_*` / `E_TXT_*`），设计侧只保证两件事：每个码都有归属界面；不同族的码不共用同一段文案。**架构师给出码表后，按上表把码填进 7 个界面的「附加控件」列即可，不需要改版式。**

> 错误块不显示 `ImportError.detail`（那是给开发者的）。所有面向用户的文案来自 `code → 文案` 映射表，缺映射时降级为「导入没成功，换个文件试试」+ 强制显示错误码，**不允许静默失败**。

### P5 阅读器

**路由** `/read/:bookId/:chapter?`

**目标**：消失。屏幕上除了正文几乎什么都没有。

**信息层级**

1. 正文（唯一常驻元素），18px 默认 / 1.8 行高 / `#2A2F2C` / 纸白，列宽 34em 居中
2. 章名（顶部，随滚动淡出）
3. 阅读进度：底部 2px 细线（`neutral-200` 轨道 + `brand-600` 进度），**不显示百分比数字**；点击展开为「第 3 章 · 41%」
4. 划线：**一种颜色**（`--highlight`，见 §3.7），14% 叠加底 + 2px 下边线。已验算：四种纸色上正文对比 10.35–11.88:1，边线 3.71–4.89:1。工具条上的划线按钮就是「划线」本身，点开**没有色板**——没有第二种颜色可选，就不给一个假的色板
6. 笔记入口：点击已有划线 → 行内浮出小气泡（「写笔记」/「删除」），不跳页
7. 章末小测：章节末尾自然出现卡片（不弹窗）：「这一章记住了吗 · 5 道题」+ 「开始」（次级按钮）+ 「跳过」
8. 翻章：左右边缘点击区 + 键盘 ←/→；章节末尾有「下一章」按钮

**顶部/底部工具条**（点击屏幕中央 1/3 区域切换，2.5s 无操作自动隐退）
- 顶部：返回 / 章名 / 目录 `List` / 更多
- 底部：上一章 / 进度 / 下一章 / 排版 `Type`（字号 5 档 + 行距 3 档 + 纸色 4 种）/ 划线 `Highlighter`
- **隐藏时不留任何占位**，正文高度不变（避免 CLS）

**状态**

- 加载：正文骨架（6 行灰条），不用 spinner。
- 空态（章节为空/损坏）：「这一章没读到内容」+ 「跳到下一章」+ 「换个文件重新导入」
- 错误态（文件丢失，localStorage 被清）：说明 + 「重新导入」（保留笔记，按书籍 hash 关联）
- 边界：超长段落、阿拉伯数字与英文混排（`text-autospace`）、生僻字缺字（回退字体时行高不跳）、图片（EPUB 内图片宽度 100%，`aspect-ratio` 占位防 CLS）

**动效克制**：翻页**不做**任何滑动或翻书动画（`MOTION_INTENSITY = 3`）。只做 120ms 透明度过渡。理由：阅读中任何非必要的空间运动都会打断眼动。

### P8 心理援助资源

**路由** `/crisis`

**目标**：给一个出口，并且不把它做成产品功能。这一页存在的唯一理由是「用户此刻可能需要的不只是读书」。


**信息结构（自上而下）**

| # | 元素 | 规格 |
|---|---|---|
| 1 | 标题 | 「心理援助资源」，22px / 590 |
| 2 | 核对月份 | 「最近核对：YYYY-MM」，12px `#5F6660`，等宽数字；数据来自 `crisis_resources.json` 的 `verified_at` 字段，**前端不 hardcode** |
| 3 | 一句说明 | 「下面是公开可查的心理援助渠道。是否联系、联系哪一家，由你自己决定。」13px `#5F6660`。**不写「我们建议你」**——建议是一种压力 |
| 4 | 资源列表 | 按地区分组（无地区字段的归「全国」置顶）。每条：**机构名**（15px/510）/ **地区** / **号码**（16px，`JetBrains Mono` + `tabular-nums`，`tel:` 链接）/ **最近核对日期**（12px `#5F6660`）。条目之间 1px `border-soft` 分隔，不用卡片盒子 |
| 5 | 页底 | 「**号码打不通或已变更，请提 issue 告诉我们。**」+ issue 链接（`target="_blank"`，标「将离开本站」） |

**四禁止**（PM + SPEC §7.1.1 三条底线 + team-lead 2026-10-18 加的第四条，缺一条即退回）：

| # | 禁止 | 为什么 |
|---|---|---|
| 1 | **禁止任何书籍推荐**（书卡、书单、"顺便推荐"、同主题书目） | 把求助和读书绑在一起，正是这条资源条要避免的暗示 |
| 2 | **禁止「读完这本书你会好起来」类关联**（含「阅读也能帮到你」「很多读者读完……」，以及任何把阅读当疗法的措辞） | 这是越界的承诺，而且把责任推回给一个正在难受的人 |
| 3 | **禁止阅读入口与进度提醒**（「继续读」「你今天还没读」「已读 3 章」都不许出现） | 这一页不服务留存 |
| 4 | **禁止任何埋点统计** | 无 page view、无自定义事件、无 `utm_`、不引第三方脚本；`/crisis` 是全站**唯一零观测页面**。用户点进来是因为他不太好过，**那一刻的行为不该成为我们的数据**。实现上要求这一页不 import 任何统计模块，构建产物里该路由 chunk 不含埋点代码 |

**返回：只给一个普通的「返回上一页」，不给任何方向性引导**

| 项 | 规格 |
|---|---|
| 形态 | 页顶左侧一个 44×44 命中区的返回箭头（`ArrowLeft` 24px），页底一行 13px 文字链「**返回上一页**」 |
| 行为 | `history.back()`——把他送回**他来的地方**（可能是 `/about`，也可能是浏览器上一个页面） |
| 禁止的文案 | 「返回推荐结果」「继续选书」「回到书单」「看看为你挑的书」——**一个都不许**。那等于在他最脆弱的一刻把他推回货架 |
| 无历史可退时 | 退化为指向 `/` 的中性文字链「**回到首页**」，不写「去选书」 |
| 不做的事 | 不做"你可能会想看"、不做「离开前要不要保存」、不弹挽留 |

**入口白名单（写死，不得新增第四处）**

| # | 入口 | 说明 |
|---|---|---|
| ① | **结果页危机条按钮** | 唯一主入口，按需出现（只在「情绪与自我」域） |
| ② | **`/about` 页固定文字链接** | **全站唯一一处固定入口**，只有这一条，不进任何分组、不加图标 |
| ③ | URL 直达 | `/crisis` 可被直接访问 |

**实现约束（让白名单可被机器数出来，而不是靠人记）**：上表三个入口的元素上**必须带 `data-crisis-entry` 属性**，取值只能是 `crisis-bar` / `about` / `direct`。全站带该属性的节点数就是入口数——验收层直接数节点，不需要读文案、不需要判断语义。**新增第四处入口 = 出现第四个 `data-crisis-entry`，CI 当场红。**

> 除了这三处，**不得新增任何入口**：底部导航、设置页、书库空态、错误页、导入失败页、toast 里都不加。入口越少越说明它是应急通道而不是功能；但完全零入口（只能靠记 URL）就变成藏起来了，那也不是要的效果——`/about` 那一处固定链接的意义是「想找的时候能找到」，不是「随时提醒你」。

**无障碍**：`tel:` 链接的 `aria-label` 写成「拨打 北京市心理援助热线 010-82951332」（读屏不会把号码读成数字串）；日期写全（`2026-08`，不写 `8月`）；列表用 `<ul>`，每条 `<li>` 内机构名做 `<h2>` 以外的普通文本（避免标题层级污染）。返回箭头 `aria-label="返回上一页"`。

**导航位置**

| 项 | 决定 |
|---|---|
| 页面清单排序 | **P8**，排在 P7 笔记页之后（照 SPEC §7 的清单） |
| 主导航 | **不列**。主导航是「书库 / 笔记 / 设置」三项，加第 4 项等于把安全网做成一个产品功能，会把「我在读什么」这条主线稀释掉；而且它只在特定情境下有用，常态下是噪音 |
| 若必须进导航 | 收进「更多」而不是与 P6/P7 平级；文案用「心理援助资源」，**不用「求助」「心理援助」四个字以下的缩写** |

**状态**：数据为空 → 「资源列表暂时没加载出来」+ issue 链接（**不给假数据、不给「暂无」**）；这页没有 loading 态（静态 JSON，直出）。

## 8. 符合度的视觉表达

### 8.1 为什么不用百分数

1. **分数是序数，不是基数**。规则加权打分给出的是排序能力，不是概率。「83% 符合」在数学上没有定义——83% 的什么是符合？用户会理所当然地理解为「有 83% 的可能性我会喜欢」，而我们没有这个数据。
2. **假精度会招来无法回答的追问**。一旦出现 83% 与 79%，用户必然问「差在哪 4%」。我们的答案是「权重不同」——这个答案对用户没有价值，只会削弱信任。
3. **分数不稳定**。权重是可以在版本迭代中调整的，一调所有百分数全变。显示出具体数值等于承诺一个我们无法维持的 SLA。档位则天然抗变化（只要排序不变，档位就不变）。
4. **百分数不能承载行动建议，档位可以**。「高度契合」可以说清「这本直接对着你的问题」；「83%」什么都说不清。
5. **上百本书的分数就是长尾分布**。大量书会挤在 40–60% 区间，用户看到一片「52%」「49%」只会更困惑。

**替代方案：3 档 + 文字标签 + 命中依据（PRD §7.3 的三层结构）。**

### 8.2 三档的命名与阈值（全项目唯一写法）

枚举值以 **`Tier`（types-draft）+ PRD §7.2/§7.3 + SPEC §6.3⑦** 为准（三处逐字一致，且明文禁止别写法），中文显示名以 **PRD §7.3 固定三词**为准，一一对应，不存在第二套写法：

| `Tier` | 阈值（`score_bp`） | 中文显示名（固定） | 语义 | 方块填充 | 出现位置 |
|---|---|---|---|---|---|
| `strong` | ≥ 8000 | **高度契合** | 「这就是你现在要的」 | 3 / 3 | 第 1 位 |
| `worth` | 6000 – 7999 | **较为契合** | 「方向对，但有一处不贴」 | 2 / 3 | 第 2–4 位 |
| `explore` | < 6000 | **换个角度** | 「不是对症的，但方向相关」 | **不显示**（见下） | 第 5 位 |

> **为什么不叫「备选」「推荐」「猜你喜欢」**：「备选」读作次品，「探索」读作没结论，「强烈推荐 / 你可能喜欢 / 猜你喜欢」读作「书好不好」。而我们要表达的是「对你多合适」。「换个角度」是收益不是降级——用户看到它知道该拿它做什么（换个方向想这件事），而不是知道它排第五。
>
> **只允许一种写法**：`strong / worth / explore`。本表中文名固定三词，「值得一试 / 备选探索」作废；`fit` / `high` / `mid` / `low` 四个值在 PRD 与 SPEC 里都是明文禁止的。设计给的 token 路径与 CSS 变量必须能在代码里逐字找到——否则就是返工。

**第三档不显示档位方块（硬规则）**：`explore` 卡片**不渲染符合度指示器**，但**保留「换个角度」四个字的文字标签**（PRD 要求第 5 位卡片上看得见它），其余只留可用性标签与按钮。

为什么去方块留文字：三档里它只有 1 格，这个 1 格方块的全部信息量是「这本不行」，而分组标题「也可以看看」+ 说明行「这几本不是对症的，只是方向相关」已经把定位说完了——同一句话在卡上说两次，就把「有启发价值」的推荐意图变成了抱歉。**文字留着是因为「换个角度」是收益陈述，方块留着是程度判决**，删的应该是后者。规则落在 §8.4 与 P2「第三组卡片的简化规则」。

### 8.3 三档的视觉方案（实测驱动）

**先给一个实测结论，它决定了方案形态**：

| 档位 | 浅色值 | 对白卡 | 与 `strong` | 与 `worth` |
|---|---|---|---|---|
| `strong` 高度契合 | `#2F6449` | 6.91:1 | — | — |
| `worth` 较为契合 | `#3D4340` | 10.12:1 | **1.46:1** | — |
| `explore` 换个角度 | `#5F6660` | 5.91:1 | **1.17:1** | **1.71:1** |

**三档的颜色两两对比度只有 1.17–1.71:1**。这意味着：如果把三档做成三个不同颜色的圆点或标签，**在任何屏幕上都无法可靠区分**（远低于 3:1 的可分辨经验底线）。所以颜色不能当第一编码——这不是审美偏好，是算出来的约束。

**最终方案：可数方块 + 文字标签，颜色只做强化。**

```
strong    [■][■][■]  高度契合
worth     [■][■][ ]  较为契合
explore   （无方块）  换个角度
```

| 项 | 规格 |
|---|---|
| 指示器 | 3 个 8×8px 方块，`--radius-xs`(3px)，间隙 3px，总宽 30px |
| 填充 | `strong` 3 个全填 / `worth` 2 个。填充色：`strong` `brand-600`，`worth` `neutral-800`；未填方块用 `neutral-200` 轨道色。**`explore` 不渲染指示器**（§8.2 硬规则） |
| 文字标签 | 11px / 510 / 与方块同一行，间距 8px。颜色同填充色。**`explore` 卡片只有这个文字标签、没有方块**（`neutral-700`，11px），且**必须渲染**——PRD 要求第 5 位卡片上看得见「换个角度」四个字 |
| 暗色 | 填充色换 `brand-300` / `#C2C8C3`，轨道 `#2E3532` |
| 无障碍 | 容器 `role="img"` + `aria-label="高度契合，第 3 档（共 3 档）"`；3 个方块 `aria-hidden`。`explore` 卡片无指示器，靠分组标题 `aria-labelledby` 说明 |

**为什么是方块而不是圆点或分段条**：
- 圆点（dot）在 8px 下会被读成「状态灯」，且三个圆点容易被误认为「加载中」的指示器。
- 分段条（一根条切成 3 段）在小尺寸下段与段的间隙会被抗锯齿吃掉，变成一根实线，可数性丧失。
- 方块有明确的直角边界，8px 下依然可数，且视觉上「像刻度」——这与「档位」的语义直接对应。

**为什么档位文字用 11px**：它必须与方块同处一行且不抢书名的视觉权重。11px + 510 在一行 44px 高的区域内可读（`#5F6660` 在 `#FFFFFF` 上 5.91:1，达标）。

**为什么 `explore` 不用红/橙**：它不是错误，只是「不是首选」。用警示色会让用户觉得自己的问题被否定了。三档全部落在中性/品牌色域内，情绪恒定。

### 8.4 排序如何在视觉上体现

**不显示序号。** 顺序由**分组标题 + 视觉密度**表达：

- 第 1 组「今晚就能开始」：卡片给 1px `brand-400` 描边（实测对白卡 3.25:1，作为图形边界达标）+ 档位行前加「最对症」文字标签（11px，`brand-700`，`brand-50` 底，`--radius-xs`）。
- 第 2 组「读完这本再看」：1px `neutral-300` 描边，无标记。
- 第 3 组「也可以看看」：无书脊卡、无档位方块、无 S1 回引段，书名降为 16px，**视觉权重最低**，但可用性标签与主按钮完整保留（简化规则见 P2 的「第三组卡片的简化规则」表）。

理由：
1. 档位 + 分组标题已经表达了强度与先后。同一组内第 2 与第 3 的差别，来自权重里某个 0.05 的系数，没有决策意义。
2. 序号会诱导用户把「排名」读成「质量排名」，进而问「为什么这本排第 2」——这和百分数是同一类错误：给出无法支撑的精度。
3. 「`01 / 02 / 03`」这种编号视觉是 2026 年 AI 生成页面的强特征（每节一个编号标签），要主动规避。
4. 用户真实行为是「看前 2–3 张然后决定」。而 PRD §7.4 的 R1（第 1 位必须 3 小时内可完成或可直读）已经保证第一张卡是「今晚能开始」的那本——这比任何序号都更能指导行动。

## 9. 可用性三态的视觉区分

### 9.1 最小视觉成本方案

三态在卡片里必须同时满足：一眼可分 / 不抢档位的注意力 / 落在一个固定位置（用户第二次就能预判）。

**方案：同一位置的纯文字标签，靠「底色有无 + 不同动词 + 按钮视觉层级」三重区分。**

PRD §9.1 明确要求卡片上是**文字标签，不用图标**——这条我采纳并强化：图标从卡片上撤掉，只在详情页与文件列表使用。理由：卡片上已经有书脊卡、档位方块两组图形，再加第三个图形符号会让 280px 高的卡片变成符号拼盘；而**动词本身就是最强的编码**（PRD §9.4 要求三态不用同一个动词）。

| 态 | 标签样式 | 标签文案 | 主按钮文案 | 按钮层级 |
|---|---|---|---|---|
| `inline`（公版内置） | `brand-50` 底 / `brand-700` 字 / `--radius-xs` / 高 20px / 11px 510 | **可直接阅读** | **阅读** | 主按钮（实心 `brand-600`） |
| `bring_your_own`（需自备） | `neutral-100` 底 / `neutral-800` 字 / 同尺寸 | **需自备电子书** | **导入后阅读** | 次级按钮（1px 描边） |
| `external`（仅书目） | **无底**，仅文字，`neutral-700` | **仅书目信息** | **查看来源** | 纯文字按钮 |
| `read-local`（已导入过，`ReaderEntry` 第四态） | `brand-50` 底 / `brand-700` 字 | **已导入** | **继续读** | 主按钮（实心） |

`read-local` 是 ARCH `ReaderEntry` 判别联合里的第四种情况，PRD 三态表里没有。它必须单独设计，否则用户导入过的书会显示「需自备电子书」，看起来像没生效。

**`inline` 的标签必须带版本副行**：主标签「可直接阅读」右侧 12px `#5F6660` 显示「公版原文 · 附白话注释」（取自 `license_note` / `public_domain_reason`）。理由：同一本公版书有无注释、底本不同，差异极大，用户有权知道自己在读哪一个（PRD §9.4 第 3 条）。

**为什么这个组合可行**：
- **底色有无**是最强的区分信号（有色 / 灰 / 无），且不依赖色相分辨——色弱用户也能区分「有底 vs 无底」。灰度截图上三个标签依然可分。
- **动词不同**（阅读 / 导入 / 查看）承担第二重编码，且是用户扫读时唯一必须读到的字段。
- **按钮视觉重量递减**（实心 → 描边 → 纯文字）与「可即刻阅读的确定程度」同构。PRD §9.4 要求「`inline` 是主按钮、`bring_your_own` 是次级按钮，让『多一步』在视觉上成立」，这里正好落地。
- 三层编码没有一层依赖色相，因此**即使把界面去色也仍然可判断**。

### 9.2 文案原则：把「读不了」变成「下一步做什么」

| 禁止的写法 | 采用的写法 | 理由 |
|---|---|---|
| 「暂无资源」 | 「需自备电子书」 | 「暂无」归因于我们的缺失；「需自备」是动作，且承诺了可行性 |
| 「不可用」 | 「仅书目信息」 | 「不可用」是在否定用户的时间；后者是如实描述我们提供了什么 |
| 「该书籍不支持在线阅读」 | 「导入后阅读」 | 前者以系统为中心，后者是用户接下来要做的事 |
| 「版权受限，无法提供」 | 「这本书为在售版权作品，需自备电子书」 | 承认限制 + 立刻给出路径 |
| 「开始阅读」（用在 `bring_your_own` 上） | 「导入后阅读」 | PRD §9.4 硬规则：措辞含糊等于欺骗 |

**四条硬规则（第 3、4 条进验收）**：
1. 任何 `bring_your_own` 或 `external` 的卡片，**必须紧邻一个可点的下一步**。不允许出现「无法阅读」且没有按钮的卡片。
2. 标签文案控制在 **7 个汉字以内**，保证在 320px 宽的手机上与档位同排不换行。
3. **禁止把「需自备」说成故障**：全站不得出现「暂不可读」「资源缺失」「暂不支持在线阅读」；不得出现灰掉（`disabled`）的可读按钮。首发 300 本里约 250 本需要导入，且「习惯与行动 / 工作与意义 / 认知与思考」三个域结构性没有 `inline` 书（扩库也解决，因为这类书全在版权期内）——所以「要自备」是**常态不是异常**。把它说成故障，用户会等一个永远不会来的版本。
   验收检索：选「习惯与行动」域，结果页全文检索 `暂不可读|资源缺失|暂不支持在线阅读|灰`，命中数必须为 0。
4. `inline` 卡片标签必须带版本副行（见上表下的说明）。

**一个容易被忽略的立场问题**：PRD §10.3 给出 `inline` 只占 25%——**4 本书里有 3 本需要自备**。所以 `bring_your_own` 是**常态不是异常**。它在视觉上绝不能用警示色、不能被做成「缺货提示」，否则用户会觉得这个产品什么书都没有。它用中性色，且排序上已经被 ARCH 的 `availability` 因子（权重 500）温和地向后推了——**界面不需要再补刀**。

## 10. 空状态与边界

统一规则：**空状态必须包含「发生了什么 + 为什么 + 一个可点的下一步」三件套**。禁止只放一句「暂无数据」。所有空状态用同一个 `Inbox` 图标（32px，`neutral-400`），不按场景画不同插画——插画会引入第二套视觉语言。

| 场景 | 标题 | 说明 | 主操作 | 次操作 |
|---|---|---|---|---|
| 诊断无结果（`empty_reason: 'no_candidate'`，L4 后仍无） | 这几本都还差点意思 | 你的描述里同时提到「记不住」和「想放松」，这两个方向的书不太重合。 | 放宽点条件（回 P1，保留已选） | 直接看「记忆方法」书单 |
| 诊断无结果（`empty_reason: 'all_excluded'`） | 你已经把候选都排除了 | 上一轮你标了 6 本「读过 / 不想看」，候选取不满 3 本。 | 恢复排除的书 | 重新诊断 |
| 库外书（有元数据无深度字段） | **暂无深度推荐** | 「这本书我们只有一个简介，还没人工读过、没法告诉你读完能得到什么。你可以先记下书名。」 | 记下书名（加入想读） | 查看来源 |
| 搜不到书 | 没找到「xxx」 | 换个关键词试试，或者用一句话描述你想解决的问题。 | 用描述找书 | 清空筛选 |
| 导入失败 | 具体原因（见 P4 错误表） | — | 重试 | 改用 TXT / 换个文件 |
| 无笔记 | 划线从第一段就可以开始 | 选中任意文字就能划线、写笔记。 | 回到上次读的地方 | 了解笔记怎么用 |
| 书单全部读完 | 这一单读完了 | 5 本，34 条笔记，2 次小测复习。 | 重新诊断一次 | 查看我的笔记 |
| 搜索无结果（库内，带筛选） | 这个组合下没有书 | 试着去掉「已读完」或缩短时间范围。 | 清除筛选 | — |

**边界处理**

- 超长书名：列表卡 2 行截断（`-webkit-line-clamp: 2`），详情页全展开，均不加 tooltip（hover tooltip 在触屏无效）。
- 超长作者串（多作者）：列表只显示第一作者 + 「等」，详情页全列。
- 结果不足 5 本（`strong + worth < 3`）：明确写「只找到 N 本对得上的」，**不补 `explore` 充数**（ARCH §3.8 硬规则）。
- `axis_sources` 有 `'default'`（用户跳过了题）：结果页顶部一行如实说明「你跳过了 2 个问题，这几本主要按主题和篇幅匹配」。
- 零宽字符/异常空白：数据层清洗，UI 不处理。
- 极端字号（用户 22px + 320px 屏）：chip 与徽标允许换行，卡片高度自适应，禁止水平滚动。
- 书库列表超过 100 项：虚拟滚动（`Library` 页才需要，推荐结果页永远 ≤ 8 项，不做无限流）。

| Token | 值 | 用途 |
|---|---|---|
| `--ease-standard` | `cubic-bezier(0.2, 0, 0, 1)` | 绝大多数状态变化（快出慢收） |
| `--ease-exit` | `cubic-bezier(0.4, 0, 1, 1)` | 元素退出（退得比进来快） |
| `--ease-enter` | `cubic-bezier(0.05, 0.7, 0.1, 1)` | 元素进入（轻微减速，无回弹） |
| `--ease-linear` | `linear` | 仅进度条与骨架位移 |

**禁止弹性缓动**：全站不使用 `cubic-bezier(0.68, -0.55, 0.265, 1.55)` 及任何 `overshoot`/`back` 类曲线。理由：回弹在产品界面里表达「玩具感」，与「诊断器」的严肃语气冲突；且回弹会让连续操作（快速连点 chip）产生视觉余震。

### 11.2 哪些地方做，哪些地方不做

| 做 | 为什么 |
|---|---|
| chip / 按钮 / 链接的状态过渡 80–150ms | 让「我点到了」变得确定 |
| 理由展开/折叠 200ms 高度 + 透明度 | 空间连续，用户知道内容从哪来 |
| 工具条淡入淡出 200ms | 阅读器需要「消失」的感觉 |
| 骨架微光 | 只在真的等待时出现 |
| 档位方块在卡片进入视口时延迟 30ms 依次填充（仅首次） | 一处克制的「发现奖励」，帮助用户第一次理解「3 个方块 = 3 档」 |

| 不做 | 为什么 |
|---|---|
| 页面切换动画 / 路由过渡 | local-first 应用切换是瞬时的，加过渡是在假装网络延迟 |
| 滚动视差、`IntersectionObserver` 逐节 fade-in | AI 生成页面的最强特征之一，且干扰扫读 |
| 书脊卡的 hover 3D 倾斜 | 装饰，且在小尺寸下会让文字失焦 |
| 「AI 正在思考」打字机/点阵动画 | 我们是规则打分，做这个等于撒谎 |
| 数字滚动增长（如 62 → 0 的动画） | 无真实含义的数字动画 |
| 列表项 stagger 入场（每项延迟 50ms） | 让列表等待，纯装饰 |
| 任何超过 400ms 的动画 | 产品界面上限 |

**`prefers-reduced-motion: reduce`**：所有 `transform`/`height` 过渡改为 `opacity` 0ms 直切；骨架微光改为静态 `brand-100` 块；自动隐退的工具条改为常驻（改为点击切换）。焦点环**不减弱**。

## 12. 无障碍

### 12.1 对比度底线（全部实测，见第 3 节表格）

- 正文文本 ≥ 4.5:1 —— 最低实测组合是 `#5F6660` on `#F4F6F4` = **5.44:1**。
- 大字号（≥24px 或 ≥18.66px/粗）≥ 3:1 —— 实际全部远超。
- UI 控件边界与图形 ≥ 3:1 —— 输入框/复选框边界用 `neutral-500`（3.13–3.40:1）；暗色用 `#6B736D`（3.42–3.74:1）。
- 焦点环 ≥ 3:1 —— 浅色 `brand-600` 6.91:1，暗色 `brand-300` 8.30:1。
- **不靠颜色单独传达信息**：符合度用「填充方块数 + 文字」，可用性用「底色有无 + 文字」，错误用「图标 + 具体文字」，**划线用「2px 下边线 + 同色叠加底」**（v1 单色：叠加底对纸底只有 1.13–1.15:1，**能看出「这里有划线」的其实是那条 2px 边线，所以边线不可减到 1px、不可去掉**）。任何只看灰度的场景都必须仍然可判断。四色 + 线型的双通道方案在 §3.7 附录，v1 不启用。

### 12.2 键盘

| 区域 | 键位 |
|---|---|
| 全局 | `Tab` 顺序 = 视觉顺序；`/` 聚焦搜索；`Esc` 关闭当前层 |
| P1 问卷 | `↑`/`↓` 在 chip 组内移动，`Space` 选中，`Enter` 提交 |
| P2 卡片列表 | `J`/`K` 上下切卡；`Enter` 展开理由；`R` 开始读 |
| 阅读器 | `←`/`→` 翻章；`Space` 下翻一屏；`H` 划线；`N` 写笔记；`Esc` 退出全屏 |
| 模态/抽屉 | 焦点陷阱；`Esc` 关闭后焦点回到触发元素 |

### 12.3 焦点环

`outline: none` **全站禁止**。统一 `:focus-visible` 规格：

```
box-shadow: 0 0 0 2px var(--bg), 0 0 0 4px var(--focus-ring-color);
```

双层（先背景色再品牌色）保证在任何底色上都能看清，包括 `brand-50` 浅底与深色纸。

### 12.4 屏幕阅读器

- 所有纯图标按钮必须有 `aria-label`（如目录按钮 `aria-label="打开目录"`）。
- Lucide 1.0 默认给图标加 `aria-hidden="true"`，**不要手动删**；图标所在的按钮自身必须有可读名称。
- 符合度指示器：容器 `role="img"` + `aria-label="高度契合，3 档中的第 3 档"`；3 个方块为装饰 `aria-hidden`。
- 可用性徽标：不做 `aria-label`，直接用文本节点（「需自备电子书」本身就是可读文本），避免重复播报。
- 阅读进度：`role="progressbar"` + `aria-valuenow/valuemin/valuemax` + `aria-valuetext="第 3 章，全书 41%"`。
- 理由展开区：`<button aria-expanded aria-controls>`。
- 结果数量变化（「5 本里有 1 本很对症」）：`aria-live="polite"`，只播报一次。
- 页面切换后焦点移到 `<h1>`（`tabindex="-1"`）。

### 12.5 触摸与移动

- 所有可点区域 ≥ 44×44px（视觉尺寸可小，用 `::after` 扩展命中区）。档位标签不可点，故可小于 44px。
- chip 间距 ≥ 8px。
- 手机端主按钮吸底并加 `padding-bottom: env(safe-area-inset-bottom)`。
- 阅读器左右翻页热区宽 15%，中间 70% 为工具条切换区，避免误触。

### 12.6 其他

- `<html lang="zh-CN">`。
- 主体内容有 skip link（「跳到正文」）。
- 尊重系统字号放大：界面用 `rem`，用户浏览器放大到 200% 时纵向布局不破。
- 表单（搜索框、笔记输入）永远有可见 `<label>`（可用 `sr-only`），不靠 placeholder 当标签。

## 附录 A 交接给前端的验收清单

按 P0 优先级排序，逐条可测：

> **总则（v1.9，适用于本附录每一条「检索命中 0 即为通过」类验收）**
> 一律适用 **SPEC §12** 的三态规则（`pass` / `fail` / **`not-verified`**），**原文不在此重复**——状态语义的作用域是全项目所有 `*:audit` / `test:*`，不只是本附录全部条目，所以它归 SPEC。
> 本附录只落四件附加要求：
> 1. **每条必须写明检索范围与分母**（扫哪些路径、扫到多少）。一条写着「命中 0」的检查，可能只是**没扫到该扫的地方**——它和「真的干净」在报告里长得一模一样，而后者才是我们想知道的。
> 2. **范围为空 = 未验证，不是通过**。`tools/copy-audit.mjs` 与 `tools/doc-audit.mjs` 已按此实现：前者 0 文件输出「未验证」，后者分母 ≤0 直接 fail。
> 3. **分母要选「本来可能出问题的地方」，不是选「我们实际检查的条数」**（team-lead v1.11）。锚点检查的分母 = 标题数 + 锚点链接数（每一个可能出问题的位置），不是链接数（我们实际核对过的对象）；`grep 状态很差` 的分母 = **扫了多少个文件**，不是扫到多少个匹配——因为它要抓的是「文件根本没扫到」。
> 4. **报数取最坏值**（team-lead v1.13 升格为报数规范）：**凡是区间，报会让人更保守的那一端。** 例：第 3 屏高度 864–904 报 **904**，因为报 864 的人下一步一定是"还有余量"；控件消失带走 92px 报 **92**（不是 60）；一屏能看几张报 **2.59**（不是 2.83）。**这条不是精确性要求，是决策方向要求**——同一个数报错两端，一个让人谨慎，一个让人放心，而人在两种状态下做的判断不一样。
> **一个从没真正跑起来的检查，比没有检查更危险——它会让人以为门是关着的。** 这与删掉「截图人工核」同一理由：**门禁的可信度是整体资产，坏一层就掉一层。**
>
> **豁免要贵，检查才可信。** 逐行豁免（`<!-- doc-audit:ignore 原因 -->`）是唯一形式，但还要加半句：**每次动用豁免都要在 PR 里被看到**，否则逐行豁免会退化成「每行都挂一条」。这个项目目前只有一条 emoji 禁令，**为一个大字标题上的装饰性符号花掉一次豁免，下一个真正需要的豁免就没那么好批了。**
>
> 三个脚本的分工（都在 `tools/`，`prebuild` 全跑）：`contrast-check.mjs` 管颜色对比度（27 个色对）；`copy-audit.mjs` 管文案禁词（**`--targets=src` / `--targets=dist` 各算一段，各自分母、各自三态、判定不相加**）；`doc-audit.mjs` 管文档机械事实（表格列数 / 悬空锚点 / emoji，**只查这三样**——需要判断的检查一律不做成闸门，那属于评审清单）。

**P0（不通过即退回）**

1. 全站零 emoji 功能图标。扫描正则 `[\x{1F300}-\x{1F9FF}\x{2600}-\x{26FF}\x{2700}-\x{27BF}]` 在 `src/` 中零命中（UGC 内容除外）。
2. 无紫色→粉渐变，无 Indigo→Pink 任意组合，无 `background-clip: text` 渐变文字。
3. 无「Welcome / Lorem / 开始你的阅读之旅 / 解锁」类空话。所有空状态含「发生了什么 + 为什么 + 下一步」三件套。
4. **所有颜色来自 `design-tokens.json`——两条断言必须同时成立**（架构师 v1.11）：
   ① `grep -rE '#[0-9a-fA-F]{3,8}' src/` 的**命中文件集合 == `{src/styles/tokens.css}`**（`#fff`/`#000` 的 rgba 遮罩例外）；
   ② `src/styles/tokens.css` **首行必须有** `/* generated from docs/design-tokens.json — do not edit */`。
   **为什么必须两条**：只写 ① 会放过「**手写一份同路径文件冒充生成物**」——路径对、内容手写，grep 全绿。①验的是「色值没散出去」，②验的是「那一份不是人手写的」。**生成物的可信度不在路径上，在那行标记上。**

**P0 v1.12–v1.14 新增（内容偏好开关的五条断言，逐条可脚本化）**

36. **`include_heavy` 必须真的改变结果，否则控件不得渲染**：取同一画像（域 / 感受 / 条件 / 收获全部固定），**只翻 `include_heavy` 一个布尔值**，跑两次推荐，**两次结果的 `book_id` 集合必须不同**（顺序不比，只比集合）。若集合相同 → **该画像下这个控件不得渲染**。
    **两个口径别混用**：实现时预检可以直接算「该用户域 ∩ 难度 ≤ 上限 ∩ 书带 `grief` / `terminal_illness`」的候选集是否非空（便宜，且能提前决定渲不渲染）；但**验收必须真跑两次比集合**——**候选集非空而结果集合不变，说明过滤根本没接上**，而这时"预检说该渲染"恰好会把那个 bug 掩盖成"没问题"。**同一件事的两个测法，便宜的那个用来决定渲不渲染，贵的那个用来证明它没撒谎。**
    为什么判据是「集合不同」而不是「有没有过滤日志」：日志能证明代码跑了，集合能证明**用户可感知的差别存在**。**一个渲染出来但从不改变结果的控件，比不渲染更糟**——它让用户以为自己做了个决定。首发 300 本里，某些域可能一本 `grief` / `terminal_illness` 都没有，那时这个开关在该画像下就是空的；**特例处理只有一种：不渲染**，不许改成禁用态、不许加"当前书单暂无此类"的说明（那等于把内部数据状态摊给用户）。
    附带一条：`EX-trauma` **不受这个布尔值影响**——同一画像下带 `suicide` / `sexual_abuse` 标注的书，在 `include_heavy = true` 时**仍然不得出现**。两件事一起测，否则这个开关会被实现成"显示全部"。
37. **内容偏好问句节点的三词零命中**：容器带 `data-heavy-question`，断言 **`[data-heavy-question]` 子树内「自杀」「自伤」「性暴力」三词各命中 0**（该子树用 DOM 查询取，不用全页 grep）。**范围是子树，不是全站**——危机条、`/crisis` 页、`crisis_resources.json` 都在这棵子树外面，这条断言不管它们说什么。三词全查（含「自杀」）的理由见 P1「禁用词检索按节点收窄」一段。
    为什么必须先取子树再检索：**全站 grep 一个词，命中的九成是别人的正当文案**，于是下一个人会去加白名单；而 `data-heavy-question` 这个容器名是**实现时自己写上去的**，它一旦挪位或改名，断言就红——**红的是一次改名，不是一次违规，但正好逼人回来看这句话还在不在。**
38. **控件不渲染时不留空位（与 36 配对，一个测"该不该在"，一个测"不在时长什么样"）**：用「情绪与自我 + 越轻松」的 fixture（该格候选集为空），断言 ① `[data-heavy-question]` 节点数 = 0 ② **该 fixture 与「人生转折」fixture 的第 3 屏内容高差 = 92px（60 控件 + 32 间距），误差 > 4px 即 fail** ③ 第 3 屏容器无 `min-height` / 无高度固定的占位块，DOM 中不存在高度 ≥ 8px 且无文本的空节点 ④ 该控件原位置附近检索「这类话题|这次不用选|暂无可选|该类内容」命中 0。
    为什么 ② 用「差值 = 92」而不是「等于某个总高」：总高会因字号、字体度量、平台滚动条而漂，**而"少了哪一块、少多少"是布局意图本身**。**差值一旦是 0，说明有空占位；一旦是 60，说明只删了控件忘了删那 32px 间距**——这两个错都不会让页面看起来坏，只会让它在某个域里凭空矮一截或多一段空白。
    **还必须验「它不存在时整屏仍然成立」**（这是「可能不存在的组件」与「一定有只是内容不同」的验收分界）：⑤ 该 fixture 下 3-e 是最后一个内容块，其下方到吸底按钮之间只有正常留白，**页面不出现第二个滚动锚点或空白区** ⑥ **不存在「与第 1/2/4 屏等高」类固定高度样式**（该容器上检索 `min-height|height:\s*\d{3,}px` 命中 0）——这条不是洁癖：**那条指标会逼着实现去补空行凑数**，和骨架卡那次是同一个坑。
39. **「未答」信号可观测（`answered` 与 `rendered` 两个布尔量）**：断言三种组合各自可达且互不混淆——① 结构条件不成立 → `rendered = false`，DOM 节点数 0 ② 渲染但用户只滑过、未点任何一枚 → `rendered = true` · `answered = false` ③ 用户点「一起看」**或**点「先不用」→ 均置 `answered = true`。
    **③ 里的「点『先不用』」是这一条的全部价值**：它视觉上已经是选中态，**最容易被实现成 no-op**，而一旦做成 no-op，「点了确认」和"从头没动"就又落回同一个 `false`——**v1.12 花一整轮消灭的歧义，会从交互实现这一侧原样长回来。**
40. **折叠线准入（上线门槛，不是版式建议）**：断言「页面加载完成、未发生任何滚动时，控件整体在可视区内」——`rect.top >= 0 && rect.bottom <= innerHeight - 吸底按钮区(80) - 安全区(34)`。**不满足则不许上线**（当前实测顶边 804–844 > 可用 642，故 M1 这个控件即使渲染也不满足上线条件，须先按 P1「三条禁术」之外的唯一解法——**减 3-a / 3-b 行数，归 SPEC**——把内容压到 642 以内）。
    为什么这条要单列成验收而不是写在 P1 里：**它测的不是"好不好看"，是"用户有没有被问到"。** 一个在折叠线以下的默认值控件，落库值和"没滚动"完全无法区分，**而排除故障的人会从"规则没生效"开始查**（见 P1 那段改正留档）。
