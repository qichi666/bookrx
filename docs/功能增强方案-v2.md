### 0.1 编号规则

- `F` = 功能点编号，全局唯一，后续文档引用此编号。
- **层**标记该功能点的性质：
  - `L0 可见度`：不新增业务能力，只让已有能力被看见
  - `L1 横向宽度`：新增独立页面，扩展产品可逛的面积
  - `L2 纵向闭环`：补齐某条业务链路的断点，让流程能走完
- `P0 / P1 / P2` = 优先级，判定标准见 §4。

## 2. 逐项说明

### F1 · 首页工作台化

**增强目的**
把首页从「问卷第一步」改成「产品总览页」，让未登录、未答题的陌生人第一眼看到产品能做什么，而不是只看到一个开始按钮。

**针对并解决的具体问题**
- 现状：`QuizView.vue` 第一屏只有一个动作——从若干困境域里选一个。首屏可点入口数 = **1**。
- 访客必须先答完 4 屏问卷（选域 → 选标签 ≤3 并指定主诉 → 5 组 chip → 自由文本），才能在结果页第一次看到「书单」这个概念。
- 结果：10 个页面里，第 2 到第 10 页在访客形成第一印象之前**全部不可见**。评价方看到的不是「一个读书产品」，而是「一个问卷工具」。
- 这不是审美问题，是**信息架构问题**：把最贵的资产（68 本书、33 类困境、34 项标注、确定性打分）放在了一条必经 4 步才能抵达的路径末端。

**预期收益**
- 首屏可点入口 **1 → 6**（开始诊断 + 4 张功能卡 + 继续读）。
- 访客 3 分钟内的可达页数 **2–3 页 → 8–9 页**。
- 让「书单库 / 书架 / 导入 / 阅读方法」从二级入口升到一屏内，使产品面积在首屏被完整表达。
- 新增「继续读」区块，让回访用户一进来就能续读，而不是重走问卷。

**必要性判断依据**
1. **代码事实**：`QuizView.vue` 的 `step = ref(1)` 决定了首屏只有选域一个动作；`AppHeader.vue` 只渲染 3 个链接，其中不含 `/booklist`。
2. **竞品事实**：StoryGraph、微信读书、豆瓣读书的首页均为内容聚合页（推荐流 / 书架 / 榜单），没有一家把「填问卷」放在首页第一屏。Reading Well 的入口是书单目录页，不是评估流程。
3. **转化逻辑**：诊断是**门槛动作**，书单是**价值动作**。把门槛动作放在最前面，等于要求用户在还不知道能得到什么的情况下先付出成本。这不是「简洁」，是顺序错了。
4. **不可替代性**：F3/F7/F9/F10 新增的页面如果没有首页入口，等于新增了四个「只有知道 URL 才能到」的孤岛——F1 是它们的**前置条件**。

**实现要点**
- 改动文件：`src/views/QuizView.vue`（模板重排，问卷逻辑不改）、可能需要新建 `src/components/home/*`。
- 保留原有问卷四屏逻辑与 `buildDiagnosis` 调用链，**不改任何派生逻辑**。
- 「继续读」区块数据源：`shelf` 表 + `progress` 表，取 `group !== 'finished'` 且最近更新的一条；无数据时整块不渲染（不显示空状态占位）。
- 数字条（68 本 / 33 类困境 / 34 项标注）建议从 `derived.json` 与 `taxonomy` 运行时读取，**不硬编码**，避免数据更新后文案失真。
- 遵守 `src/ ≤300 行`：若 `QuizView.vue` 超限，把工作台拆成独立组件。

**验收口径**
- 首屏（375px 与 720px 两档）可点入口数 ≥ 6。
- 未答问卷时可从首屏直达 `/booklist`、`/library`、`/import`、`/framework` 且不报错。
- 已有进度时「继续读」出现且点击直达 `/reader/:id` 对应章节。
- 无进度时首屏不出现空状态文案。
- 原有问卷 4 步流程端到端仍通过（现有 E2E 断言不得回归）。

### F2 · 全局导航扩展（3 → 6）

**增强目的**
让全局导航成为产品地图，而不是三个零散链接。

**针对并解决的具体问题**
- 现状：`AppHeader.vue` 只渲染三个链接——书架、怎么读书、关于。
- `/booklist`（书单库）**完全不在导航里**，只能从结果页进入；`/import` 与 `/library` 被合并成同一个判断条件（`isLibrary`），语义上「导入」被吞掉了。
- 后果：用户进入任意非结果页后，**没有任何路径能回到书单库**。产品里体量最大的一块内容（68 本书的全量书单）在导航层面是不存在的。

**预期收益**
- 导航入口 **3 → 6**，覆盖书单、书架、统计、怎么读书、关于 + 品牌回首页。
- 消除「进了书籍详情就回不到书单库」的死角。
- 让「导入电子书」成为一级可达动作，而不是藏在书架页里的按钮。

**必要性判断依据**
1. **代码事实**：`AppHeader.vue` 第 40–42 行仅三条 `router-link`；`isLibrary` 用 `route.path === '/library' || route.path === '/import'` 合并判断，说明设计时把导入当成了书架的附属。
2. **可用性事实**：项目历史上已因「危机页、关于页进去之后没有返回入口」被用户实测困住两次（见 `AppHeader.vue` 顶部注释）。同一类缺陷（导航不完整）**已经发生过一次**，当前是第二次的潜在形态。
3. **成本极低**：改动集中在一个 98 行的组件内，无数据依赖、无状态迁移，是所有功能点里投入产出比最高的一项。
4. **与 F1 强耦合**：F1 的卡片入口点进去之后，必须有导航能横向切换，否则用户仍然只能「返回」。

**实现要点**
- 改动文件：`src/components/AppHeader.vue`（唯一）。
- 移动端 375px 下 6 个链接会溢出：需折叠为「品牌 + 汉堡菜单」或「品牌 + 3 主链 + 更多」。**必须实测 375px 无横向溢出**（本项目此前 7 个页面实测均无溢出，不得由本项引入第一个）。
- `data-crisis-entry` 配额只有 2 个（结果页 + `/about`），**导航栏不得新增**，否则门禁会红。
- 触控目标高度：当前 `.btn-back` 为 36px，低于 44px 推荐值；扩展导航时建议一并提到 44px。

**验收口径**
- 任意页面（阅读器除外）可 1 次点击到达 `/booklist`、`/library`、`/framework`、`/about`。
- 375px 下导航不换行溢出、不遮挡内容，可点元素高度 ≥ 44px。
- `data-crisis-entry` 总数仍为 2，配额门禁通过。
- 阅读器页（`route.name === 'reader'`）仍不渲染导航（全屏阅读约束不变）。

### F3 · 书单库独立化

**增强目的**
把 `BooklistView` 从「结果页的附件」升级为「可独立浏览、筛选、排序的书库」，让 68 本书成为一个可以被探索的对象，而不是一次性推荐输出。

**针对并解决的具体问题**
- 现状：`/booklist` 依赖 sessionStorage 里的 `Diagnosis`。没有诊断结果时，这个页面要么空白、要么回退到首页——**它无法独立存在**。
- 68 本书的全部价值被绑在「必须先答完问卷」这一个前提上。访客想「先看看你有什么书」，没有路径。
- 标签厚度数据说明另一个问题：33 个标签覆盖中位仅 4 本，8 个标签仅 3 本。在单次推荐场景下，用户只能看到 3–5 本，**感知不到库的厚度**；但允许自由浏览时，「某标签下只有 3 本」是可以被接受的，因为用户能看到全貌。

**预期收益**
- 让「68 本 / 33 类困境 / 34 项标注」这组数字**变成可验证的事实**，而不是文案。
- 支持按标签、难度（1–5）、预计时长（1.5–20h）、形式、可用性（inline / 外链）筛选与排序。
- 无诊断也可访问：访客能先逛库，再决定要不要做诊断——**降低首次价值获取的门槛**。
- 为 F4（导出）、F10（对比）提供承载页面。

**必要性判断依据**
1. **代码事实**：`BooklistView.vue` 存在且已有渲染能力，但路由 `/booklist` 不在 `AppHeader` 中，且依赖 `Diagnosis`——说明它当前被设计为结果页的下游，而非独立入口。
2. **竞品事实**：Reading Well 的入口就是五套**分类书单目录**（心理健康 / 家庭 / 儿童 / 青少年 / 失智），用户先选书单再选书；StoryGraph 有 A–Z 主题书单与 Custom Tags。**所有「处方式」竞品都把「书单目录」当作一级入口**，而不是推荐流程的产物。
3. **数据事实**：核心库难度分布 1:10 / 2:31 / 3:17 / 4:9 / 5:1，时长 1.5–20h——这两个维度已经具备做筛选的离散度，不需要补数据就能支撑筛选器。
4. **风险可控**：筛选排序是纯前端计算，无新增存储、无新增网络请求，不触碰打分体系（**不得让筛选逻辑反向影响推荐排序**）。

**实现要点**
- 改动文件：`src/views/BooklistView.vue`、新建筛选组件（建议 `src/components/filters/*`）。
- 无 `Diagnosis` 时必须能渲染全量 68 本，按 `book_id` 升序作默认序，**不显示分档标签**（"强匹配/值得一试"是诊断结果的概念，无诊断时无意义）。
- 有 `Diagnosis` 时保持现有分档展示，筛选作为叠加层。
- 筛选状态建议写入 URL query（hash 路由下用 `?tag=xx&diff=2`），使筛选结果可分享、可刷新保持。
- 遵守 `src/ ≤300 行`，筛选器拆组件。

**验收口径**
- 直接访问 `#/booklist`（无诊断）不报错、不跳转，渲染 68 本。
- 每个筛选维度单独与组合使用均正确；标签筛选结果数与本轮实测的标签厚度一致。
- 筛选后刷新页面，筛选条件保持。
- 有诊断时进入，分档标签与现有逻辑完全一致（回归断言不得变化）。

### F4 · 书方导出与打印

**增强目的**
产出一份可带走、可打印、可转发的「书方」文件，让推荐结果离开浏览器之后仍然存在。

**针对并解决的具体问题**
- 现状：推荐结果只是一串网页卡片。用户关掉页面，结果就没了。
- 66/68 本核心书是 `bring_your_own`（外链），点击即跳转豆瓣——**旅程在跳转那一刻结束**，用户手里什么都没留下。
- 没有可分享物：无法给朋友看「系统给我开了这几本」，也无法带去咨询室给咨询师看。
- Reading Well 的核心实物是一张**推荐表**，Book Therapy 卖的是**最少 10 页的 PDF 报告**。本项目在这一环完全空白。

**预期收益**
- 产出单页可打印样式（困境标签 + 分档分组 + 每本一行：书名 / 作者 / 难度 / 预计时长 / 一句推荐理由 / 来源链接）。
- 可选导出 JSON / Markdown，便于存档或二次处理。
- 成为**唯一能脱离浏览器存在的产出物**，也是外部评价时最容易验证「这东西真的能用」的证据。
- 为危机场景提供合规出口：可打印的书方比屏幕更易转交给第三方。

**必要性判断依据**
1. **竞品事实（双证据）**：英国 Reading Well 的运作核心是「GP 开推荐表 → 患者凭表到图书馆免费借阅」，2013 年至今借出 430 万册；Book Therapy 的 £29.99 产品就是一份 48 小时内邮件送达的 10 页报告。**两个成熟产品都把「可带走的凭证」当作交付主体**。
2. **产品事实**：本项目 66/68 是外链书，用户在站内的停留时间天然很短。没有凭证，等于把所有沉淀价值都让给了豆瓣。
3. **成本最低**：数据全部已在内存（`Diagnosis` + 打分结果），只需打印样式与序列化。**不需要新增任何数据字段或接口**。
4. **可验证性**：这是唯一一个「打印出来就能拿去给别人看」的功能，对项目成熟度评价的边际贡献最大。

**实现要点**
- 改动文件：`src/views/BooklistView.vue` 或结果页新增入口；新建 `src/lib/booklist-export.ts`（纯函数，便于测试）。
- 打印样式用 `@media print`，需处理：隐藏导航与按钮、分页不断行（`break-inside: avoid`）、去掉背景色以省墨。
- 导出内容**不得包含**任何诊断性措辞（"你有 X 症"），只用用户自选标签原文。这是项目安全阀，必须遵守。
- JSON 结构需带 `schema_version`，便于后续兼容。
- 现有 `catalog/` 下书单 JSON 已冻结，导出应**读取运行时数据重新生成**，不复用冻结文件。

**验收口径**
- 浏览器打印预览（Chrome）下：A4 纵向、无导航、无按钮、每本书条目不被分页截断。
- 导出的 JSON 可被 JSON.parse 且含全部推荐书目与 `schema_version`。
- 导出文案审计：不含「诊断 / 症 / 治疗 / 疗效」等医疗措辞（沿用现有 `copy-audit` 词表）。
- 无诊断时「导出」按钮不出现。

### F5 · 想读清单与排队

**增强目的**
在「看到推荐」和「开始阅读」之间加一个「先存起来」的中间态，并允许用户自己安排顺序。

**针对并解决的具体问题**
- 现状：`shelf` 表已有 `group` 字段（含 `finished` 等），但没有「想读」这一态。
- 用户看到 5 本推荐，通常只会立刻读 1 本，剩下 4 本**没有任何地方可以放**——关掉页面就丢了。
- 66/68 是外链书，用户点去豆瓣之后没有任何机制把他拉回来。
- 没有任何「接下来读什么」的队列，回访用户每次都要重新做决定。

**预期收益**
- 新增 `want` 组，推荐卡片直接「加入想读」，一次点击完成。
- 支持拖动排序，形成「接下来 5 本」的队列。
- 补上产品唯一的**留存回路**：推荐 → 存下 → 下次回来继续。
- 与 F6（读后回执）形成闭环：想读 → 在读 → 读完 → 回执。

**必要性判断依据**
1. **代码事实**：`useReaderSession.ts` 中已有 `shelf.value.group !== 'finished'` 的判断，说明 `group` 字段已存在且被使用，**扩展成本是加一个枚举值而非改表结构**。
2. **竞品事实**：StoryGraph 的 **Up Next Queue**（排队接下来 5 本）是其核心留存机制之一；微信读书有书架；豆瓣有「想读」。**所有做阅读产品的都有这个态，唯独本项目没有。**
3. **链路事实**：现有链路是「推荐 → 点开外链 → 结束」。中间缺一个站内锚点，这是留存为零的结构性原因，不是运营问题。
4. **排序诚实性**：本功能只影响「用户自己的队列顺序」，**不得反向影响推荐打分**。若未来要用想读行为调整推荐，必须作为独立权重项并保持确定性（禁止随机、禁止时间依赖）。

**实现要点**
- 改动文件：`src/storage/db.ts`（`shelf` 组枚举）、`src/views/LibraryView.vue`（新分组 tab）、推荐卡片组件（加按钮）。
- `group` 新值建议 `want`；需检查所有对 `group` 做全等判断的位置，避免默认分支误判。
- 排序字段需持久化（`sort_order: number`），拖动后需在一个事务内批量写，避免逐条写导致 N 次事务。
- 「想读」组内条目**不参与** `furthest_locator` 逻辑（还没开始读）。

**验收口径**
- 加入想读后刷新页面仍在。
- 拖动排序后刷新顺序保持。
- `finished` / 在读 / 想读三组互斥，一本不会同时出现在两组。
- 现有书架分组显示与统计不受影响（回归）。
- `src/ ≤300 行`，`storage` 层不得引入逐条事务。

### F6 · 读后回执

**增强目的**
在用户读完一本书时收集一次极轻量的反馈，让「推荐准不准」第一次有数据，并让反馈能反过来改善后续推荐。

**针对并解决的具体问题**
- 现状：`telemetry.ts` 只记 `domain_counts` / `tier_counts` / `total` 三个聚合值，**没有任何「这本书有没有用」的信号**。
- 结果：项目无法回答最基本的产品问题——推荐到底准不准？三档阈值（8000 / 6000 bp）是拍出来的，没有校准数据。
- 标签厚度本就很薄（中位 4 本），如果某些标签下的书实际「不适合」，系统完全无从得知。
- Reading Well 的 92% / 81% / 90% 三个效果数字，全部来自**读后调查**。没有回执，就没有任何可对外陈述的效果指标。

**预期收益**
- 三个选项 + 一句可选理由，全程 10 秒内完成，不打断阅读。
- 得到「有用率」指标，可用于校准分档阈值与标签权重。
- 回执可作为「这本书在这个标签下的实际适配度」参与排序（需保持确定性：只做确定性加权，不做随机/时间依赖）。
- 为对外材料提供第一个**真实量化指标**，而非自评。

**必要性判断依据**
1. **代码事实**：`telemetry.ts` 字段清单已验证只有三项，**不存在任何效果反馈通道**。
2. **竞品事实**：Reading Well 的效果数据（92% 认为有帮助、81% 帮助理解状况、90% 专业人员认为有用）全部来自读后调查；StoryGraph 有评分 + Reading Journal；Book Therapy 提供 **2 周邮件跟进**。**三个成熟产品都把读后反馈当作产品的一部分，而不是可选项。**
3. **体系自洽性**：项目已经有一套精密的七因子打分与三档阈值，但这些参数的取值**没有任何数据支撑**。一个自称「确定性可解释推荐」的系统，如果不能证明自己准，可解释性就只是形式。
4. **成本极低**：一个三选一弹窗 + 一次写库，无新页面、无新依赖。

**实现要点**
- 改动文件：`src/views/ReaderView.vue`（读完触发）、`src/storage/db.ts`（新增回执表或复用 notes 表）、`src/engine/*`（若参与排序）。
- 触发条件：`progress` 到达末章末偏移，且该用户尚未反馈过这本书（避免反复弹）。
- 数据结构：`book_id` / `verdict: 'useful' | 'neutral' | 'unfit'` / `reason?: string` / `created_at`。
- 若接入排序：必须是**确定性加权**（`src/domain` 内禁止 `Math.random` / `Date.now` / `new Date` / `performance.now`），且回执缺失时权重为中性值，不得让「没反馈的书」系统性吃亏。
- 弹窗必须可一键关闭且不阻塞退出阅读。

**验收口径**
- 读完最后一页后弹窗出现一次；关闭后不再出现。
- 三种回执均正确落库，刷新后仍在。
- 同书不重复弹窗。
- 若参与排序：同输入同输出（连续两次计算结果完全一致）；无回执的书排序分数与改动前一致。
- 阅读器的进度保存、翻页、划线、笔记全部回归通过。

### F7 · 阅读统计页

**增强目的**
把分散的阅读行为（时长、本数、标签分布）聚合成一个可见的积累，让用户感知「我在这里留下了东西」。

**针对并解决的具体问题**
- 现状：`telemetry.ts` 只有三个计数，**无时长、无连续天数、无历史**。
- `progress` 表存了位置但不存时长，用户看不到自己读了多久。
- 书架只有「在读 / 读完」两个静态分组，没有时间维度。
- 后果：产品没有任何「积累感」。阅读是长期行为，没有统计就没有回访理由。

**预期收益**
- 连续阅读天数、本周/本月时长、累计读完本数、困境标签分布。
- 成为导航第六个入口（`统计`），进一步扩大产品面积。
- 为 F12（读书计划）提供真实的速度基线（当前只能用 6h 中位预计时长估算）。
- 是「产品有在认真做」的直观证据——一屏图表比十段文案有说服力。

**必要性判断依据**
1. **代码事实**：`telemetry.ts` 字段清单已确认只有 `domain_counts` / `tier_counts` / `total`，`progress` 表无时长字段——**数据基础不存在，必须新增采集**。
2. **竞品事实**：StoryGraph 在 2026 年新推「自定义日期区间 Wrap-Up 图形」与「任意两段统计对比」，是其年度主推功能；微信读书有阅读时长榜与时长兑币。**统计是阅读类产品的标配留存机制。**
3. **数据可得性**：`ReaderView.vue` 已有 `pauseClock()` / `flushProgress()` 机制（本轮刚修过 `onVisibility` 时序），说明计时能力已存在，**只差把时长落库**。
4. **前置性**：F12（读书计划）若无真实阅读速度，只能用固定中位数估算，计划必然失真。F7 是 F12 的数据前提。

**实现要点**
- 改动文件：`src/lib/telemetry.ts` 或新建 `src/storage/stats.ts`、新建 `src/views/StatsView.vue`、`src/main.ts` 加路由、`AppHeader.vue` 加入口。
- 时长采集：复用现有 clock 机制，**按会话累计**而非按秒写库（避免高频写）；页面 hidden 时 flush（现有 `onVisibility` 已做）。
- 连续天数：以本地日期为准（`Date` 只能在非 `src/domain` 层使用）。
- 图表：优先纯 CSS / SVG，避免引入图表库（当前项目零 UI 依赖，不要为此破例）。
- 数据全在本机，**不得上报**，与项目「数据不出机器」定位一致。

**验收口径**
- 读 10 分钟后统计页时长增加且刷新保持。
- 跨天访问后连续天数正确 +1；中断一天后归零。
- 无任何数据时显示空状态而非 NaN / 0 图表。
- 新增路由不影响危机页独立 chunk 约束（门禁 `assert-crisis-chunk` 通过）。
- `src/views/` 下新文件 ≤300 行。

### F8 · 可信度面板（为什么推荐这本）

**针对并解决的具体问题**

**必要性判断依据**

3. **定位一致性**：项目自称「确定性推荐」，可解释性是这套说法的**验证物**。不展示，等于自我否定。

**实现要点**

**验收口径**
- 有诊断时展开面板，七个因子均有可读的中文标签与数值。
- 面板显示的各因子得分与 `src/engine` 内部计算结果一致（需一条对拍测试）。

- 375px 下得分条不溢出。
- 文案审计不含医疗措辞。

**验收口径**

- 分享文件不发起任何网络请求（Network 面板零请求）。

### F10 · 书籍对比

**增强目的**

- 与 F3（书单库）结合，形成「浏览 → 勾选 → 对比」的自然路径。
- 纯计算功能，零数据成本，是提升产品「厚度感」性价比很高的一项。

2. **竞品空白**：StoryGraph 有统计对比但比的是「我的两段时间」，不是「两本书谁更适合我」；豆瓣对比的是评分；Reading Well 是单本书单。**「按我的处境对比两本书」这个动作，目前没有产品做。**
3. **行为事实**：F5 引入想读清单后，用户会积累多本候选，对比需求随之产生——**F10 是 F5 的自然下游**。
4. **风险低**：纯前端计算与展示，不触碰存储与打分。

**实现要点**
- 改动文件：新建 `src/views/CompareView.vue` 或书单库内抽屉组件、`src/main.ts` 加路由。
- 上限 3 本（超过则并排不可读）；不足 2 本时给明确提示。
- 雷达图用 SVG 手写，不引入图表库。
- 需处理「两本同分」的同分情况（六级全序已保证可区分，但展示时要说清差别在哪个因子）。

**验收口径**
- 选 2 本与 3 本均正确渲染，不溢出。
- 各维度数值与书详情页一致（对拍测试）。
- 375px 下需降级为纵向堆叠或横向滚动，不得溢出。
- 未选满 2 本时按钮不可用且有提示。

### F12 · 读书计划

**增强目的**
把「推荐了几本」转成「这几周读什么」，给用户一个可执行的节奏。

**针对并解决的具体问题**
- 现状：推荐只回答「读哪本」，不回答「怎么读完」。
- 核心库预计时长最短 1.5h、中位 6h、最长 20h——**跨度 13 倍**，用户没有任何依据安排。
- F5 的想读清单只能排序，不能分配到时间。
- 后果：想读清单容易变成一个只增不减的堆积场。

**预期收益**
- 按预计时长自动排 4 周计划，每周 1–2 本，可手动调整。
- 与 F7（统计）联动：有了真实阅读速度后，计划按实际速度重算而非固定中位数。
- 提升想读清单的转化率（从「存着」到「排上日程」）。
- 让产品从「推荐工具」变成「阅读管理工具」，是产品定位的一次升级。

**必要性判断依据**
1. **数据事实**：`est_reading_hours` 已是 34 字段之一，且实测跨度 1.5–20h——**排期所需的数据已存在**。
2. **竞品事实**：StoryGraph 的 Up Next Queue 是「排队」而非「排期」，没有时间维度；微信读书无计划功能。**这是竞品也没做好的空位，但也是需求真实度最低的一项**，故列 P2。
3. **前置依赖**：无 F7 的真实速度数据时，计划只能用 6h 中位数估算，误差可能达数倍——**因此 F12 必须排在 F7 之后**。
4. **风险**：计划类功能容易变成「定了不做」的负反馈。必须允许随时重排，且不设「未完成」的惩罚性提示。

**实现要点**
- 改动文件：新建 `src/views/PlanView.vue` 或并入书架页。
- 排期算法放在 `src/domain`（纯函数，禁时间依赖），输入为书目时长 + 每周可用时长，输出为周次分配。
- 允许拖拽调整周次；调整后重新平衡剩余周次。
- 不做提醒推送（无账号、无服务端，浏览器通知权限成本过高）。

**验收口径**
- 选 5 本、每周 6 小时，排期结果总时长误差 ≤ 单本最大时长。
- 手动拖拽后重新平衡不产生空周（除非书目不足）。
- 计划中的书与想读清单保持同步（删书后计划同步更新）。
- 排期函数同输入同输出。

## 3. 明确不做的项

| 不做 | 理由 |
|---|---|
| 账号体系 / 云同步 | 「数据不出机器」是差异化定位，不是缺陷。加账号即失去唯一的结构性优势 |
| 用户评分 / 星级 | 一旦引入群体均分，就变成豆瓣模式，与「按你的处境匹配」正面冲突 |
| UGC 书评 / 社区 | 无内容审核能力；且会稀释确定性推荐的可信度 |
| ML / LLM 生成书单 | 直接摧毁「同输入同输出」这一核心护城河。可解释性依赖确定性 |
| 心理测评量表 | 越界。项目定位是「读书入口」，不是筛查工具；「不做诊断 + 危机优先」是最值钱的安全阀 |
| 推送 / 提醒 | 无账号、无服务端，浏览器通知权限成本与收益不匹配 |
| 打卡排行榜 | 社交攀比与「按困境匹配」的私密性冲突 |

## 4. 实施顺序与优先级判定标准

### 4.1 优先级判定标准

- **P0**：不做则产品在外部看来「不像成品」；或某项是其他功能的前置条件。
- **P1**：显著提升产品面积或可信度，但缺了不影响主链路走通。
- **P2**：深度功能，依赖 P0/P1 的数据或视图，且不解决「体量观感」问题。

### 4.2 建议顺序（按依赖与收益排序）

```
第一批（观感，1–2 天）
  F2 导航扩展 → F1 首页工作台

第二批（面积 + 凭证，2–3 天）
  F3 书单库独立化 → F4 书方导出

第三批（闭环，2–3 天）
  F5 想读清单 → F6 读后回执

第四批（可信度与深度，3–4 天）
  F8 可信度面板 → F10 书籍对比 → F9 书摘卡片

第五批（数据积累，需先跑一段时间）
  F7 阅读统计 → F11 笔记总览 → F12 读书计划
```

**关键约束**：F12 必须在 F7 之后（否则排期无真实速度基线）；F10 建议在 F5 之后（想读清单是它的用户来源）；F1 必须在 F3/F7/F9/F10 之前（否则新页面没有入口）。

### 4.3 每批完成后的验收要求

- `npm run check` 全绿（当前基线：54 文件 412 条，新增功能须同步新增测试）。
- `npm run build` 的断言全部通过。
- 真实浏览器（dev 与 preview 各一遍）无 console error / warning。
- 375px 无横向溢出（当前 7 个页面实测均无，不得引入第一个）。
- `data-crisis-entry` 配额仍为 2。

## 5. 给实现者的全局约束

1. **行数纪律**：`src/` 单文件 ≤300 行，`tools/` ≤400 行（由 `style-audit.mjs` 强制）。
2. **可复现性**：`src/domain` 内禁止 `Math.random` / `Date.now` / `new Date` / `performance.now`。所有新增算法若落在 `domain` 层，必须满足同输入同输出。
3. **门禁三态**：通过 / 失败 / **未验证**。扫到 0 个文件不得报通过。
4. **安全阀不可动**：危机页文案、`data-crisis-entry` 配额（2 个）、「不做诊断」的措辞边界，任何改动都必须单独评审。
5. **文案审计**：新增用户可见文案不得含「诊断 / 症 / 治疗 / 疗效」等医疗措辞（沿用现有 `copy-audit` 词表）。
6. **零 UI 依赖**：当前项目无 UI 组件库、无图表库。新增可视化优先手写 SVG / Canvas，不为此引入依赖。
7. **数据不上报**：所有新增采集（时长、回执、统计）只写本机 IndexedDB，不发起任何外发请求。
8. **诚实呈现**：标签厚度中位仅 4 本、最薄 3 本。涉及「有多少本可选」的展示**必须如实**，不做美化的模糊表述。
