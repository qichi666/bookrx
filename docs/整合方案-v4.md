## 0. 合并口径与冲突裁决

两份方案不是简单叠加——它们在 6 个点上给出了不同答案。先裁决，再合成，否则后续实现会左右摇摆。

### 0.1 六处冲突与裁决

| # | 冲突点 | v3（local-first） | v2（功能增强） | **裁决** | 理由 |
|---|---|---|---|---|---|
| 1 | 导航入口数 | 3 → **5** | 3 → **6** | **5 个** | 375px 下 6 个链接必然折叠成汉堡，等于没扩展。5 个（书架/书单库/统计/怎么读书/关于）已能表达全部面积，剩余入口交给 F1 首页卡片 |
| 2 | F3 书单库优先级 | P1（第二批） | P0 | **P0** | F1 首页有「书单库」卡片，若 `/booklist` 不能独立访问，这张卡片就是死链。F3 是 F1 的**成立条件**，不能降级 |
| 3 | F4 导出形态 | 拆成打印 P0 / JSON P0 / 摘图 P1 | 合并为一个 F4 | **按 v3 拆分** | 三者实现路径与验收口径完全不同（`@media print` / 序列化 / Canvas），合在一起无法分批交付，也无法分别验收 |
| 4 | 本地档案 | P1，新增模块 | 未提及 | **采纳，编 F12，降为 P2** | 原设计要**所有用户数据表加 `profile_id`**，是全案最大的迁移风险；而单人使用时价值接近零。必须排在 F5/F6/F7 之后。实现时改按档案分库，见 0.3 |
| 5 | 治理面板 | P2，新增模块 | 未提及 | **采纳，编 F13，确认为 P2** | 对外部观感零贡献，仅为维护者服务。可在核心库扩量后再做 |
| 6 | 连续天数口径 | 未细化 | 「断一天归零」 | **改为冻结额度** | 借鉴 Hikara / Bookly 的 streaks with freeze credits。断一天清零是负反馈设计，会把用户推走（Goodreads 替代品调研里被反复提到的正是「压力而非减阻」的批评） |

### 0.2 采纳但需升级为前置条件的一项

v2 完全没写、v3 写了但埋在第 2.4 节的一句：**存储迁移**。

- IndexedDB `v1 → v2`：只加表/字段/索引，**不改旧字段语义**
- 新增 `profiles` / `sessions` / `receipts` 三表
- 旧表**不加** `profile_id`，隔离改由库边界负责，见 0.3
- 多标签页靠 `onversionchange` 让路（本轮已实现，需保持）
- **多表事务清单必须完整**：事务里要 `objectStore(name)` 的表必须在 `db.transaction(stores)` 清单内，少一张即 `NotFoundError`

**结论**：迁移必须排在 F5（想读）/ F6（回执）/ F7（统计）/ F12（档案）之前，作为它们的物理前提。这是一条独立的批次前置项，编号 **F0**。

### 0.3 实现阶段的两处裁决（规划 ≠ 落地，这里是最终口径）

**裁决一：F6 回执不接回推荐算法。** 3.3 与第 4 节原写「确定性回馈排序」「唯一把回执接回算法」，实现时否决。理由有两条，第二条是硬的：① 回执是读者当下的一次主观判断，用它反复加权会形成自我强化，把人困在第一次的选择里；② 更关键的是，**一旦本机回执参与打分，同一份问卷在不同时间会得到不同结果**，直接摧毁 F8 主打的「可复现」与六级全序。回执的落地用途是：读完不再重复弹、本机统计里的有用率、以及用户自己导出。它不进 `src/domain`，也不进排序。

**裁决二：F12 改为按档案分库，不做全表 `profile_id`。** 原设计要给十张表改键、改索引、回填默认档案，并让每一个读写函数都记得带上过滤条件——只要漏一个函数，就出现「切了档案还看得见上一个人的笔记」这种最伤信任的事故。实现改为：默认档案沿用 v1 老库名 `bookrx`（老数据零迁移），其余档案各自一个 `bookrx:p:<id>` 库，档案清单固定写在默认库的 `profiles` 表。隔离由数据库边界保证，读写函数一行未改；`tests/storage/profile-isolation.test.ts` 用真实 IndexedDB 验证书架 / 笔记 / 会话互不可见。界面在 `/profile`，不入主导航，由关于页与治理面板的小字链接进入。

**编号勘误**：0.1 节原把本地档案 / 治理面板写为 F13 / F14，与第 2 节模块总表冲突，已统一为 **F12 / F13**，以总表为准。

## 1. 统一思路

### 1.1 一句话

> **把产品从「一次性推荐工具」升级为「处方 → 留存 → 积累 → 凭证」四段闭环的 local-first 阅读管理应用，全部能力在本机完成，推荐内核保持确定性可解释。**

### 1.2 四段闭环（两份方案的合成骨架）

```
① 处方          ② 留存          ③ 积累          ④ 凭证
诊断 → 打分      想读 → 在读      时长 → 回执      打印 / JSON / 摘图
→ 推荐            → 读完          → 笔记 → 统计
   ↑                                                    |
   └────────────── 回访理由 ←───────────────────────────┘
```

| 段 | 解决什么 | 对应模块 | 竞品对标 |
|---|---|---|---|
| **处方** | 「我该读什么」——已有能力，但不可见、不可解释 | F1 F2 F3 F8 | Reading Well / Book Therapy（有处方，无算法） |
| **留存** | 「看到的不丢」——当前**完全缺失**，66/68 外链书一跳走就断 | F5 F6 | StoryGraph Up Next Queue |
| **积累** | 「我读进去了」——当前**完全缺失**，无时长无天数 | F7 F9 F11 F12 | StoryGraph Stats V4 / Hikara / Bookly |
| **凭证** | 「能带走」——当前**完全缺失**，无可分享物 | F4 | Reading Well 推荐表 / Book Therapy PDF |

### 1.3 四条不可动摇的架构原则（两份方案一致，予以保留）

1. **问卷主链路不被阻塞**：诊断 → 打分 → 推荐仍是第一入口，扩展模块是结果下游与回访理由，不是前置。
2. **隐私承诺语义不变**：「数据不出机器」不是承诺，是**没有服务器可以上报**。新增数据只写 IndexedDB，导出是用户主动触发的下载。
3. **确定性内核不受污染**：`src/domain` 内禁 `Math.random` / `Date.now` / `new Date` / `performance.now`；日期、排序持久化字段放 `storage` / `lib`。
4. **单人维护现实**：治理面板服务唯一维护者，不引入服务端权限体系。

### 1.4 定位的一句话表述（对外可用）

> 一个不上传任何数据、不需要注册、推荐结果可解释且可复现的阅读处方工具——诊断之后给你一张能打印带走的书方，读完之后帮你记住自己读过什么。

## 3. 竞品调研（本轮实搜，2026-11-08）

### 3.1 竞争格局：四类，各自回答不同问题

| 类别 | 代表 | 回答的问题 | 商业模式 | 与本项目关系 |
|---|---|---|---|---|
| **A 综合追踪（有账号/云）** | Goodreads、StoryGraph、Hardcover、Fable、Literal、Bookly、Bookmory、LibraryThing | 「我读过什么 / 下一本读什么」 | 免费 + 订阅 | 功能参照系 |
| **B 处方式书单（bibliotherapy）** | Reading Well（英国）、Book Therapy | 「我这个状况该读什么」 | 公共医疗 / £29.99 一份 | **定位最接近** |
| **C local-first 无账号** | Openreads、Hikara、BookWyrm、Seekquel、NextChapter、nextly.page、lokl | 「我的阅读数据归谁」 | 免费 / 自托管 / 订阅 | **架构最接近** |
| **D 中文阅读与心理服务** | 微信读书、豆瓣读书、得到/帆书、简单心理 | 「读什么 / 找谁帮忙」 | 会员 / 咨询抽成 | 本土语境参照 |

### 3.2 逐个竞品：关键功能 / 优势 / 不足

#### A 类

**The StoryGraph**（免费 / Plus $49.99 年）
- 关键功能：mood + pace 筛选选书、四分之一星评分、Content Warnings 前置、Buddy reads（剧透锁定）、Reading Challenges、Custom Tags & Lists（可筛选 TBR 并分享）、Reading Journal（绑进度）、**Up Next Queue**、2026 新增 **Private Books**（私密书不进主页/统计/信息流）与 **Stats V4**（标签统计对比、过滤子集、平均读完天数、自定义区间 Wrap-Up 图形）
- 优势：统计最深、元数据最细、把「读后感受」结构化成可计算字段
- 不足：**推荐是 ML 输出、不可解释**（被批评的主要点）；社交规模小于 Goodreads；自定义图表与额外筛选需 Plus；有用户报告数据丢失导致连读记录断裂；Goodreads 导入丢 ISBN

**Hardcover**（免费 / Supporter $4.99 月）
- 关键功能：半星评分、moods、tags、content warnings、**逐本隐私（public / private / friends-only）**、lists、iOS/Android、可**从 Goodreads 与 StoryGraph 双向导入**
- 优势：设计现代、导入最开放、逐本隐私粒度细
- 不足：社区较小、冷门书评分少；额外统计在付费档

**Goodreads**（免费，Amazon 旗下）
- 关键功能：1.5 亿会员、公开评分与书评、年度 Reading Challenge
- 优势：规模无可替代、几乎每本书每个版本都有评论
- 不足：统计远弱于 StoryGraph/Hardcover；界面陈旧；推荐噪音大；**公开更新把私人爱好变成表演**（隐私最弱）

**Fable**（免费有广告 / Plus $5.99 月或 $49.99 年）/ **Literal**（免费）
- 关键功能：读书会、章节讨论、剧透感知讨论室、社交信息流
- 优势：群体共读的结构化最强
- 不足：社交压过私人追踪；Fable 免费版有广告、streaks 与高级统计需 Plus；Literal 稀有版本目录有缺口

**Bookly**（免费 + PRO 订阅）/ **Bookmory**
- 关键功能：**阅读计时器**、每次会话统计（时长/页数/阅读速度）、连续天数
- 优势：把「读的行为」而非「书的清单」作为核心
- 不足：免费版限制可追踪书籍数量；无按处境匹配

**LibraryThing**
- 关键功能：编目（管理你拥有的副本）
- 优势：藏书管理最专业
- 不足：不是阅读行为工具，无推荐

#### B 类

**Reading Well / Books on Prescription**（英国 Reading Agency，2013 起全国推广）
- 关键功能：GP / 链接员 / 专业人员「开方」→ 患者凭推荐表到公共图书馆**免费借阅**；五套书单（心理健康 / 家庭 / 儿童 7-11 / 青少年 / 失智）
- 选书机制：对照 **NICE 指南**质量门控 + 专家与「有亲身经历者」共同评审 + RCGP / RCPsych / BPS / Mind / NHS IAPT 联合背书
- 效果数据（**官网今日核实**）：累计借出 **430 万册**（旧资料写 380 万，已过时）；**92%** 受访者认为书有帮助；**97%** 年轻人愿意推荐给朋友；**90%** 专业人员认为书在咨询时间之外提供了支持
- 优势：**证据等级 + 权威背书 + 实物凭证**三件套，是「书方」这件事最完整的实现
- 不足：**强依赖线下基础设施**（GP 转介 + 实体图书馆），中国没有对应体系；无算法、无个性化排序；无数字端沉淀

**Book Therapy**（booktherapy.io）
- 关键功能：£29.99「个性化书方」= 48 小时内邮件送达、**最少 10 页报告**、7–10 本；50 分钟 bibliotherapy 咨询 £70；app 内含 A–Z 主题书库 + **private journaling portal**（含多个分类门户）
- 优势：人写的推荐理由质量最高；有明确交付物；有读后跟进（2 周邮件）
- 不足：**人力不可扩展**；价格高；不是自助产品

#### C 类

**Openreads**（开源、免费、无需账号）
- 关键功能：**默认私密、数据在设备上**、基础图表、**无社交（single-player by design）**、CSV 随时导出
- 优势：与本项目隐私立场**完全一致**，是「无账号也能做完整追踪」的实证
- 不足：**没有任何「按处境匹配」的推荐内核**；统计仅基础图表

**Hikara**（免费 / Basic $3.49 月 / Premium $6.99 月）—— **本轮新发现，最危险的邻近竞品**
- 关键功能：**找出书籍之间的连接**（echoes / challenges / bridges，每个带强度分并附解释）；session log；**streaks with freeze credits**（连续天数带冻结额度）；goals；pace insights；从照片提取划线、每天回看一条；Goodreads 导入
- 优势：**定位与本项目高度重叠**——「帮你理解你的阅读，而不只是记录」；可安装 web app（与 PWA 形态一致）；免费档书库不限量
- 不足：无原生 app；社区小；AI 功能有月度限额；**没有「按困境/处境匹配」这一层**

**BookWyrm**（开源、联邦、自托管）
- 关键功能：广告零、开源、联邦（与 Mastodon 互通）、书架 / 阅读日期 / 进度 / 书评 / 书单 / 小组、CSV 导入导出
- 优势：数据主权最彻底，可自建实例
- 不足：**需要选实例或自建服务器**，门槛高；社区安静；无推荐算法

**Seekquel**（免费）
- 关键功能：**可重排首页卡片、可关闭不用的卡片**；逐项可见性设置；KOReader / Calibre 集成
- 优势：「首页由用户自己组装」这个交互值得直接借鉴
- 不足：默认不是全私密（推荐预设保留公开主页）；社区小

#### D 类

**微信读书**（2.1 亿注册 / 500 万 DAU / 年费约 ¥168）
- 关键功能：海量正版、AI 问书、听书、好友划线「想法」、阅读时长统计与画像、时长兑书币、好友时长排行榜、本地传书（EPUB/TXT/PDF）
- 优势：资源与体验最强，社交与激励闭环成熟
- 不足：**总榜是「累计阅读量 + 好评率」流量加权**，评的是大众喜爱度不是「适合你」；账号强制；数据在腾讯

**豆瓣读书**（免费）
- 关键功能：纯用户评分沉淀、书评、小组、想读/在读/读过
- 优势：评分公信力、冷门书发现
- 不足：评的是「文学价值」不是「此刻适合我」；不解决行动决策

**简单心理**（咨询抽成 / 课程）
- 关键功能：心理测试（3+ 量表）、9+ 维度专家 1v1 访谈评估、咨询匹配、课程、免费热线、精神科顾问
- 优势：从评估到服务的最短路径，专业背书强
- 不足：**书单只是内容营销素材**（materials 页面的推荐文），没有筛选、依据、回执，不是产品功能

### 3.4 结论：空位在哪

**三组交集，目前没有产品同时做：**

1. **「按处境匹配」+「可解释」+「可复现」**
   - Reading Well 有处境与证据，但无算法、无线下以外通路
   - StoryGraph 有算法，但黑箱、不按处境
   - Book Therapy 有处境与人写理由，但 £29.99 / 48 小时不可扩展
   - → **本项目是唯一「零成本 + 确定性 + 可解释 + 按处境」的组合**

2. **「无账号」+「按处境推荐」**
   - Openreads、Hikara 证明无账号可以支撑完整体验，但**都没有推荐内核**
   - 所有有推荐的产品都要求账号
   - → **无账号 + 有推荐 = 空白**

3. **「可带走凭证」+「数字端」**
   - Reading Well / Book Therapy 有凭证但是纸质/PDF 的线下流程
   - 所有数字产品只有 CSV
   - → **数字端生成处方笺 = 空白**

**同时必须承认的落后项（不能回避）：**

- **统计能力**：StoryGraph / Bookly / Hikara 都比本项目强一个量级，且 Hikara 的 streak 冻结额度设计更成熟
- **书籍元数据**：Goodreads 1.5 亿会员的评论覆盖，本项目 68 本核心库无法相比
- **书籍间关联**：Hikara 的 echoes / challenges / bridges 是目前唯一做「书与书之间关系」的产品，本项目完全没有
- **导入导出生态**：Hardcover 可双向导入 Goodreads 与 StoryGraph，本项目的 JSON 只能自己读

## 4. 整合方案 vs 竞品：逐模块对照

判定口径：**独有** = 无竞品做；**领先** = 有竞品做但我们做法更优；**持平** = 与主流相当；**落后** = 不如主流，需补。

| 模块 | 竞品谁在做 | 我们的做法 | 判定 |
|---|---|---|---|
| **F0 存储迁移** | 全部有（各自的后端） | IndexedDB v1→v2，只加不改，旧表零改动；档案隔离靠分库 | 持平（工程必需，非差异） |
| **F1 首页工作台** | 全部有（首页即内容聚合） | 开始诊断 + 4 功能卡 + 继续读 + 数字条 | 落后→补（当前首屏入口仅 1） |
| **F2 导航 3→5** | 全部有 | 书架/书单库/统计/怎么读书/关于，375px 折叠 | 落后→补（当前 `/booklist` 不在导航） |
| **F3 书单库独立化** | Reading Well（分类书单目录）、StoryGraph（Custom Lists） | 无诊断可逛全量 68 本 + 四维筛选 + 筛选入 URL | 落后→补（当前依赖诊断） |
| **F4 凭证（打印/JSON/摘图）** | Reading Well（推荐表）、Book Therapy（10 页 PDF） | 单页 A4 处方笺 + `schema_version` JSON（**不存分数**）+ Canvas 摘图 | **领先**——数字端零成本生成，两家竞品靠人力/纸面 |
| **F5 想读队列** | 全部（Up Next Queue 最典型） | `shelf` 加 `want` + 拖动排序 | 落后→补（当前无中间态） |
| **F6 读后回执** | Reading Well（年度调查）、StoryGraph（评分+mood）、Book Therapy（2 周跟进） | 三选一 + 可选理由 + **明确不进排序** | 持平（刻意不接回算法，以保可复现，见 0.3） |
| **F7 阅读统计** | StoryGraph（最深）、Bookly、Hikara、微信读书 | 概览/时间线/分布，手写 SVG，streak **带冻结额度** | 落后→补（当前 telemetry 只有 3 个计数） |
| **F8 可信度面板** | 无（StoryGraph 黑箱、豆瓣均分、Book Therapy 人写） | 七因子中文得分条 + 该标签共几本 + 置信由来 | **独有** |
| **F9 书籍对比** | 无（StoryGraph 比的是时间段不是书） | 2–3 本并排 + 七因子雷达 | **独有** |
| **F10 笔记总览** | Book Therapy（journaling portal）、Alia（marginalia + 全文检索） | 跨书时间线 + 按标签 + **全文检索** | 落后→补（当前只能在单本内看） |
| **F11 读书计划** | StoryGraph（Challenge 有时限，非排期） | 按 `est_reading_hours` 排 4 周 + 拖拽调整 | **领先**（竞品只有目标量，没有排期） |
| **F12 本地档案** | Hardcover（逐本隐私）、Openreads（单机） | 一个档案一个 IndexedDB 库，清单固定存默认库；`/profile` 页切换 | 持平（场景窄，但竞品也没有等价物） |
| **F13 治理面板** | 无（属维护者内部工具） | `/admin` 只读，不入导航 | **独有**（对外无感知，仅维护者价值） |

**汇总**：14 个模块里 **5 项独有/领先**（F4 凭证、F8 可解释、F9 对比、F11 排期、F13 治理），**6 项落后需补**（F1/F2/F3/F5/F7/F10），**3 项持平**（F0/F6/F12）。

→ **产品的问题不是「想法不够新」，而是「7 项行业标配都没做」**。这也解释了为什么它看起来单薄：不是缺创意，是缺基础设施。

| # | 借鉴点 | 来源 | 并入 | 具体做法 | 价值 |
|---|---|---|---|---|---|
| **G1** | **streak 冻结额度** | Hikara / Bookly（freeze credits） | F7 | 连续天数不「断一天归零」，改为每月 2–3 次冻结额度，消耗一次保住连续记录 | 避免负反馈把用户推走；这是 Goodreads 替代品调研中反复出现的批评点（工具加压而非减阻） |

| **G5** | **可解释要写成句子，不只画条** | Hikara（echoes/challenges/bridges 每条都附解释） | F8 | 每个因子除得分条外，给一句人话：「这本 260 页、约 6 小时，你选了『时间紧』，所以篇幅这项给了高分」 | 分数条只证明「算过」，句子才证明「算对了」 |

## 7. 风险与红线

1. **内核污染**：统计/日期/随机误入 `src/domain` 会破坏「同输入同输出」。靠分层 + 现有门禁拦截。
2. **迁移事故**：多表事务清单漏表即 `NotFoundError`（v3 文档记录：删除档案漏 `profiles` 是实测踩过的点）；v2 代码与 v1 库反向打开可能停在「无表」损坏态。分库方案下删档案改为「关全部连接 → `deleteDatabase` → 删默认库里的清单记录」，三步缺一都会留下孤儿库或悬空清单项；另外若别的标签页还开着该库，`deleteDatabase` 会 `onblocked`，必须给出可读的提示而不是静默卡住。
3. **文案合规**：新增文案不得含「诊断 / 症 / 治疗 / 疗效」等医疗措辞（沿用 `copy-audit` 词表）；危机入口配额恒为 2；不做诊断。
4. **数据厚度诚实**：33 标签中位仅 4 本、最薄 3 本，涉及「有多少可选」必须如实，不美化。
5. **依赖纪律**：不引入图表库 / UI 库 / 截图库；图表手写 SVG，摘图用 Canvas 2D。
6. **行数与可复现**：`src/` ≤300 行、`tools/` ≤400 行；`domain` 禁时间与随机。
7. **门禁基线**：当前 54 文件 / 412 断言。新增功能同步补测试，不与实现期的更大数字混用对比。
8. **不当的功能别加**：账号/云同步、用户星级、UGC 社区、ML/LLM 生成书单、心理测评量表、推送、打卡排行榜——理由见 v2 §3。
